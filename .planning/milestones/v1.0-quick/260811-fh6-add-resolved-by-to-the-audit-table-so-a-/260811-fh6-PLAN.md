<decisions>

**D-FH6-01 — `resolved_by` is nullable `text` with NO foreign key.**
Direct precedent, D4 (`schema.ts` ~line 320): `actor_id` deliberately carries no FK because 8 of 57 call
sites pass a literal non-user string ("system" ×7, "guest" ×1), one of them the QRPh unrefundable-rail
alert this table exists for — an FK would 23503 exactly the rows the table exists to record. `resolved_by`
is the same argument one step harder: it is a name **typed at a CLI** by someone who may correspond to no
`user` row at all (a contractor, a finance person, a shared ops handle). It is PROVENANCE, not a join key.
Say so in the column comment, and do not "tighten" it later.

**D-FH6-02 — THE CAVEAT, and it is a deliverable, not a footnote.**
This column records an **ASSERTED** identity, not an **AUTHENTICATED** one. The CLI has no session; anyone
with `DATABASE_URL` can run it and type any name. A `resolved_by` that *looks* authoritative but is
self-asserted is actively dangerous in the dispute it exists for — it manufactures confidence the data
cannot support. The honest framing, to be used consistently:

> `resolved_by` records **who claims to have discharged the row**. It is meaningful in combination with
> shell / database access control, and it is **not proof of identity on its own** — the CLI has no session.

Stated in at least these three places, with the literal phrase `asserted, not authenticated` present in
each: the **schema column comment**, the **runbook**, and the **CLI's own `--by` help text**. No document
anywhere may describe the column as proof of who discharged an alert.

**D-FH6-03 — the CLI REQUIRES `--by`; there is NO default, silent or otherwise.**
Not the OS username, not `USER`, not `USERNAME`, not `OPS_OPERATOR`, not a config file. Rationale to
record verbatim in the code: *a name a human deliberately typed is a stronger audit record than one the
machine filled in, and a silent default would make every discharge look attributed while attributing
nothing.* Absent or blank `--by` ⇒ refuse, print the usage block, `process.exitCode = 1`, write nothing.
The parameter is REQUIRED at the type level for the same reason — see `<call_sites>` for the eight sites
that forces, and fix them in Task 1.

**D-FH6-04 — the existing guard already protects the new column; VERIFY, do not assume.**
`resolveAlert`'s `AND resolved_at IS NULL` makes a second run a ZERO-ROW update. Adding `resolved_by` to
the same `SET` list therefore inherits the protection: a re-resolve with a different name updates no row,
so the original discharger survives. That is a claim about a predicate, so it is **measured** — mutation
M1 removes the guard and must redden cases 16 and 17. Do not add a second guard clause
(`AND resolved_by IS NULL`); a redundant predicate would make the real one untestable.

**D-FH6-05 — NO BACKFILL, EVER.**
The 27 rows discharged on 2026-08-10 (runbook §4a) have no recorded discharger and must keep none.
Inventing one would be fabricating an audit record. This is not merely "we won't run an UPDATE": it must
hold under **re-resolve** too — running `ops:alerts:resolve -- <one of the 27> --by "Someone"` must report
`already_resolved` and leave `resolved_by` NULL, because the guard excludes the row. Pinned by case 17.

**D-FH6-06 — the render shows `BY`, and STILL omits `ACTOR`. This NARROWS D-DJ4-05, it does not reverse it.**
D-DJ4-05 omitted `actor_id` from the history render because it is the actor of the ORIGINAL event
(`system` for every money action, runbook §4) and, in a discharge-ordered list, an `ACTOR` column reads as
"who discharged this". The *reason* is now partly gone — there IS a discharger fact to show — but the two
remain different facts, and the decision is to show `resolved_by` and keep omitting `actor_id`, for three
reasons in this order:

1. **Two person-shaped columns in one discharge-ordered row is WORSE than one.** With `ACTOR = system` and
   `BY = Jane`, a reader scanning for "who" now has two candidates and must know which is which; the
   hazard D-DJ4-05 identified is amplified, not removed, by adding a correctly-named neighbour.
2. **`actor_id` carries no information in this view.** It is `system` for every money action, so on the
   rows a reviewer actually reads it is a constant column — pure width and pure confusion risk.
3. **The fact is not lost.** `listResolvedAlerts` still RETURNS `actorId` (unchanged), and the full row
   including `actor_id` is one psql away (runbook §3). Only the terminal render drops it.

Rejected alternative, on the record: *both columns, clearly labelled* (`EVENT ACTOR` / `DISCHARGED BY`).
It is defensible and it was considered — it fails on (2), because the extra width buys a constant, and on
(1), because "clearly labelled" is a bet that a stressed operator reads headers.

**D-FH6-07 — NULL renders as `unrecorded`.**
NOT `—`: the adjacent `ERROR` column already uses `—` to mean "this row has no error", so reusing it would
make two different absences look identical. NOT blank: a blank reads as "the field is empty because
nothing happened". `unrecorded` reads as **not captured**, which is exactly what it is. Runbook §6a must
say plainly that `unrecorded` means *discharged before the column existed, or discharged outside the CLI*
— it does **not** mean nobody.

**D-FH6-08 — the `--by` requirement moves to a pure module so it can be tested and mutated.**
`scripts/ops-alerts.ts` cannot be imported by a test: it opens a postgres client and calls `main()` at
module load. So argv parsing for the `resolve` verb goes into a new **pure, DB-free**
`src/lib/ops/resolve-args.ts`, which the script imports (the `@/` alias under `tsx` is already proven —
see the script's header note). `parseDays` is deliberately **NOT** moved: it is not this task's subject,
moving it is scope creep, and its behaviour is already documented in runbook §6a.

**D-FH6-09 — the email path cannot acquire a name, structurally.**
`UnresolvedAlert` gets no `resolvedBy` field, `listUnresolvedAlerts` is byte-unchanged, and an unresolved
row has `resolved_by IS NULL` by definition — so the digest could not print a name even if it selected
one. `src/inngest/` and `src/lib/email.ts` stay untouched; `tests/ops/alert-digest.test.ts` changes by
**exactly one line** (the `resolveAlert` call site gains its third argument) and must stay green.

**D-FH6-10 — migration `0025`, GENERATED, and NO INDEX.**
A plain nullable text column is fully Drizzle-expressible, so it goes through `drizzle-kit generate` (the
schema.ts rule — only the GiST EXCLUDE stays hand-written), which also keeps `_journal.json` and
`0025_snapshot.json` consistent for `npm run db:migrate`. No index: D-DJ4-06's accepted Seq Scan and the
deferred retention decision (schema.ts:350-354) stand untouched, and an index on `resolved_by` would grow
without bound for a column nothing filters on.

**A `[BLOCKING]` migration is verified against `information_schema` plus a fresh-schema replay, NEVER
against `tsc`.** Types come from `schema.ts`, so a declared-but-unmigrated column leaves `tsc` and
`next build` green while every integration test runs against a table without the column. Recorded as
**T-08-40**. Mutation M4 makes this measurable rather than quoted.

**Generate, then READ the emitted SQL.** Expected form, matching `0023`/`0024`:

```sql

```

`tests/helpers/db.ts:121` rewrites the literal `"public".` prefix to the isolated schema. If the generator
emits the **unqualified** form above, the rewrite is a no-op and the statement lands in the isolated schema
via `SET search_path` — correct. If it emits `"public"."audit"`, the rewrite retargets it to the isolated
schema — also correct. Either way the proof is the replay, not the reading: case 14 asserts against

**Both databases need the migration.** `npm run db:migrate` for dev (`drizzle.config.ts` loads

**Do not hand-edit the journal.** `drizzle-kit generate` writes `idx: 25` / `tag: "0025_audit_resolved_by"`.
Use `npm run db:generate -- --name audit_resolved_by` so the tag is deterministic rather than a random
adjective-animal.
