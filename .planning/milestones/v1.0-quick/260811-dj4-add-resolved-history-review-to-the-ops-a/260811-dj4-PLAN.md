<design_decisions>
These are DECIDED. Implement them; do not re-litigate them mid-task. Cite the ID in the code comments.

**D-DJ4-01 — "History" means every row with `resolved_at IS NOT NULL`, UNSCOPED by outcome.**
`resolved_at` has exactly ONE code writer in this repository (`resolveAlert`), so `resolved_at IS NOT NULL`
is *precisely* the set of human discharge acts — that is a fact derivable from the code, not a preference.
And `resolveAlert` is deliberately NOT scoped to `outcome = 'needs_attention'` (alerts.ts:130-132, pinned by
case 6b: "an operator handed an id discharges THAT id"). **The read side must mirror the write side**, or
discharges exist that no surface can review — which would reproduce D2 one level down. The `outcome` column
is therefore RENDERED, so a discharge on an `error`/`ok` row is visible at a glance, and is visible ONLY
here.

**D-DJ4-02 — Ordered by `resolved_at DESC`, tie-broken by `created_at DESC`.**
`created_at DESC` answers "when did the money event happen" and the unresolved queue already answers it. A
review is over discharge ACTS: a batch handled in one sitting (the 27 rows of 2026-08-10) must appear
contiguous. Both timestamps are returned so the money-event question is still answerable per row. The
`created_at DESC` tie-break makes a same-instant batch deterministic ("newest money event first").
**No `NULLS LAST`**, deliberately, and not an oversight: the `NULLS LAST` in `listUnresolvedAlerts` exists
to match `audit_needs_attention_idx`'s declared ordering. There is no index here (D-DJ4-06) and the
predicate makes NULLs impossible. Do not cargo-cult it in.

**D-DJ4-03 — 30-day default window, 200-row limit, honest truncation.**
Two bounds because they bound different things: the window bounds the *question* ("recent discharges"), the
limit bounds the *output* regardless of how many discharges fell in the window. The CLI requests `limit + 1`
and prints `N+ in window — showing the N most recently discharged` when it gets the extra row — the shipped
digest idiom (alerts.ts:53-58). Constants are `DEFAULT_HISTORY_DAYS = 30` and `DEFAULT_HISTORY_LIMIT = 200`,
declared SEPARATELY from `DEFAULT_ALERT_LIMIT` even though the numbers coincide: that one is a bound on an
operator's inbox, these are bounds on a terminal, and collapsing them would let a change to one silently
move the other.

**D-DJ4-04 — ONE narrow projection: `meta->>'error'`. Never the `meta` column. This is a DELIBERATE
widening, argued here, and it is the only one.**
The D2 question is "what was discharged, **and on what basis?**" — and the operator's own psql keyed on
`meta->>'error'`, because the 27-row classification turned on the literal string `'resend 503'`. A history
verb that cannot show it answers half the question.

Why it is safe, in the order the reasoning actually runs:
1. **The CLI is not a privilege boundary.** It connects with `DATABASE_URL`; anyone who can run
   `npm run ops:alerts:history` can already run `SELECT * FROM audit`, and the runbook §3 *tells them to*.
   The verb adds no read capability its runner does not already hold. **Email is a different reader set** —
   it forwards, archives and indexes — which is the entire reason the digest is bound tighter. The digest
   path is byte-untouched here.
2. **It is a single named key, chosen on content grounds.** By convention across this codebase's
   `recordAudit` sites, `error` holds an exception/API message; identifiers live under `bookingId`,
   `transferId`, `paymentId`, `last4`. Those keys stay unreachable.
3. **The structural enforcement survives intact.** A NEW type `ResolvedAlert` carries
   `error: string | null` and **no `meta` field**. `UnresolvedAlert` and `OpsDigestRow` are unchanged. So
   re-exporting the column is still a compile error at every consumer, and the email path cannot acquire
   `meta` by an accident on this task's surface.
4. **Residual risk, on the record and ACCEPTED:** an error string could in principle embed something an
   operator would rather not paste into a ticket, and terminal output escapes into tickets more readily than
   a psql session does. The disposition is accept (T-DJ4-01), narrowed by (2), and it goes in the runbook.
   The render truncates the column at 48 chars **for table readability, not as a PII control** — say so in
   the comment rather than dressing a cosmetic rule up as a safeguard.

**D-DJ4-05 — the history render OMITS `actor_id`.**
Not a width hack. `actor_id` is the actor of the ORIGINAL event (`system` for every money action per runbook
§4), and there is no `resolved_by` (§7 — a discharge is non-repudiable by absence). In a list *ordered by
discharge time*, an ACTOR column is read as "who discharged this". That misreading is actively dangerous in
a dispute, so the column is absent and §6a says why. The module still RETURNS `actorId`; only the render
drops it.

**D-DJ4-06 — NO INDEX, NO MIGRATION. Seq Scan accepted, with the threshold recorded.**
`audit_needs_attention_idx` is PARTIAL (`WHERE outcome='needs_attention' AND resolved_at IS NULL`) and
**does not serve resolved rows at all**. This query will Seq Scan + Sort. That is accepted: `audit` holds 27
rows today, and the window+limit bound the result, not the scan. The index that would fix it —
`CREATE INDEX ... ON audit (resolved_at DESC) WHERE resolved_at IS NOT NULL` — requires a migration, which
this task **forbids**, and it is not a free win either: unlike the partial unresolved index it would grow
**without bound**, which is the exact property `schema.ts:346-354` singles out. It therefore belongs with
the deferred RETENTION decision, not bolted on here. Record this in the module header and in the SUMMARY.
**If, while implementing, you conclude the index is genuinely required, STOP and report — do not add one.**

**D-DJ4-07 — the `days` bound is a BIND PARAMETER, deliberately not a literal.**
`listUnresolvedAlerts` emits its predicate as a SQL literal because the planner cannot prove
predicate-implication through a bind parameter, and a partial index is at stake. **Neither condition holds
here**: there is no index to defeat (D-DJ4-06), and `days` is a CALLER value. Literalising it would be an
injection surface. Write `resolved_at >= now() - make_interval(days => ${days}::int)` — Postgres clock, per
the project's zero-JS-clock rule (`src/lib/units.ts`), the same discipline every fixture in
`tests/ops/alerts.test.ts` already follows. A JS-computed cutoff would make host/Docker clock skew look like
a query bug. Put a one-line comment saying why the j3z literal trick is NOT copied here.

**D-DJ4-08 — read-only verb.** No un-resolve, no `resolved_by`, no writes. A discharge time is a historical
fact. This also makes it safe to run live against the dev database during verification.
</design_decisions>
