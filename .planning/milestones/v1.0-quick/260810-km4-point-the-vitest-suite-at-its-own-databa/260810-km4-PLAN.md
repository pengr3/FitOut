daily mail about money that does not exist — the exact noise that trains an operator to stop reading the alert.

per-run leak report, the accumulated dev rows classified and discharged on the record, and the now-false standing
"run vitest with NO `DATABASE_URL` override" rule corrected wherever it is stated as live guidance.

**F1 — the leak path.** `src/lib/db/index.ts` is `drizzle(postgres(process.env.DATABASE_URL!), { schema })`,

85 files call `setupTestDb()`. The gap between those numbers is the blast surface, and it is not enumerable.

**F2 — `recordAudit`'s swallow is load-bearing. Do NOT touch it.** `src/lib/audit.ts:111` swallows the INSERT
failure on purpose: 57 awaited call sites, many inside `catch` blocks on the PayMongo webhook's 200-ACK path,
where a throw makes PayMongo retry against the confirm authority. This is why "let the stray write fail" is a
*silent* outcome, and why the design below relocates-and-reports instead.

**F3 — `tests/setup.ts` forcing is required, and it inverts a documented behaviour.** Today it sets
`DATABASE_URL` only `if (!process.env.DATABASE_URL)`, and `.env.local` (loaded two lines above,
non-overridingly) always supplies it — so changing only the fallback literal is a **no-op**. The assignment must
become unconditional. `drizzle.config.ts:19-21` states the non-override ordering is exactly what keeps a one-off
`DATABASE_URL=… npm run db:migrate` working; that file is a SEPARATE PROCESS and is not touched here, so its
contract survives intact. The suite's escape hatch becomes an explicit `TEST_DATABASE_URL`.

**F4 — ordering is safe.** `setupFiles` run before the test file's module graph is imported, and
`tests/helpers/db.ts`'s `baseUrl()` reads `process.env.DATABASE_URL` at CALL time inside `setupTestDb()`. So
forcing the value in `tests/setup.ts` redirects both the per-file isolated schemas AND the app singleton, and
`tests/helpers/db.ts` needs no functional change. `globalSetup` however runs in the MAIN vitest process and does
NOT see `setupFiles` — it must load dotenv and resolve the URL itself.

**F5 — extensions: this is the trap.** Live probe of the dev DB returned

<decisions>
These four are settled. Implement them; do not re-litigate. Deviate only under the execute-plan deviation rules,
and record it if you do.

**DEC-1 — the test database's `public` schema IS migrated.** The alternative (leave it empty so a stray write
fails) is rejected: per F2 that failure is swallowed, so it buys containment at the price of *no signal at all*,
and it would be indistinguishable from a broken connection. Migrating `public` makes every stray write land
somewhere real, inspectable and truncatable, keeps non-swallowing singleton consumers (the Better Auth Drizzle
adapter, module-load-time server-action imports) working so containment does not turn into mass breakage — and
lets Task 2's report NAME the leaking code paths per run. **Loudness is delivered by the report, not by letting
the write fail.**

**DEC-2 — precedence is `TEST_DATABASE_URL` > derived `<base>_test`, and the suite's assignment is FORCING.**
A shell `DATABASE_URL` no longer steers the suite; that is the point. `TEST_DATABASE_URL` is the deliberate
hatch. Non-vitest processes (`drizzle-kit`, `tsx scripts/*`, Playwright, `next dev`) are untouched.

**DEC-3 — the `_test` suffix is a hard, structural invariant.** `tests/global-setup.ts` TRUNCATEs; a
misconfigured `TEST_DATABASE_URL` pointed at `fitout` would destroy the dev database. Resolution therefore
THROWS unless the resolved database name ends in `_test`. This lives in the shared module so all three consumers
inherit it and none can opt out.

**DEC-4 — the accumulated dev rows are DISCHARGED via the existing `ops:alerts:resolve` CLI, never DELETEd.**
`audit` is append-only and money-adjacent. The existing per-id CLI (shipped by `j3z`) already sets `resolved_at`
with a guard, and its one-row-at-a-time shape is a feature here: each discharge is an explicit act. No new CLI
mode, no bulk delete, no change to `src/lib/ops/alerts.ts`.
</decisions>
