# Phase 8 — UI Design Contract

> Visual and interaction contract for Group Bookings (GROUP-01..05). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This phase adds NO new design system, tokens, fonts, or color values.** It EXTENDS the FitOut design system locked across Phases 02–07 (shadcn `radix-nova` / neutral / lucide / Geist; the 8-point spacing scale; 4-size / 2-weight typography; the 60/30/10 coral-accent contract). Every surface below composes from, or clones, a component that already ships in `src/components/ui` or `src/components/{booking,host}`.
>
> **The phase's shape is set by ONE invariant** (08-CONTEXT § Specific Ideas): **one payer, one exclusive lock.** The organizer's booking is a normal Phase-5 paid booking; RSVP is an informational coordination layer bolted on top. Nothing here touches money movement or the GiST exclusion constraint. Design accordingly — the RSVP surfaces are *coordination UI*, calm and low-stakes; the one genuinely high-stakes correctness surface (the headcount cap, GROUP-05/SC#4) is enforced server-side and merely *reported* in the UI.

**Accent (FitOut Coral) reserved for — EXPLICIT, exhaustive list this phase:**
1. **`Invite people`** — the group-creation CTA on a confirmed, group-eligible booking (`/bookings/[id]`). This is the phase's headline action; it is the ONE coral on that surface. **[researcher's call]** — the currently-shipped coral `Find another space` on the confirmed branch demotes to a `ghost` text link so one-primary-per-surface holds. See Open Question 3.
2. **`Yes, I'm coming`** — the RSVP-accept primary on `/invite/[token]`. The one coral on the invite page; `Can't make it` is neutral `outline`.
3. **Inherited seams, unchanged:** `Book this space`, `Confirm & pay`, `Pay now`, the `SlotPicker` selected-run fill + anchor ring, the Search button.

Accent is **NOT** used for: `Copy link`, `Regenerate link`, any `Remove` control, the `Can't make it` / decline button, the `Log in instead` link, the "who's coming" roster, the headcount figure, guest/account tags, any RSVP-state badge, or the top-up nudge.

### The management + decline actions are neutral, NOT destructive-red

**`Remove` attendee**, **`Regenerate link`**, and **`Can't make it`** all use **neutral `outline`** buttons. Rationale, continuous with the Phase-2 unlist decision and the Phase-7 cancel decision: none of these destroys data or is unrecoverable. Removing an attendee frees a seat and they may RSVP again if they still hold the link; regenerating the link is a *security* action (it kills a leaked link) that preserves everyone already on the roster; declining is an expected, reversible RSVP outcome (toggle-until-session-start, D-120). Red would misrepresent all three as errors. `--destructive` does **not** appear anywhere in the group/RSVP surfaces.

## Surface contracts

### 1. Group entry point on `/bookings/[id]` (D-119) — MODIFY the shipped confirmed branch

The differentiator's front door. **Exclusive-mode `confirmed` bookings only**, session still ahead (any confirmed booking qualifies — instant-book or request-to-book — since both reach `confirmed` only after payment). Pending / requested / approved / cancelled / declined / completed do **not** show it.

| State | Contract |
|---|---|
| Not yet a group | Coral **`Invite people`** button, placed in the confirmed-branch forward-action slot (`bookings/[id]/page.tsx:558-568`). Submitting creates the `group` row (server action — snapshots `capacity_snapshot` from `listing.maxOccupancy`, D-111) and routes to `/bookings/[id]/group`. Helper beneath: `Invite friends to this booking and track who's coming.` |
| Already a group | Neutral `outline` **`Manage group · {N} coming`** link → `/bookings/[id]/group`. Not coral — once the group exists, management is a calm return trip, not a headline action. |
| `Find another space` | **[researcher's call]** — demote from coral to a `ghost` text link so the coral `Invite people` is the single primary. See Open Question 3. |

The cancel entry (D-104, shipped) is untouched and stays below its `Separator`.

Owner-gated RSC. **The organizer is `booking.bookerId`; the RSC re-checks it (Security V4), the route group is never the gate.** A non-organizer (or a stranger) gets the same bare 404 the booking detail uses — no enumeration oracle.

**Layout (top → bottom):** page title → headcount → share-link block → "who's coming" roster → (conditional) top-up nudge → manage actions.

| Element | Contract |
|---|---|

| **Headcount (GROUP-04 focal)** | `{confirmed} of {capacity_snapshot}` at Display 28/600 `tabular-nums`, with a Label-400 caption `spots filled`. Optional subtle `progress` bar beneath **[researcher's call — text is sufficient; the bar is a nicety, skip if over budget]**. At the cap: caption becomes `This group is full.` (muted, never red). |
| Share-link block (D-118) | Label `Your invite link` (14/600) + a **read-only** full-width `input` holding the absolute URL (`{origin}/invite/{token}`) + a neutral **`Copy link`** button (client, `navigator.clipboard`, `sonner` toast `Link copied`). The token is a real access credential — render it, never log it. |
| "Who's coming" roster | A `card`-wrapped list. **Organizer is row #1, labelled `You · organizer`** (D-113). **Privacy [researcher's call]:** the roster ("who's coming") is **organizer-only**. Attendees on the public invite page do NOT see the guest list — only their own confirmation. *Rationale: guest names + attendance are personal data the invitees did not consent to publish; GROUP-04 assigns the roster to the organizer, not to every link-holder.* See Open Question 4.

### 3. `/invite/[token]` — public RSVP page (GROUP-02, GROUP-03, D-116, D-118, D-120, D-122) — NEW

The first surface in the app reachable **without a session and without owning anything** — the token is the sole credential. It sits OUTSIDE `(app)`/`(host)` (like `/listings/[id]`), header-less, but carries a **FitOut wordmark lockup** at the top of the card so an invited stranger knows what they've opened (brand trust; the wordmark is the one inherited coral-lockup use, 02-UI-SPEC accent #5).

**Layout (top → bottom):** wordmark → event summary → identity block → RSVP choice.

| Element | Contract |
|---|---|
| Event summary (D-122) | Title `You're invited to {space}` (Heading 20/600). Then venue-local `{date}, {time} ({City} time)` and the address **per `listing.showExactAddress`** (exact or approximate), each with a leading lucide glyph (`Calendar`, `MapPin`). Body 16/1.5. |
| Identity block (D-116, the guest-or-login fork) | **Logged in:** `RSVPing as {name}` (from the account) — no name field. **Logged out:** the "continue as guest or log in" pattern — a required guest **name** `input`, an **optional** email `input` with incentive helper `Add your email to get a confirmation and a link to change your answer.` (D-117), plus a quiet `Log in instead` `ghost` link that carries the token through so they return here. |
| RSVP choice (D-120) | Two buttons: coral **`Yes, I'm coming`** (primary) and neutral `outline` **`Can't make it`**. One RSVP = one person, **no +guests** (D-120) — there is no quantity control. |
| Confirmation (D-122) | On submit → a calm confirmation state in the same card: `You're in — see you there.` (yes) / `Thanks for letting us know.` (no) + the event summary retained. **Account or guest-with-email** also gets it by email/in-app; **blank-email guest gets ON-SCREEN only** (D-117) with a muted line `This is your only confirmation — we don't have an email to reach you.` |

| **Full** (D-112, courtesy) | If `confirmed-yes >= capacity_snapshot`, the `Yes, I'm coming` button is `disabled` with a neutral `alert`: `This group is full — all {N} spots are taken.` `Can't make it` stays available. **The UI is a courtesy; the server seat-claim is the gate** — a yes that looked open but loses the race resolves to the calm raced copy below, never a crash. |
| **Closed** (D-120, RSVP closes at `startsAt`) | Neutral `alert`: `RSVPs have closed — this session has already started.` No choice buttons. Evaluated against the **DB clock**, server-side. |
| **Voided / cancelled** (D-121) | If the underlying booking was cancelled, or the link was regenerated/revoked, the calm state: `This invite is no longer active. Ask the organizer for the latest link.` No RSVP. |
| Unknown token | Renders the **same** calm "no longer active" state as a revoked link — **not** a distinguishable 404 (no enumeration oracle for a shared, guessable-length credential). |
| Error | `We couldn't save your RSVP. Try again.` → retry. Not red. |

### 4. Group notifications (D-122) — extend the compile-checked union

Group RSVP events are new **types**, not new infrastructure (`fitout/notify` → durable `notification` row + email; onFailure `needs_attention` audit — all shipped). Adding each type is the **four-file compile-checked change** (D-122 / D-92 era): pgEnum + TS union (`schema.ts`), Zod union (`validation/notification.ts`), `sendForType` (`inngest/functions/notify.ts`), and `describeNotification` (`notification-item.tsx`). **No `default:` clause** in any of the four — an omission must stay a compile error.

This contract fixes the **render treatment**; the exact payload discriminated-union shape is a planner call (per 08-CONTEXT § Discretion, mirroring the D-86 pattern).

| Event | Recipient | Channel | Icon (lucide) | Copy tone |
|---|---|---|---|---|
| RSVP received (yes) | Organizer | in-app + email | `UserRoundCheck` | `{name} is coming to {space}` · `{date}, {time} ({City} time)` |
| RSVP received (no) | Organizer | in-app + email | `UserRoundX` | `{name} can't make {space}` · muted |
| RSVP confirmation | Attendee (account) | in-app + email | `CalendarCheck` | `You're going to {space}` · `{date}, {time} ({City} time)` |
| RSVP confirmation | Attendee (guest-with-email) | email only | `CalendarCheck` | same copy; blank-email guests get none (D-117) |
| Group cancelled (D-121) | Every reachable yes attendee | in-app (accounts) + email (accounts + guests-with-email) | `CalendarX2` | `{space} on {date} was cancelled.` · calm, never an alarm colour |

- **Every group notification `href` is an ABSOLUTE URL** (`${BETTER_AUTH_URL}/...`) — the 07-10 convention, because the same string is the email CTA and a root-relative href is a dead link in a mail client. Organizer notifications link to `/bookings/[id]/group`; attendee notifications link to `/invite/[token]`.
- **`href` passes the shipped `safeHref` render allow-list** (`notification-item.tsx`) — root-relative or `http(s)` only.

## Copywriting Contract

| # | Rule | Why it is locked |
|---|---|---|

| **G2** | The email field on the invite page is **optional and framed as a benefit**, never a gate. | D-117 — a blank-email guest is a valid, supported RSVP (pure headcount). The email is the "be kept in the loop" incentive, not a requirement. |

## Screen / State Contract

| Screen | States the executor must implement |
|---|---|
| `/bookings/[id]` (confirmed) | not-a-group (coral `Invite people`) · already-a-group (`Manage group · N coming`) · creating (pending) · not eligible (no entry: pending/requested/approved/cancelled/declined/completed/past-start) |
| `/bookings/[id]/group` | loading (skeleton) · empty (no RSVPs) · populated (yes rows + collapsed no rows) · at-cap (full caption) · top-up-nudge visible (fee>0, over declaredPax) · removing attendee (in-flight + confirm) · regenerating link (confirm) · copy toast · poller-refreshing (silent) · error · **not-organizer → 404** |
| `/invite/[token]` | logged-out guest form · logged-in prefilled · submitting · confirmed-yes · confirmed-no · blank-email-guest ("only confirmation") · returning + change-answer · **full** (yes disabled) · **closed** (session started) · **voided/cancelled** · **unknown token** (same as voided) · raced-full-on-submit · error |
| Reserve page (fee>0) | `declaredPax` = 1 · stepped up (re-quoting) · surcharge line visible · at max (`maxOccupancy`) · fee=0 (no stepper, no line — unchanged) |
| Wizard pricing step | `extraHeadFee` = 0 (flat, `included` hidden) · fee>0 (`included` shown) · no occupancy_mode control |
| Group notifications | organizer rsvp-yes · organizer rsvp-no · attendee confirmation (account / guest-email) · attendee group-cancelled · blank-email guest (no notification) |

**Visual hierarchy / focal point (locked, per surface):**
- **`/bookings/[id]/group`:** the **headcount figure + the roster are the working area** — GROUP-04 is "see the headcount and who's coming". The share/manage controls are secondary.
- **`/invite/[token]`:** the **RSVP choice (`Yes, I'm coming`) is the focal point**; the event summary is context above it.

**Interaction rules (locked):**
- **The cap is enforced server-side** by the D-112 `FOR UPDATE` seat-claim — the UI's "full" state is a courtesy, never the gate. A yes that loses the race resolves to the calm raced copy, never a crash. (Analogous to the shipped `SlotPicker` "UI is a courtesy" rule.)
- **The DB clock is the sole authority** for RSVP-close-at-`startsAt` (D-120) — never a JS clock.
- **All pricing is server-computed** (D-108) — `declaredPax` re-quotes server-side; `PriceBreakdown` and the surcharge line receive frozen props and sum nothing.
- **Owner/organizer gating happens in the action/RSC**, never the route group. Non-organizer and missing return the same calm 404 (no enumeration oracle). The public invite route is gated by the **token**, and unknown = revoked = the same calm inactive state.
- **Guest names are escaped at every render + in every email/notification** (G6). No `dangerouslySetInnerHTML`; reuse `safeHref` for invite links in notifications.
- **One RSVP = one person, no +guests** (D-120) — no quantity control on the invite page.
- **`occupancy_mode` has no v1 UI** (D-109) — do not render a mode toggle.

**Accessibility (non-negotiable):**
- Guest/account tags and RSVP-state are **icon + text, never colour-only** (the neutral badges are hue-indistinguishable by design).
- The headcount figure exposes meaning to AT beyond the numeral (e.g. `aria-label="{confirmed} of {N} spots filled"`).
- The share-link `input` is a labelled, readonly, selectable field; `Copy link` has an accessible name and announces success (`sonner`).
- The `PaxStepper` +/− controls have accessible names (`Add a guest` / `Remove a guest`) and the field is a labelled number input.
- Both confirm dialogs (remove / regenerate) trap focus, are keyboard-dismissable, and return focus to the trigger.
- The roster is a list with associated name↔meta pairs that survive linearisation; the organizer row is programmatically identifiable.
- The invite page is fully operable signed-out and keyboard-only; the "full"/"closed"/"cancelled" states are announced (`role="status"`), not colour-only.
