# Quick: make the checkout clearance's argument order enforceable, not just correct

## What is being closed

`17.1-REVIEW.md` **WR-04**. `src/app/listings/[id]/book/page.tsx:546-552` is CORRECT TODAY and
measured — 80px at 320 / 639 / 640 / 768 / 1023 and 48px at 1024 / 1280, both themes (`17.1-EVIDENCE.md`
§ P4). **Nothing is broken. This task changes no rendered pixel.** It closes the gap between "correct"
and "hard to break", on a call whose fragility mechanism is currently documented nowhere.

The call:

```tsx
<main className={cn("mx-auto w-full max-w-4xl px-4 py-8 sm:py-12", STICKY_BAR_CLEARANCE, "sm:pb-20 lg:pb-12")}>
```

`cn` is `clsx` + `extendTailwindMerge` (`src/lib/utils.ts:41-47`). `tailwind-merge` resolves a
`py-*` / `pb-*` conflict by **deleting the earlier class before any CSS exists**, so argument ORDER
decides survival — a fact the ~30 lines of comment above this call (`:515-545`) never mention, because
every one of their three ⚠ paragraphs reasons about Tailwind v4's **cascade layers**, which is a
different mechanism at a later stage.

## The measurement that decides everything below

Probed at HEAD, 2026-08-31, through this repo's own `cn` (`npx tsx`, one script, deleted after):

| order | `cn(...)` output |
|---|---|
| **SHIPPED** `cn(P, K, T)` | `mx-auto w-full max-w-4xl px-4 py-8 sm:py-12 pb-20 sm:pb-20 lg:pb-12` |
| **HOISTED** `cn(K, P, T)` | `mx-auto w-full max-w-4xl px-4 py-8 sm:py-12 sm:pb-20 lg:pb-12` — **`pb-20` GONE** |
| **FLATTENED** into one string | `py-8 sm:py-12 lg:pb-12` — **both `pb-20` and `sm:pb-20` GONE** |

where `P = "mx-auto w-full max-w-4xl px-4 py-8 sm:py-12"`, `K = STICKY_BAR_CLEARANCE = "pb-20"`,
`T = "sm:pb-20 lg:pb-12"`.

HOISTED — moving the named constant to the front of a call whose first argument is a bare literal — is
the single most plausible "tidy" anyone will ever perform on this line, and it leaves `<main>` reserving
**32px (`py-8`) under a 64px bar below 640px**: strictly worse than the defect Phase 17.1 just repaired,
which was 80px below 640px and only failed from 640px up.

## Shape A is REJECTED, and the reason is measured rather than argued

Shape A was: fold the breakpoint variants into `STICKY_BAR_CLEARANCE` so the class list carries one term
instead of two that can reorder against each other. Probed the same way, with
`KA = "pb-20 sm:pb-20"`:

| order | output |
|---|---|
| A shipped `cn(P, KA, "lg:pb-12")` | `… px-4 py-8 sm:py-12 pb-20 sm:pb-20 lg:pb-12` — byte-identical to SHIPPED |
| **A hoisted** `cn(KA, P, "lg:pb-12")` | `… px-4 py-8 sm:py-12 lg:pb-12` — **BOTH terms gone** |

**Shape A does not remove the fragility; it doubles the blast radius.** The killer is `py-*`, not the
sibling `pb-*`: `py-8` deletes a preceding `pb-20` and `sm:py-12` deletes a preceding `sm:pb-20`, so
folding the two survivors into one argument means the same hoist now deletes both instead of one. It buys
nothing on the exact edit it was proposed to prevent.

Its cost, for the record, since the shared constant has three consumers:

| consumer | today | under Shape A |
|---|---|---|
| `src/app/listings/[id]/book/page.tsx:549` | load-bearing (`[17-D9]` / DRIVE 2) | unchanged pixels, doubled deletion risk |
| `src/app/listings/[id]/(detail)/layout.tsx:80` — `cn("flex min-h-dvh flex-col", K, "lg:pb-0")` | `flex min-h-dvh flex-col pb-20 lg:pb-0` | gains `sm:pb-20`: a **no-op on computed padding** (no `sm:py-*` in that list to beat) but a change to a shipped route's emitted classes for a hazard that route does not have — hoisting there keeps `pb-20` (measured) because there is no `py-*` in its arguments |
| `e2e/mobile-booker-path.spec.ts:618,847` | interpolates the constant into failure prose as `${STICKY_BAR_CLEARANCE} = 80px = 64 + 16` | reads `pb-20 sm:pb-20 = 80px = 64 + 16` — a third file to amend for a fix that does not fix |

**Shape B is adopted:** runtime behaviour stays byte-identical; the ordering constraint is written at the
call site AND pinned by a gate that goes red on the reorder.

## The gate has to read the real call site, not a copy of it

The obvious Shape B test — import `cn`, retype the three arguments in the test, assert the output contains
`pb-20` — **is not a guard**. It is a second copy of the argument list, and it stays green forever while
the real file is reordered. That is the exact defect class this repo has already paid for twice, in
writing: `tests/design/helpers/strip-comments.ts:12-26` (the brand recipe reported 21/21 passed while the
primary booker CTA was no longer coral) and `tests/design/sticky-offset.test.ts:9-13` ("a per-file map
would say these files are correct today; the failure this gate exists to catch is the NEXT one").

So the gate **parses the real source with the TypeScript AST**, resolves the actual argument list, feeds
it through the real `cn`, and asserts nothing was deleted. That is the established idiom in this suite —
`sticky-offset.test.ts:155-160` (`import ts from "typescript"` + `stripComments`), and the same node
classes visited by `leak.test.ts:213-250` and `skeleton-measurements.test.ts:211-239`.

And it is a **rule, not a path inventory**: the subject is *every `cn()` call in `src/` that composes
`STICKY_BAR_CLEARANCE`*, so the next route that grows a sticky bar is covered on the day it is written.
Two sites match today; the detail layout is one of them and is currently NOT fragile (measured above) —
which is precisely why the rule must not be scoped to the checkout file.

### Task 1 — the gate: a source-derived rule that no `pb-*` is merged away

**files:** `tests/design/clearance-merge-order.test.ts` (new)

**action:**

Write the gate in this suite's register — a header that states the rule, its derivation, and its blind
spots, then the assertions. Model the structure on `tests/design/sticky-offset.test.ts` (read
`:1-45` for the header shape and `:155-250` for the AST walk, the `collectSourceFiles` recursion and the
repo-relative `label()` normalisation, which handles Windows separators). Import `ts from "typescript"`
(devDependency, `package.json:85`) and `stripComments` from `./helpers/strip-comments`.

**The subject.** Walk `src/` for `.ts`/`.tsx`. A SITE is a `CallExpression` whose callee is the identifier
`cn` and whose argument list contains the identifier `STICKY_BAR_CLEARANCE`. Two exist today:
`src/app/listings/[id]/book/page.tsx:547` and `src/app/listings/[id]/(detail)/layout.tsx:80`.

**Resolving a site's arguments.** String literals resolve to their text. The identifier
`STICKY_BAR_CLEARANCE` resolves by importing the real constant from `@/lib/design/measurements` — the `@`
alias is configured at `vitest.design.config.ts:36`. **Any other argument shape (template literal,
conditional, spread, object) is a FAILURE, not a skip**, reported as one named violation: an argument the
gate cannot resolve is one nobody can check by reading either. Same fail-closed direction as
`sticky-offset.test.ts`'s treatment of an unresolvable offset (`:~245`).

**The rule.** For each site: collect every `pb-*` class in the resolved arguments as
`[variant, class]`, where `variant` is everything before the final `:` (`""` for unvariant, `"sm"` for
`sm:pb-20`). The expected survivor for a variant is the LAST `pb-*` at that variant in argument order —
that is what a deliberate override means. Then run the REAL `cn(...)` over the same resolved arguments and
parse `pb-*` out of the output. A VIOLATION is any variant present in the arguments whose expected
survivor is missing from or different in the output. Report it with the file, the line, the class that
vanished and the output string, so the failure is readable without opening a REPL.

Assert the violations array deep-equals `[]`, with a message that states the mechanism:
`cn` is tailwind-merge, which DELETES a `pb-*` that precedes a conflicting `py-*`, so a `pb-*` composed
before the layout string is not a smaller padding — it is no padding.

**The positive half** (the same paired shape `sticky-offset.test.ts` uses, so one bad edit produces two
readable failures rather than one). Pin the resolved per-variant `pb` map per site:

- `src/app/listings/[id]/book/page.tsx` → `{ "": "pb-20", sm: "sm:pb-20", lg: "lg:pb-12" }`
- `src/app/listings/[id]/(detail)/layout.tsx` → `{ "": "pb-20", lg: "lg:pb-0" }`

Write beside that table the measured route behaviour it encodes: 80px at 320 / 639 / 640 / 768 / 1023 and
48px at 1024 / 1280 on `/listings/[id]/book`, both themes (`17.1-EVIDENCE.md` § P4).

**The guard-the-guard.** Pin TWO counts separately, each with the reasoning `sticky-offset.test.ts:~185`
gives for `EXPECTED_STICKY_SITES` — that "somebody added a site" and "somebody broke a site" must not be
the same failure:

- files under `src/` that import `STICKY_BAR_CLEARANCE` → **2**
- matched `cn()` sites → **2**

Both are needed and they fail in different directions: the second dropping to 1 means the constant stopped
being composed through `cn` (so the rule silently stops covering it), while the first staying at 2 means
the import is still there. State what a change to each number means, and that the correct response to a
new site is to read it and extend the positive table deliberately.

**Blind spots, stated so the next reader under-trusts the file** (this suite's convention): it reads
SOURCE, not computed geometry — it proves the class survives the merge, not that the box renders 80px;
that measurement is `e2e/mobile-booker-path.spec.ts`'s `expectDocumentEndClearsBar`, which CI does not
run (`.github/workflows/ci.yml:841`). It understands `pb-*` only — a clearance expressed as `mb-*` or an
inline style is invisible. It follows the constant, so a clearance hard-coded as a bare literal with no
constant is out of subject by construction.

**verify:**

```
npx vitest run --config vitest.design.config.ts tests/design/clearance-merge-order.test.ts
```

**done:** the file exists and passes at HEAD with no source file modified. The count assertions read 2
