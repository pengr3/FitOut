# Quick: write the `transformation` prohibition that 16.1-04 declared and never wrote

## What is missing, stated precisely

Plan `16.1-04-PLAN.md:313` declares, as T-16.1-01's second-layer defence:

> This plan passes no `transformation` and no `options` key that could carry one; **the source
> assertion prohibits the literal** and the widget was MEASURED to drop it from `paramsToSign` and
> the POST anyway (probe E6)

No such assertion was ever written. It appears in no task action and no acceptance criterion of
16.1-04 — only in that threat-model mitigation prose — which is why the executor's `Deviations:
None` was literally true. The 16.1 security audit found the hole and recorded it as **W-1**.

**This is not an open vulnerability, and the plan must not pretend otherwise.** The boundary control
for T-16.1-01 lives in `src/app/api/cloudinary/sign/route.ts` and is triple-pinned there:
`ALLOWED_SIGN_KEYS` (`:80`, four entries, `transformation` deliberately excluded with the reasoning
written out at `:70-79`), the 400-before-signer gate (`:159-162`), and the value-smuggling checks
(`:217-238`). T-16.1-01 is **CLOSED**. What is missing is the *regression pin* on the client — the
thing that would go red if someone re-added a `transformation` key to the widget's options in a
future edit.

So the whole deliverable is: **one assertion, in one existing test file, watched RED once.**

## Measurements taken during planning — do not re-litigate these

Run against `src/components/listing/photo-uploader.tsx` at `f3967b7`, using this repo's own
`stripComments` implementation:

| Question | Measured answer |
| --- | --- |
| Occurrences of `transformation` in the RAW component | **1** — at `:211`, inside a `//` comment ("the security boundary is the transformation the preset carries") |
| Occurrences in `stripComments(source)` | **0** |
| Case-insensitive matches in the stripped source (`/transformation/gi`) | **`[]`** — nothing, not even `Transform`-family tokens (`CSS.Transform.toString`, `transform`, `transition` do not contain the substring) |
| `optionsRegion(CODE)` matches? | **yes**, 791 chars, carrying all six keys (`folder:`, `multiple:`, `maxFileSize:`, `clientAllowedFormats:`, `sources:`, `maxFiles:`) |
| Occurrences inside `optionsRegion(CODE)` | **0** |

**Consequence 1 — stripping alone is sufficient; region-narrowing is NOT needed for this
prohibition.** The known pitfall (a whole-file `not.toContain` going falsely RED because the correct
file names what it forbids in prose) is real here — the raw file *does* contain the token — but
`stripComments` removes it completely, so the assertion is green against the correct component
today. This is unlike the photo-cap prohibition, where narrowing *was* required because
`delayDuration={200}` put the digits back outside any comment. Assert over the whole stripped `CODE`,
not over the region: it is the strictly stronger property (it also catches a `transformation` added
in a second widget, a helper, or a prop rather than an options key), and the measurement above shows
it costs nothing in false reds.

**Consequence 2 — the existing "file was really read" guard does NOT cover this prohibition.** That
guard anchors on `CldUploadWidget` (`:188`) and `export function PhotoUploader` (`:102`). **Both sit
OUTSIDE the `options={{ … }}` body** (`:205-263`). A phantom block comment of the kind 16.1-03 hit —
a `/*` sequence inside a line comment opening a block the regex then closes far below — could
swallow the entire options object and leave that guard green, making this new prohibition vacuously
green. That is the falsely-GREEN half of the `verify-workflows.mjs:24-32` finding, and it is not
hypothetical: it is the exact failure 16.1-03 measured.

The fix costs one line and reuses what is already there: `optionsRegion()` **throws** with an
explanatory message when it matches nothing, so calling it inside this test is a self-reporting
anchor. Require it to still carry `maxFiles:` and the assertion is proven to be reading real code.
**Do not write a second narrowing helper.**

**Consequence 3 — one correction to make honestly rather than leave.** W-1 cites the prose
occurrence as `:271`. The single occurrence in the component is at **`:211`**. The substance of W-1
is unaffected (one occurrence, in a comment, stripped) but the plan records the right line so the
next reader is not sent to the wrong one.

## Scope boundary, recorded so it is not re-litigated

The declared pin is **`transformation`**. The assertion below is written case-insensitively
(`/transformation/i`), which additionally catches `Transformation` and the compound
`eager_transformation`/`raw_transformation` forms at no cost — measured green.

It deliberately does **not** grow into a prohibition on bare `eager:` or `allowed_formats:`, even
though `route.ts:70-79` names all three as the same class of mistake. Those two are bounded where it
counts — `ALLOWED_SIGN_KEYS` refuses to sign them and the route answers 400 before the signer is
reached — and neither was declared by 16.1-04. Adding undeclared prohibitions is scope this task does
not own. Nothing declared is being dropped.

`src/` is **read-only** here except transiently during the observed-RED mutation in Task 2, which
must be reverted before anything is committed.
