# Quick Task 260813-0h2 — Fix G-01: ScrollArea children overflow their panel

## What was wrong

Radix `ScrollArea.Viewport` renders every child inside ONE wrapper div and hardcodes
`style={{ minWidth: "100%", display: "table" }}` on it
(`@radix-ui/react-scroll-area/dist/index.mjs:130`). `display: table` shrink-wraps to max-content, so
`min-width: 100%` is a floor with no ceiling — long unbreakable content widens the wrapper past the
panel and the overflow is clipped.

Reported by the developer during phase 10 UAT (test 6) on the notification panel. Measured in
Chromium: viewport **384.0px**, wrapper and every row **976.9px**, overflowing **592.9px** to the
right, flush at the left.

**Not a phase-10 regression.** Removing IN-14's `max-h-[inherit]` leaves the row at 976.9px
unchanged; phase 10's scroll fix is only what made the list long enough to read and therefore to
notice. Both shipped call sites were affected — `notification-bell.tsx:150` (`max-h-96`) and
`slot-picker.tsx:155` (`max-h-72`) — so the fix went in the primitive, not at either call site.

## What changed

**`src/components/ui/scroll-area.tsx`** — the Viewport now forces that wrapper to a block box. The
in-file comment carries the diagnosis and the horizontal-ScrollArea caveat.

The caveat is recorded rather than engineered around: `ScrollArea` hardcodes `<ScrollBar />`
(orientation defaults to vertical), so a horizontal scrollbar is unreachable through this wrapper,
and `orientation="horizontal"` appears nowhere in `src/`. Anyone adding horizontal support must edit
this file, so the comment lands in front of them. Building a conditional for a case that cannot
currently occur would have added exactly the unreachable code the previous ticket had to go back and
correct a comment about.

## Two gates, because neither layer alone is sufficient

| Layer | File | Proves | Runs in |
|---|---|---|---|
| Compiled stylesheet | `tests/design/scroll-area.test.ts` | the rule is **emitted** | `npm run build` (`lint && test:design && next build`) |
| Real browser | `e2e/scroll-area-overflow.spec.ts` | the rule **lands**, in measured pixels | `npx playwright test` |

A source scan alone was refused. The whole trap here is that a class name can be present, spelled
plausibly, and produce nothing — this repo has been bitten twice (`z-dialog` compiled to silence
because Tailwind v4 has no z-index namespace; `text-label` was deleted by tailwind-merge at every
call site while the source still read correctly). The override has two spellings that BOTH compile
under Tailwind 4.3 and any number that do not, so only the emitted CSS can tell them apart.

And the emitted CSS cannot prove the rule *lands*: jsdom performs no layout, so
`getBoundingClientRect()` returns zeros and a measured width is out of reach of every test under
`tests/design/**`. Widths are the actual claim, so they are measured with the same instrument that
produced the original diagnosis.

The Playwright gate targets `/dev/theme` — **no auth, no DB**. The gap was reported on the
notification panel, which needs a signed-in session and 20 seeded rows; a gate with those
prerequisites is one that stops running. `/dev/theme` renders two ScrollAreas and needs neither.

## Both gates were watched failing first

Recorded verbatim in each file's header rather than summarised here, per this repo's convention.

- **Design gate** — the override token was deleted from the Viewport's `className` while **the
  caveat comment was deliberately left entirely in place**. That is the point of the run: Tailwind's
  content scan is raw text, so a class quoted inside a comment is emitted exactly like one in a
  `className`. Had the comment named the token, the compiled assertion would have stayed green
  against a fully broken tree. Assertion 3 pins the property (raw token count must equal
  comment-stripped token count) so a future reword cannot silently re-arm the collision. Phase 10
  hit the source-scan form of this three times; this is the compiled form, and it is worse, because
  the artifact it fakes is the one meant to be un-fakeable.
- **Playwright gate** — same mutation, and **the dev server already running on :3000 was stopped
  first** so Playwright booted its own against the mutated tree. Otherwise a stale server would have
  served the fixed bundle and laundered the result.

## Scope decision that inverted the request

The task asked to consider adding `min-w-0` / truncation to the notification row. **It needs
neither, and the reason inverts the request:** `notification-item.tsx` already carries `min-w-0
flex-1` (:268) and `truncate` (:270), and all 15 `describeNotification` titles are hardcoded
literals — the treatment was correct but inert. More importantly `truncate` implies
`white-space: nowrap`, which is consistent with *causing* the 976.9px max-content. Additional
truncation would have widened the wrapper, not narrowed it.
