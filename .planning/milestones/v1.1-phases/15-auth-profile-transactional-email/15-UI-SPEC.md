# Phase 15 — UI Design Contract

> Visual and interaction contract for the four auth screens, the profile page, and the one branded
> shell every FitOut email renders through. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## What this document is, and what it deliberately does not touch

**Phases 10–14 shipped a gated design system, a pattern layer, an app shell, the booker path and the
host tooling.** Colour, the four type roles, focus, status tones, elevation, motion, the contrast
inventory, the three card patterns, the state families, the one overlay primitive and the typed
inventories (`contrast-pairs.ts`, `measurements.ts`, `selector-contract.ts`, `status-tones.ts`,
`live-regions.ts`, `accent-uses.ts`, `visual-baselines.ts`) are **LOCKED**. `npm run build` =
`lint && test:design && next build`, so a raw hex under `src/app/**`/`src/components/**`, an arbitrary
type size, an undeclared `data-testid`, a raw `<Card>` in an unlisted file or a fourth accent kind
already fails the build today.

**This document re-decides none of that.** Everything below either *consumes* an existing token,
pattern or recipe, or names precisely where a declared inventory must be **EXTENDED** — always "add or
amend a row in the declared inventory, with its reason", never "invent a value at the call site."

This file adds three things:

| # | Adds | Requirement |
|---|------|-------------|
| 1 | **The auth composition** — one centered card on a quiet ground, wordmark above, coral on the one primary action (15-CONTEXT D-162) | AUTHUI-01, AUTHUI-03 |
| 2 | **The profile design pass** — `PageHeader` + two `PanelCard`s around a save-state model that does not move | AUTHUI-02 |
| 3 | **The email shell** — 600px, single-column, table-based, inline hex from `tokens.generated.ts` only, a preheader, a text wordmark, a plain-text twin; all 19 sends adopt it and **not one trigger moves** | EMAIL-01, EMAIL-02, EMAIL-03 |

**The standard, restated.** Phase 11: *a gate that has silently never failed is worse than no gate.*
Phase 13: *if our screen and the user's own record disagree, our screen is wrong.* Phase 14:
*an absence must never be dressed as a failure.* Phase 15 adds the one 15-CONTEXT carries implicitly,
and it binds both halves of the phase: **one identity, two surfaces** — the text wordmark on the auth
card and the text wordmark in the email header are ONE treatment, and any divergence between them is a
defect, not a nuance.

**PROJECT D-138 binds: `court` is the SINGLE product theme.** Every new baseline is court-only. Every
colour figure quoted below is court's; `contrast.test.ts` still measures both themes because the token
contract did not change.

**PROJECT D-130 binds.** Polish may reshape layout and hierarchy; it may not move logic or weaken a
v1.0 invariant. The anti-enumeration branches, the callback-URL guard, the session revocation on
reset, the server-side capability mapping and every send trigger are untouchable (§ GATE-NOREG).

**PROJECT D-136 binds. ZERO schema migrations.** Nothing below needs a column.

**Decision-ID namespace.** Bare `D-NNN` in this file means **15-CONTEXT D-160…D-163**. PROJECT-scope
numbers are written `PROJECT D-130`. Earlier phases are written `14-CONTEXT D-150`.

⚠ **A comment containing a banned token trips the design greps.** Where this document instructs source
prose — including comments inside the email shell — it instructs **descriptive naming**, never
quotation of a banned class or a raw colour value.

## Spacing Scale

**Inherited unchanged from Phase 10 (D-05, global).** The declared legal set:
4 (`*-1`) · 8 (`*-2`) · 12 (`*-3`) · 16 (`*-4`) · 24 (`*-6`) · 32 (`*-8`) · 48 (`*-12`) · 64 (`*-16`).

All prior exceptions carry forward; **Phase 15 renders one of them — the 44px touch target** — and
declares **no new app-side box exception**. The auth column keeps the shipped `max-w-sm` (384px) and
`py-12` (48px, a ladder step); the card's padding is `PanelCard`'s own `p-4 sm:p-6`.

### Email spacing — declared as constants beside the shell, values on the app's own ladder

The email shell cannot read the spacing tokens, so its pixel values are declared once, in the shell
module, each a multiple of 4, and never retyped per send:

| Slot | Value | Derivation |
|---|---|---|
| Column width | **600px** | EMAIL-01's requirement text. `width="600"` attribute (Outlook) + `max-width:100%` inline (narrow mobile clients) |
| Outer ground padding | **24px** top/bottom | one `lg` step of quiet around the column |
| Card cell padding | **32px 24px** | 32 vertical / 24 horizontal — the panel-scale rhythm at email width |
| Wordmark block → body | **24px** | the same wordmark-to-card distance the auth screen uses |
| Paragraph spacing | **16px** (`margin:0 0 16px`) | the app's default element spacing |
| CTA block margins | **24px 0 24px** | a section break either side of the one action |
| CTA inner padding | **12px 24px** | yields a ≥44px-tall tap target at 16px/1.5 label |
| Footer rule → footer text | **24px** padding-top over a 1px border-top | section padding |

**No other pixel value.** A send needing a bespoke gap is a scope alarm — its content belongs in
paragraphs, not in layout.

### One duplication this phase ends, mechanically

`mx-auto w-full max-w-2xl px-4 py-10` is hand-typed twice — on `(app)/profile/page.tsx:36` and its
`loading.tsx:18`. **Resolution: `/profile` adopts the existing `BOOKING_SHELL`**
(`"mx-auto w-full max-w-2xl px-4 py-8 sm:py-12"`, already in `measurements.ts`) on the page AND the
plate — the same width, the booker surfaces' shared vertical rhythm, and one owner instead of two
literals. The only rendering change is vertical padding 40px → 32px mobile / 48px `sm:` up, which is
what stops `/profile` being the one booker-shell page with its own rhythm (the exact argument
`HOST_PANEL_SHELL` made for `/host`). Flagged in § Open Questions.

## Typography

**Inherited unchanged.** Four named roles, per-theme, pinned by `tests/design/type-scale.test.ts`.
Arbitrary `text-[NNpx]` is banned by ESLint **and** a Vitest gate.

| Role | court | Phase 15 uses it for |
|------|-------|----------------------|
| Display | 28 / 1.15 / 600 / -0.02em | **Nowhere.** No Phase-15 surface carries a display-scale heading |
| Heading | 20 / 1.30 / 600 / -0.01em | The auth card's `<h1>` (via `PanelCard title` at `text-heading`); `/profile`'s `<h1>` (via `PageHeader`); the profile panels' `<h2>` titles |
| Body | 16 / 1.50 / 400 / 0 | Form inputs and their values; the forgot-password uniform message; email body paragraphs (mapped, § The Email Shell) |
| Label | 14 / 1.43 / 400 / 0 | Field labels, form descriptions, cross-links, error/status lines, the card's secondary links; email footer text (mapped) |

**The wordmark treatment — ONE declaration, three consumers.** `site-chrome.tsx:95` declares
`BRAND_CLASS = "text-lg font-semibold tracking-tight"` (18px / 600 / -0.02em court, ink inherited
`--foreground`; no logo asset, D-127). This constant is **exported** and the auth layout's wordmark
imports it — the falsifiable form of "one identity, two surfaces". The email wordmark renders the
same treatment as inline styles: `font-size:18px; font-weight:600; letter-spacing:-0.02em;` ink =
the `--foreground` hex from `tokens.generated.ts`.

### Four type rules this phase adds

**1. `/profile`'s `<h1>` stops being the app's last 24px outlier.** `profile/page.tsx:38` renders
`text-2xl font-semibold tracking-tight` — the same outlier Phase 14 retired on the wizard.
**Decision: the heading becomes `PageHeader`'s `<h1>`** at the 20px every adopted surface uses, and
the plate moves in the same commit (its own header comment says it exists only because the page had
not adopted the pattern). **Falsifiable:** `/profile`'s `<h1>` and any adopted booker page's `<h1>`
compute an identical `font-size` at 320 / 768 / 1280.

**2. The auth card's heading is a real `<h1>`, and it is the document's only one.** Today the four
auth pages render `CardTitle` — a `<div>` — and **no `<h1>` at all**. The `PanelCard` conversion
passes `titleAs="h1"`, so each auth document gains exactly one `<h1>` at `text-heading`.
**Falsifiable:** `getByRole("heading", { level: 1 })` resolves to exactly **1** on all four auth
routes, in every state (including forgot's post-submit branch and reset's missing-token branch).

**3. No 12px interactive text on an auth card.** `login/page.tsx:148` renders `Forgot password?` at
`text-xs`. It moves to `text-sm` (14px), matching the card's other links. The non-interactive "or"
divider keeps its `text-xs` — it is chrome, not a control.

**4. The profile section headings become the pattern's own.** `text-lg font-medium` (18px) on the two
`<h2>`s becomes `PanelCard`'s `title` at `text-heading` (20 / 600), with the explanatory sentence as
the pattern's `description`. Zero hand-rolled heading classes survive on the surface.

- **`PublicHeader` leaves this layout.** D-162 puts the wordmark *above the card*; a second wordmark
  in a header is byte-for-byte the duplication SHELL-01 removed (the shipped layout's own comment
  block records both that removal and that "Phase 15 may decide otherwise with the whole surface in
  front of it" — this is that decision, taken). The cross-navigation the header carried is already on
  every card (`Create an account` / `Log in` / `Back to log in`). Flagged in § Open Questions.
- **`SiteFooter` stays.** SHELL-02's recorded argument binds: `/terms` and `/privacy` must be

- **The centering column becomes `<main>`.** The shipped tree renders no `<main>` on any auth
  document, and `(auth)/error.tsx`'s header records why it could not add one (a landmark only present
  in the failure state encodes an error). Putting the landmark in the LAYOUT dissolves that caveat:

- **The ground stays `bg-muted`** — the shipped quiet ground, a declared pairing, and now also the
  email's outer-ground figure (§ Color).
- **The wordmark**: text `FitOut`, the exported `BRAND_CLASS`, links `/`, centered, 24px above the
  card (`space-y-6`). It is the first tabbable element on the page. Browser-default focus indicator,
  exactly like the header links (the DS-05 recipe is for controls that override their outline; this
  link overrides nothing).
- **Expected build-output side effect, stated so it is not "fixed":** with the header's session read
  gone, the four auth routes may flip `ƒ Dynamic` → `○ Static`. That is the harmless inverse of the
  flip plan 11-10 predicted when the header arrived. The security boundary was never the layout
  (per-page gates + middleware, unchanged).

## The Email Shell (EMAIL-01 · EMAIL-02 · D-160 · D-161)

### The contract in one paragraph

**One renderer, nineteen adopters.** Every exported send in `src/lib/email.ts` composes
`renderEmail(content)` (name illustrative) which returns `{ html, text }`; the private `send()` gains
a `text` parameter and passes both to Resend. Subjects, recipients, argument lists, call sites and
the conditions under which anything fires are **byte-identical** — EMAIL-01's "not a single send
trigger moving" is proved by `tests/booking/notify-emission.test.ts` and the auth flow tests passing
with the trigger-graph assertions unmodified, not claimed.

### The content type — one derivation, two outputs (the week-strip lesson applied to email)

```
type EmailContent = {
  preheader?: string            // optional override; DEFAULT: the first sentence of the text part
  heading: string               // RAW — the renderer escapes it for HTML
  paragraphs: string[]          // RAW — escaped for HTML; verbatim (unescaped) in the text part
  cta?: { label: string; href: string }   // label + href escaped for HTML; the raw href gets its
                                          // own line in the text part
  tableHtml?: string            // PRE-ESCAPED raw block — the ops digest's table ONLY. A send
                                // passing this must also pass tableText for the plain-text twin
  tableText?: string
}
```

- **Escaping becomes structural (WR-01, strengthened).** The renderer HTML-escapes `heading`, every
  paragraph, the CTA label and the CTA href at the one choke point, so no send can forget. Literal
  prose apostrophes rendering as entities is correct HTML and invisible to a mail client. The
  **plain-text part takes the raw strings** — it is `text/plain` and escaping it would be a defect.
  `renderOpsAlertDigest` keeps its own per-field `escapeHtml` (its output enters via `tableHtml`, the
  one pre-escaped slot) and stays a pure exported renderer so the PII assertion keeps reading the
  body directly. **`tests/auth/email-escaping.test.ts` passes with ZERO edits** — the escaped URL
  still appears in the `href`, the raw payload still appears nowhere in the HTML. A new structural
  test drives one injection probe through **every string parameter of all 19 senders** and asserts
  the raw payload absent from every rendered HTML — the same guarantee, now over the whole surface.
- **The plain-text part cannot drift from the HTML** because both are projections of one
  `EmailContent`. Shape: heading line · blank · paragraphs · blank · `{cta.label}: {raw href}` ·
  blank · footer lines. No send authors a second copy of anything.
- **The preheader is DERIVED by default** — the first sentence of the text part — so it also cannot
  drift. Mechanics: one `<div>` immediately after `<body>` with the standard suppression styles
  (display none, zero max-height, hidden overflow, `mso-hide:all`) plus zero-width-joiner padding so
  trailing body text does not leak into the preview line. No send passes an override initially; the
  parameter exists so a future phase can without re-architecting.

### The 600px skeleton — Outlook-safe even though Outlook verification is blocked (D-163)

```
<body style="margin:0;padding:0;background:{--muted}">
  [preheader div]
  <table role="presentation" width="100%" (ground)>
    <tr><td align="center" style="padding:24px 0">
      <table role="presentation" width="600" style="max-width:100%;background:{--card}">
        <tr><td style="padding:32px 24px">
          [wordmark block: "FitOut", 18px/600/-0.02em, {--foreground}, padding-bottom:24px]
          [heading: <h1-equivalent as a styled <p> or <h1>>, 20px/600, {--foreground}]

                then IFF SUPPORT_EMAIL !== null: the support line]
        </td></tr>

```

Construction rules, each independently checkable against the rendered string:

- **`role="presentation"` on every layout table** so screen readers in web clients do not read the

- **`border-radius` is progressive enhancement** — Outlook squares the CTA; accepted.
- **`lang` and a `<title>`** on the HTML document; the title is the subject's text.
- The ops digest's table keeps its semantics (`<th>` headers, per-cell borders now coloured from

## Anti-Patterns — reject these in plan review

- **A second wordmark on an auth screen.** The layout renders one; a page or card adding another
  recreates the SHELL-01 defect this composition exists to end.
- **An image, webfont, `<style>` block, flex or grid in an email.** The shell is tables and inline
  styles — the Outlook-safe construction D-163 mandates even though Outlook verification is blocked.
- **A hex typed anywhere in the email pipeline.** Colour enters through `THEME_TOKENS[...]` reads
  only. A hand-typed value is exactly the drift DS-12 measured and closed.
- **A retyped theme name in `email.ts`.** One owner, two readers (§ EMAIL-02).
- **`React Email`, `MJML`, or any templating dependency.** D-66, restated by the ROADMAP constraint.
- **Moving, adding or removing a send trigger** — including "helpfully" awaiting a `void` call in
  `auth.ts` or adding a second dispatcher. SC#3 and D-83 both bind.
- **Enriching the verification/reset emails** — an expiry line, an "if you didn't request this"
  sentence, a post-reset landing change. AUTHFB-01/02 stay in the backlog; near-free is a roadmap
  amendment to PROPOSE, not scope to absorb.
- **A placeholder support address, a "coming soon" contact, or an unguarded `mailto:`.** D-161/D-64.
  The slot is wired and empty; only `SUPPORT_EMAIL !== null` lights it.
- **A visible fabricated sender identity.** The sender is `EMAIL_FROM`'s reach only (D-160).
- **Coral anywhere but the one primary per card and the one CTA per email.** `Save profile`,
  `Continue with Google`, `Upload photo` and every link stay neutral.
- **A green "saved"/"updated" treatment.** Both notices carry their own D-14 comments; the sentences
  are the signal.
- **A `role="status"`/`role="alert"` on content present at first paint.** The two demotions in § The
  Auth Composition are the rule applied; do not reintroduce the shape elsewhere.
- **An `EmptyState` on an auth screen.** Nothing here has a data list; a fabricated empty state is
  an absence dressed as content.
- **Extracting an `AuthCard` pattern or any fourth card container.** DS-11 says three;
  the four `PanelCard` call sites + one layout ARE the shared composition.
- **A `data-testid` not in `selector-contract.ts`.** Compile error, not review comment.
- **Touching the avatar mechanism beyond styling.** Removal and crop are Phase 16 (CROP-01/03);
  leave the action row able to hold the future control, add nothing.
- **A skeleton for the `Member since` line or the first name.** Data-derived and conditional — the
  plate's own comment already rules it out; keep it ruled out.
- **Quoting a banned class or a raw colour value in a comment** — including comments inside the email
  shell. Three plans have been burned; name tokens descriptively.
- **A schema migration.** PROJECT D-136.

## Open Questions — flagged for the PM, not blocking

1. **`PublicHeader` leaves the `(auth)` layout.** D-162's "wordmark above the card" plus SHELL-01's
   no-two-wordmarks rule force the choice, and every navigation the header offered a **signed-out
   visitor** survives on the cards. A signed-in visitor on `/forgot-password`/`/reset-password` — an
   intentionally reachable path (`src/middleware.ts:68-69`, "a user resetting from a verified-but-stale
   device") — loses the header's mode switch, notification bell and profile link and must route
   wordmark → home to reach them; accepted tradeoff (checker-verified 2026-08-24), no route is
   orphaned and tab order stays sound. Reversible by re-adding the header and demoting the centered
   wordmark — one layout edit; nothing else depends on it.
2. **The verification and reset emails' CTA labels** (`Verify email` / `Reset password`) replace a
   raw URL rendered as anchor text — the one copy change in the email half, taken because a shell
   button cannot carry a URL as its label and the raw URL survives in the plain-text part. If the PM
   reads this as AUTHFB-01 territory, the fallback is the URL as the button's visible label — ugly
   but zero new words.
3. **`/profile` adopts `BOOKING_SHELL`**, shifting vertical padding 40px → 32/48px to match every
   other booker page. If the PM prefers the shipped rhythm, the alternative is a one-line
   `PROFILE_SHELL` constant — the duplication still ends either way.
4. **The ops digest wears the branded shell.** EMAIL-01 says all 19 sends and this spec obeys it; an
   operator-only email arguably wants density over identity. Excluding it later is bounded but larger
   than one row — the adopters, visual-hierarchy and accent-budget rows plus acceptance criteria
   #13/#16 all say "all 19", and an 18/19 split reintroduces the special case the shell exists to end
   — a noted EMAIL-01 carve-out if the PM prefers.
5. **Forgot/reset drop the Google button and divider** — they never had them; recorded so nobody
   "completes" the composition by adding them. A recovery flow offering an OAuth sign-in is a flow
   change, not a restyle.
