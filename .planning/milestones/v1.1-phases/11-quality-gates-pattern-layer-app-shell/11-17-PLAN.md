⚠ CORRECTION TO THE UI-SPEC's STATED RULE (11-RESEARCH § STATE-01, measured against the build manifest):

  The UI-SPEC says "a route needs a loading.tsx if its page.tsx awaits anything." Implemented as an await
  grep that flags all four (auth) pages, whose awaits are inside CLIENT-SIDE EVENT HANDLERS
  (`await authClient.signIn.email(…)`), not server renders. All four are "use client" and all four build as
  ○ Static; a loading.tsx for them would never render.

  THE CORRECT DISCRIMINATOR IS: **the default export is `async`.** It correlates 1:1 with the build
  manifest's ƒ (Dynamic) marker across all 25 pages — measured, not assumed — and it is AST-checkable with
  this repo's existing ts.createSourceFile idiom.

  20 routes qualify · 2 have one today · 18 are new.
  Does NOT need one — 5 routes: (auth)/login, (auth)/signup, (auth)/forgot-password, (auth)/reset-password
  (all "use client", sync, ○ Static) and /dev/theme (sync server, ○ Static). This matches the UI-SPEC's own
  carve-out that the static legal pages get no loading.tsx.

  NOTE: plan 11-10 moved three of these routes into route groups. The 20 are enumerated in this plan's
  `files_modified` at their POST-MOVE paths.

The / case, counter-intuitive and stated so nobody deletes half of it:
  SearchResults wraps router.push in startTransition, so React keeps the current UI and flags isPending
  rather than falling back to loading.tsx. That in-component skeleton is CORRECT and must not be deleted;
  loading.tsx covers first load and hard navigation. BOTH must render the SAME CardGridSkeleton, or the
  same page shimmers two different ways depending on how you arrived.

Skeletons NOT to build: nothing under ~1s, and nothing whose box metrics are unpredictable — a skeleton that
does not match its content causes the layout shift it was built to prevent. Where metrics are unpredictable,
use an in-place spinner.
