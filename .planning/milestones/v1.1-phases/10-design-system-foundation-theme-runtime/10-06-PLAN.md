  <action>
    Make four changes to `buttonVariants` and add one size.

    Base string (`:8`): replace `focus-visible:border-ring focus-visible:ring-3 focus-visible:ring-ring/50`
    with `focus-visible:ring-2 focus-visible:ring-ring focus-visible:ring-offset-2 focus-visible:ring-offset-background`.
    Declaring `ring-offset-background` explicitly is required, not optional: Tailwind's default
    `--tw-ring-offset-color` is a literal `#fff`, which is a leak in all but name and would be visibly
    wrong on grove's tinted `#f7fcfc` background. The offset band guarantees the indicator has a verified
    3:1-or-better surface on both sides. Leave `text-sm font-medium` alone — it now renders at the theme's
    emphasis weight because plan 10-04 aliased `--font-weight-medium` onto it; that is an accepted visible
    change requiring zero edits here.

    Add a `brand` variant:
    `bg-brand text-brand-foreground hover:bg-[color-mix(in_oklch,var(--brand),var(--foreground)_10%)]`.
    Do NOT write `hover:bg-brand/90`. `10-RESEARCH.md` § Code Examples still contains a CVA block with
    that exact string and copying it verbatim reintroduces the failure: an alpha tint over a light surface
    lightens, and `brand-foreground` on `brand/90` measures 4.04:1 in court and 3.87:1 in grove against a
    4.5 bar. The `color-mix` form darkens instead — court `#c32b37` at 5.41:1, grove `#137470` at 5.36:1 —
    and it is not a new vocabulary: it is the idiom already shipped at `:16` for `secondary`. This is also
    not a `--brand-strong` escape hatch: there is still exactly one brand value and zero per-call-site
    judgement, because the hover lives once, inside the variant.

    Change `default`'s hover from `hover:bg-primary/80` to
    `hover:bg-[color-mix(in_oklch,var(--primary),var(--foreground)_10%)]` — for consistency of mechanism
    only; the shipped `/80` measures 9.19:1 and was never failing. `default` otherwise stays neutral
    `--primary` near-black (D-21); do not change `defaultVariants`.

    Change `destructive`'s hover from `hover:bg-destructive/20` to
    `hover:bg-destructive hover:text-destructive-foreground`. Deepening the tint moves the surface toward
    the text colour, which is the wrong direction and is why `/20` measures 4.01:1; the solid fill with
    the new `--destructive-foreground` token measures 5.52:1 in both themes.

    Add a `touch` size to the `size` map, following `default`'s shape:
    `h-11 gap-1.5 px-4 has-data-[icon=inline-end]:pr-3 has-data-[icon=inline-start]:pl-3`. `h-11` is
    44px and is already on the 4px grid, so it needs no arbitrary value. It is an explicit opt-in size
    (D-22), never a responsive default — a responsive default would silently change every dense host
    table's mobile rendering at once. Record in a comment that nothing enforces adoption automatically, so
    Phase 17's a11y audit is the mechanism that catches missed call sites.

    Leave `text-[0.8rem]` at `:27` in place: the leak pattern is px-only and the 4 vendored rem sites are
    recorded, tolerated debt. Leave the `dark:`-prefixed utilities in this file untouched — THEME-05 pins
    the vendored count at exactly 56.

    Create `tests/design/button-variants.test.ts` importing `buttonVariants` from
    `@/components/ui/button`. Assert over the classes that actually paint: `buttonVariants({ variant: "brand" })`
    contains `bg-brand`, `text-brand-foreground` and `color-mix(in_oklch,var(--brand)`, and does NOT
    contain `bg-brand/90`; `buttonVariants({ size: "touch" })` contains `h-11`;
    `buttonVariants()` with no arguments contains `bg-primary` and does NOT contain `bg-brand` (D-21 —
    the un-varianted button is neutral); the returned base string contains `focus-visible:ring-ring` and
    `focus-visible:ring-offset-background` and does NOT contain `ring-ring/50`;
    `buttonVariants({ variant: "destructive" })` contains `hover:bg-destructive` and
    `hover:text-destructive-foreground` and does NOT contain `hover:bg-destructive/20`.
