<objective>
Widen the server-computed all-in table from one figure per key to `{space, fee, total}`, and flip
`PriceBreakdown` across the Server/Client boundary so the listing rail can render the real component.

Purpose: BFLOW-04's claim is that the rail and checkout show *the same fact*, and the only way to make
that true rather than asserted is for there to be one component. The spec calls this a re-render; it is a
boundary change on the money surface, and it is the second architectural seam.
Output: `AllInParts`, a client `PriceBreakdown` with a `surface` prop, and the phase's price gate.
</objective>

The widened table. `ALL_IN_TABLE_MAX_HOURS` is 24, so `hourly` holds 24 keys.

  export type AllInParts = { space: number; fee: number; total: number };
  export type AllInTable = {
    hourly: Record<number, AllInParts>;
    fullDay: AllInParts | null;
    perPass: Record<number, AllInParts>;
  };

Everything that makes the current table correct MUST survive: `computeServiceFee`'s rate argument stays
OMITTED (its default IS `SERVICE_FEE_BPS`, so the table is produced by the same call checkout makes); the
table stays keyed by the selection the booker actually made, because the fee rounds ONCE over the whole
space price and a client-side multiply drifts by up to n-1 centavos; and a MISSING KEY still means no
estimate line, never a client computation.

`PriceBreakdown`'s one new prop:

  surface?: "rail" | "checkout"      // defaults to "checkout", so the shipped call site is byte-identical

  |                                              | "rail"                        | "checkout"                                        |
  | rows, order, weights, tabular-nums, `Total`   | identical                     | identical                                         |
  | trailing line                                 | `Includes our service fee.`   | `Includes our service fee. You'll pay this now.`  |
  | total hook                                    | `rail-price-total`            | `price-total` (shipped, unchanged)                |

⚠ THE TESTID GATE IS BIDIRECTIONAL AND ITS COLLECTOR READS STRING LITERALS ONLY. `tests/design/
selector-contract.test.ts`'s AST walk resolves a `data-testid` value only when it is a string literal (or
a JSX expression wrapping one). `data-testid={MAP[surface]}` and `data-testid={cond ? "a" : "b"}` both
resolve to null, so the declared row would be "rendered NOWHERE in src/" and `npm run build` fails.

THE SHAPE THAT WORKS, and it is a planner decision rather than an executor's: render the total row through
TWO sibling JSX branches, each with its own literal `data-testid`, both consuming ONE shared class
constant so AC#8's computed-style identity is true by construction rather than by copy-paste. A single
element with a computed id is the shape that goes red on day one.

⚠ `price-breakdown.tsx` carries a GREP TRIPWIRE (its header states it). Two whole-source greps guard its
copy: one for the tax-sounding bundle (C1 / D-73), one for the three C7-forbidden reassurances enumerated
in `.planning/milestones/v1.0-ui-specs/07-UI-SPEC.md`. NONE of those phrases may be spelled contiguously
anywhere in that file, comments included. The rail's line is a strict PREFIX of the shipped checkout line,
which is exactly what keeps it safe — do not "improve" it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server money computation -> client render | A client component may receive money as a finished figure; never as the ingredients to compute one (D-130) |
| declared copy contract -> rendered copy | A price surface that re-bundles the fee under a tax-sounding label is a regulatory and trust failure |
| one hook, two documents | Two breakdowns in one document sharing one testid makes the DB-vs-DOM parity assertion read whichever came first |
