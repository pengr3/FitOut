THE MEASURED DEBT: `ui/calendar.tsx` sets `--cell-size` to the 7-step (28px). Four things read it — the day
button's `min-w`, both nav buttons (`size-(--cell-size)`), the weekday row and the caption.

OVERRIDE 1 (necessary, not sufficient): `CALENDAR_CELL` on the `Calendar` ROOT's `className`. That re-sizes
nav, weekday and caption in one edit because all three read the variable.

OVERRIDE 2 (the day button, and the one that must be measured): go through the EXISTING
`components={{ DayButton }}` seam, which passes `className` through `cn(base, defaultClassNames.day,
className)` — i.e. tailwind-merge. The override's shape is `aspect-auto min-w-0 h-11 w-full` plus the
existing selected/hover data-attribute classes.

  ⚠ MEASURE-FIRST, DO NOT ASSUME THE MERGE. `cn()` is clsx + tailwind-merge v3. tailwind-merge's `size`
  group is declared as conflicting with `h`/`w`, which removes EARLIER `h-*`/`w-*` — not later ones. So a
  later `h-11` does NOT delete the earlier `size-auto`; both survive into the class string and the winner
  is decided by Tailwind v4's own utility ordering in the emitted stylesheet. AC#14 is not satisfied until
  a rendered `boundingBox()` says so.

  ESCAPE HATCH, if the merge does not resolve cleanly: the `classNames={{ day: ... }}` prop. But
  `ui/calendar.tsx` spreads `...classNames` LAST, so that path REPLACES the composed default and every
  dropped class must be restated — the `group/day` marker, the cell radius, `p-0`, `text-center`,
  `select-none` and the range selectors. Take it only if the measurement forces it, and if you do, list
  every restated class in the SUMMARY.

  ⚠ `src/components/ui/calendar.tsx` IS NEVER EDITED. The cell size is a `className` variable override.

THE 41px WIDTH IS A DECLARED CONSEQUENCE, NOT A FAILURE. Seven 44px cells is 308px; at the 320px floor
with `px-4` the content box is 288px. The cell's HEIGHT stays 44px at every width; its WIDTH is `1fr` and
falls to about 41px between 320px and roughly 376px viewport. 41 clears the WCAG 2.5.8 AA 24px bar with
room to spare, and the alternative — a horizontally scrolling month grid — fails both the responsive and
the keyboard gate.

THE TWO SKELETONS:
  day panel (slots)  SLOT_CHIP_BOX x 8, inside `role="status" aria-busy="true"` with `aria-label` AND an
                     `sr-only` child reading `Loading times for {day}`; every bar `aria-hidden="true"`
                     (the region shape already landed in plan 12-06; this plan adopts the BOX)
  month grid (NEW)   7 x 6 cells at CALENDAR_CELL, `role="status" aria-busy="true"`, `aria-label` AND an
                     `sr-only` child reading `Loading the calendar`, hook `data-testid="skeleton-calendar"`

⚠ RESEARCH Pitfall 9 — `SLOT_CHIP_BOX` is `h-11 w-20`, and the UI-SPEC derives the `w-20` half from "the
real chip's minimum". MEASURED: the real chip has `min-h-11` but NO minimum width; its width is
content-driven. If the constant becomes the single source of both, the REAL CHIP MUST GAIN ITS MINIMUM
WIDTH IN THE SAME COMMIT, or the skeleton and the chips are not the same box and the constant's whole
argument fails.

MOTION: `--motion-fast` 120ms / `--motion-base` 200ms / `--motion-slow` 320ms, capped at 320ms by
`tests/design/motion-budget.test.ts` with the pulse and spin animations exempt. The month grid gets NO
enter/exit animation at all; the only motion is the nav button's own `--motion-fast` transition.
