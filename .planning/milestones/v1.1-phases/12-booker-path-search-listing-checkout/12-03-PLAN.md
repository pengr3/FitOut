<interfaces>
The context, and it is BIDIRECTIONAL — the UI-SPEC does not say so, and it is the whole composition:

  type HoldCtx = {
    expiresAt: string | null;        // ISO instant, published by the PAGE
    expired: boolean;                // published by the COUNTDOWN, read by ReserveView
    publishExpiresAt: (iso: string | null) => void;
    markExpired: () => void;
  };

Today `reserve-view.tsx` passes `onExpire` DOWN into `HoldCountdown`. With the countdown in the header the
wiring inverts. Two values total. No hold data is fetched in the layout; no money or availability
computation moves client-side.

`book/layout.tsx` stays a Server Component. Wrapping `{children}` in a client provider does NOT client-ify
the page — `children` is still server-rendered and passed through as an already-rendered node. That is the
standard App Router composition and it is the reason this works at all.

The header slot's contract:

  HOLD_COUNTDOWN_BOX = "h-8 min-w-24"    (from 12-01; 96px reuses AUTH_SLOT_CONTROL rather than inventing
                                          a second reservation width)
  data-testid="hold-countdown"           (exactly 1 per document — no digits in the rail)
  role="timer" + aria-live="off" on the digits            (shipped and correct; not re-decided)
  a SEPARATE sr-only polite region whose text changes exactly ONCE in the component's life
  sr-only accessible name: `Time left to confirm`
  final 60s: numerals turn `text-destructive` — the ONLY destructive use on this path, and never the sole
             carrier, because the threshold announcement fires at the same moment
  on expiry: the static string `Hold expired`, NO role="timer", NO live region
  before publish: an empty HOLD_COUNTDOWN_BOX

The one way back (12-UI-SPEC § Checkout):

  Button variant="ghost" size="touch" asChild wrapping a Link
  placement: the LAST element of the checkout main column, below the summary. Never in the header, never
             in the rail, never in the sticky bar.
  href:      `/listings/{id}` carrying the same `?date=&start=&end=` window the booker searched
  label:     `Back to the listing`
  beneath:   `We'll keep your hold — the timer keeps running.` (text-xs text-muted-foreground)

  ⚠ It must NOT carry `resume=1`. That param auto-fires a hold on arrival (`book-cta.tsx`'s resume block),
  which would turn a back link into a hold-creating GET — the T-04-GETDUP shape. Safe by construction
  otherwise: `createPendingHold` replays a booker's OWN hold for the same window rather than minting a
  second one.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| checkout page -> layout header | An untrusted or unauthorised hold value must never reach the header by a second read path |
| booker navigation -> hold creation | A GET that creates a hold is a duplicate-hold vector |
| client countdown -> confirm authority | The countdown is a display cue; it must never be the thing that decides a hold is alive |

| T-12-03-GETDUP | Tampering | the way-back link | mitigate | `href` is `/listings/{id}` with the searched window only and explicitly WITHOUT `resume=1`; asserted by `e2e/shell.spec.ts` (`<a href>` inside `<main>` === 1, starts with `/listings/`, contains no `resume`) |
| T-12-03-HOLDIDOR | Information disclosure | hold read | mitigate | The owner-gated read, the path-id cross-check and both `notFound()` calls in `book/page.tsx` are byte-unchanged; the layout fetches NO hold data and the provider carries one ISO string and one boolean |
