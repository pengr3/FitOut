## The three things this plan is actually about

### 1. The prediction is committed at its own SHA, so the ordering is checkable

*"A prediction written after reading a diff is not a prediction, it is a description."* That claim is worthless if the only evidence for it is where the text sits in a file. `D1` was written into `17.1-EVIDENCE.md` and **committed as `9507989`**; `gh workflow run baselines.yml --ref dev` was invoked afterwards, producing run 33336290052 at `e2863a7`. The ordering is a fact about git, not about prose.

`D1` names **all 36 rows** — 2 expected to move with their mechanism, 34 expected to hold each with the reason it should hold — and folds in two things §7a could not have known:

- **`§ P4`'s measured rows.** Plan 17.1-04 shipped **Shape A**, whose whole point was that it moves nothing (`checkout-320` 80px→80px, `checkout-1280` 48px→48px, and no `checkout-768` baseline exists). The counterfactual Shape B would have moved `checkout-320` by +32px and forced the prediction to **3 changed**. Folding `§ P4` in *before* dispatching is what let the number stay at 2 honestly rather than by luck.
- **The seam.** `baselines.yml` boots the app with `npm run dev`, so 17.1-06's `instrumentation.ts` was **live inside the generation job** — a condition none of §7a's three runs had. `D1` predicted zero rows in advance, specifically so that a moved row would read as the seam's doing rather than be explained away afterwards. Zero rows moved.

### 2. The generation run is not the evidence, and the record says so in its own text

Run **33336290052** (`baselines`, `workflow_dispatch`, `e2863a7`) went **success**, staged **2** files, and pushed `e48654f`. §7b records it under the heading *"Generation run — NOT the evidence"* and then says why in body text rather than leaning on the heading:

> the commit is pushed with `GITHUB_TOKEN`, and a `GITHUB_TOKEN` push triggers no workflow — so **at the instant this run went green, nothing had ever compared against the two PNGs it had just written.**

The recursion-prevention property and the nobody-has-verified-these property are the *same sentence*, and only the first half is memorable. The job's own `always()` step fired the `::warning::` saying so on the run page.

### 3. Something compared — and that is §7d

`ci.yml`'s trigger block, read off the **parsed** tree, is `triggers=["push","pull_request"]`. **No `workflow_dispatch`**, and "Re-run all jobs" on an older run re-runs at that run's SHA, which predates the new PNGs. ## ⚠ For the orchestrator — four uncommitted artefacts, deliberately

`git status --porcelain` shows the §7d edit and this SUMMARY, plus `STATE.md` / `ROADMAP.md` once state is recorded. **All four are intentionally uncommitted** and listed under `uncommitted_for_orchestrator:` above — this repo's established idiom (quick `260828-qd5`).

**The reason is the deliverable itself.** §7d asserts `headSha == git rev-parse HEAD`. Any commit landing after `d87ff54` moves `HEAD` and makes that assertion false — so the act of committing the record would destroy the thing the record claims. §7d cannot exist before the run it describes, so it cannot be inside the commit that triggered it.

The plan enumerates *"§7d's record and the plan SUMMARY"* as the only two. `STATE.md` and `ROADMAP.md` are held the same way for the same reason: they are downstream documentation of a run that has already happened, and committing them would move `HEAD` exactly as a §7d commit would. Holding them uncommitted honours the invariant the plan's "only two" exists to protect.

**When you commit them,** that docs-only commit will trigger its own `ci` run. Its conclusion must **also** be green, and §7d carries a labelled slot for it — **append it as a confirmation line, never as a replacement** for run 33336650152 on `d87ff54`.
