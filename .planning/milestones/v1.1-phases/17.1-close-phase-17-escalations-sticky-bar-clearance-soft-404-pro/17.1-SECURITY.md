## 4. Accepted risks log

### AR-1 — T-17.1-04 · Information Disclosure (ASVS V4) · `src/app/(app)/bookings/[id]/not-found.tsx`

**Disposition: ACCEPTED.** This is a deliberate design property, not an omission.

The booking owner gate serves **one document for two different facts**. `page.tsx:279` reads
`if (!bk || bk.bookerId !== userId) notFound();` — a single call for both "no such booking" and "that
booking is not yours" — and `page.tsx:226` does the same for an absent session. All three land on
`(app)/bookings/[id]/not-found.tsx`, which renders one `EmptyState`: *"We couldn't find that booking"*
/ *"The link may be old, or the booking may belong to a different account."* The same status, the same
copy, the same timing. That is `T-04-CONFIRMIDOR`: distinguishing the two cases would turn booking-id
enumeration into an existence oracle. The sibling route `cancel/page.tsx:156` and `group/page.tsx:117`
carry the identical shape, and `group/page.tsx:11` documents the invariant in prose.

**Verified unchanged by this phase.** The only commit in phase 17.1 touching that path is `7c3444b`
(plan 17.1-02), and its diff on that file is **+5 / −2, entirely inside a `//` comment block** — it
re-points a cross-reference from the `(detail)/not-found.tsx` this phase deleted to `src/app/not-found.tsx`,
and says so in the comment itself. No render, no branch, no status, no copy moved.

**Residual risk accepted:** a caller who can guess a booking id learns nothing about whether it exists.
The accepted cost is the inverse — a legitimate owner who is signed into the wrong account is told only
that the booking may belong to a different account, and cannot tell a typo from a permissions problem.
That trade is deliberate and is the correct one for this route.

**Re-open if:** any `bookings/[id]/**` route gains a second not-found boundary, a distinguishing status
code, distinguishing copy, or a measurably different response time between the two cases.

## 5. Transferred risk

### TR-1 — TF-D29 · Tampering (supply chain) · `package.json` → **TRANSFER, accepted as documented**

**Finding, independently re-measured at audit time — it is real:**

```
$ npm ls undici --omit=dev
fitout@0.1.0
`-- better-auth@1.6.14
  `-- vitest@4.1.8
    `-- jsdom@29.1.1
      `-- undici@7.27.0

$ node -e "…package-lock.json…"

node_modules/undici version=7.27.0 dev=false peer=false optional=false
node_modules/vitest version=4.1.8  dev=false peer=false optional=false
```

`better-auth` is a **production** dependency declaring `vitest` as an optional peer; npm satisfies it
from the hoisted root copy, and a peer edge originating at a production package is not a dev edge. The
consequence is general and load-bearing: **`devDependencies` is not a production-exclusion boundary in
this repo.** Any argument of the form *"it is a devDependency, so production never resolves it"* is
unsound here until this is closed.

**Genuinely pre-existing and unchanged by this phase.** `[17-D29]` records the same reading at `2822284`
(before the `undici` declaration) and at `ab7001b` (after it) — identical. The only manifest commit in
phase 17.1 is `ab7001b`, a one-line pin approved at a blocking human supply-chain gate.

**Transfer documentation exists and is adequate** — `deferred-items.md` `[17-D29]` carries: found-by,
owner file, severity, the traced mechanism, the measurement in both directions, the cheapest correct
fix (assert the intended scope with `npm ci --omit=dev --dry-run`, or pin the peer out of the production
graph), an explicit **do-not-do-this** (deleting the `undici` pin loses version control and keeps the
exposure), and a named owner.

**Registered correctly:** raised by SUMMARY 05 as `threat_flag: supply-chain` on `package.json`, mapped
to `[17-D29]`. Not an unregistered flag.

**⚠ Gap in the transfer target, recorded rather than smoothed over.** `[17-D29]` names the owner as
*"whichever plan next opens `package.json` for a dependency decision; and Phase 18's CI/deploy work,
where the production install is actually performed."* The first half is a real, actionable owner. The
second half **points at a phase that does not carry that work**: `ROADMAP.md:779-793` scopes Phase 18 as
*Search-Results Map* — MAP-01…MAP-04, a net-new booker-facing feature — with no CI, deploy or
production-install work in its Success Criteria or its scope-discipline note. A transfer to a phase whose
charter cannot receive it is a transfer that will quietly not happen.
**Recommended:** re-point `[17-D29]`'s phase reference at whichever phase actually owns the production
install, or land the cheap half now (the `npm ci --omit=dev --dry-run` assertion is a test, not a
re-scoping, and it is what keeps the property true once decided).
