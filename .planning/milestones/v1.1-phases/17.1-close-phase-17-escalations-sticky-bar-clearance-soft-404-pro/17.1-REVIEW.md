### WR-01: The deny-of-one net-connect predicate is host-exact — a non-default port or any sibling `paymongo.com` host leaves the machine

**File:** `instrumentation.ts:125`, `instrumentation.ts:166`
**Issue:** `INTERCEPTED_HOST` is compared with `!==` against the value `undici` passes the predicate,
which is `url.host` — **host including the port** (`node_modules/undici/lib/mock/mock-utils.js:432`,
`checkNetConnect`). The interceptor itself is keyed on the exact origin string
`https://api.paymongo.com`, so any request whose `url.origin` differs falls through to the predicate,
and the predicate admits everything that is not byte-equal to `api.paymongo.com`.

I measured this by installing the seam verbatim and probing:

```
https://api.paymongo.com/v1/linked_accounts      => HTTP 404              (intercepted)
https://API.PayMongo.COM/v1/linked_accounts      => HTTP 404              (intercepted — URL lowercases)
https://api.paymongo.com:443/v1/linked_accounts  => HTTP 404              (intercepted — :443 stripped)
https://api.paymongo.com:8443/v1/...             => THREW code=23 timeout (LEFT THE MACHINE — real TCP connect)
http://api.paymongo.com/v1/...                   => UND_MOCK_ERR_MOCK_NOT_MATCHED (blocked — fails closed)
https://payments.paymongo.com/v1/...             => THREW ENOTFOUND       (LEFT THE MACHINE — real DNS lookup)
```

Casing and the explicit `:443` are safe (the WHATWG URL parser normalises both), and a scheme
downgrade fails closed. But a non-default port and every sibling `*.paymongo.com` host egress
normally, with the `Authorization` header attached if `paymongoFetch` ever builds such a URL.

This is not reachable today — `PAYMONGO_BASE` is a hard-coded const at `src/lib/paymongo.ts:24` with no
port and no env input. It becomes reachable the moment a second PayMongo host is added (their docs
already use more than one hostname family) or a port is appended for a local proxy. The header's claim
at `:82` — *"It fails CLOSED for PayMongo"* — is narrower than stated, and the file at `:84-85` offers
the predicate as *"the standing 'zero outbound requests' assertion"*, which is the claim that breaks.

**Fix:** widen the deny to the origin family. Still a deny-of-one policy — nothing about the
allow-everything-else design changes.

```ts
/** The origin family this seam refuses. `url.host` carries the port, so match it explicitly. */
const INTERCEPTED_HOST_PATTERN = /(^|\.)paymongo\.com(:\d+)?$/i;

agent.enableNetConnect((host) => !INTERCEPTED_HOST_PATTERN.test(host));
```

and add a case to `tests/security/paymongo-seam.test.ts` asserting that
`fetch("https://api.paymongo.com:8443/v1/x")` rejects with `UND_MOCK_ERR_MOCK_NOT_MATCHED` rather than
attempting a connection.

### WR-02: `new MockAgent()` discards any dispatcher already installed — "every other host passes through untouched" is false

**File:** `instrumentation.ts:152`, `instrumentation.ts:168`
**Issue:** `new MockAgent()` with no `opts.agent` constructs its own fresh `Agent`
(`node_modules/undici/lib/mock/mock-agent.js:47`), and `setGlobalDispatcher(agent)` then overwrites
whatever was on `Symbol.for("undici.globalDispatcher.1")`. The previous dispatcher is not wrapped, not
chained, and not restored — it is dropped. Measured:

```
global before: SentinelAgent
global after:  MockAgent
sentinel dispatch calls for a non-PayMongo host: 0
```

The header states the opposite twice — `:121-122` *"Every other host passes through untouched"* and
`:92-94` *"It returns a 404 to ONE origin and nothing else."* Both are true only when nothing else
had installed a dispatcher.

Concrete failure: Node 24 (this box runs v24.13.0) installs an `EnvHttpProxyAgent` as the global
dispatcher when `NODE_USE_ENV_PROXY=1`. A developer or CI runner behind a proxy who sets that variable
gets a dev server whose *entire* outbound surface silently stops honouring the proxy — including
`api.resend.com`, which `[17-D28]` deliberately leaves live. The symptom is a connect timeout on every
outbound host with no message naming this file, on a boot hook nothing in `src/` imports and therefore
nothing points a developer at.

**Fix:** either preserve the prior dispatcher or refuse to run silently on top of one. `MockAgent`
reads `agent[kClients]` from the injected agent, so only an `Agent` can be handed through — so the
honest form is a named, loud check:

```ts
const { MockAgent, setGlobalDispatcher, getGlobalDispatcher, Agent } = await import("undici");

const previous = getGlobalDispatcher();
if (!(previous instanceof Agent)) {
  // A proxy agent, another seam, or NODE_USE_ENV_PROXY. Say so — silently replacing it changes the
  // routing of every host this seam promises not to touch.
  console.warn(
    "[instrumentation.ts] replacing a non-default global dispatcher " +
      `(${previous.constructor.name}); every outbound host now bypasses it.`,
  );
}
const agent = new MockAgent({ agent: previous instanceof Agent ? previous : undefined });
```

At minimum, correct `:92-94` and `:121-122` so the claim matches the code.

### WR-03: Nothing verifies the seam is actually installed in a running server — every positive test stubs the guard the real boot depends on

**File:** `tests/security/paymongo-seam.test.ts:195`, `:217`, `:234`; `instrumentation.ts:147`
**Issue:** Guard 2 reads `process.env.NEXT_RUNTIME`, and **every** test that proves the seam works
stubs it (`vi.stubEnv("NEXT_RUNTIME", "nodejs")`) before calling `register()` directly. No test — and
no e2e row — observes the value the framework actually supplies, or that the hook is loaded at all
from the repo root while `src/` exists.

That matters because the failure is silent in both directions:

1. If `NEXT_RUNTIME` is ever absent or spelled differently in a boot path, `register()` returns at
   `:147` and the seam is dead. All 13 tests stay green.
2. `register()` has no `try`/`catch` and emits nothing on success. If `await import("undici")` or
   `setGlobalDispatcher` throws (e.g. an install without dev dependencies), the promise rejects, the
   server keeps serving, and the seam is absent.

And the e2e cannot cover the gap **by design**: the seam's whole point is that its 404 is
indistinguishable from a real gated PayMongo failure, so the four spec rows that assert
`Let's pick up where you left off` render identically whether the request was intercepted or whether
it left the machine and got a real 4xx. `grep -rn "instrumentation" e2e/ tests/` returns zero hits
outside the seam's own test. Combined with `playwright.config.ts:113`
(`reuseExistingServer: !process.env.CI`, which adopts a server booted before this file existed), a
dead seam is currently undetectable.

**Fix:** give the seam one observable and read it. This is a detector, not an escape hatch — it cannot
turn the seam off:

```ts
setGlobalDispatcher(agent);
// The one line that distinguishes "installed" from "silently absent". Read by the e2e webServer
// check below; a boot that does not print it did not install the seam.
console.info("[instrumentation.ts] PayMongo seam installed (dev-only, plan 17.1-06)");
```

and either grep the `webServer` stdout in a Playwright `globalSetup`, or add a test that asserts the
literal Next actually defines — `node_modules/next/dist/build/define-env.js:79` pins
`'process.env.NEXT_RUNTIME': isEdgeServer ? 'edge' : isNodeServer ? 'nodejs' : ''` — so a rename in a
Next upgrade goes red on the guard rather than on nothing.

### WR-04: The clearance classes are order-fragile under `tailwind-merge` — one plausible tidy silently deletes `pb-20` entirely

**File:** `src/app/listings/[id]/book/page.tsx:546-551`
**Issue:** The 30-line comment above this `cn()` call reasons carefully and correctly about Tailwind
v4's *cascade layers* — and never mentions `cn()` itself. `cn` is `clsx` + `extendTailwindMerge`
(`src/lib/utils.ts:1-2`), and `tailwind-merge` resolves `py-*` / `pb-*` conflicts by **deleting** the
earlier class before any CSS is emitted. Order in the class list therefore decides survival, not just
precedence.

The shipped order is safe. Measured against the repo's own `tailwind-merge`:

```
twMerge("mx-auto w-full max-w-4xl px-4 py-8 sm:py-12", "pb-20", "sm:pb-20 lg:pb-12")
  => "mx-auto w-full max-w-4xl px-4 py-8 sm:py-12 pb-20 sm:pb-20 lg:pb-12"   ← all four survive
```

But hoisting the named constant to the front of `cn()` — the single most plausible "tidy" on a call
whose first argument is a bare literal and whose second is the named knob — deletes it:

```
twMerge("pb-20", "mx-auto w-full max-w-4xl px-4 py-8 sm:py-12", "sm:pb-20 lg:pb-12")
  => "mx-auto w-full max-w-4xl px-4 py-8 sm:py-12 sm:pb-20 lg:pb-12"          ← pb-20 GONE
```

In that state `<main>` reserves 32px (`py-8`) under a 64px bar below 640px — a **worse** regression
than the one this phase just fixed, and at the 320px floor the phase treats as its positive control.
A full reorder into `pb-20 py-8 sm:pb-20 sm:py-12 lg:pb-12` drops both `pb-20` and `sm:pb-20`.

The only instrument is `expectDocumentEndClearsBar` in `e2e/mobile-booker-path.spec.ts`, and
`.github/workflows/ci.yml:841` shows CI runs exactly one e2e spec (`e2e/price-parity.spec.ts`). So the
guard for a money-route occlusion regression is a spec that never runs in CI, on a repair whose
fragility mechanism is undocumented at the site.

**Fix:** state the mechanism at the call site and make the ordering constraint enforceable, e.g.

```tsx
// ⚠ ORDER IS LOAD-BEARING FOR A SECOND REASON THE PARAGRAPHS ABOVE DO NOT COVER: `cn` is
// tailwind-merge, which DELETES a `pb-*` that precedes a conflicting `py-*` before any CSS exists.
// `STICKY_BAR_CLEARANCE` must stay AFTER "…py-8 sm:py-12" and `sm:pb-20` AFTER `sm:py-12`.
// Measured: hoisting the constant to the front of this call drops `pb-20` outright.
<main className={cn("mx-auto w-full max-w-4xl px-4 py-8 sm:py-12", STICKY_BAR_CLEARANCE, "sm:pb-20 lg:pb-12")}>
```

and add a cheap unit assertion (a `tests/design/**` case, which *does* run inside `npm run build`)
pinning `cn(...)` for this exact argument list to contain `pb-20` and `sm:pb-20`.

### WR-05: `sm:pb-20` hard-codes `STICKY_BAR_CLEARANCE`'s value, decoupling the constant across 640–1023px

the spelling) — but per WR-04 that instrument is not in CI.

**Fix:** derive the `sm:` variant from the same source of truth rather than re-typing the number, e.g.
export a second literal beside it so both move together and neither is composed at runtime:

// src/lib/design/measurements.ts
export const STICKY_BAR_CLEARANCE = "pb-20";
/** The same clearance re-declared for the `sm:` layer, which `sm:py-*` would otherwise beat.
 *  Written out because Tailwind v4 scans source TEXT — a composed name emits nothing. Move both. */

### IN-02: The guard-position derivation can be defeated by a statement on the signature's own line

**File:** `tests/security/paymongo-seam.test.ts:257-263`
**Issue:** `firstStatement` skips blank lines, `//` lines, and lines starting with
`export async function`. A statement placed on the *same* line as the signature —
`export async function register(): Promise<void> { audit(); ` — is filtered by that last clause, and
the derivation then returns the guard line and passes, with code running above guard 1 on every boot.
The filter also does not skip `/*` or ` * ` lines, so a JSDoc inside the body reds (conservative, and
correct).
**Fix:** derive from the body after the opening brace rather than after the signature:

```ts
const openBrace = SOURCE.indexOf("{", SOURCE.indexOf("export async function register"));
const body = SOURCE.slice(openBrace + 1);
const firstStatement = body.split(NEWLINE).map((l) => l.trim())
  .find((l) => l.length > 0 && !l.startsWith("//") && !l.startsWith("/*") && !l.startsWith("*"));
```
