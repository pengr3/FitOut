<objective>
Build the confirmation moment, and make it decay.

Purpose: BFLOW-08 asks for a distinct post-payment view that *"decays into the normal booking-detail
page on later visits"*. D-60 chose the mechanism — consume the param, do not persist it — and rejected
both a cookie and a column. D-61 keeps it inside the same route because a second URL costs the booker a
navigation. The whole design is safe only because the ordinary detail is already complete, which plan
13-10 delivered and `detail-completeness.test.tsx` proves; that is why this plan runs sixth and not
first. 13-RESEARCH Pitfall 2 is the one bug that would only appear under a slow webhook: consuming the
param anywhere the poller can reach re-renders the RSC without it and bounces a paying booker to
checkout mid-confirm.

Output: the moment, the consumer mounted in exactly one place, and an e2e spec that measures the decay
instead of describing it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL query string → confirmation UI | `?paid=1` arrives from a third-party redirect and is trivially forgeable |
| client history rewrite → server render | `replaceState` changes what the next `router.refresh()` renders |
| confirmation copy → the booker's belief | A confirmation that overstates what happened is a money statement |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-11-PARAMSPOOF | Spoofing | `?paid=1` | mitigate | The moment's trigger is the param AND `status === 'confirmed'`, both, always. A forged param on a non-confirmed booking renders nothing new, and no branch moves off DB status. The webhook remains the sole confirm authority (PROJECT D-57) |
| T-13-11-POLLBOUNCE | Denial of Service | poller + consumer interaction | mitigate | The consumer is mounted on the confirmed branch only (asserted: exactly one occurrence), and the e2e counts `framenavigated` events over a seeded pending row driven through all 8 poll attempts. The mount point is proved load-bearing by a watched red |
| T-13-11-BACKINTO | Tampering | history stack | mitigate | `replaceState`, never `pushState`: the booker cannot Back into a moment whose premise has since changed. Asserted by the e2e's Back case |
| T-13-11-EMAILEXPOSE | Information Disclosure | D-63's full email line | accept | The address is the session user's own, on their own owner-gated booking behind auth (ASVS V8); masking defeats the only reason the line exists |
| T-13-11-ADDRSCOPE | Information Disclosure | the moment's full address | mitigate | Sourced through `bookedListingAddress()` (13-09) on a `confirmed` booking — precisely the case the host was promised |
| T-13-11-DECAYLOSS | Repudiation | the decay | mitigate | `detail-completeness.test.tsx` is re-run as an acceptance criterion here: the decay is safe only because every fact in the moment is repeated below, and that link is asserted rather than assumed |
| T-13-11-SC | Tampering | npm/pip/cargo installs | mitigate | **No package is installed.** Any proposed install is a scope alarm |
</threat_model>
