<objective>
Build the third payment state and finish the second, so *not completed*, *pending settlement* and
*reversed* are three visibly different things that never conflate.

Purpose: STATE-05 names three states and one of them renders nothing today. D-70 makes it net-new and
gives it a hard boundary: if the hold has already expired this is NOT the not-completed state, because
`hold-expired-state.tsx` already owns that landing. D-71 freezes the pending poller's mechanics — they
are correct and are not re-decided — and adds only what it lacks: the booking is safe, and they will
be told. 13-RESEARCH Pitfall 2 is the trap this plan must not fall into: whatever landing the
`pending`-without-param branch gets, the poller must not be able to reach it, because being shown
*"you haven't been charged"* while a payment is settling is a false money statement and is worse than
being bounced to checkout.

Output: the net-new state, the pending state's promise, the probe-driven pending discriminator, and
the distinctness proof.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PayMongo probe → which state a booker sees about their own payment | A third-party read decides between "you haven't been charged" and "your payment reached us" |
| retry CTA → checkout session creation | A second minting path is a real double-charge, already paid for once (₱1,470 on an unrefundable rail) |
| poller → route branching | `router.refresh()` re-renders the RSC for the current URL; a branch that changes underneath it navigates the booker away mid-webhook |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-07-DOUBLECHARGE | Tampering | not-completed retry | mitigate | The retry is a `<Link>` to the reserve page, whose `confirmBooking` claims a compare-and-swap checkout lease and EXPIRES the persisted session before minting a new one. No second minting path; asserted by grepping the component for `createCheckoutSession` / `confirmBooking` and finding zero |
| T-13-07-FALSENOTCHARGED | Repudiation | pending branch discriminator | mitigate | A null or failed probe falls to the shipped redirect, never to the not-completed state. Showing "you haven't been charged" while a payment settles is a false money statement; the failure direction is chosen and recorded in code |
| T-13-07-POLLNAV | Denial of Service | `PendingPaymentState` + `page.tsx` | mitigate | No `?paid=1` consumer is mounted in this plan and none may be mounted at or above the pending branch (D-89). Plan 13-11 mounts it on the confirmed branch only, and 13-11's e2e asserts a seeded pending row completes 8 poll attempts with zero navigations |
| T-13-07-FAKECONFIRM | Spoofing | pending state | mitigate | The poller only calls `router.refresh()`; it never fabricates a confirmed state client-side, and the webhook remains the sole confirm authority (PROJECT D-57). Mechanics are frozen and the freeze is asserted by diff |
| T-13-07-ALARMCOLOUR | Repudiation | both states | mitigate | Zero `destructive` tokens and zero error affordances on the pending state at any threshold; a failed checkout is not the booker's error and DS-10 reserves `attention` for a genuine failure needing a human |
| T-13-07-PROBEDOS | Denial of Service | probe on the render path | mitigate | `probeCheckoutSession` is deadline-bounded and never throws (13-03) |
| T-13-07-SC | Tampering | npm/pip/cargo installs | mitigate | **No package is installed.** Any proposed install is a scope alarm |
</threat_model>
