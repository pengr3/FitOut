<objective>
Decide the mask's styling route by measurement, and prove the preview is byte-honest.

Purpose: two things in this phase can only be settled by a real browser. One is a cascade question RESEARCH
could reason about but not observe. The other is IC-02 — *the preview IS the contract* — which is the whole
reason this phase exists and which cannot be asserted anywhere jsdom runs.

Output: the winning scrim route with its inventory consequence, four byte-honesty proofs, and GATE-STATES.

**R3 / R7 — the route is chosen by a measurement, and this plan is where the measurement happens.**
The library injects its stylesheet UNLAYERED into `document.head` at mount; Tailwind v4 utilities live
inside a cascade layer; unlayered beats layered regardless of source order. Both the library's
`.reactEasyCrop_CropArea` rule and a Tailwind utility flatten to specificity (0,1,0), so the LAYER decides
and the library is expected to win. Delta-6's `classes.cropAreaClassName` route is therefore the right
INTENT and is **not guaranteed** to work. RESEARCH could not observe it — no dev server, no Docker at
research time — so it named the fallback and required a Playwright `getComputedStyle` assertion as the
proof. **Do not write a plan step that assumes the class route silently.**

**And the inventory is coupled to the answer.** `EXPECTED_DILUTED_TOKENS` has **20** keys today, not the
21 the 16-UI-SPEC states — counted by parsing the literal, and confirmed twice. The gate is BIDIRECTIONAL
(`brand-recipe.test.ts:1004-1019`): a declared key with no site in the tree is *"dead weight … DELETE it
rather than leave it"* and fails just as loudly as an undeclared site. So: class route -> the row is added
and the count goes 20 -> 21. Inline-style route -> the row is **NOT** added and the count stays 20. Adding
it anyway fails.
</objective>

<interfaces>
The library paints the mask with the crop-area element's own `box-shadow` and `color` (shipped CSS,
verbatim):
  .reactEasyCrop_CropArea {
    border: 1px solid rgba(255,255,255,0.5);
    box-shadow: 0 0 0 9999em;      /* the scrim */
    color: rgba(0,0,0,0.5);        /* so the scrim is 50% black by default */
  }

Two facts that follow and that a plan must not get wrong:
  - **The scrim is driven by `color`, not by a background.** Delta-6's "--foreground at 55%" is spelled
    `text-foreground/55`. A `bg-*` utility would do NOTHING at all.
  - Delta-6 also claims 55% "is `react-easy-crop`'s own default weight". **Measured, the default is 50%.**
    The 55% call still stands on its own merits (it is lighter than the shipped `foreground/80` and IC-04
    wants the cut-off region legible), but do not repeat the agreement claim in a comment — it is false.

THE TWO ROUTES, named by mechanism rather than by letter, because RESEARCH §A5 and the planning brief
label them in opposite orders:

  CLASS ROUTE (preferred, matches Delta-6, keeps the inventory row honest):
    classes={{ cropAreaClassName: cn("border-2 border-background text-foreground/55", <the DS-05 recipe>) }}
    -> if it wins: ADD `"foreground/55"` to EXPECTED_DILUTED_TOKENS (20 -> 21)

  INLINE-STYLE ROUTE (fallback; an inline style always beats any stylesheet rule):
    style={{ cropAreaStyle: { borderWidth: 2, borderColor: "var(--background)",
                              color: "color-mix(in oklch, var(--foreground) 55%, transparent)" } }}
    -> if this is what ships: ADD NOTHING. `color-mix(` is explicitly EXEMPT from the leak gate
       (`design-leak-patterns.mjs:150`: "a color-mix over two declared tokens is not a leak, it is this
       phase's prescribed hover idiom"), so this route passes the gate — it simply produces no diluted-token
       site and therefore no row.

  A THIRD ROUTE IS FORBIDDEN: `disableAutomaticStylesInjection` + importing the vendor CSS. It puts a
  vendor stylesheet into our bundle graph, is the "parallel UI system" 999.2 rejected `cropperjs` for, and
  buys nothing the two routes above do not.

The expected computed values either route must produce, and which the assertion pins:
  borderWidth  "2px"
  borderColor  resolves to the same computed value as `--background` in the court theme
  color        resolves to `--foreground` at 55% alpha

The diluted-token row's template is `foreground/90`'s (`brand-recipe.test.ts`, near `:361`): same status
word `recorded`, same "carries no text" clause, and the same multi-line comment above it stating what
would falsify the claim. Status vocabulary is defined at `:349-356` (`declared` / `exempt` / `inert` /
`recorded`).

    body of the server-action request with `page.route`. Prefer the request capture: it proves the bytes that

    (a) THE RUNTIME INVARIANT (cheap, total, catches a future second decode). With
        `exif-orientation-6.jpg` open, assert in the page that the cropper's `<img>` `naturalWidth` equals the

        a refactor which reintroduces a second decoder.

    (b) THE END-TO-END EXIF PROOF (the named acceptance criterion). With `exif-orientation-6.jpg`:
        - sample a pixel at a known offset of the PREVIEW by drawing the cropper's `<img>` into a scratch
          canvas inside `page.evaluate` and reading it;
        - decode the produced Blob back in the page and sample the SAME relative offset;
        - assert the two match within a per-channel tolerance of +/- 8 (YCbCr conversion rounds; the tolerance
          belongs here, not in the generator).
        Then assert the stronger, unambiguous half: the fixture's coloured corner block lands in the corner
        the CORRECTED orientation puts it in, not the one the raw raster would. State in a comment that an
        uncorrected decode would put it in a different corner, which is exactly why the fixture has a corner
        block at all.

    (c) THE WHITE MATTE AND THE STILL FRAME.
        - `transparent.png`: assert the produced Blob's pixel in the fixture's known TRANSPARENT region
          decodes to white (within tolerance), and — the IC-02 half that matters — assert the STAGE showed
          white there BEFORE the confirm, by sampling the rendered stage. D-177 made the wrapper
          `bg-background`, which is `oklch(1 0 0)` in court, so the on-screen matte and the encoded matte are
          the same white in the shipped theme. Record the observed on-screen value.
        - `animated.png`: assert the produced Blob's sampled pixel matches FRAME ONE's colour, not frame

    (d) ALWAYS 400x400. With `small-300.png` (a 300px source, `maxZoom === 1`), decode the produced Blob and
