### Δ1 — The overlay primitive is `ResponsiveDialog`, and that changes the dialog's shape at both widths

| | |
|---|---|
| **999.2 said** | § 2a: *"Primitive: shadcn `Dialog` (installed), `sm:max-w-md`"*; § 1c: the removal confirm is shadcn `alert-dialog`. |
| **True now** | `src/components/patterns/responsive-dialog.tsx` is **THE** overlay primitive (RESP-01). Its own header names this phase as the tiebreak that created it: *"the ROADMAP's own Phase 16 dependency line, which names the deliverable by name — 'Depends on … Phase 11's responsive-dialog pattern'."* `tests/design/sheet-absent.test.ts` asserts `ui/sheet.tsx` does not exist and that no gesture dependency is declared. |
| **Contract** | **Both** overlays this phase renders — `ImageCropDialog` and the avatar-removal confirm — compose `ResponsiveDialog`. Neither reaches for `ui/dialog.tsx` directly, neither adds `alert-dialog`, and neither reimplements a focus trap, an escape behaviour or a close button. |

**Five consequences that are contract, not commentary:**

1. **Width is the pattern's and is not overridable.** `ResponsiveDialogProps` exposes no `className` and no
   width prop; `DialogContent` is `max-w-[calc(100%-2rem)] sm:max-w-sm` (`ui/dialog.tsx:73`) = **384px** on
   desktop. 999.2's `sm:max-w-md` is unreachable and is dropped. The stage cap (Δ2) is sized to fit it.
2. **Mobile is a bottom sheet, not a centred box.** Below `sm:`: `w-full max-w-none`, bottom-anchored,
   `rounded-t-xl`, `max-h-[85dvh]`, **`overflow-y-auto`**, slide-up motion. This is a genuinely different
   surface from the one 999.2 designed against, and it creates Δ2 and Δ4.
3. **Padding is `p-4`, not `p-6`**, and the content box is `grid gap-4` (`ui/dialog.tsx:73`). The 16px header
   → body → footer rhythm arrives from the primitive and **must not be restated** at the call site.
4. **A visible close `×` renders at every width** (`showCloseButton` defaults true), giving three dismiss
   affordances — overlay click, `Escape`, and the button. 999.2 planned for two. See Δ3.
5. **`hideTitle` is NOT used on the crop dialog**, even though the pattern's header names *"a media crop
   canvas"* as a candidate. `hideTitle` puts the whole `DialogHeader` into `sr-only`
   (`responsive-dialog.tsx`, the `DialogHeader className` line) — **including the description**, and the
   description is this dialog's only disclosure of the pan / pinch / slider affordances. Hiding the title
   would hide the instructions. Title visible, description visible.

### Δ2 — The crop stage's size is recomputed from the real primitive, plus a viewport-height term

| | |
|---|---|
| **999.2 said** | § 2b / § Spacing: a square of `min(320px, 100vw − 5rem)`, derived from `DialogContent` being `w-[calc(100%−2rem)]` with `p-6`. |
| **True now** | `DialogContent` is `p-4` (32px total horizontal padding), and the mobile sheet is `w-full max-w-none` — so the `−2rem` outer inset does not apply below `sm:` at all. Desktop inner width = 384 − 32 = **352px**. Mobile inner width = **`100vw − 2rem`**. |
| **Contract** | The stage is a square of **`min(320px, 100vw − 2rem, 40dvh)`**. |

**Every term derived:**

| Term | Where it comes from |
|---|---|
| `320px` | The cap. Fits inside the 352px desktop inner width with 32px of breathing room, and keeps the stage from becoming the only thing on a tall phone. |
| `100vw − 2rem` | The mobile sheet's real inner width: full-bleed content minus `p-4` on each side. |
| `40dvh` | **New, and it exists because the sheet can scroll.** Non-stage chrome on mobile measures ≈ 300px (header ≈ 60 + zoom row 44 + note 20 + stacked `size="touch"` footer 128 + three 16px gaps). Against `max-h-[85dvh]`, a 640px-tall phone leaves ≈ 244px for the stage and a 568px-tall phone ≈ 183px. A `dvh`-relative cap keeps the confirm button on screen without a scroll on the common phones instead of pushing it below the fold. |
| `dvh`, never `vh` | The measured iOS Safari behaviour `responsive-dialog.tsx` records for its own `85dvh`: `vh` sizes against the largest viewport, and the part that gets clipped is the bottom — which is where the footer and its confirm live. |

**Worked:** 320 × 568 → 183px stage · 360 × 640 → 256px · 390 × 844 → 320px (capped) · desktop → 320px.
**Even at 183px the stage is > 4× a fingertip**, and the slider remains the primary zoom control on small
screens (999.2 § 2d, unchanged).

### Δ3 — "Not dismissable while saving" has no prop on the pattern; ONE guard covers all three affordances

| | |
|---|---|
| **999.2 said** | § 2f: while saving, *"the dialog is not dismissable (`onEscapeKeyDown` / `onInteractOutside` prevented)"*. |
| **True now** | `ResponsiveDialogProps` forwards `onCloseAutoFocus` and nothing else from `DialogContent`. `onEscapeKeyDown` and `onInteractOutside` are not exposed, and neither is a way to disable the close button. |
| **Contract** | The adopter owns `open` and guards **once**, in `onOpenChange`: `if (!next && saving) return;`. Radix routes `Escape`, overlay click **and** the close `×` through that single callback, so one guard makes all three inert — which is the same "one overlay mechanism, one behaviour" argument the pattern exists for. **Three separate handlers are forbidden.** |

**The recorded trade:** for the ~1s the save is in flight, the close `×` is a control that does nothing. It is
visible but inert. The visible busy signals are the confirm reading `Saving…` and `Cancel` rendering
`disabled`; the `×` carries neither. This is bounded and sub-second, and the alternative — editing the shared
pattern's chrome — was weighed and declined here because the chrome would *change shape mid-interaction*
(the `×` vanishing when the user presses Save), which is worse jank than a briefly-inert control.

**Reversal, named and cheap:** if UAT calls the inert `×` a real defect, add ONE optional prop to
`responsive-dialog.tsx` — `dismissLocked?: boolean`, defaulting `false`, which sets `showCloseButton={false}`.
Every existing adopter stays byte-unchanged.

### Δ4 — The sheet is its own scroll container, so `touch-action: none` is now load-bearing, not belt-and-braces

| | |
|---|---|
| **999.2 said** | § 2b: *"`touch-action: none` on the stage so a drag never scrolls the page behind the dialog. Radix already locks body scroll; this covers the stage itself."* |
| **True now** | That reasoning was written for a centred dialog whose only scroller was the body. The mobile presentation is `max-sm:max-h-[85dvh] max-sm:overflow-y-auto` — **the sheet scrolls independently of the body**, and Radix's body lock says nothing about it. On a phone tall enough to need it, a vertical drag on the stage would scroll the sheet instead of panning the photo. |
| **Contract** | `touch-action: none` on the stage container (via `react-easy-crop`'s `classes.containerClassName`) is **mandatory and is the only thing standing between a pan gesture and a scroll**. It is an acceptance criterion of CROP-04's hardware walk, not an implementation detail: **the walk must include a vertical drag on a phone short enough that the sheet actually scrolls.** |

Δ2's `40dvh` cap and this guard are **both** required. Neither is sufficient: the cap reduces how often the
sheet scrolls at all; the guard makes the stage safe when it does.

### Δ5b — `responsive-dialog.tsx` gains ONE additive prop: `onOpenAutoFocus`

**This is the only edit this phase makes to a shared pattern, and it is required rather than convenient.**

D-168 traded away `alert-dialog`'s enforced safe-action focus and made "focus lands on `Keep photo`" a
**binding mitigation**. Under `ResponsiveDialog` that mitigation is currently unimplementable:

- Radix autofocuses the first tabbable element in `DialogContent`. DOM order is header → children → footer →
  close `×`, and `DialogFooter` is `flex-col-reverse … sm:flex-row` (`ui/dialog.tsx:119`) — **so DOM order and
  visual order are inverted on mobile.** Making `Keep photo` DOM-first to win the focus puts the *destructive*
  action on top of the mobile stack, under the thumb. Making `Remove photo` DOM-first fixes the layout and
  focuses the destructive action. There is no DOM order that satisfies both.
- `ResponsiveDialog` forwards `onCloseAutoFocus` but not `onOpenAutoFocus`, so the adopter cannot take the
  decision either.

**Contract:** add `onOpenAutoFocus?: (event: Event) => void` to `ResponsiveDialogProps`, forwarded verbatim to
`DialogContent`. It is the exact twin of the `onCloseAutoFocus` prop already there, with the same
justification shape — *Radix's own behaviour is correct for most adopters; this is here for the ones it is not.*
Default `undefined`, so **every existing adopter is byte-unchanged**, and that must be asserted, not assumed.

The removal confirm passes a handler that prevents the default and focuses `Keep photo`. With focus decided
mechanically, the footer's DOM order is free to serve the layout: **`Remove photo` first, `Keep photo`
second** → mobile puts `Keep photo` on top (thumb-reachable) with `Remove photo` below; desktop puts
`Keep photo` on the right, where the recommended action sits (matching the crop dialog's
`Cancel` → `Save photo` order).

---

### Δ5c — The crop dialog has no trigger, so `onCloseAutoFocus` is MANDATORY on it

`responsive-dialog.tsx` records a measured Radix defect: modal `DialogContent` suppresses the browser's own
focus restore in order to focus `triggerRef`, and `triggerRef` is populated **only** by `<DialogTrigger>`. An
adopter with no trigger gets the suppression with none of the restore — `Escape` drops focus to `<body>` and
the next Tab restarts the page. A real WCAG failure that nothing warns about.

| Overlay | Trigger | Contract |
|---|---|---|
| `ImageCropDialog` | **None.** It opens programmatically from the file input's `change` handler, after the guards and the decode. | **MUST pass `onCloseAutoFocus`** that prevents the default and returns focus to the `Upload photo` / `Change photo` button. This is the case the prop was added for. |
| Removal confirm | The `Remove photo` button, passed as `trigger` | **MUST leave `onCloseAutoFocus` undefined** — Radix's own behaviour is correct here. It is still a **controlled** dialog (Δ3's pending guard needs the `open` prop); `trigger` and controlled `open` compose, so it gets both the guard and a real `triggerRef`. |

**Neither overlay supplies `closeLabel`.** The prop's own doc scopes it to overlays that share a route
*simultaneously*; exactly one of these two is mounted at any instant, so the vendored `Close` is never
ambiguous in a screen reader's element list.

**Visual hierarchy / focal point (locked, per surface):**

- **Crop dialog:** the **stage is the screen**. Title above, one slider below, two buttons under that. Nothing
  else may be added — no filters, no rotation, no format picker, no dimension readout, **and no accent**.
- **`/profile` avatar field:** the 64px circle is the anchor; controls sit beside it, `Change photo` before
  `Remove photo`.
- **Wizard photos step:** the **grid stays the working area**; the preview is a footnote beneath it, never
  above and never inside a tile.

**Interaction rules (locked):**

- **Nothing reaches the network before `Save photo`.** No pre-upload, no speculative upload, no "we'll clean
  it up if you cancel."
- **The default framing is always zoom 1, centred.** The product does not guess (IC-01).
- **Zoom can never exceed the source's real pixels** beyond the derived bound (IC-05).
- **The preview is byte-honest** (IC-02) — including EXIF orientation, proven with a rotated test image, and
  including the white matte, which is visible before confirming.
- **A cancel is a true no-op** from either entry state, **including resetting the file input's `value`** so
  the same file can be re-picked (D-174).
- **A save failure never closes the dialog** (F5).
- **One guard, three dismiss affordances** (Δ3). Never three handlers.
- **Focus never lands on a destructive action** (Δ5b), and **focus never drops to `<body>` on close** (Δ5c).
- **A pan gesture never scrolls the sheet** (Δ4).
- **The listing side changes no bytes and no upload params, and edits no shipped render surface.** If a task
  finds itself editing `ALLOWED_SIGN_KEYS`, a delivery URL, or a ratio in `photo-gallery.tsx` /
  `search-result-card.tsx` / `listing-card.tsx` / `patterns/result-card.tsx`, it has left this phase.
- **Every control is reachable and operable by keyboard**, including panning the crop, with the DS-05 focus
  recipe visible on every one of them.

**CROP-04 is discharged by a PM hardware walk (D-175), recorded like EMAIL-03 was.** Desktop touch emulation
does not satisfy it and no automated suite can. The `human_needed` UAT document names the device(s) and OS and
walks: **drag-pan · pinch-zoom · the slider · a vertical drag on a viewport short enough that the sheet
scrolls (Δ4) · cancel → re-pick the same file (D-174) · removal.** Planning must not claim CROP-04 from a
Playwright run.
