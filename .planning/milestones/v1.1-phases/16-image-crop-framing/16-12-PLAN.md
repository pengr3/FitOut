<objective>
Ship CROP-03: the phase's only destructive action.

Purpose: there is no `removeAvatarAction` of any kind today, and `profile-form.tsx:119-122` reserved the
seam with a sentence — *"a destructive affordance shipped ahead of the action behind it is a button that
lies."* This plan lands the action and the affordance together.

Output: a destroy helper, a server action, the confirm UI, an integration spec, and the fourth
`profile-pass.test.tsx` assertion.

**D-169's ordering is behaviour, not chrome, and it exists so the UI never lies.** Null `avatarUrl` and
`avatarPublicId` on the user row FIRST, then destroy the Cloudinary asset best-effort. If the destroy
fails the user still sees a truthful UI and we have an orphaned asset — logged, tolerated, and swept by
Phase 16.1's orphan audit. The reverse order risks a live row pointing at a destroyed asset: a broken
image on a public profile.

**The mistake to forbid explicitly (RESEARCH §C11).** An un-guarded `await destroy(...)` turns a
Cloudinary outage into `AVATAR_REMOVE_FAILED_MESSAGE` on a profile whose avatar is ALREADY gone. That is
the UI lying, arriving through the other door — the exact thing D-169's ordering exists to prevent. Note
also that `cloudinary.uploader.destroy` RESOLVES with `{ result: "not found" }` for a missing id and only
REJECTS on network or auth failure, so both branches must be handled and neither may change the action's
result.
</objective>

`export enum`, and **any re-export at all** — `export * from` and `export { a } from` are flagged
unconditionally, because *"a re-export out of a `"use server"` file is the same violation as the original
export, and it is exactly the shape a 'compatibility shim' would take while looking like a fix."*
