    `AXE_TAGS` is the const tuple `["wcag2a", "wcag2aa", "wcag21a", "wcag21aa", "wcag22aa"]`. Its docblock
    names D-138 (court only) and states the two measured facts that make it correct rather than merely
    declared: `heading-order`, `region`, `landmark-one-main` and `page-has-heading-one` are
    `best-practice`-tagged and a `runOnly` tag filter therefore excludes them; and `target-size`
    (SC 2.5.8) is disabled by default in axe-core, so a `wcag22aa` tag alone buys nothing.

    `makeAxe(page)` returns `new AxeBuilder({ page })` with **exactly one** `.options()` call carrying
    BOTH `runOnly: { type: "tag", values: [...AXE_TAGS] }` AND
    `rules: { "heading-order": { enabled: true } }`. Never `.withTags(...)`, never a second `.options()`,
    never `.withRules()` / `.disableRules()` — each of those assigns to the builder's internal option
    object and `.options()` replaces it wholesale, so the natural `.withTags([...]).options({rules})`
    spelling silently drops the tag filter and runs axe's wider DEFAULT rule set while reading like a
    stricter gate. Put that reason in the source, above the call.

    `heading-order` is enabled EXPLICITLY, with its reason beside it — it is best-practice-tagged, so the
    tag filter would exclude it, and this is the UI-SPEC correction RESEARCH Pitfall 1 names. Do NOT
    enable `target-size`: `expectTargets` in `e2e/overflow-320.spec.ts:905` already owns the 24px
    `TARGET_FLOOR_PX` with its measured argument, and a second definition of the same floor is exactly
    the drift `expectRing`'s one-import-site rule exists to stop.

    Chain `.exclude("nextjs-portal")` with its reason committed beside it: `playwright.config.ts`'s
    `webServer` is `npm run dev`, so every scanned page carries `<nextjs-portal>`; its shadow root is
    attached `mode:"open"` (measured in `node_modules/next/dist/compiled/next-devtools/index.js:3834`)
    and axe-core walks open shadow trees by design. It is not this application's DOM — `freeze.css`
    hides it and `e2e/error-leak.spec.ts:176` removes it, both for this same reason. This is a
    COMPONENT-level exclusion, so it does not consume the `global-error` route-level exclusion budget.
    `disableRules` is forbidden outright (AC#17).

    `expectAxeClean(page, where)` runs `.analyze()` and asserts in this order, never a different one:
    first `results.passes.length > 0`; then a `scannedNodes` total summed across
    `passes`/`violations`/`incomplete` node arrays, `> 0`; only then that the violation list — projected
    to readable strings of the form rule id, impact, node count and the first node's target — equals `[]`.
    The two guards are mandatory and run FIRST: `.analyze()` over a page that failed to load returns zero
    violations and reads exactly like a pass, which is the scan-of-nothing failure this repository has
    recorded eight times. Each message names the measurement and says why the number below it means
    anything, in `expectNoOverflow`'s voice.

    Take `where: string` as the last positional argument and prefix every message with it — the house
    calling convention for `e2e/helpers/`.
  </action>
