<objective>
Make the incoming transformation un-omittable by refusing to mint a signature without it.

Purpose: R-1's answer, inverted from how CONTEXT.md framed it. Cloudinary validates a signature
against **exactly** the parameter set it receives, so a signed parameter can be neither omitted (401,
probe E2/E10) nor overridden (401, probe E3). The server therefore never needs to ADD a parameter —
it needs to **refuse to sign at all** unless the client's own set already carries the one we require.
`ALLOWED_SIGN_KEYS` was never the obstacle; converted from a permissive allow-list into a required-key
equality gate, it IS the enforcement point.

Output: a sign route that mints nothing without `upload_preset`, a closed F-1 bypass, and the two
tests RESEARCH § R-1.6 calls layers 2 and 3.

**The one measurement that shapes this plan, and it is a constraint rather than a note.** Probe E11:
a client-supplied `transformation` **chains after** the preset's and stored a **4000×6000** asset from
a 2048-capped preset. The allow-list gains **exactly one** key. `transformation`, `allowed_formats`
and `eager` must NEVER join it. The load-bearing security control that made R-1 look impossible is the
control that makes the answer safe — and Pitfall 1 names the failure shape precisely: a diff that
touches only the `Set` literal has widened the surface and gated nothing, because a caller can still
post `{folder, source, timestamp}`, receive a perfectly valid signature, and upload unbounded.

**Path 5b is in scope and is not optional.** It currently mints
`{signature, timestamp, apiKey, cloudName, folder}` for any signed-in owner — no preset, no
transformation, no format gate. It has no production consumer (tests only), which is why it is cheap
to close and exactly why it must be: criterion 3 says the client cannot influence the stored asset,
and 5b is a client-reachable path that hands out a signature with no bound on it at all.

**What this plan does NOT do.**

- **It does not touch `src/lib/listing/cloudinary-provenance.ts` or its test.** RESEARCH § R-1.5
  measured that an incoming transformation returns a PLAIN delivery URL with no transformation
  components, which is exactly the anchored shape `isOwnCloudinaryAsset` requires. D-165 needs no
  change and wants none. Its accepted residual — that the url and the publicId need not agree about
  the file EXTENSION (`cloudinary-provenance.ts:22-23`) — becomes **load-bearing** the moment `f_auto`
  ships, because `f_auto` stores `.jpg` for a `.heic` source and can store `.png` for a `.jpg` one.
  Record that in the route's header so nobody "tightens" it later and breaks the pipeline.
- **It does not add `eager` anywhere.** `eager` derives an extra asset and leaves the ORIGINAL stored,
  failing criteria 3 and 5 outright, and its derived URL carries transformation components that
  `isOwnCloudinaryAsset` rejects by design (its own test asserts a benign `f_auto,q_auto` is rejected,
  at `cloudinary-provenance.test.ts:216`).
- **It does not weaken the shipped gates.** The session gate, the 30/60s per-user-id rate limit, the
  ownership check and the folder scoping are untouched, and their existing cases must stay green.
</objective>
