## Accomplishments

- **U1 is closed, and the dishonest half of it is what actually mattered.** Before this plan the component's error toast promised *"an image under 10MB"* and **nothing anywhere in our code enforced a size limit on the host path** — the copy was describing a Cloudinary default. `maxFileSize: LISTING_MAX_BYTES` makes the declared limit and the widget's enforced limit the same imported number, and the sentence that promised it is deleted rather than reworded.
- **U2 is closed with a SPREAD, not a second copy.** `clientAllowedFormats: [...LISTING_ALLOWED_FORMATS]` is literally the array `scripts/cloudinary-preset.ts` builds the preset's `allowed_formats` from, so the picker cannot offer what the boundary refuses (RESEARCH F-3). The plan flagged `avatar-field.tsx:454-465` as this repo's counter-example — a hand-typed second copy of the allowed types that makes `validation/profile.ts:21-23`'s claim that the picker "reads it here" aspirational rather than literal — and the component's own comment says in as many words that the residual was not inherited.
- **U3 is closed, and it was the load-bearing removal.** `sources: ["local", "camera", "url"]` became `sources: ["local"]`. The remote-address source (T-16.1-15) is a documented client-side-validation bypass: it hands Cloudinary an arbitrary address to fetch, so **there is no local file to measure** and the ceiling and the format list above are defeated *by construction*, not by a bug — and FitOut was offering it from its own UI. The webcam source went with it; the practical loss is desktop-webcam capture only, because on mobile the local source already opens the OS photo picker, which offers the camera on both iOS and Android.
- **The widget now sends the parameter the sign route requires.** `uploadPreset={LISTING_UPLOAD_PRESET}` is a **top-level prop**, never an `options` key — the ordering hazard measured in `next-cloudinary@6.17.5` (`options` is spread LAST, so a key there silently WINS over the prop, and an unset prop silently falls back to `NEXT_PUBLIC_CLOUDINARY_UPLOAD_PRESET`) is written into the component beside the prop and pinned by two assertions that fail independently. `NEXT_PUBLIC_CLOUDINARY_UPLOAD_PRESET` remains absent from `.env.example` and `.env.local` and is now structurally kept that way (T-16.1-09).
- **One generic sentence became three, and not one of them is authored in this component.** `onError={(error) => toast.error(listingUploadRefusal(error))}`. The comment beside it records the coupling honestly: the three reasons are distinguishable **only** by matching vendor English — there is no error code, no enum, no discriminant field — so a vendor reword degrades to upload-failed *by design*, and the failure mode of a copy change is a less specific message rather than a misleading one.
- **`maxFiles` stopped being a second copy of the server cap, and the summary says how far that gets.** `Math.max(1, LISTING_MAX_PHOTOS - photos.length)` narrows the 18-orphans-from-one-click window; it **does not close it**, because the server-side count can change between render and upload. ## Decisions Made

- **Re-run the mutations rather than inherit them.** See the interruption section above. The re-run cost about four minutes and converted the plan's most valuable claim from an assertion about a previous process into an observation.
- **Narrow to the `options={{ … }}` region for the photo-cap prohibition, alongside stripping.** `delayDuration={200}` further down the file contains the cap's digits as a substring, so `not.toContain("20")` over the whole file is falsely RED against a correct component — the *falsely-red* half of the `verify-workflows.mjs:24-32` finding arriving from a direction stripping cannot help with. 16.1-PATTERNS § S-2's region narrowing answers it, and the narrowing **throws** with an explanatory message if it matches nothing, so a restructured widget reports itself instead of silently asserting over an empty string.
- **Derive the prohibited literals from the imported constants.** `String(LISTING_MAX_BYTES)`, `String(LISTING_MAX_PHOTOS)`, `LISTING_UPLOAD_PRESET` and each entry of `LISTING_ALLOWED_FORMATS` are read at test time, so if the declaration's values ever change the prohibition follows them instead of going quietly stale against a number nothing uses. `fitout_listing_v1` is *additionally* asserted as a raw literal, so a rename of the constant's value cannot leave the old name behind in the component.
- **Pin `sources` in both directions.** `toContain('sources: ["local"]')` alone stays green if a **third** source is appended, because the substring survives; the separate `not.toMatch(/["']url["']/)` and `not.toMatch(/["']camera["']/)` prohibitions are what actually bound the option. Mutation 2 reds both, which is how the pair was confirmed to be doing two different jobs rather than one job twice.
- **`uploadPreset` is asserted by COUNT, not by presence.** `count(CODE, "uploadPreset={LISTING_UPLOAD_PRESET}") === 1` — exactly once and in prop position, because the property is positional and a second occurrence would mean the widget was restructured.
