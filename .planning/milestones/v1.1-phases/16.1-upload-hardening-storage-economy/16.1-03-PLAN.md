<objective>
Stop the repo being silent about the one piece of configuration that lives outside it.

Purpose: RESEARCH § R-1.6 layer 4, and Pattern 3 — *"when a value must live outside the repo, do not
let the repo be silent about it. Declare it in source, apply it with a committed script, verify it
with the same script, and name the residual window in prose."* The preset `fitout_listing_v1` does not
exist on the account yet (RESEARCH § Runtime State Inventory). It is the phase's load-bearing security
control and it lives only in the dashboard/Admin API. This plan builds the tool that creates it from
the declaration and the tool that proves it still matches.

Output: `scripts/cloudinary-preset.ts`, an npm script beside the other five, and a design-config test
that pins the pure half and the rule-F2 property.

**Two decisions this plan makes explicitly, because PATTERNS.md § "cloudinary-preset.mjs" says the
choice must be named.**

1. **`.ts` run through `tsx`, not `.mjs` run through `node`.** RESEARCH § R-1.6 layer 4 requires that
   both modes read *only* `upload-policy.ts`, and that is the whole value of the reconciler. Plain
   `node` can neither `import` a `.ts` file nor resolve the `@/` alias, so a `.mjs` script would have
   to **re-spell the transformation string** — a second copy, which is precisely the rule-F2 defect
   this phase exists to end. `scripts/ops-alerts.ts:52-54` already imports `@/lib/ops/alerts` and runs
   as a tsx script, and `tsconfig.json:21-23` maps `@/*` → `./src/*` which tsx honours. **The cost,
   recorded rather than absorbed:** `tsx` is NOT a declared devDependency — it resolves at 4.22.4 via
   `drizzle-kit@0.31.10` and `vite@8.0.16`. Four shipped npm scripts (`db:seed`, `db:test:setup`,
   `email:previews`, `ops:alerts`) already rest on that same undeclared transitive, so this adds no
   new class of fragility; it inherits an existing one, and the script header says so the way
   `scripts/verify-workflows.mjs:116-121` records `yaml`'s.
2. **`--verify` fails closed on an unrecognised vendor key.** RESEARCH probe E12 measured the Admin
   API returning `settings.transformation` as a parsed ARRAY of objects
   (`crop`/`width`/`height`/`quality`), but that probe's preset was created before `f_auto` was
   chosen, so **the key the vendor uses for the `f_` component is not measured.** The script must not
   guess and pass. It canonicalises both sides through one explicit prefix table and treats an
   unknown key, on either side, as a FAILURE with the raw payload printed. Plan 16.1-07's `--apply`
   +`--verify` UAT run is where the real spelling is observed; if the table needs a row, that is a
   one-line change made with the evidence in hand rather than a green that meant nothing.

**What this plan does NOT do.**

- **It does not run `--apply`.** Creating the preset mutates live vendor state and is a human
  checkpoint in plan 16.1-07, with the output pasted into the phase record.
- **It does not install anything.** RESEARCH § Package Legitimacy Audit: this phase has no package
  candidate to audit. A proposed `npm install` here is a deviation and the gate runs first.
- **It does not read or write any FitOut database, and it touches no schema.** GATE-06.

<interfaces>
From plan 16.1-01, the ONLY source of every value this script sends or checks:

  LISTING_UPLOAD_PRESET            the preset name
  LISTING_INCOMING_TRANSFORMATION  "c_limit,w_<edge>,h_<edge>,q_auto,f_auto"  — PARSED, never retyped
  LISTING_ALLOWED_FORMATS          the six-entry array, sent as the comma-joined `allowed_formats`

Cloudinary Admin API, both endpoints measured (probe E12):

  POST   /v1_1/<cloud>/upload_presets            body { name, unsigned:false, transformation, allowed_formats }
  PUT    /v1_1/<cloud>/upload_presets/<name>     same body shape, for an existing preset
  GET    /v1_1/<cloud>/upload_presets/<name>     → { name, unsigned:false, settings: { transformation:[{…}], allowed_formats:[…] } }

  Auth: HTTP Basic, `<CLOUDINARY_API_KEY>:<CLOUDINARY_API_SECRET>`. No SDK needed — three `fetch`
  calls. (The `cloudinary@2.10.0` SDK is present and its Admin API would also work; plain `fetch`
  keeps the script free of the SDK's global-config side effects.)

The canonicalisation table, written once and used for BOTH sides of the diff:

  c_<v> → crop        w_<n> → width (number)     h_<n> → height (number)
  q_<v> → quality     f_<v> → fetch_format

  ⚠ `f_` → `fetch_format` is the ONE row not confirmed against a live GET (see § objective). An
  unknown short prefix, or a returned long key not in this table, is a hard failure — never a skip.

Environment, allow-listed exactly like `scripts/send-email-previews.ts:216-238`:
`CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`. Nothing else is read from
`.env.local`. `NEXT_PUBLIC_CLOUDINARY_UPLOAD_PRESET` is NOT read and must stay unset — it is a silent
fallback inside next-cloudinary and the preset name is a repo constant.

Exit-code contract, copied from `scripts/verify-workflows.mjs:61-138`:

  0  every checked property holds (or `--apply` reconciled successfully)
  1  a property FAILED (drift), or a hard stop fired (no mode given, unknown flag, unknown vendor key)
  3  THE TOOL COULD NOT RUN — no credential. NOT a drift finding, and reporting it as one would train
     people to ignore the check.

      Any unrecognised argument → print the offending argument and the usage, exit 1, with the

      to fix it, and **exit 3** — not 1.
    - **Two exported PURE functions**, so the arithmetic half is unit-testable without a network or a
      credential:
      `canonicalizeTransformation(spec: string)` — split the declared string on commas, split each
      token on its first underscore, map the prefix through the table in `<interfaces>`, coerce `w_`
      and `h_` to numbers, and THROW a named error on an unknown prefix;
      `presetDrift(remote, declared)` — return a list of human-readable difference lines (empty means

      that the table does not know is a difference line, never silently ignored.

      the entry point (compare `process.argv[1]` against this module's own resolved path). This is
      what lets Task 2 import the pure functions without the script executing.
    - **`--verify`**: `GET` the preset. A `404` is a FAILURE (exit 1) with the message stating the
      preset does not exist and that `--apply` creates it — never "nothing to compare". Otherwise
      print the raw `settings` payload it received, then print each checked property with the value it
      read (name, unsigned, each canonicalised transformation component, the format list), then print
      the drift lines. Exit 0 only when the drift list is empty.
    - **`--apply`**: `GET` first. On 404, `POST` to create; otherwise `PUT` to update. Send
      `unsigned: false` explicitly. Then **re-run the same verify path** and exit on ITS result, so
      `--apply` can never report success against a preset it did not actually leave matching.
    - **One extra invariant in `--verify`, cheap and worth it** (RESEARCH § I-4): also `GET` the
      account's preset list and report any preset with `unsigned: true`. An unsigned preset is a
      standing upload hole on any Cloudinary account; `ml_default` was checked on 2026-08-26 and is
      `unsigned: false`. Report it as a distinct FAILURE line so the check is re-run at the phase gate
      rather than trusted from a research note.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo declaration → Cloudinary account configuration | the reconciler is the only committed writer of that configuration |
| `.env.local` → this script | a server credential is loaded into a developer-run process; the allow-list is what bounds it |
| Cloudinary Admin API response → our drift verdict | an unrecognised vendor key must not be read as agreement |
