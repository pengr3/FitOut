## Accomplishments

- **The 18-orphans-from-one-click case is closed at the only branch where closing it is safe.** A listing holding 18 photos where the host selects 20 used to produce 18 unreachable, permanently-billed assets: all 20 upload browser→Cloudinary, 2 persist, 18 are refused at the cap, the uploader toasts and returns, and nothing destroyed anything. `persistPhoto`'s `position >= LISTING_MAX_PHOTOS` branch now destroys the asset best-effort before returning the same sentence it always returned.
- **And the constraint that makes that safe is written where the next refactorer reads it, in the file's own voice.** The ⚠⚠ block above the branch says in as many words that the same destroy two branches up is a DESTRUCTIVE IDOR: everything below `isOwnCloudinaryAsset` has proven the id names an asset our pipeline produced under this listing's folder, and every refusal above it has proven nothing of the sort — so a destroy there lets any signed-in caller delete another host's cover photo or `fitout/avatars/<victim-userId>` by naming it and accepting the refusal. It names the tests that hold the line rather than leaving only the reasoning.
- **The unsafe placement was watched producing exactly that attack, in CI, with no credential.** Moving the destroy to immediately before the provenance call reds SIX assertions for one relocation — and the received value on the traversal case is `["fitout/listings/<id>/one", "fitout/listings/<id>/../../avatars/victim"]`. The mutated action DESTROYED the avatar id. Transcript below.
- **A deleted listing stops being a permanent bill.** `softDeleteListing` reads its photo rows, sets `deletedAt`, then destroys each asset. The read is above the write and the destroy is below it, and both halves of that ordering are argued in the docblock and asserted in source.
- **All three destroy call sites now handle both of the vendor's failure shapes.** `uploader.destroy` RESOLVES `{ result: "not found" }` and REJECTS only on network/auth failure, so the bare `catch` `removePhoto` carried had handled one of two — the orphan a non-ok resolve leaves behind was invisible in the log. `warn` = the vendor answered and declined; `error` = we never got an answer. Neither reaches the host at any of the three sites.
- **A mutation that came back GREEN is recorded as a finding rather than quietly passed over.** D-188's behavioural pair is blind to the bare positional move of the photo read, and the test file now says so and carries the assertion that is not blind to it. See Deviations.

## Decisions Made

- **The destroy is in the cap branch and nowhere else.** Not on the `db.insert` failure path — a throw there is also post-provenance, so it would be *safe*, but it is a second call site the decision did not ask for and it would need its own test. Recorded here so the omission reads as a choice.
- **`console.warn` for the non-ok result, `console.error` for a throw, at all three sites** (RESEARCH Open Question 5, taken as the plan directs). The two shapes are then distinguishable in a log, which is the whole point of handling them separately: one says the vendor answered and declined, the other says we never got an answer. Leaving one of three sites on the weaker shape would have guaranteed the next reader copied the wrong one.
- **The cross-listing provenance case uses TWO hosts, not one host with two listings.** The attacker owns their own listing, so session and ownership both PASS and the guard that refuses is `isOwnCloudinaryAsset` — which is the real IDOR shape, and it puts the assertion on the branch that actually matters rather than on a self-inflicted mix-up.
- **`expect(destroys()).toEqual([])`, never `not.toContain(id)`**, on every rejection path — an empty-array assertion also catches a destroy of the WRONG id, which is precisely the shape the IDOR would take. And `toEqual([overflow.publicId])` on the cap path rather than `toContain`, so a cleanup that also swept something else is red.
- **A source-ordering assertion added for `softDeleteListing`.** See Deviations — this resolves a gap between the plan's own Task 2 and Task 3, and the mutation run proves it was not optional.
