<objective>
Put the client-side half of the boundary on the widget, from the same declaration the server half
reads.

Purpose: three of the roadmap's five measured gaps live in twenty-two lines of this file. U1 — no size
limit exists on the host path at all, while the toast at `:186` promises *"an image under 10MB"* and
nothing in our code enforces it. U2 — no format allow-list, so SVG, TIFF, HEIC and animated GIF all
pass. U3 — `sources` includes `"url"`, which lets a client hand Cloudinary an arbitrary remote address
and defeats any client-side size check by construction. This plan closes all three and wires the
preset that makes the server-side gate reachable at all.

Output: a widget block whose every value is imported, and the source assertions that keep it that way.

**The honest limit on what this plan can prove, stated once.** The widget's actual behaviour lives in
a cross-origin iframe of vendor code. CI can prove which options we pass; it cannot prove what
Cloudinary's widget does with them, and it holds no credential to try (`T-11-CISECRET`,
`ci.yml:151`/`:875`). So this plan's automated gate is a source assertion, deliberately, and the
behavioural halves — an `.svg` picked in the widget showing the wrong-format sentence, a >10 MiB file
showing the too-big sentence, a HEIC that uploads AND renders — are named human steps in plan 16.1-07.
Writing an acceptance criterion an executor cannot satisfy would be worse than naming the gap.

**Two things measured about the widget that shape the code.**

1. **`uploadPreset` is a top-level PROP, not an `options` key.** In `next-cloudinary@6.17.5` the widget
   composes `getUploadWidgetOptions({ uploadPreset: prop ?? process.env.NEXT_PUBLIC_CLOUDINARY_UPLOAD_PRESET,
   uploadSignature, ...options })` — `options` is spread **last**, so an `options.uploadPreset`
   silently wins over the prop, and an unset prop silently falls back to an **environment variable**
   that is not in `.env.example` or `.env.local` today and must stay that way. Passing the prop from
   the repo constant keeps the name greppable and keeps that env var from ever becoming load-bearing.
2. **For both client-side refusals the widget still requests a signature from our endpoint** — one of
   the 30-per-60s budget — but makes **no** POST to `api.cloudinary.com`. So a refused file never
   reaches Cloudinary and never reaches `persistPhoto`. Nothing to handle; worth knowing when reading
   a rate-limit graph.

**What this plan does NOT do.**

- **It does not add a client-side destroy.** `addPhoto` at `:112-121` drops a refused upload on the
  floor today; D-187 fixes that SERVER-side in plan 16.1-05, because the client holds no credential
  and `persistPhoto` refusing is precisely the moment the server knows the id passed provenance.
- **It does not skin the widget or fight its chrome.** D-179 says the visible surface is error copy,
  not widget styling. The widget renders its own English error inside its iframe as well, so our
  sentence is a second surface; RESEARCH Open Question 1's recommendation is to ship beside it and
  observe in UAT, which plan 16.1-07 does.
- **It does not touch the render at `:305`** (`src={photo.url}`), which is one of the eight sites
  criterion 3 requires to be unchanged, nor `PHOTO_REQUIREMENT_REGION_NAME` at `:64-82`, nor the
  dnd-kit reorder, nor `MIN_PHOTOS`.
</objective>
