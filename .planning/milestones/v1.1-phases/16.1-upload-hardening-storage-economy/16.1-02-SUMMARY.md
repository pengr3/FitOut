# Phase 16.1 Plan 02: The Sign-Route Equality Gate Summary

**`POST /api/cloudinary/sign` now mints nothing at all — on either path — unless the caller's own parameter set already carries `upload_preset` equal to the repo constant, which is what makes the incoming transformation un-omittable; the F-1 bypass that handed any signed-in owner an unpresetted signature is closed, and the three keys that would hand the ceiling back are excluded by a source assertion that has been watched failing.**

## Accomplishments

- **The direction of the fix is the inverted one RESEARCH § R-1.1 identified, and the code now says so in its own voice.** The route does not ADD a parameter to a client's upload — it cannot, because Cloudinary validates a signature against exactly the set it receives. It REFUSES to sign for a caller whose set does not already carry the preset. `paramsToSign.upload_preset !== LISTING_UPLOAD_PRESET` returns 400 before `signUploadParams` is reached, so the transformation is not merely requested, it is un-omittable: probes E2/E10 make dropping the key a 401 and E3 makes changing it a 401.
- **Pitfall 1 is closed by construction, not by hope.** A body of `{folder, source, timestamp}` — every key allow-listed, folder correctly scoped — used to return 200 and a usable signature. It now returns 400 with `api_sign_request` never called, and there is a behavioural case asserting exactly that, in the strong form.
- **RESEARCH F-1 is closed.** Path 5b signs `{ folder, timestamp, upload_preset }` and returns `uploadPreset` alongside the signature. Before this it minted `{signature, timestamp, apiKey, cloudName, folder}` for any signed-in owner: no preset, no transformation, no format gate, with every gate above it (session, rate limit, ownership, folder scope) reporting success. Criterion 3 was false while that path existed.
- **The phase's highest-value new test exists and has been observed RED twice.** Widening `ALLOWED_SIGN_KEYS` with `"transformation"` reds three assertions; respelling the constant as a string literal reds a fourth. Both mutations were applied, run, transcribed and reverted with a verified-empty diff.
- **Two signers became one.** `signListingUpload` is gone from `src/lib/cloudinary.ts` — the grep was re-run first and confirmed `sign/route.ts:109` as its only caller repo-wide (`src/`, `tests/`, `e2e/`, `scripts/`). This is the rule-F2 shape the phase exists to end, and it removes the only signer whose type could not carry a preset.
- **D-165 is byte-unchanged and green, and the reason it must stay that way is now written into the route it serves.** `f_auto` means a `.heic` source is stored as `.jpg` and a `.jpg` can be stored as `.png`; `cloudinary-provenance.ts:22-23` deliberately does not require the url and the publicId to agree about the extension. That accepted residual is now LOAD-BEARING, and the route's header says so in as many words so nobody "tightens" it later.

## Decisions Made

- **Delete `signListingUpload` rather than widen it.** The plan made this conditional on a re-run grep; it returned one call site (`sign/route.ts:109`) plus the declaration, so the delete was taken. Two signers for one job was the duplication this phase exists to end, and the deleted one was the one whose `{ timestamp, folder }` type could not carry a preset without a change anyway.
- **The forbidden keys are sent ALONGSIDE a valid preset in the behavioural loop.** Sending them with no preset would have been ambiguous — the 400 could have come from the preset gate rather than the allow-list. With a correct preset in the body, the only thing that can produce the 400 is the exclusion, which is the property under test.
- **`format` added as a fifth prohibited token in the source assertion.** The plan names four (`transformation`, `allowed_formats`, `eager`, `overwrite`); RESEARCH § R-1.6 layer 2 names five. `format` is absent from the route's stripped code today, so including it costs nothing and catches the shortest spelling any format key could regrow under. Recorded as an addition, not a substitution — all four of the plan's tokens are asserted.
- **The `ALLOWED_SIGN_KEYS` count is narrowed to the declaration by regex before counting.** An unrelated `new Set` elsewhere in the file could otherwise satisfy an unnarrowed count. The assertion compares the sorted entry names, not just the arity, so a four-entry set with the wrong fourth key is also red.
