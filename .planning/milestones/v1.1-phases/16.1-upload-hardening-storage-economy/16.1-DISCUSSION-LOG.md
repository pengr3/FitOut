## The size ceiling

### Q1 — What limit should FitOut declare for a listing photo?

| Option | Description | Selected |
|--------|-------------|----------|
| 10 MB — make the copy true | The shipped toast already promises "under 10MB". Declaring 10MB makes an existing sentence honest with no host-visible change. Downside: a number inherited from a vendor default rather than chosen | ✓ |
| 5 MB — one number across the product | Matches `AVATAR_MAX_BYTES`; a single ceiling to learn. Downside: refuses a real camera, and the shipped copy has to change | |
| 20 MB — generous, since we re-encode anyway | Costs nothing on disk since the transformation bounds storage. Downside: may exceed the account's actual plan limit | |

**User's choice:** 10 MB — make the copy true
**Notes:** → D-180. Claude flagged that the plan limit must be verified before 10 MB is declared, since
declaring a limit the vendor refuses below would reproduce the exact defect being fixed (→ R-3).

### Q2 — How hard does the 10 MB need to bite on the direct-to-Cloudinary path?

An option was **deliberately not offered**: checking the widget's reported `info.bytes` server-side.
It is client-supplied, so a caller who bypassed the widget also lies about it — a guard in shape only.

| Option | Description | Selected |
|--------|-------------|----------|
| Advisory + hard storage bound | Widget refuses client-side; a bypassing caller still gets a stored asset bounded by the transformation. The limit is honest about being a courtesy, not a security boundary | ✓ |
| Truly enforced at Cloudinary | Limit rides in as a server-fixed upload param. No bypass. Cost: likely needs a named upload preset — ambient off-repo config this codebase has refused before | |
| Enforced, and verified on the write | `persistPhoto` asks Cloudinary's Admin API what the asset weighs, destroying if over. Cost: a vendor call on a hot write path, which `cloudinary-provenance.ts` explicitly declined to add | |

**User's choice:** Advisory + hard storage bound
**Notes:** → D-181. Claude flagged immediately afterwards that this answer is **conditional**: it holds
only if the transformation itself cannot be omitted by a bypassing caller. That became R-1, the
phase's blocking research question.

### Q3 — What long-edge cap should a stored listing photo get?

| Option | Description | Selected |
|--------|-------------|----------|
| 2048px | Sharp in the lightbox on a laptop and most desktops; only a retina 4K viewer at full-screen would notice. Bulk of the bandwidth win | ✓ |
| 2560px — protect the lightbox | Never soft for anyone. Costs ~50–80% more bytes per view for a difference most bookers on phones never see | |
| 1600px — bandwidth first | Biggest win, fine for grid/cards/mosaic, but visibly soft full-screen on a large monitor — and photos are what sells a space | |

**User's choice:** 2048px
**Notes:** → D-182. Sized against `photo-lightbox.tsx:353`, the only render site that shows the image
at full size.

### Q4 — Two ceilings (5 MB avatar / 10 MB listing) — acceptable?

| Option | Description | Selected |
|--------|-------------|----------|
| Fine — different surfaces, different jobs | An avatar becomes a 400×400 circle; 5 MB is already generous there. No code moves | ✓ |
| Unify at 10 MB | One ceiling to learn. Touches `AVATAR_MAX_BYTES` and the 16-UI-SPEC-pinned copy | |
| You decide | — | |

**User's choice:** Fine — different surfaces, different jobs
**Notes:** → D-183. `AVATAR_MAX_BYTES` and `AVATAR_TOO_LARGE_MESSAGE` stay byte-unchanged.

## Formats & the iPhone problem

### Q1 — HEIC: which allow-list?

| Option | Description | Selected |
|--------|-------------|----------|
| JPEG / PNG / WebP — match the avatar path | Reuses `AVATAR_ALLOWED_TYPES`' exact three; one answer to "what's an image". Cost: a host whose phone sends real `.heic` is refused for a normal-looking photo | |
| Add HEIC/HEIF — accept what phones shoot | Nearly free, since we re-encode anyway. Removes a baffling refusal. Cost: listing and avatar allow-lists now differ; needs verifying against the account | ✓ |
| You decide | — | |

**User's choice:** Add HEIC/HEIF
**Notes:** → D-184. A deliberate divergence from the avatar allow-list, recorded as such.

### Q2 — Animated GIF: keep or refuse?

| Option | Description | Selected |
|--------|-------------|----------|
| Refuse — a listing photo is a photo | Nobody asked for it; mosaic and lightbox are built for stills; a multi-frame asset is the one input where re-encoding can make the file BIGGER | ✓ |
| Accept, flattened to a still | Nothing refused; host gets the frame every surface would have shown anyway. Cost: confusion that the animation "didn't work" | |
| Accept as-is — let it animate | Could sell a space. Cost: net-new capability, fights the storage goal, fails the roadmap's net-new test | |

**User's choice:** Refuse
**Notes:** → D-184.

### Q3 — Which widget sources survive?

| Option | Description | Selected |
|--------|-------------|----------|
| local + camera | Drops `url`, keeps the two a real host uses. Makes client-side checks meaningful | |
| local only | Tightest. Drops in-widget camera capture too; on mobile `local` already reaches the camera through the OS picker, so the loss is desktop-webcam only | ✓ |
| Keep all three | No host-visible change. Cost: `url` is the one source where nothing can be bounded client-side | |

**User's choice:** local only
**Notes:** → D-185. The PM took the tightest option, going a step beyond the recommendation.

### Q4 — What does a host see when a file is refused?

| Option | Description | Selected |
|--------|-------------|----------|
| A sentence per reason | Too-big / wrong-format / failed each get their own, matching the three the avatar path already ships. Host learns what to fix | ✓ |
| Keep one sentence, made truthful | Least code; widget shows its own inline reason first. Cost: a host who misses the inline message has to guess | |
| Let the widget speak, no toast on refusal | Fewest overlapping messages. Cost: the wording becomes the vendor's — the exact problem this phase exists to fix on the size limit | |

**User's choice:** A sentence per reason
**Notes:** → D-186. Notable because ROADMAP's `UI hint: no` says error copy is this phase's ONLY
user-visible surface — so copy is the visible deliverable, not an afterthought.

## Orphan accounting

**The first attempt at this question was dismissed by the PM**, who then asked for an explanation:
*"i dont understand the orphaned is it in retrospect?"* Claude had led with jargon rather than with
the thing itself. It was re-explained in plain terms — a file at Cloudinary with no database row
pointing at it, invisible and billable forever — with a worked example of the most reachable case
(18 photos uploaded, refused at the 20-photo cap, 18 unreachable files from one click), the
distinction between true orphans and merely valueless assets, and an honest note that at FitOut's
current size the cost is negligible and the real problem is not knowing what we store.
**The question was then re-posed in those terms and answered.** Logged here because the first framing
was the defect, not the question.

### Q1 — How far should the phase go on orphaned files?

| Option | Description | Selected |
|--------|-------------|----------|
| Stop new ones only | `persistPhoto` destroys the file when IT refuses; plus destroy-on-listing-delete. Small, safe, no new vendor surface. Recovers nothing already orphaned | ✓ |
| Stop new ones AND count the old ones | Adds a report-only audit via the Cloudinary Admin API. Zero delete risk; finally yields the real number. More work, new vendor surface, manual follow-up | |
| Stop new ones AND delete the old ones | Adds a reaper that destroys what it can't account for. Only self-healing option. Risk is real and permanent — a bad diff eats live listing photos | |
| Do nothing this phase | Document and move on. Cheapest; the 18-orphan case keeps firing | |

**User's choice:** Stop new ones only
**Notes:** → D-187. Claude added the constraint that makes it safe: the destroy may run ONLY after
provenance has PASSED, never on the rejection path, or the cleanup itself becomes an arbitrary-delete
primitive against our own Cloudinary account.

### Q2 — What happens to photos when a listing is soft-deleted?

| Option | Description | Selected |
|--------|-------------|----------|
| Grace period, then delete | Photos survive ~30 days then a job removes them. Cost: needs a scheduled job | |
| Delete the photos immediately | Simplest, storage freed at once. Cost: the soft delete stops being reversible in the way a host would notice | ✓ |
| Leave the photos alone on delete | Smallest change, honours the soft delete as designed. Cost: paying indefinitely for unreachable listings | |

**User's choice:** Delete the photos immediately
**Notes:** → D-188. Claude checked afterwards and reported back that the objection raised in the
question does not hold: **there is no restore path anywhere** — nothing sets `deletedAt` back to null,
and `listing.ts:416` says the soft delete exists for FK safety, not for undo. The PM's choice was
better-founded than the question implied.

## EXIF / GPS — *(re-opened by the PM at the wrap-up gate)*

At the "ready for context?" gate the PM chose to discuss EXIF rather than accept Claude's disposition.
Scouting for it turned up the finding that reframed the criterion: FitOut has a **shipped, deliberate**
location-privacy design (D-09 / T-05-PII) — `publicListing()` coarsens coordinates server-side,
`listing-map.tsx` renders a ~600m fuzz circle instead of a pin, and the page tells the booker
*"Approximate area. The exact address is shared after booking."* A photo carrying EXIF GPS is served
publicly with the exact coordinates in it. So criterion 5 is not a courtesy — it is a side channel
around a guarantee already made.

Claude attempted to prove the leak locally and **could not**: the seeded fixtures are Unsplash URLs,
not real uploads. Recorded as R-2 rather than asserted. (Aside surfaced in the process: those seeded
URLs would now be *refused* by the D-165 provenance guard.)

### Q1 — Does the host hear about the stripping?

| Option | Description | Selected |
|--------|-------------|----------|
| Strip silently | Not a feature — it closes a hole in a promise the listing page already makes. Nobody opts into their own guarantee working | ✓ |
| Strip, and say so | One line of reassurance, mattering most to a host listing a home gym. Cost: one more string | |
| Strip, with an opt-out | Maximum control. Argued against: net-new capability, and a toggle whose OFF state publishes someone's home coordinates is a hazard dressed as a choice | |

**User's choice:** Strip silently
**Notes:** → D-189.

## Backfill — *(delegated to Claude, then handed back)*

The PM delegated backfill at the outset, when it was presented as a bandwidth question. After the
EXIF finding, Claude handed it back rather than deciding on a guess: if the leak is real, already-
published photos would be leaking exact coordinates *now*, which is a different decision with a
different urgency. It turned on one fact Claude could not obtain from the repo.

### Q1 — How much real host-uploaded photo content exists in production?

| Option | Description | Selected |
|--------|-------------|----------|
| None — no real hosts have uploaded yet | Backfill is a non-question; nothing to process, no privacy victim | ✓ |
| A handful — team and test listings only | Cheap and low-risk backfill, worth doing for uniformity; nobody's address exposed | |
| Real hosts with real photos | Leak has real victims; backfill not optional and should be sequenced first | |
| I'm not sure | Then the phase starts by counting the live account and probing one asset | |

**User's choice:** None — no real hosts have uploaded yet
**Notes:** → D-190, **no backfill, because there is nothing to backfill**. This retroactively confirmed
that "stop new ones only" (D-187) was proportionate rather than a compromise, and made the whole phase
coherent as preventive rather than remedial work. The condition that would reverse D-190 is recorded
in CONTEXT.md.
