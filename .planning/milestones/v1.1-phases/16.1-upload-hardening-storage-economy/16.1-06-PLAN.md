<objective>
Make the tree stop promising things this phase decided not to do, and stop our own tooling bleeding
two billed assets per run.

Purpose: **seven** source comments point at Phase 16.1 — not the two CONTEXT.md names — and **five of
them become FALSE the day this phase ships.** Four promise an orphan audit that D-187 declines; three
promise a real pixel guard that D-191 closes as unnecessary. A comment that describes work which was
considered and rejected is worse than no comment: it sends the next reader looking for a phase that
decided against them. And `e2e/avatar-crop.spec.ts` performs one real Cloudinary upload in each of
three cases; the third cleans up after itself and the other two do not, so every local run leaves two
more abandoned assets behind.

Output: seven truthful comments, teardown on two e2e cases, and a discharged deferred item.

**D-191, decided under Claude's discretion and recorded with its reasoning.** Roadmap U4 frames a
40MP image inside 5 MB as *"a decompression bomb against whatever decodes it"* — but **FitOut has no
decoder.** `uploadAvatarAction` does `arrayBuffer()` → `Buffer` → `upload_stream`; the bytes are never
decoded server-side. The bomb, such as it is, detonates at Cloudinary, for whom 40MP is unremarkable.
Storage is already bounded by D-171's retained `{ width: 400, height: 400, crop: "fill" }` transform.
Adding a header-parsing dimension check would be new code defending against a threat this architecture
does not have — and it would contradict this phase's own central argument, which is that every
"custom solution" in this domain requires putting a decoder on our server and the entire safety case
(D-04, D-181, D-191) is that there is not one. **The condition that reverses it goes into the source,
not just here:** the day any server-side code decodes uploaded image bytes, the guard becomes
necessary and this decision is void.

**D-192, with its first question answered.** CONTEXT asked whether `overwrite: true` +
`public_id: userId` already makes repeat runs idempotent for a fixed test user, in which case pinning
the user would be cheaper than teardown. **Measured: no.** `e2e/helpers/avatar-session.ts:56` mints
`e2e.avatar.<Date.now()>.<random>@example.com` every run, so a new signup means a new `user.id`, a new
`public_id`, and `overwrite: true` overwrites nothing. Pinning is the EXPENSIVE option, not the cheap
one: the helper deliberately drives the real signup form with no seed and no DB fixture — its header
argues that at length — and a fixed email fails signup on the second run against the unique
constraint. The third case in the same file already demonstrates the cheap fix, and it is the one this
plan copies.

**Two facts that make the shape of the fix non-obvious, both measured.**

- **These are not orphans.** All 28 `fitout/avatars` assets have a matching `user.avatar_public_id`
  row. They are *abandoned-but-referenced*: a real `user` row for a throwaway account nothing will
  ever read again. So an Admin-API diff sweep — the very thing D-187 declines — **would never have
  found them.** Teardown is the only mechanism that reaches them. Designing the fix around "delete
  assets with no DB row" is RESEARCH Pitfall 9 and would find nothing.
- **Driving the shipped control is the only honest tool.** The spec's own discipline
  (`:2562-2568`, `:853-860`) is *"Fabricating one would mean asserting against our own forgery."* A
  direct `destroyAvatar` in an `afterAll` would need `CLOUDINARY_API_SECRET` inside the e2e process,
  which no other e2e helper has. Pressing `Remove photo` uses the product's own path, forges nothing,
  needs no credential, and deletes both the asset and the row.

**What this plan does NOT do.**

- **It adds no pixel guard, no `sharp`, no image-header parser and no dependency.**
- **It does not touch `AVATAR_MAX_BYTES`, `AVATAR_ALLOWED_TYPES`, `AVATAR_OUTPUT_PX`, the 400×400
  transform, or any avatar refusal sentence.** D-183 and D-171 both stand; these are comment edits.
- **It does not build a sweep.** The four comments that promise one are corrected to say it was
  declined and why, not rescheduled.
</objective>
