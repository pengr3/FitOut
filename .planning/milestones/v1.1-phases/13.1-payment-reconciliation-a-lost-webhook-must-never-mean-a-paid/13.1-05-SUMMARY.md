### The fourth path, and why it is reported rather than wired

`cancelUnpaidHold` flips a booker's own `approved` hold to `cancelled` **and sets `expires_at = NULL` in the
same statement**, with no expire call anywhere in the function. An `approved` row is exactly the scope
`src/app/actions/booking.ts:840` claims a checkout lease under, so it can carry a live payable session — and
because `queryRetirableSessions` selects `expires_at <= now()`, **nulling the column removes the row from the
sweep's candidate set in the very statement that orphans its session.** It is the only known orphaning path
with no backstop at all.

It is **not lapse-driven** (a booker withdrawing on purpose), so it sits outside D-113 as written and outside
this plan's `files_modified`. Concretely, wiring it needs a fifth member on `RetireTrigger` — i.e. a diff on
`src/lib/payments/retire-checkout.ts`, which this plan's own verification requires to be **EMPTY**. Full
write-up, including the one-call fix, is in this phase's `deferred-items.md`.

### Break 1 — THE ONE THE PLAN SINGLED OUT: the `createPendingHold` retire moved INSIDE the transaction

A genuine move (the post-commit call deleted, the call placed after the reclaim UPDATE), not a duplication.

```
❯ tests/booking/hold-lapse-retires-session.test.ts (10 tests | 3 failed)
     × (2) THE POST-COMMIT PROOF — the retire sees the COMMITTED `cancelled` row on a second connection
     × (3) A REJECTING POLICY CANNOT FAIL A BOOKING — the hold still succeeds and the row is still cancelled
     × (6) A 40P01 RE-RUN REPLACES THE RECLAIMED LIST, never accumulates it

AssertionError: THE RETIRE RAN INSIDE THE TRANSACTION. A second, independent connection read this booking
at the moment the policy was called and saw the PRE-reclaim row — i.e. the flip had not COMMITTED yet.
D-113 requires the provider call to happen after the slot is durably freed, because this transaction runs
under SAVEPOINT/rollback and can be re-run wholesale on a 40P01: an in-tx call fires once per attempt,
against a flip the rollback may have undone. Do NOT fix this by relaxing the assertion — move the call back
after the transaction promise resolves.: expected 'pending' to be 'cancelled' // Object.is equality

Error: PayMongo is down                                                             ← case (3)

AssertionError: the retire fired on a rolled-back transaction attempt — an in-tx (or accumulating)
implementation would hand the policy a session id belonging to a flip that no longer exists in the
database: expected [ … ] to have a length of 1 but got 2                            ← case (6)
```

**Three divergences from the prediction, all recorded rather than smoothed:**

1. **IT DID NOT HANG.** The red_watch predicted "the second connection sees the pre-reclaim row, **or the
   case hangs on the uncommitted write**". Under READ COMMITTED a plain SELECT never blocks on an
   uncommitted UPDATE — it reads the previous row version — so the failure is a clean, readable assertion.
   A guard that could hang here would be worse, not stricter.
2. **Case (6) reddened, unpredicted.** Its 40P01 proxy throws only *after* the callback returns, so an in-tx
   retire fires on the rolled-back attempt too: the policy is handed one session id **twice**, the second
   time for a flip that no longer exists. Exactly the double-fire the post-commit placement prevents — it
   surfaced on its own.
3. **Case (3) reddened**, because the move takes the call site's own `catch` with it. See the finding below.

### Auto-fixed Issues

**1. [Rule 2 — Missing critical functionality] Each retire call site needs its OWN catch. The plan's placement turns a PayMongo outage into a failed booking, and it was MEASURED doing so.**

- **Found during:** Task 1, first run of the new spec.
- **The plan's instruction, verbatim:** *"the retire is inside the existing `try`, which is only acceptable because `retireCheckoutsForBookings` cannot throw … State that dependency explicitly so nobody later 'hardens' the policy by making it throw."* Written exactly that way — including the comment forbidding a local try/catch.
- **What happened when it was run** (the plan's own acceptance criterion, expressed as a case):

  ```
       × (3) A REJECTING POLICY CANNOT FAIL A BOOKING — the hold still succeeds and the row is still cancelled
     Error: PayMongo is down
      ❯ tests/booking/hold-lapse-retires-session.test.ts:409:39
  ```

  `createPendingHold` did not return a hold at all. The rejection reached the outer `catch`, fell through
  `mapBookingError`'s unknown-error **re-throw**, and left the caller with a raw error — **with the slot
  already freed and COMMITTED**. A booker refused because a third party was down is 13.1-CONTEXT D-113
  violated in its own words: *"FREEING THE SLOT MUST NEVER DEPEND ON THE PROVIDER ANSWERING."*
- **The plan is internally unsatisfiable here.** Its placement and its criterion ("with the retire mock REJECTING, `createPendingHold` still resolves a SUCCESSFUL hold") cannot both hold.
- **Fix:** both `units.ts` call sites and `expireOne`'s helper wrap the call in their own `catch`, with an empty binding (provider prose is discarded, T-05-15 / T-08-44) and a log line that **names the broken contract** rather than hiding it. The dependency the plan wanted stated is still stated — at length, at every site.
- **Why this is not the "redundant guard" trap this phase has already recorded twice:** the asymmetry. Today the catch is unreachable (13.1-04's contract holds it). The day it becomes reachable, its absence costs a **total booking outage** and its presence costs a log line. That is why it stays.
- **Committed in:** `7cb34c1`, `93f98de`
