<objective>
Establish D-105's single confirm path before anything else in this phase exists.

The finding this plan is built on (evidence in `<idempotency_finding>` below): the confirm is **already
safely re-entrant at the row level**, but it is **inline in an HTTP handler** and therefore not reusable.
So D-105 is satisfied by a behaviour-preserving **extraction** plus a **proof**, not by re-architecting
idempotency.

Purpose: every later caller in this phase — the 5-minute sweep (plan 02) and the settling-screen fast path
(plan 03) — reaches `confirmed` through this one module. Two roads to `confirmed` is how one payment
produces two payout-ledger rows and two emails.
Output: one exported confirm module, a widened provider read that carries the `pay_...`, a webhook route
that calls rather than owns, and a concurrency proof that the guard is real.
</objective>

<idempotency_finding>
## The question the orchestrator asked, answered with evidence

**Verdict: re-entrant at the row level. NOT reusable. The work is extraction, not redesign.**

1. **`paymongo_event` is an event-id ledger, not a booking-level guard.** `route.ts:403-409` selects on
   `paymongoEvent.id === eventId` *before* the transition and inserts *after* it (`route.ts:478`). It
   dedupes redeliveries of the same PayMongo event. **A reconciliation sweep has no event id, so this
   ledger neither guards nor can guard it.** The sweep must NOT fabricate one — that would be a second,
   weaker idempotency mechanism, which is exactly what D-105 forbids.

2. **The real claim is the status-scoped UPDATE** at `route.ts:434-440`:
   `UPDATE booking SET status='confirmed', expires_at=NULL, payment_id=…, payment_method=… WHERE id=$1 AND
   status IN ('pending','approved') RETURNING id`. Under READ COMMITTED a concurrent second UPDATE of the
   same row blocks on the row lock, then re-evaluates its WHERE against the committed version — sees
   `confirmed` — and returns zero rows. **Exactly one caller can ever get ≥1 row, concurrently or
   sequentially.** This is a genuine atomic claim, the same discipline `payout-reconcile.ts:15-18` records
   for `AND state='processing'`.

3. **The only side effect on the winning branch is gated on that claim.** `emitBookingConfirmed` fires
   under `rows.length > 0` (`route.ts:446-452`) — one transition, one `fitout/notify`, one email, one
   durable in-app row. The loser falls to `handleGoneSlot`, which re-reads and returns immediately when
   `status === 'confirmed'` (`route.ts:151-155`) — no double email, no spurious refund.

4. **No payout-ledger row is written at confirm time at all.** It is written T+24h by
   `payout-sweep.ts:187-197` with `ON CONFLICT (booking_id, kind) DO UPDATE … WHERE state='failed'`.
   Confirming twice therefore cannot produce two payout rows, and that guarantee is downstream and
   untouched by this phase.

5. **The blocker is structural.** All of the above lives inside `export async function POST`
   (`route.ts:414-453`) as inline statements. There is no exported function a cron or a server action can
   call. That — and only that — is what this plan changes.

**One real gap this extraction must close.** `getCheckoutSession` (`paymongo.ts:369-398`) reads
`attributes.payments[0].attributes.source.type` but **discards `payments[0].attributes.id`**. A confirm
driven by a probe would therefore land `payment_id = NULL`, and `isApiRefundable` fails closed — so every
later cancellation refund on that booking would be judged unrefundable and routed to the manual-return
path. That is a silent money bug this phase would otherwise create, so the read is widened here.
</idempotency_finding>
