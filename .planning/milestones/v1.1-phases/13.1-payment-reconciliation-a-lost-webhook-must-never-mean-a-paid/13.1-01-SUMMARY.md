## Decisions Made

**1. The `pay_...` is read envelope-first, and the collision is recorded rather than silently resolved.** See Deviation 1 — this is the most consequential judgement in the plan.

**2. A failed refund reports `gone-manual-return`, never `gone-refunded`.** The plan's union does not name a "refund attempted and threw" member. Reporting `gone-refunded` there would be precisely the thing D-108 forbids: an outcome value that reads as if the money moved when it did not. The audit record and log line on that branch are unchanged.

**3. The webhook discards the outcome.** Explicitly instructed by the plan and correct on its own terms: a rejected ACK makes PayMongo retry an already-handled event forever (T-06-15), so the route's behaviour must not become outcome-dependent.

**4. `handleGoneSlot`'s alert non-idempotence was recorded, not fixed.** See Deviation 3.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] The plan's specified read path for the `pay_...` would have returned `null` against this repo's own contract fixture**

- **Found during:** Task 1
- **Issue:** The plan's `<interfaces>` block and Task 1's action both locate the captured payment id at `data.attributes.payments[0].attributes.id` — "two `attributes` deep". But `tests/payments/paymongo-calls.test.ts`'s own fixture (which the plan itself calls "the contract here"), the response-shape docblock already in `src/lib/paymongo.ts`, and `src/app/api/paymongo/webhook/route.ts`'s verified-event read all put the id on the payment resource's **envelope** at `payments[0].id` — PayMongo's `{ id, type, attributes }` shape. Implementing only the prose path would have made `paymentId` come back `null` for every realistic body, i.e. it would have shipped **exactly the `payment_id = NULL` silent money bug this field was added to prevent** — a reconciled booking whose every later cancellation refund is judged unrefundable and permanently routed to manual return.
- **Fix:** Read **both**, envelope first: `attributes.payments?.[0]?.id ?? attributes.payments?.[0]?.attributes?.id ?? null`. The collision is written at the field and in the response-shape docblock, naming which reading came from where and why neither was deleted. Both placements are pinned by their own case, so neither can regress while the shape remains un-live-verified.
- **Verification (measured, not reasoned):** with the implementation temporarily reduced to the plan's literal prose-only path, case (8) went **RED**: `AssertionError: expected null to be 'pay_env_1' // Object.is equality`. Restored from a saved copy in the scratchpad — never `git checkout --`.

## The Idempotency Question, As The Executor Found It

**Agreeing with `<idempotency_finding>` on every point, with one correction and one addition.**

Confirmed by execution, not inspection:

1. **The status-scoped UPDATE is the claim, and it holds under real concurrency.** Two independent Postgres connections racing the same row produce exactly one `"confirmed"` and one `"already-confirmed"`, and the row carries the winner's `pay_...` — the loser's differing payment id and rail never reached it. The finding's READ-COMMITTED reasoning is correct as written.
2. **Every side effect really is gated on winning the claim.** One `booking_confirmed` emission across both the sequential and the concurrent re-entry; zero refunds; zero audits.
3. **`paymongo_event` is an event-id ledger, not a booking-level guard.** Untouched and left in the route, as the finding requires. The new spec deliberately calls `confirmPaidBooking` **directly**, with no event ledger anywhere in the picture — which is precisely the situation the sweep will be in, and the claim still holds.
4. **The blocker really was purely structural.** Not one statement's logic needed to change to make the path reusable.

**The correction:** the finding says the loser "falls to `handleGoneSlot`, which re-reads and returns immediately when `status === 'confirmed'` — no double email, no spurious refund". True, and now expressed in the type (`"already-confirmed"`). But the same re-read does **not** short-circuit on a `cancelled` row, which is why the alert repeats (Deviation 3). The finding's §3 is right about the two failure modes it names and silent about a third.

**The addition:** the status scope is load-bearing for a second, unstated reason — it is also what keeps a terminal booking out of the confirm. Remove it and the D-58 backstop becomes dead code. That was discovered by the deliberate break, not by reading.
