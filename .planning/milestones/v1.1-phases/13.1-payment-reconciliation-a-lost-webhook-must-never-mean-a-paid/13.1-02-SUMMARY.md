# Phase 13.1 Plan 02: The Reconciliation Sweep Summary

**A 5-minute singleton cron now asks PayMongo what it already knows about every recent paid-but-unconfirmed booking and routes anything paid through 13.1-01's single confirm path — the guarantee that a lost webhook is a delay measured in minutes rather than a person who paid and got nothing — with its cadence pinned as an inequality over the real `HOLD_TTL_MINUTES`, its scope pinned past both D-111 fixtures, and four deliberate breaks performed to prove none of it is asserted vacuously.**

## Accomplishments

- **The asymmetry is closed.** `payout-reconcile.ts` polls what we OWE; nothing polled what we have been GIVEN. `payment-reconcile.ts` now does, in the same shape — singleton cron, `dbConn`-injectable step functions, one `step.run` per row.
- **The cadence is an inequality, not a comment.** `RECONCILE_MIN_AGE_MINUTES + RECONCILE_INTERVAL_MINUTES < HOLD_TTL_MINUTES` (2 + 5 < 15) is asserted against the constant imported from `@/lib/availability/units`, and the shipped cron is derived from the same number so the two cannot drift apart.
- **Four deliberate breaks, all performed, all recorded verbatim in the specs' own headers** — the interval lengthened past the TTL; the cron hardcoded away from the constant; the status scope widened to admit terminal rows; the D-111 epoch removed. Each reddened exactly the case that owns it.

## The chosen `RECONCILE_EPOCH`, and why

**`2026-08-22T12:00:00+08:00`** (= `2026-08-22T04:00:00Z`), a literal `Date`, not a `process.env` read.

The plan asked for an instant "strictly after `2026-08-21T18:17:00+08:00`". **That bound is wrong, and it was measured wrong rather than argued wrong.** `13.1-CONTEXT.md`'s evidence table reports the later fixture as paid at "2026-08-21 18:17", and the plan converted that to Manila time. The row's actual `created_at` — read from dev — is `2026-08-21 18:17:12.839383+00`, i.e. **18:17 UTC**, which is EIGHT HOURS LATER than the plan's bound. An epoch honouring the prose (10:17Z) would have selected `09f32400-b636-46e1-973a-b930a073a936` on the first pass and confirmed it — sweeping the exact fixture D-111 exists to protect, on a booking carrying a real ₱1,050.00 GCash capture.

The chosen instant is after both fixtures by more than nine hours, is in the past at ship time (so a newly-created booking is genuinely sweepable), and is meaningful on its face: noon Manila on the day this phase shipped.

## The shipped cron string

```
TZ=Asia/Manila 2-59/5 * * * *
```

Minute :02 and every five minutes after. Start minute 2 collides with none of the five occupied slots (:00 payout sweep, :15 request expiry, :30 payout reconcile, :45 reminders, 08:50 ops digest) — asserted, not eyeballed. The `START-59/STEP` spelling is deliberate: the bare `2/5` form is a Quartz extension, while `2-59/5` is valid POSIX/vixie cron and is accepted by every parser in the chain.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — Missing critical functionality] The candidate set is `pending` OR `approved`, not `pending` alone**

- **Found during:** Task 1
- **Issue:** The plan's Task 1 specified `status = 'pending'`. But `confirmPaidBooking` confirms from `status IN ('pending','approved')` — an instant pay confirms from `pending`, a **host-approved request** (PAY-05 / D-63) from `approved`, and both are paid through the same PayMongo checkout and therefore lose the same webhook. A `pending`-only sweep would leave the entire request-to-book payment mode with **no reconciliation at all**: the booker pays, the webhook is lost, and nothing on any schedule ever notices. The dispatch's own hard constraint reads "scope this sweep's candidate set to `pending` / `approved`".
- **Fix:** `WHERE status IN ('pending','approved')`, mirroring the confirm's own claim exactly, with the reasoning written at the query. `requested` (not yet payable) and every terminal status stay out.
- **Verification:** case (0b) asserts an `approved` row IS selected alongside the control; case (1) asserts `confirmed`/`cancelled`/`requested` are not; break 3 reddens case (1) on demand.
- **Files modified:** `src/inngest/functions/payment-reconcile.ts`, `tests/payments/payment-reconcile.test.ts`
- **Committed in:** `1919f37` / `5417901`

**2. [Rule 1 — Bug] The plan's D-111 epoch bound would have swept the fixture it was written to protect**

- **Found during:** Task 1
- **Issue:** The plan required `RECONCILE_EPOCH` to be "strictly after `2026-08-21T18:17:00+08:00`" (= 10:17Z). The later fixture's actual `created_at` is `2026-08-21 18:17:12.839383+00` — **18:17 UTC**. Any epoch satisfying only the plan's bound admits that row, and the first pass would have probed it, found PayMongo's real ₱1,050.00 GCash capture, and confirmed it. That is the destruction of a fixture PM explicitly ruled out of scope, on a booking holding real money.
- **Fix:** the epoch is pinned at `2026-08-22T12:00:00+08:00`, after both fixtures by >9h. The cadence spec's case (5) asserts against the **measured** `created_at` of both rows (named in the failure message), not against the plan's prose.
- **Verification:** the shipped predicate run verbatim against the dev database returns **0 rows**; both fixtures re-read `pending` / NULL after every gate; break 4 reddens the case on demand.
- **Files modified:** `src/inngest/functions/payment-reconcile.ts`, `tests/payments/payment-reconcile-cadence.test.ts`
- **Committed in:** `1919f37` / `ac14625`

**3. [Rule 1 — Bug] The sweep's query threw on every call: a Date cannot be bound into drizzle's `sql` template here**

- **Found during:** Task 3 (six of the eighteen cases reported `Failed query:` before a single behaviour was measured)
- **Issue:** `AND created_at >= ${RECONCILE_EPOCH}` makes drizzle tag the parameter as timestamptz (OID 1184), whose postgres.js serializer expects a string:
  `TypeError: The "string" argument must be of type string or an instance of Buffer or ArrayBuffer. Received an instance of Date` (`ERR_INVALID_ARG_TYPE`, `types: [1184, 23, 20]`). **Shipped, the guarantee would have failed its query on every single pass.** `npx tsc --noEmit` was clean and `npm run lint` was clean.
- **Fix:** `${RECONCILE_EPOCH.toISOString()}::timestamptz`, with the measured error recorded at the constant's declaration and at the query.
- **Files modified:** `src/inngest/functions/payment-reconcile.ts`
- **Committed in:** `acc5eea`

**4. [Rule 3 — Blocking] `mockPayMongo` had no `getCheckoutSession`, which the plan's stubbing instruction requires**

- **Found during:** Task 3
- **Issue:** The plan says to stub "`probeCheckoutSession`'s underlying provider call through `mockPayMongo`", but the shared helper carried no such stub.
- **Fix:** added `mockPayMongo.getCheckoutSession` (+ its `mockClear` in `reset()`), documented as being deliberately UNDER the probe so the probe's own guarantees run. Additive only; no existing stub changed.
- **Files modified:** `tests/helpers/mocks.ts`
- **Committed in:** `5417901`

**5. [Rule 3 — Blocking] A backtick inside an SQL comment terminated the `sql` template literal**

- **Found during:** Task 3 — `[PARSE_ERROR] Expected ',' or ')' but found 'Identifier'` from `vite:oxc`, which skipped all 18 cases.
- **Fix:** the measured error text inside the in-SQL comment was rewritten without backticks. (A template literal cannot carry one, however comment-like the surrounding text looks.)
- **Committed in:** `acc5eea`

**6. [Rule 3 — Blocking] `tsc` rejected the case (4) mock implementation**

- **Found during:** Task 3's final gate — `TS2345`: the mock's `id` parameter is optional (it carries a default), so an implementation typed `(id: string)` is not assignable. Vitest does not typecheck, so the suite was green while `tsc` was not.
- **Fix:** `(id?: string)` with the reason recorded inline.
- **Committed in:** `5417901`
