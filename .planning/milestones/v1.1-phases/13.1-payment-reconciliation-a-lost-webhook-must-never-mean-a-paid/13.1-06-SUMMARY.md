## RESIDUAL 1 — shape (a) vs shape (b), and why the brief's description of the problem was incomplete

### The measurement that decided it

The brief, `deferred-items.md`, and `13.1-VERIFICATION.md` all say the same thing: `cancelUnpaidHold` sets
`expires_at = NULL` **and that nulling is precisely what puts the row permanently beyond the retire sweep**,
which selects `expires_at <= now()`.

That is true, and it is **one of two independent exclusions**. Read against the actual selector
(`src/inngest/functions/checkout-retire.ts:171-189`):

```sql
WHERE status IN ('pending', 'approved')     -- ← clause ONE
  AND checkout_session_id IS NOT NULL
  AND expires_at IS NOT NULL
  AND expires_at <= now()                   -- ← the clause the brief names
  AND expires_at > now() - make_interval(mins => 30)
```

`cancelUnpaidHold` writes `status = 'cancelled'` (or `'declined'`) **in the same UPDATE**. So the status flip
excludes the row on its own, and removing the nulling leaves that exclusion untouched. **Shape (b) closes
nothing.**

This is not reasoning — it is `tests/booking/cancel-unpaid-hold-retires-session.test.ts` **case (12)**, which
performs the withdrawal, hands the row its lapsed-but-inside-lookback `expires_at` back (option (b)'s exact
post-change shape), and asserts `queryRetirableSessions` still does not select it. **Case (11)** is its
guard-the-guard: an untouched lapsed hold on the same schema **is** selected, so case (12)'s `not.toContain`
cannot pass against an empty result.

And the break that proves case (12) can move — widening the selector to
`('pending','approved','cancelled','declined')` — shows what shape (b) would really have cost:

> `AssertionError: OPTION (b) WOULD HAVE WORKED and this file's whole call site is redundant […]: expected [ 'bk_cuh_12', 'bk_cuh_11' ] to not include 'bk_cuh_12'`

The same widening reddens **case (2) of `tests/payments/checkout-retire.test.ts`** — *"a CONFIRMED booking is
never selected — its session was paid, and retiring it destroys evidence."* Making the sweep able to reach a
terminal row is how you build a cron that expires the session of a real, paid booking.

### What the other dependents on the nulling turned out to be

Checked before choosing, because the brief said to:

| Consumer | Depends on the NULL? | Measured |
|---|---|---|
| `reminders.ts` `pre_expiry` | No | Status-scoped (`b.status = 'approved'`), so a `cancelled` row with a live window is not selected |
| `bookings/[id]/page.tsx` `deadlineLabel` | No | The `lapsedApproval` branch requires `cancelledBy === null`; this path writes `'booker'` |
| `re-request.ts` `lapsed` | Belt-and-braces only | `isResendableLapse` already requires `cancelledBy IS NULL` |

So option (b)'s collateral damage is genuinely small — which is worth recording, because it means the case
against it rests entirely on the fact that **it does not work**, not on a scare story. That is the stronger
argument and it is the one in the code comment and in `deferred-items.md`.

### What shipped

- **A fifth `RetireTrigger` member, `booker-cancel-hold`** — with a header stating plainly that it is the one
  member that is *not* an accelerant, and why: nothing else in the codebase reaches these rows.
- **`RETURNING id, status, checkout_session_id`.** `checkout_session_id` because `loadBookingRow` (shared by
  all three cancel actions) does not select it and must not start to; and because a booker can claim a
  checkout lease between the pre-read and the flip, so a retire keyed off the pre-read would be stale-NULL
  exactly on the sharpest path — `request-expiry.ts`'s finding, applied here for the identical reason.
  **`status` because the policy's alert rule keys on it**, and `row.status` is the pre-flip value. The
  `deferred-items.md` prescription named only the session id; the status is this plan's addition.
- **The call runs BEFORE `notifyCancellation`,** which diverges from `request-expiry.ts`'s notice-then-retire
  order. That file states the order between its two side-effects cannot matter; here it can, in one
  direction: if the process dies between them, a missed notification is recoverable by anyone asking, and a
  still-payable session is not. Both remain independent — neither is inside the other, and `emitNotify`
  swallows its own transport errors.
- **Its own `catch`, empty-bound, naming the broken contract.** 13.1-04's structural never-throw contract
  makes it unreachable today. It exists because 13.1-05 measured what an undefended site costs.

## RESIDUAL 2 — the runbook, and the correction the brief did not anticipate

### `checkout_paid_after_lapse` is not a single situation

The brief describes it as money held for a booking that no longer exists. **That is true for three of its
four triggers and false for the fourth**, and an operator acting on the brief's framing would have refunded a
booking that was about to be confirmed.

The policy's alert guard is `probe.status === "paid" && row.bookingStatus !== "pending"`. Enumerated against
each call site:

| `trigger` | `bookingStatus` | Is any reconciler on it? |
|---|---|---|
| `retire-sweep` | `pending` | — no alert is written at all (deliberately silent; 13.1-02 owns the row) |
| `retire-sweep` | **`approved`** | **YES** — `queryUnconfirmedPaid` is also `status IN ('pending','approved')`, so `payment-reconcile` will confirm it and file a `webhook_missed` row for the same booking |
| `stale-hold-reclaim` / `open-capacity-reclaim` | `cancelled` | No |
| `request-expiry` | `cancelled` / `declined` | No |
| `booker-cancel-hold` | `cancelled` / `declined` | No |

So **§4b forks on `meta.bookingStatus` before it says anything else.** On `approved` it tells the operator to
expect the reconciler to fix it, to check the booking reached `confirmed`, and — if it did not after several
sweep intervals — to consider the two known reasons: the cron is not ticking (**→ the deploy checklist**) or
the booking predates `RECONCILE_EPOCH` (`2026-08-22T12:00+08:00`, D-111's no-backfill bound), in which case
nothing will ever confirm it and it becomes the terminal case.

On `cancelled` / `declined` the section is unhedged: **this row is the only report the payment will ever
produce**, treat it with `auto_refund_manual`'s urgency, return the money (§5 if the rail is QRPh/UBP), do
**not** confirm the booking (the slot may be re-sold), do **not** expire the session (it is paid), and if the
trigger is `booker-cancel-hold`, **tell the person** — they withdrew deliberately and a silent refund is its
own support ticket.

It also records what the alert does **not** cover: a `paid` session on a still-`pending` row is deliberately
silent, so that a future narrowing of the reconciler's scope reads as a hole rather than a surprise.

### `webhook_missed` is informational, and says so

Measured rather than assumed: by the time the row is written, `confirmPaidBooking` has already run to
`"confirmed"` — the booking is `confirmed`, `payment_id` and the rail are persisted on the same statement,
`emitBookingConfirmed` has fired, and `payout-sweep`'s candidate query is booking-status driven, so the host
payout follows normally. **There is nothing to refund, re-charge or re-send**, and §4c says so in those
words. The real signal is a *cluster* in one window, which points at webhook delivery, not at money.

`paidWithinHold` is documented as the one field worth reading and explicitly **not** an action:
`false` means they paid after their window and got the slot because it was still free.

## RESIDUAL 3 — the deployment note

`.planning/ops/` had **no deployment checklist**, so one was created and says so in its own opening. It is
deliberately the smallest honest one: §5 lists what it does not cover (hosting, rollback, smoke test,
monitoring, and the fact that nothing enforces the file).

- **Both crons named explicitly**, with ids and cron strings read off the source rather than the comments:
  `payment-reconcile` (`TZ=Asia/Manila 2-59/5 * * * *`) and `checkout-retire-sweep`
  (`TZ=Asia/Manila 4-59/5 * * * *`), each with what its silence costs. All nine registered functions are
  tabulated, because the array in `src/app/api/inngest/route.ts` is the only source of truth.
- **Registered ≠ ticking, and the checklist says which one matters.** Check 1 is the Functions list; check 2
  is the Runs view, where **at least one run of each must appear within ~10 minutes of a deploy.**
  `{ "scanned": 0, "outcomes": {} }` is documented as the healthy steady state so nobody reads a quiet run as
  a broken one.
- **The three-way failure is called out:** the two crons and `ops-alert-digest` fail as a set — the first two
  can work perfectly and you would still never see the rows they file.
- **Env vars split into fail-loudly and fail-quietly**, which is the distinction a deploying operator
  actually needs: `INNGEST_SIGNING_KEY` throws at module load in production; `OPS_ALERT_EMAIL` logs and
  no-ops, and unset in a deployed environment means nobody is reading the money alerts.
