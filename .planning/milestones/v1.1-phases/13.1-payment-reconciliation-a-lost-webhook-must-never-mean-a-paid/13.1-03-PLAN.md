<objective>
Give the person who is actually sitting there an answer in seconds instead of minutes.

The sweep (plan 02) is the guarantee. This is the fast path, and the relationship is asymmetric on purpose:
if this entire plan were reverted tomorrow, a paid booker would still always end up with a booking — just
up to five minutes later. Nothing here may become load-bearing for that promise.

Purpose: close the gap between "the webhook is late" and "somebody is watching a spinner about their money".
Output: one authenticated server action reusing the sweep's own reconcile body, called exactly once when
the frozen poller gives up — with no new copy on the calmest surface in the app.
</objective>

<design_decision>
## The fast path adds no copy, and that is the design

D-109 says a probe that resolves may state what it learned, and a probe that learns nothing must not invent
reassurance. The strongest way to satisfy both is to say nothing new at all:

- If the probe reconciles, the row becomes `confirmed` and `router.refresh()` re-renders the **confirmed
  surface**. The booker gets their booking. That is the answer; a sentence about it would be a worse one.
- If the probe learns nothing, the existing `takingLonger` copy stands, exactly as 13-20 left it.

So this plan introduces **zero new strings** on `pending-payment-state.tsx`. STATE-05's ban on an error
affordance while the webhook is outstanding cannot be violated by a plan that adds no affordance, and
`tests/design/pending-copy.test.ts` needs no edit — which is itself the assertion that D-102's four removed
claims did not quietly grow a fifth.
</design_decision>

    Create `src/app/actions/reconcile-payment.ts` with the `"use server"` directive. Export
    `RECONCILE_RATE_LIMIT` (a named constant, not literals at the call site — the discipline
    `CANCEL_RATE_LIMIT` sets), a closed `ReconcileNowOutcome` union of exactly `"reconciled"`,
    `"unchanged"`, `"denied"` and `"rate-limited"`, and `reconcilePaymentNow(bookingId: string):
    Promise<ReconcileNowOutcome>`.

    The order of checks is the security design and must be written in that order:
    1. Resolve the session through `auth.api.getSession({ headers: await headers() })`. No session →
       `"denied"`, with NO provider call. An unauthenticated caller must not be able to make FitOut hit
       PayMongo.
    2. Rate-limit on `reconcile-payment:${userId}`. Set the window generously enough that a booker
       reloading the page a couple of times is never limited, and tightly enough that a scripted loop
       cannot turn one session into provider load. Not ok → `"rate-limited"`, again with no provider call.
    3. Read the booking by id and check `booker_id` equals the session user id. Any mismatch, or no row →
       `"denied"`. Return the SAME value for "not yours" and "does not exist" so the action cannot be used
       to learn whether a booking id exists.
    4. If the row is not `pending`, or carries no `checkout_session_id`, return `"unchanged"` without
       probing. There is nothing to ask the provider about.
    5. Otherwise call `reconcileOne` with the row's id, session id, `expires_at` and `created_at`. Map its
       outcome: `"confirmed"` → `"reconciled"`; everything else → `"unchanged"`.

    Three rules to state in the module header as rules, not observations:
    - **D-104.** This action reads NOTHING from the URL. It does not receive `searchParams`, it does not
      look for the checkout-return parameter, and it would behave identically if that parameter had never
      existed. The authority is the server-to-server provider read inside `reconcileOne` — the same source
      of truth as the webhook over a different transport — and a query parameter still confirms nothing.
    - **D-105.** This action owns no UPDATE, no probe of its own, and no alert policy. It resolves who is
      asking and then delegates. If reconciliation behaviour ever needs to change it changes in one place,
      and that place is not here.
    - The returned value is a CLOSED ENUM and never carries provider prose, an error message, a `cause` or
      a retry hint. `checkout-probe.ts`'s discard discipline ends at a `null`; this must not re-open a route
      out of it through a server-action return value that lands in a browser.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `reconcilePaymentNow` | NEW. An internet-reachable server action that can transition a booking to `confirmed` and cause an outbound provider call. This is the sharpest new surface in the phase. |
| Server action → PayMongo REST | A booker-triggerable outbound provider read. |
| Server action → browser (return value) | Provider knowledge crossing back to an untrusted client. |
| RSC → client component (props) | `bookingId` handed down server-derived, never read from the URL by the client. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13.1-20 | Elevation of Privilege | `reconcilePaymentNow` | mitigate | Session required, then `booker_id` equality against the session user, both BEFORE any provider call. Asserted in Task 2 by provider-call count, so a check that returns the right value while still probing fails. |
| T-13.1-21 | Information Disclosure | booking-existence oracle | mitigate | "Not yours" and "does not exist" return the identical closed-enum value, asserted equal to each other in Task 2 so the branches cannot drift apart later. |
