# Phase 23: Production Domain, Email & Reachable Support - Context

**Gathered:** 2026-09-11  
**Status:** Ready for replanning

<domain>
## Phase Boundary

Make FitOut reachable at its owned production domain, make every production origin and provider
callback agree on that domain, and make the existing support and transactional-email paths honest.
This phase connects the already-built support affordances and Resend transport to `fitout.live`; it
does not add a help desk, ticketing, inbound-email processing, a mailbox product, a new identity
provider, database changes, or new notification types.
</domain>

<decisions>
## Implementation Decisions

### Public domain topology

- **D-01:** `https://fitout.live` is FitOut's canonical public production origin. It is the value for
  customer-facing links, canonical metadata, Better Auth's fallback origin, payment return URLs, and
  provider webhook destinations.
- **D-02:** `www.fitout.live` is assigned to the Vercel project solely to redirect to
  `https://fitout.live`; it is never a second canonical application origin.
- **D-03:** `https://ops.fitout.live` remains a distinct production host for the existing staff
  surface. It must be assigned to the same Vercel project and supplied through `OPS_APP_URL`; it must
  not share marketplace session cookies or become a public-site alias.
- **D-04:** Vercel is the authoritative DNS and deployment control plane for the purchased domain.
  Keep its website-routing records intact while adding only the exact third-party mail-authentication
  records generated by Resend. Do not commit DNS values, provider tokens, or screenshots containing
  credentials.

### Launch support address

- **D-01:** `pengr.clmc.3@gmail.com` is the real, monitored launch support address. It is not a
  placeholder: it may be published in the app and receive replies until a dedicated account exists.
- **D-02:** The future dedicated support account replaces that address at the one existing
  `SUPPORT_EMAIL` declaration. The outbound mail reply address must read the same source, so the
  future swap cannot leave the website and transactional mail pointing at different inboxes.

### Transactional mail and delivery reputation

- **D-07:** Resend remains the sole outbound transport. Verify the dedicated sending subdomain
  `send.fitout.live` in Resend and send production mail as `FitOut <updates@send.fitout.live>`.
  This keeps sender reputation separate from the public/ops hosts while remaining visibly FitOut.
- **D-08:** Copy the exact SPF, DKIM, and required MX records that Resend displays for
  `send.fitout.live` into Vercel DNS; add a monitoring DMARC record for the organisational domain if
  it does not conflict with an existing record. Do not invent or copy sample values from a document.
- **D-09:** Every transaction through the shared Resend transport sets `Reply-To` to the monitored
  `SUPPORT_EMAIL`. Gmail is the reply destination; Resend inbound-email webhooks are not a mailbox
  replacement and remain out of scope.

### Environment and API configuration

- **D-10:** Configure the public and mail values as Vercel **Production-only** variables:
  `BETTER_AUTH_URL=https://fitout.live`, `NEXT_PUBLIC_APP_URL=https://fitout.live`,
  `OPS_APP_URL=https://ops.fitout.live`, `EMAIL_FROM=FitOut <updates@send.fitout.live>`, and the
  server-only `RESEND_API_KEY`. Production variables never leak through a `NEXT_PUBLIC_` key.
- **D-11:** Preview deployments must retain their exact generated `VERCEL_URL` host behavior and must
  not impersonate `fitout.live`. The plan must remove any localhost fallback that can leak into a
  Vercel preview's metadata, links, or Better Auth origin while preserving exact-host allow-listing and
  the public-default fail-closed routing rule.
- **D-12:** Audit every external configuration that stores a public URL, then update and prove only the
  relevant entries: Google OAuth production origin/callback, PayMongo webhook, Didit webhook, and
  Inngest serve endpoint where configured. Cloudinary and Neon have no domain callback to change.
  The production public host is `fitout.live`; staff-only links remain `ops.fitout.live`.

### Proof and handoff

- **D-13:** Completion requires Vercel domain health, Resend verification, real delivery to the monitored Gmail inbox, and a real reply arriving
  there, not only a green unit test or Resend dashboard status.
- **D-14:** Production proof covers the public auth path, a booking/notification path, staff invitation
  when safely available, and each configured external webhook's authenticated receipt without using a
  bearer URL or real customer data as evidence.
- **D-15:** The manual handoff records the safe future-inbox replacement procedure: create and monitor
  the dedicated inbox, change `SUPPORT_EMAIL` once, deploy, repeat the delivery/reply walk, and only
  then retire the launch Gmail address.

### Agent discretion

- Select the smallest focused test set and redacted evidence format that prove the domain topology,
  sender/Reply-To contract, callback destinations, and preview-versus-production origin behavior.
- Choose the exact Vercel UI or CLI sequence, provided no secret is written to the repository and DNS
  records are copied only from the live provider dashboards.
</decisions>

<code_context>
## Existing Code Insights

### Reusable assets

- `SUPPORT_EMAIL` is already the one public contact constant; the footer, payment states, trust
  copy, and email shell are already composed around it.
- `send()` in `src/lib/email.ts` is the one Resend call site, so adding `Reply-To` there covers every
  existing transactional email without duplicating per-template configuration.
- `src/lib/app-origins.ts` already models only exact public, ops, and Vercel-preview authorities;
  it is the right seam for removing preview localhost leakage without introducing wildcard trust.
- `tests/design/site-contacts.test.ts` changes its assertions automatically when `SUPPORT_EMAIL`
  changes from `null` to a string, and the auth-origin tests already model production and preview hosts.

### Integration points

- Vercel owns the `fitout.live` DNS zone, deployment domains, and environment configuration; Resend
  owns sender-domain verification and delivery observability.
- Better Auth, metadata, mail CTAs, payment returns, and notifications currently derive URLs from
  public-origin configuration. They must all resolve to the same explicit production origin.
- Google OAuth, PayMongo, Didit, and Inngest are the only provider dashboards that can retain a
  customer-visible FitOut callback. Their values must be inventoried rather than guessed.
- The existing Better Auth and notification mailers share `src/lib/email.ts`; this phase must preserve
  the production rule that missing email configuration never logs token-bearing URLs.
</code_context>

<deferred>
## Deferred Ideas

- A dedicated `support@fitout.live` mailbox or Google Workspace: replace the launch Gmail address using
  D-02 after the account exists.
- Shared-inbox workflows, ticketing, inbound Resend webhooks, and automatic support triage: separate
  support-product work, not needed for a monitored launch address.
- Moving the public canonical host to `www.fitout.live`: Vercel recommends that topology, but this
  phase retains the user-chosen `fitout.live` public address and a one-way `www` redirect.
</deferred>
