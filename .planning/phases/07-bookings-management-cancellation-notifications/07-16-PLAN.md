<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → refund destination submission | The booker supplies personal financial data that directs where real money goes |
| FitOut → PayMongo `/v2/batch_transfers` | An outbound disbursement to an arbitrary bank account |
| session → destination binding | A hijacked session must not be able to redirect a refund |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-94 | Tampering | **Payout redirection** — a hijacked session changing the refund destination | mitigate | The destination is accepted ONLY inside the already-owner-gated cancel flow, bound to the authenticated booker AND that specific booking id, and the amount is server-frozen at `quote.totalRefundCents`. A destination is NEVER read from a prior request, a session value or a stored record. Tests 5 and 7. |
| T-07-95 | Information disclosure | **PH Data Privacy Act (RA 10173)** exposure of bank details | mitigate | Collect-and-never-store: details pass straight through to the transfer; only the transfer id and a masked last-4 are persisted. Tests 3 and 4 assert no row and no log line contains the account number or name. PCI-DSS does not apply (not card data). |
| T-07-96 | Tampering | Refund/payout idempotency-key collision | mitigate | The refund transfer uses `refund:${bookingId}`; the payout path keeps `payout:${bookingId}`. Grep asserts both namespaces exist and neither is reused. Test 1. |
| T-07-97 | Tampering | Silent double-disbursement on retry | mitigate | A stable `Idempotency-Key` prevents the double-pay while `reference_number` rotates per attempt as PayMongo requires (test 2); assumption A3 is settled by the Task-1 probe rather than assumed. |
| T-07-98 | Denial of Service | Firing a doomed transfer above the InstaPay ceiling | mitigate | An explicit `amountCents > 5_000_000` guard takes the `needs_attention` operator-alert path instead of firing (test 6). |
| T-07-99 | Spoofing | Arbitrary/invalid institution BIC | mitigate | `institutionBic` is validated against the live `listReceivingInstitutions()` set server-side, not accepted as a free string. |
| T-07-100 | Repudiation | Building an entire workstream on a documentation claim that is now 404 | mitigate | Task 1 settles the question with an observed API outcome polled to a TERMINAL status, and the verdict plus its evidence is recorded in `refund-rail.ts`. An HTTP 200 alone is explicitly rejected as insufficient, because an async `failed` looks healthy in code while stranding the booker's money. |
