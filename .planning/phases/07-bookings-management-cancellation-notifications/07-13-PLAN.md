<objective>
Ship the four reminders on an hourly singleton cron, with at-most-once semantics enforced by a database constraint — not by Inngest's idempotency, which is documented as a 24-hour key that debouncing, batching and function pausing all bypass.

Purpose: D-87 asks for "one reminder each". Relying on a vendor dedupe TTL would make that guarantee depend on not enabling batching later. The codebase already proves the correct shape twice: `host_payout_ledger`'s `UNIQUE(booking_id)` where the INSERT is the lock, and `request-expiry`'s status-scoped `UPDATE … RETURNING`.
Output: the reminders cron, its registration, and a genuine two-connection concurrency test.
</objective>

Cron declaration (minute 45 — `:00` payout-sweep, `:15` request-expiry, `:30` payout-reconcile are taken):
```typescript
// NOTE: inngest 4.13.0 uses the 2-arg createFunction(options, handler) form — the cron trigger lives in
// options.triggers. The 3-arg (config, trigger, handler) skeleton in most online examples is STALE.
export const remindersSweep = inngest.createFunction(
  { id: "reminders-sweep", concurrency: 1, triggers: [{ cron: "TZ=Asia/Manila 45 * * * *" }] },
  async ({ step }) => { /* four due queries, each row remindered in its OWN step */ },
);
```
Each due row is processed inside its own `step.run(\`remind-${kind}-${bookingId}\`, …)` so a mid-batch failure retries just that reminder, never the whole sweep.

The four due queries — all RANGE-based against the DB clock, never an instant. An hourly cron cannot hit an offset more precisely than ±1 hour; a range plus the UNIQUE claim means a missed tick recovers on the next one and can never double-send:

`queryDuePreExpiry` (approved but unpaid — the highest-value reminder, the one D-89 accepted risk on):
```sql
WHERE b.status = 'approved'
  AND b.expires_at > now()
  AND b.expires_at <= now() + make_interval(hours => ${PRE_EXPIRY_REMINDER_HOURS}::int)
```
`queryDuePreSlaHost` (host with a pending request):
```sql
WHERE b.status = 'requested'
  AND b.expires_at > now()
  AND b.expires_at <= now() + make_interval(hours => ${PRE_SLA_REMINDER_HOURS}::int)
```
Comment on this one: `A D-96 cap-shortened SLA can make this reminder UNREACHABLE — a request 4h out gives the host a 2h SLA, so a 6h offset can never fire. The `expires_at > now()` guard handles that gracefully (no row, no send), which is CORRECT but SILENT — hence the dedicated test.`

`queryDuePreSessionBooker` / `queryDuePreSessionHost`:
```sql
WHERE b.status = 'confirmed'
  AND b.starts_at > now()
  AND b.starts_at <= now() + make_interval(hours => ${OFFSET}::int)
```
with the booker/host recipient resolved by the join (`booking.booker_id` / `listing.host_id`), each selecting the recipient's email, the listing title, timezone and city.

Every query takes an injectable `dbConn: DbConn` (never a hardcoded `db`) so integration tests can bind an isolated schema, and every query LEFT JOINs `booking_reminder` on `(booking_id, kind)` to skip already-claimed rows cheaply — while the claim, not the join, remains the authority.

`claimReminder` — CLAIM BEFORE SEND. If the send is attempted first and the process dies before the marker is written, the next tick double-sends. Claiming first means a crash loses a reminder — the strictly better failure under D-87, and consistent with `payOne`'s ordering. Reproduce that reasoning as a comment.
```sql
INSERT INTO booking_reminder (id, booking_id, kind)
VALUES (${randomUUID()}, ${bookingId}, ${kind}::reminder_kind)
ON CONFLICT (booking_id, kind) DO NOTHING
RETURNING id
```
Empty `RETURNING` ⇒ already sent ⇒ return false and emit NOTHING.

After a successful claim, call `emitNotify(...)` with the matching notification type (`reminder_pre_expiry`, `reminder_pre_session`, `reminder_pre_sla`), a `whenLabel` from `composeWhenLabel` (never a new time format), and a `formatMoney` total where relevant. Wrap the emission in the self-swallowing catch discipline: an emission failure must never fail the sweep step. Return `{ status: "sent" }` / `{ status: "skipped-claimed" }`.

Finally register `remindersSweep` in `src/app/api/inngest/route.ts`'s `functions: []` array and update its comment to name all five functions. Leave the fail-closed prod guard untouched.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Inngest cron → database | Runs unauthenticated by any user; the claim constraint is the only thing preventing duplicate sends |
| reminder query → recipient email | Selects a third party's contact address for delivery |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-76 | Denial of Service | Duplicate reminder spam (cron overlap, step retry, backfill, multi-instance deploy) | mitigate | `UNIQUE(booking_id, kind)` + `ON CONFLICT DO NOTHING RETURNING` is the lock, immune to all four; `concurrency: 1` is defence in depth, not the guarantee. Proven by the two-connection racing test. |
| T-07-77 | Spoofing | Vendor dedupe assumed sufficient | mitigate | Inngest's `idempotency` is explicitly NOT relied on (documented in the file header as a 24h TTL bypassed by batching). The guarantee is a database constraint. |
| T-07-78 | Information disclosure | Reminder sent to the wrong party | mitigate | Each query resolves its recipient by an explicit join (`booking.booker_id` for booker reminders, `listing.host_id` for host reminders); payloads carry only display strings. Test 1 asserts per-kind selection isolation. |
| T-07-79 | Information disclosure | Reminding on a terminal booking | mitigate | Every query is status-scoped (`approved` / `requested` / `confirmed`) and future-scoped; test 8 asserts a cancelled booking is never selected. |
| T-07-80 | Denial of Service | A rejecting email transport failing the whole sweep | mitigate | Each reminder runs in its own `step.run`, and the emission is wrapped in the self-swallowing catch discipline (test 7). |
| T-07-81 | Repudiation | No record of a reminder that was sent | accept | `booking_reminder` rows ARE the send history (a deliberate benefit of a table over four timestamp columns). Permanent send failures still surface via the Plan-07 `onFailure` `needs_attention` audit row. |
