<objective>
Give ROADMAP SC#3 a product path: a host can cancel a confirmed booking through the UI, behind deliberately heavier friction, and the four D-70/D-71 consequences all fire — full booker refund, an audit record, an auto-block of the freed window, and a capped cancellation fee as a signed ledger debit.

Purpose: without a UI trigger, D-70's apparatus has no way to run and SC#3 has no product path. The economics are the point: a host rejection is the one reversal nobody can fairly be billed for (D-63), but a host breaking an ALREADY-CONFIRMED booking the booker paid for is the opposite case — they can fairly be billed, and the fee self-funds the ~2.5% the platform would otherwise eat for nothing.
Output: the host cancel action, the two-pane dialog, the host booking detail page, the unblock refusal, and tests.

9. Charge the fee as a SIGNED DEBIT row, CAPPED AT WRITE TIME:
```typescript
// D-71 — the cap is enforced HERE, at write time, not at netting time. Enforcing it during the sweep
// would be too late (the row would already misstate the debt) and would have to be re-derived on every
// sweep. gross/commission are meaningless for a debit; set gross = -fee, commission = 0, net = -fee so
// the arithmetic stays coherent if anything ever sums the column.
const feeCents = Math.min(HOST_CANCEL_FEE_CENTS, row.spacePriceCents ?? row.quotedTotalCents ?? 0);
```
```sql
INSERT INTO host_payout_ledger (id, booking_id, host_id, kind, gross_cents,
  commission_rate_bps, commission_cents, net_cents, recovered_cents, currency, state)
VALUES (${randomUUID()}, ${bookingId}, ${row.hostId}, 'host_cancel_fee', ${-feeCents},
  0, 0, ${-feeCents}, 0, ${row.currency}, 'held')
ON CONFLICT (booking_id, kind) DO NOTHING
RETURNING id
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host browser → cancel action | Untrusted booking id + reason; nothing else may cross |
| host → their own punitive block | The host controls the unblock action and could otherwise defeat the consequence |
| platform wallet → booker refund | Real money leaves on a host-triggered action |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-61 | Elevation of privilege | Host cancelling another host's booking | mitigate | Owner-gate (`listing.hostId === userId` AND `hostCanHost`) BEFORE any write, plus a status-scoped UPDATE. Cross-host and missing return the IDENTICAL `DENIED` string (test 10). |
| T-07-62 | Tampering | Host evading the consequence by deleting the auto-block | mitigate | The block carries `reason = 'host_cancellation'` and `removeBlock`'s DELETE adds `AND (reason IS DISTINCT FROM 'host_cancellation')`; test 6 proves the block survives an unblock attempt while normal blocks stay deletable. This is 07-RESEARCH Open Question 3, resolved. |
| T-07-63 | Tampering | Client-supplied cancellation fee | mitigate | The fee is computed server-side as `Math.min(HOST_CANCEL_FEE_CENTS, spacePriceCents)`; the dialog renders a server prop and the action accepts only `(bookingId, reason)`. |
| T-07-64 | Tampering | Double-charging the cancellation fee | mitigate | `INSERT … ON CONFLICT (booking_id, kind) DO NOTHING RETURNING id` — the INSERT is the at-most-once lock, with no app-level pre-check. Test 4 asserts exactly one debit row after two calls. |
| T-07-65 | Tampering | Host cancels and immediately resells the slot higher | mitigate | The freed window is auto-blocked on the same listing AND unit for the exact `[startsAt, endsAt)` range (test 5), and that block is undeletable (test 6). This is D-70's stated abuse vector. |
