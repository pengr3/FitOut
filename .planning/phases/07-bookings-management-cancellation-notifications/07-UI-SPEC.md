# Phase 7 — UI Design Contract

> Visual and interaction contract for Bookings Management, Cancellation & Notifications. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This phase adds NO new design system, tokens, fonts, or color values.** It EXTENDS the FitOut design system established across Phases 02–06 (shadcn `radix-nova` / neutral / lucide / Geist; the locked 8-point spacing, 4-size / 2-weight typography, and the 60/30/10 coral-accent contract). Every surface below is a clone of, or an addition to, a component that already ships.
>
> **Phase 7 is a money-correctness phase wearing a UI phase's clothes** (07-RESEARCH § Summary). The single highest-stakes screen is the booker cancel review — ROADMAP SC#2 requires the exact refund amount be visible before confirming. Design accordingly: disclosure over density, server-computed over client-derived.

- **Every money figure uses `tabular-nums`** — mandatory on the refund breakdown so the itemised column aligns to the decimal (this is the SC#2 screen; misaligned digits read as untrustworthy).

### The cancel actions are NOT coral and NOT destructive-red

**Booker cancel** and **host cancel** both use **neutral `outline`** buttons. Rationale, continuous with the D-65/06-UI-SPEC decline decision: cancelling is an expected lifecycle outcome, not a data-destroying error. Red would misrepresent a refund the booker is contractually entitled to, and coral would advertise the action FitOut least wants taken. Weight is carried by **disclosure and step count**, not color.

`--destructive` appears in the cancel flows in exactly one place: the numerals of any **amount the user loses** (the non-refundable service fee, the host cancellation fee) may render `text-destructive` **paired with an icon or explicit label** — never color-only.

**D-79 refund detail — the exact rendering rule (load-bearing):**

The badge label is **always and only** `Cancelled`. Refund detail renders as a **separate muted line beneath the badge**, never inside it:

```
[Ban] Cancelled
₱500 refunded
```

*Rationale [researcher's call]:* badges are a fixed-width, fixed-vocabulary element shared with a table column; interpolating a variable money string into one breaks column widths on desktop and the badge grammar everywhere. A sibling line satisfies D-79's "renders as secondary detail" literally and keeps the badge derivation pure. Copy variants: full refund → `₱1,000 refunded`; partial → `₱500 refunded`; zero → `No refund — cancelled inside the no-refund window`. **Never** render a bare `₱0 refunded` without the reason.

**Icon-collision note:** `CheckCircle2` is used by both the `confirmed` booking badge and the `paid` payout badge (`payout-state-badge.tsx:34`). On `/host/bookings` these appear in adjacent columns. This collision is **pre-existing and accepted** — the column header plus the distinct labels (`Confirmed` vs `Paid`) disambiguate. Do not re-assign either; changing the shipped payout icon would break parity with `/host/earnings`, which D-105 explicitly requires.

### 3. Booker cancel flow (D-78) — the SC#2 screen

**Entry point.** On `/bookings/[id]` only (D-104). A neutral `outline` `Cancel booking` button placed **below** the primary content and separated by a `Separator` — present but not competing. Never on a list row.

**Placement of the breakdown.** A dedicated RSC route **`/bookings/[id]/cancel`**, not a dialog. **[researcher's call]** — *rationale: `quoteRefund` must be evaluated against the **DB** clock (07-RESEARCH Pitfall 6 — a JS-clock preview can show 100% while the action awards 50%). An RSC route computes `now()` server-side on every render for free; a client dialog would need a round-trip to populate and could render stale rung boundaries.*

**Layout (top → bottom):** heading → the tier + rung explanation in prose → the itemised breakdown → the refund total → confirm/back.

| Element | Copy |
|---|---|
| Heading | `Cancel this booking?` |
| Context line | `{Space title} · {date}, {time} ({City} time)` |
| Tier rationale (D-78 "which tier applies and why") | `This space uses the {Flexible\|Standard\|Strict} cancellation policy. You're cancelling {N} hours before the session starts, which falls in the {rung description} window — {X}% of the space price is refunded.` |
| Breakdown (see below) | Itemised, `tabular-nums`, right-aligned |
| Refund total | Label `Refund to you` (14px/600) · value **Display 28px/600** |
| Timing note | `Refunds usually land back on your original payment method within a few days.` |
| Confirm | `Cancel booking` — neutral `outline` |
| Back | `Keep booking` — `ghost`, the visually calmer of the two |

**The itemised breakdown — exact line set (D-78, all six elements):**

```
You paid                                      ₱1,050
  Space price                                 ₱1,000
  Service fee                                     ₱50

Space price refund (50%)                        ₱500
Service fee refund                                ₱0
  Service fees aren't refunded
─────────────────────────────────────────────────────
Refund to you                                   ₱500
```

Rules:
- **Every figure is server-computed** and arrives as a prop. Zero client arithmetic — the same contract `PriceBreakdown` documents (`price-breakdown.tsx:1-10`).
- The line is labelled exactly **`Service fee`** (D-73). See § Copywriting locks.
- `Service fees aren't refunded` renders as a muted helper directly beneath the `₱0` line — **always present**, including when the refund is 100%. The one place the booker could be surprised is the one place the disclosure must be unconditional.
- When the rung is 0%, the breakdown still renders in full with `₱0` refunds, and the tier rationale explains why. **Never** replace it with a bare "no refund" message — SC#2 requires the exact amount and its derivation be visible.

**Unpaid holds.** Cancelling a `requested` / `approved` booking moves no money. Per 07-RESEARCH § Discretion, reuse the decline/release path: a plain confirm dialog on the detail page, **no breakdown, no money UI**. Copy: title `Cancel this request?` · body `We'll let the host know and free the slot. You haven't been charged, so there's nothing to refund.` · confirm `Cancel request`.

### 4. Host cancel flow (D-80) — concretely more friction

D-80 mandates "deliberately more friction than the booker's cancel" without specifying it. **[researcher's call]** — the friction is **a required reason + an explicit acknowledgment + a second step**, not a type-to-confirm gate.

*Rationale: this mirrors the Airbnb/Peerspace host-cancellation pattern (benchmarks land better than abstractions — 07-CONTEXT § Specific Ideas), and the reason field is **load-bearing rather than theatrical**: D-70 requires an audit record against the host, and 07-RESEARCH Open Question 3 needs a `reason` value on the punitive `availability_block` so the host can't simply unblock the window.*

| Step | Contract |
|---|---|
| Entry | `/host/bookings/[id]` (or the host view of the booking) — neutral `outline` `Cancel booking`, below the fold, never inline on a row |
| **Step 1 — Reason** | Dialog. Required `select`: `Space is unavailable` · `Double-booked elsewhere` · `Maintenance or damage` · `Guest asked me to cancel` · `Other`. `Continue` stays **disabled** until a reason is chosen. |
| **Step 2 — Consequences** | Same dialog, second pane. All three consequences stated plainly as a list (below). Plus a **required checkbox**. `Cancel this booking` stays disabled until it is ticked. |
| Confirm button | `Cancel this booking` — neutral `outline` |
| Back | `Keep booking` — `ghost` |

**Step 2 copy (all three D-70 consequences, plainly):**

> **Cancelling this booking will:**
> - Refund **{₱total}** to {guest} in full — regardless of your cancellation policy.
> - Charge you a **{₱HOST_CANCEL_FEE}** cancellation fee, deducted from your next payout.
> - Block **{date}, {time} ({City} time)** on this space, so the slot can't be rebooked.
>
> ☐ I understand **{₱HOST_CANCEL_FEE}** will be deducted from my next payout.
>
> This can't be undone.

Rules:
- The fee amount is **server-computed and already capped** at the booking value (07-RESEARCH: cap enforced at write time). The UI renders the capped figure it is handed — it never applies the cap itself.
- The fee figure may render `text-destructive` **with** the explicit "deducted from your next payout" label — never color-only.
- If the host has an outstanding unrecovered debit, surface it here too: `You have {₱X} in cancellation fees still to be deducted.`

**Friction delta, explicitly:** booker = 1 step, no reason, no checkbox. Host = 2 steps, required reason, required acknowledgment. That is the contract; do not equalise them.

**Visual hierarchy / focal point (locked, per surface):**
- **`/bookings`, `/host/bookings`:** the **rows are the working area**. No page-level focal CTA. Status badges are scannable, not shouty.
- **`/bookings/[id]/cancel`:** the **refund total is the focal point** (the one Display-scale figure). The confirm button is deliberately quieter than the number it explains — the user should be reading, not clicking.

- **Expired-approval state:** the **re-request CTA is the focal point**; the explanation is calm and secondary.

**Interaction rules (locked):**
- **All money is server-computed** (Security V4). Refund amounts, tier evaluation, rung selection, and fee math arrive as props; the client sends only a booking id. **Zero client arithmetic anywhere in any breakdown.**
- **The DB clock is the sole authority** for tier rungs, expiry, and the Upcoming/Past partition. A preview computed on the JS clock can show 100% while the action awards 50% (07-RESEARCH Pitfall 6).
