Create `src/lib/booking/bookings-query.ts` — a pure query module taking an injectable `dbConn: DbConn` as its first argument (the convention every queryable follows, so integration tests can bind an isolated schema).

Header comment must record three load-bearing decisions:
1. **Owner scoping is in the WHERE, never post-filtered** (Security V4). `/bookings` filters `booking.booker_id = $1`; `/host/bookings` joins `listing` and filters `listing.host_id = $1`. The `(host)` route group is NOT the gate.
2. **The Upcoming/Past partition uses the DB clock**, not a JS boundary computed in the RSC — otherwise a booking can appear in both tabs or neither across the `now()` boundary.
3. **Keyset, not OFFSET** — a deliberate DIVERGENCE from the Phase-4 search idiom (`search-results.tsx:120` sets `?page=`). The Past tab grows without bound and `OFFSET` degrades linearly; the ordering key `(starts_at, id)` is stable and indexed by `booking_booker_idx`.

Both queries select the derived status in SQL — the `completed` value is NEVER written (D-102):
```sql
CASE WHEN b.status = 'confirmed' AND b.ends_at <= now() THEN 'completed' ELSE b.status::text END AS "displayStatus"
```

Tab predicates (D-103 — cancelled and declined live under Past, since they are equally inert):
```sql
-- upcoming
b.ends_at > now() AND b.status NOT IN ('cancelled','declined')
-- past
NOT (b.ends_at > now() AND b.status NOT IN ('cancelled','declined'))
```
Order: Upcoming `ORDER BY b.starts_at ASC, b.id ASC`; Past `ORDER BY b.starts_at DESC, b.id DESC`. `LIMIT ${limit + 1}` and, if `limit + 1` rows come back, drop the extra and emit `nextCursor` from the last kept row; otherwise `nextCursor: null`.

`queryBookerBookings` additionally LEFT JOINs the listing's primary photo (position 0) for the 48×48 row thumbnail, and selects `refund_cents` so the row can render the D-79 sibling line.

`queryHostBookings` additionally:
- INNER JOINs `user` for `bookerFirstName`,
- LEFT JOINs `host_payout_ledger p ON p.booking_id = b.id AND p.kind = 'payout'` for `payoutState` (the `kind` scope is mandatory — a `host_cancel_fee` debit row must never be read as a payout state),
- accepts an optional `listingId` filter appended as `AND b.listing_id = ${listingId}` when non-null (the D-104-adjacent multi-listing filter; server-side only).

Guard `limit` to a hard maximum (e.g. `Math.min(Math.max(limit, 1), 50)`) so a crafted query string cannot request an unbounded page.

Parse the cursor defensively: if it does not match `"{iso}|{id}"`, treat it as absent rather than throwing — a malformed cursor must yield page 1, never a 500.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → RSC query string | `?tab=`, `?cursor=`, `?listing=` are attacker-controlled |
| route group membership → access | `(host)` membership is NOT an access check |
| session → row visibility | Every row returned must belong to the authenticated user |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-28 | Information disclosure | Cross-user booking leakage (IDOR) | mitigate | Ownership is a `WHERE` predicate inside `queryBookerBookings` / `queryHostBookings`, never a post-filter. `tests/security/bookings-owner-scope.test.ts` proves zero foreign rows on both sides and both tabs. |
| T-07-29 | Elevation of privilege | Route-group-only gating on `/host/bookings` | mitigate | The RSC re-checks `session` AND `canHost` before rendering (cloned from `/host/earnings:45-54`) AND scopes the query by `listing.host_id`. Two independent gates. |
