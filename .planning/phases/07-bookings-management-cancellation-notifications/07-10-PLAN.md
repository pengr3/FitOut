Replace every `void sendXxx(...)` in these two files with an `await emitNotify({ ... })` call placed AFTER the durable write has committed and AFTER `recordAudit`, matching the shape:

```typescript
await recordAudit({ actorId: userId, action: "approve_request", outcome: "ok", meta: { requestId } });

// D-83: the send moves behind Inngest. This emits an EVENT and returns; the notify function performs the
// send with automatic retry, backoff and per-run observability, and writes the in-app notification row at
// parity (D-91). emitNotify swallows transport errors internally — a notification failure must NEVER fail
// a money/state action whose durable write already succeeded (MANAGE-03).
// NEVER inside db.transaction: inngest.send is an outbound HTTP call, and a rollback would leave an event
// already sent for a booking that does not exist.
await emitNotify({
  type: "request_approved",
  recipientId: row.bookerId,
  bookingId: requestId,
  email: row.bookerEmail,
  payload: {
    type: "request_approved",
    listingTitle: title,
    whenLabel,
    payByLabel: /* the venue-local pay-by deadline, composed here */,
    href: `/bookings/${requestId}`,
  },
});
```

- `approveRequest` → `request_approved` to the BOOKER.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server action → Inngest event | Recipient identity and display strings cross a network hop |
| database transaction → outbound HTTP | An emission inside a transaction holds a connection across a network hop and can leak events for rolled-back rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-56 | Information disclosure | Notification sent to the wrong party | mitigate | `recipientId` and `email` are read from the row the action already owner-gated and joined; no second lookup and no request-supplied recipient. Reviewed per call site during migration. |
| T-07-57 | Denial of Service | Email transport failure failing a money action | mitigate | `emitNotify` swallows and logs; test 2 proves `approveRequest` still returns `{ ok: true }` when `inngest.send` rejects. |
| T-07-58 | Repudiation | An event emitted for a booking that does not exist | mitigate | Every emission is placed AFTER the durable write commits and after `recordAudit`; emissions inside `db.transaction` are moved out, verified by reading each call site. |
| T-07-59 | Tampering | Notification spam via repeated actions | mitigate | Every action's UPDATE is status-scoped, so a repeat is a 0-row no-op that emits nothing (test 3). Rate limits on the actions remain unchanged. |
| T-07-60 | Information disclosure | Injection through interpolated display strings | mitigate | Payloads carry pre-composed strings; the email path continues to `escapeHtml` every interpolated field (`email.ts` templates are UNCHANGED in this plan), and the in-app renderer emits React text children only. |
</threat_model>
