Create `src/app/actions/notifications.ts` with a SECURITY CONTRACT header stating: notification reads and writes are OWNER-SCOPED IN THE QUERY, never post-filtered — an IDOR here leaks the other party's booking details (space title, times, amounts), which is exactly the class of leak Security V4 targets.

```typescript
export async function markNotificationRead(notificationId: string): Promise<{ ok: boolean }> {
  const userId = await requireUserId();
  if (!userId) return { ok: false };
  // Owner-scope lives IN THE UPDATE's WHERE. A foreign or missing id claims 0 rows and returns the SAME
  // calm { ok: false } — no enumeration oracle, no distinguishable "not yours" branch.
  await db.execute(sql`
    UPDATE notification SET read_at = now()
    WHERE id = ${notificationId} AND recipient_id = ${userId} AND read_at IS NULL
  `);
  revalidatePath("/bookings");
  revalidatePath("/host/bookings");
  return { ok: true };
}

export async function markAllNotificationsRead(): Promise<{ ok: boolean }> {
  const userId = await requireUserId();
  if (!userId) return { ok: false };
  await db.execute(sql`
    UPDATE notification SET read_at = now()
    WHERE recipient_id = ${userId} AND read_at IS NULL
  `);
  revalidatePath("/bookings");
  revalidatePath("/host/bookings");
  return { ok: true };
}
```
Add `rateLimit(\`mark-read:${userId}\`, { window: 60, max: 60 })` to `markAllNotificationsRead` (a generous budget — this is a cheap, non-money action, but it is an unbounded write and should not be spammable). Audit only the rate-limit denial; a routine mark-read does not warrant an audit row.

Both actions return the SAME shape for success, foreign id and missing id — the read-state of a notification the caller does not own must be unobservable.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → mark-read action | Untrusted notification id |
| notification payload → rendered DOM | Display strings originate from user-controlled listing titles and names |
| polling client → server | Repeated `router.refresh()` calls from every open tab |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-82 | Information disclosure | Reading another user's notifications (IDOR) | mitigate | `listRecent` and `countUnread` filter `recipient_id = $1` in the WHERE, never post-filtered; both layouts pass `session.user.id`. Tests 1-2 assert zero foreign rows. An IDOR here leaks the other party's booking details. |
| T-07-83 | Tampering | Marking another user's notification read | mitigate | Both UPDATEs carry `AND recipient_id = ${userId}`; a foreign id claims 0 rows and returns the identical shape (test 3), so read-state of a foreign notification is unobservable. |
| T-07-84 | Tampering | Stored XSS through a notification payload | mitigate | The item renderer emits React text children only; `grep -rc "dangerouslySetInnerHTML" src/components/notifications/` returns 0. Payloads are Zod-validated at the single insert site (Plan 07). |
| T-07-85 | Denial of Service | Unbounded polling load | mitigate | The poller is BOUNDED (fixed max attempts, cloned from `pending-payment-state.tsx`), uses a ~30s interval rather than 2.5s, and PAUSES when `document.hidden`. `markAllNotificationsRead` is rate-limited. |
| T-07-86 | Denial of Service | Unbounded panel growth | mitigate | `listRecent` is capped at 20 server-side (test 5) and the panel has a fixed `max-h-96` with an internal ScrollArea. |
| T-07-87 | Information disclosure | Unread count leaking through a shared cache | accept | Both layouts read the count per-request from the authenticated session; there is no shared cache layer in this path. |
</threat_model>
