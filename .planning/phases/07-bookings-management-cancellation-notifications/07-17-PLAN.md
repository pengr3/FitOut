<objective>
Close the four user-approved Phase-7 verification/review findings — the two Critical content-accuracy
gaps (CR-01, CR-02) that block roadmap SC#4 ("keeps everyone informed" must not mean misinformed) and
the two verifier-confirmed Warnings (WR-04, WR-06).

All four are *communication/pricing-truth* defects in otherwise mechanically-correct flows:

1. **CR-01** — every 0%-rung booker cancellation sends a false "Refund issued — ₱0 … usually lands
   within a few days" notification+email, because `formatMoney(0, …)` is a non-null string and the
   suppression guard keys on label nullability instead of the refund AMOUNT.
2. **CR-02** — `sendRequestApproved` / `sendNewRequestToHost` / `sendRequestReceived` render the flat
   config constants (12h payment window / 24h SLA) although the payloads already carry the row's real
   D-96-capped `payByLabel`/`respondByLabel` — false in writing on every short-notice request, and a
   two-channel drift from the correct in-app copy (the exact failure D-91/D-99 forbid).
3. **WR-04** — the host's own copy of a host cancellation is the booker's copy verbatim: "You're
   getting a full refund of ₱X" / "Your host cancelled" — wrong on every clause for the canceller, and
   the D-71 fee consequence appears in neither channel.
4. **WR-06** — `re-request.ts` re-derives `fullDay` by comparing the frozen space price against the
   listing's CURRENT `hourlyRateCents`, so any host rate edit makes every hourly re-request silently
   reprice at the flat day rate. This is the documented "re-derive fullDay from total ≠ rate × hours"
   anti-pattern recurring where it is PRICE-DETERMINING, not display-only.

Purpose: MANAGE-03 requires transactional messages that inform, not misinform; PAY-06 requires refund
communication that matches the money that actually moved, and re-request pricing that matches the mode
actually booked.
Output: four surgical fixes, each preceded by a regression test that FAILS against the current code —
Phase 7's discipline is that a green suite proves nothing about content unless something asserts the
content; all four of these bugs passed 639 tests precisely because nothing did.
</objective>
