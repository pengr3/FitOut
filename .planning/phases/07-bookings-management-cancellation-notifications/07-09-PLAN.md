Shared constants:
```typescript
const CANCEL_RATE_LIMIT = { window: 60, max: 5 } as const;   // mirrors the approve/confirm budgets
/** The SAME calm denial for a missing booking AND a cross-user booking (IDOR — leak nothing). */
const DENIED: CancelActionResult = { ok: false, error: "We couldn't find that booking, or it isn't yours to manage." };
/** Calm result for a 0-row cancel — already cancelled or raced (never a 500). */
const NOT_ACTIVE: CancelActionResult = { ok: false, error: "This booking is no longer active — it may have already been cancelled." };
const PAST_START: CancelActionResult = { ok: false, error: "This session has already started, so it can't be cancelled here. Message the host if something's wrong." };
```

`cancelBookingAsBooker(bookingId)` sequence — the ORDER is load-bearing:
1. `requireUserId()`; no session → calm sign-in result.
2. Owner-gated load (booking JOIN listing JOIN aliased host user JOIN aliased booker user) verifying `bookerId === userId`; null → `DENIED`.
3. `rateLimit(\`cancel-booking:${userId}\`, CANCEL_RATE_LIMIT)`; on denial `recordAudit({ action: "cancel_booking", outcome: "denied", meta: { reason: "rate_limit", … } })` and return the going-a-little-fast message.
4. Read the DB clock ONCE: `const [{ now }] = await db.execute(sql\`SELECT now() AS "now"\`)`.
5. Compute the quote server-side:
```typescript
const quote = quoteRefund({
  tier: tierOrDefault(row.cancellationPolicy),          // the BOOKING snapshot, NEVER the listing
  spacePriceCents: row.spacePriceCents ?? row.quotedTotalCents ?? 0,
  serviceFeeCents: row.serviceFeeCents ?? 0,
  startsAt: row.startsAt,
  now,                                                   // the DB clock — Pitfall 6
});
```
6. The ATOMIC, status-scoped, DB-clock-guarded flip — every guard lives in the WHERE, and a 0-row result is a calm message:
```sql
UPDATE booking
SET status = 'cancelled',
    refund_cents = ${quote.totalRefundCents},
    retained_space_cents = ${quote.retainedSpaceCents},
    cancelled_by = 'booker',
    cancelled_at = now(),
    expires_at = NULL
WHERE id = ${bookingId}
  AND booker_id = ${userId}
  AND status = 'confirmed'
  AND starts_at > now()
RETURNING id
```
0 rows → distinguish the two calm cases with ONE extra read (`SELECT status, starts_at > now() AS "future"`): past-start → `PAST_START`; anything else → `NOT_ACTIVE`. Audit both as `outcome: "denied"` with the reason. Never throw.
Comment: `D-79 — the single `cancelled` status is kept deliberately. The GiST EXCLUDE predicate is the COMPLEMENT (status NOT IN ('cancelled','declined','completed')), so a new `cancelled_partial` value would default to OCCUPYING and permanently block the slot of every partially-refunded cancellation. D-79 did not avoid an audit; it avoided a live bug.`
Comment: `Cancellation is permitted only BEFORE starts_at. This structurally eliminates the payout clawback problem: payout is not eligible until endsAt + 24h (D-55), so a refund is always just a platform-wallet refund with the host never yet paid.`
7. `recordAudit({ action: "cancel_booking", outcome: "ok", meta: { bookingId, refundCents, retainedCents, tier, refundBps } })`.
8. Dispatch the refund — ONLY when `quote.totalRefundCents > 0` AND `row.paymentId` is set AND `isApiRefundable(row.paymentMethod)`:
```typescript
await createRefund({ paymentId: row.paymentId, amountCents: quote.totalRefundCents, reason: "requested_by_customer" });
```
Wrap in try/catch: a refund-dispatch failure must NOT unwind the durable status flip (the slot is already freed and that is the correct outcome); log and `recordAudit({ outcome: "needs_attention", action: "refund_dispatch_failed" })`.
When the rail is NOT API-refundable, take the operator-alert path (`recordAudit` `needs_attention`) and leave the D-72 branch as a single documented seam for Plan 16 — do NOT build a bank-details form here.
Comment: `The POST records INTENT only. Refund status is ASYNCHRONOUS (pending -> processing -> succeeded|failed); the payment.refunded / payment.refund.updated webhook is the SINGLE WRITER of terminal state (D-57). Never display "Refunded ₱500" off this POST.`
9. `await emitNotify(...)` — AFTER the commit, never inside a transaction — one event to the booker (`booking_cancelled_by_booker` / `refund_issued`) and one to the host, each carrying a pre-composed `whenLabel` via `composeWhenLabel` and a `refundLabel` via `formatMoney`.
10. `revalidatePath("/bookings"); revalidatePath("/host/bookings"); revalidatePath(\`/bookings/${bookingId}\`);`

```sql
SET status = (CASE WHEN status = 'requested' THEN 'declined' ELSE 'cancelled' END)::booking_status,

WHERE id = ${bookingId} AND booker_id = ${userId} AND status IN ('requested','approved')
RETURNING id
```
No money moves, so NO refund quote, NO PayMongo call, and NO breakdown — just the flip, the audit, the notifications and the revalidate. Return `{ ok: true, refundCents: 0 }`.
