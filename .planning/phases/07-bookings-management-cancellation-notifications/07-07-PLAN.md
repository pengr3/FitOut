`emitNotify(event)`:
```typescript
export async function emitNotify(event: NotifyEvent): Promise<void> {
  try {
    await inngest.send({ name: "fitout/notify", data: event });
  } catch (err) {
    // A notification-transport failure must NEVER fail a money/state action whose durable write already
    // succeeded — the same discipline as request-expiry.ts:159-164. Log for operators and move on.
    console.error("[notify] enqueue_failed", { type: event.type, bookingId: event.bookingId, err });
  }
}
```
Document the honest limitation directly above it: `KNOWN BOUNDED GAP (accepted for v1). If inngest.send() itself fails, no notification is produced and onFailure never fires (the function never ran). This is the SAME accepted bounded race as Phase-6 Assumption A6 (the in-tx-reclaim dropped email). The fully-robust alternative is a transactional outbox (write an outbox row in the same transaction, drain it from a cron) — meaningful scope, deliberately deferred. The reminder crons independently re-derive state from the DB and catch most user-visible consequences. Flagged as a known limitation, not pretended closed.`
And the hard rule: `NEVER call emitNotify inside db.transaction — inngest.send is an outbound HTTP call; inside a transaction it holds a connection open across a network hop and, worse, a rollback would leave an event already sent for a booking that does not exist. Emit AFTER commit.`

`countUnread(dbConn, recipientId)`: `SELECT count(*) FROM notification WHERE recipient_id = $1 AND read_at IS NULL` — hits the partial index directly. Comment: `Do NOT add a denormalised counter on user; that is a second writer and a drift class for an already-indexed query.`

`listRecent(dbConn, recipientId, limit)`: newest-first, owner-scoped in the WHERE (never post-filtered), capped at 20.

Create `src/inngest/functions/notify.ts`. This is the FIRST event-triggered Inngest function in the repo (all three shipped functions are crons) — carry the API-version comment forward verbatim in spirit.

```typescript
export const notify = inngest.createFunction(
  {
    id: "notify",
    retries: 4,                                  // default; explicit for auditability
    triggers: [{ event: "fitout/notify" }],
    // D-90: fires ONLY after all retries are exhausted. Implemented by Inngest as a separate function
    // bound to the inngest/function.failed system event; event.data.run_id holds the FAILED run's id.
    onFailure: async ({ error, event }) => {
      await recordAudit({
        actorId: "system",
        action: "notify",
        outcome: "needs_attention",
        meta: {
          notifyType: event.data.event.data.type,
          recipientId: event.data.event.data.recipientId,
          bookingId: event.data.event.data.bookingId,
          error: error.message,
        },
      });
      console.error("[notify-alert] permanently failed", { error: error.message });
    },
  },
  async ({ event, step }) => {
    // ORDERING IS A DELIBERATE RELIABILITY CHOICE (D-91). The in-app row goes FIRST: a DB write is faster
    // and far more reliable than an SMTP hop, so the durable record is the thing that always lands and the
    // email is the best-effort amplifier. Reversed, a permanently-failing email would leave NO record at all.
    await step.run("write-notification", () => insertNotification(db, event.data));
    // Email SECOND, in its OWN step ⇒ its own retries. A retry re-runs ONLY this step because step (1) is
    // memoized — that is what makes D-91's two-channel parity non-drifting.
    await step.run("send-email", () => sendForType(event.data));
  },
);
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Inngest cloud → /api/inngest | Unauthenticated inbound HTTP; signature-verified, fail-closed in production |
| server action → Inngest event | Event data crosses a network hop and is later written to the DB |
| notification payload → rendered HTML/email | Display strings originate from user-controlled listing titles and names |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-35 | Spoofing | Forged `/api/inngest` invocation | mitigate | The existing fail-closed guard (`INNGEST_SIGNING_KEY` required in production, throw at module load otherwise) is left untouched; `serve()` verifies every inbound request. |
| T-07-36 | Tampering | Stored XSS via notification payload | mitigate | The in-app renderer emits React text children only (auto-escaped, no `dangerouslySetInnerHTML` — enforced in Plan 14); the EMAIL path `escapeHtml`s every interpolated field including the CTA url, cloning the `email.ts:73-82` contract. |
