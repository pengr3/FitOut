# Phase 18 — UI Design Contract

> Visual and interaction contract for the **two** surfaces this phase ships: the internal FitOut Ops
> console, and the booker-facing check badge. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## What this document is, and what it deliberately does not touch

Phases 10–17 shipped a gated design system, a pattern layer, an app shell, a responsive/a11y/theme audit
and a hard set of build-blocking quality gates. **Colour, the four type roles, focus, status tones,
elevation, z-index, motion, the contrast inventory, the three card patterns, the four state families, the
one overlay primitive and the seven typed inventories** (`contrast-pairs.ts`, `measurements.ts`,
`selector-contract.ts`, `status-tones.ts`, `live-regions.ts`, `accent-uses.ts`, `visual-baselines.ts`) are
**LOCKED**. `npm run build` = `lint && test:design && next build`, so a raw hex, an arbitrary type size, an
undeclared `data-testid`, a raw `<Card>` in an unlisted file, an eleventh accent use, a viewport-conditional
JSX branch or a `loading.tsx` writing its own box measurement already fails the build today.

**This document invents no primitive.** Everything below either *consumes* a shipped token, pattern or
recipe, or names precisely which declared inventory must be **EXTENDED** — and an extension is always "add
a row with its reason and move the number in the same commit", never "invent a value at the call site".

⚠ **An internal tool is not exempt in this repo.** All five design gates apply to `/ops`: themes,
320px responsive, a11y, designed loading/empty/error states, and the pinned inventories. There is no
"it's only for staff" carve-out anywhere in `tests/design/**`, and this spec does not create one.

**Decision-ID namespace.** Bare `D-NNN` means **18-CONTEXT D-206…D-248**. PROJECT-namespace numbers are
written `PROJECT D-NN`. Earlier phases are written `11-CONTEXT`, `13-CONTEXT`, `14-CONTEXT`.

⚠ **A comment containing a banned token trips the design greps.** Where this document instructs source
prose, it instructs **descriptive naming**, never quotation of a gated string.

## Spacing Scale

**Inherited unchanged from Phase 10 (PROJECT D-05, global).** The declared legal set:
4 (`*-1`) · 8 (`*-2`) · 12 (`*-3`) · 16 (`*-4`) · 24 (`*-6`) · 32 (`*-8`) · 48 (`*-12`) · 64 (`*-16`).

**Phase 18 declares ZERO new spacing exceptions.** It renders exactly one inherited one: the **44px touch
target** (`size="touch"`, Phase 12's DS-09 exception). Every ops control that acts — Approve, Reject, and
both dialog confirms — is touch-sized at every width, on the same argument `request-row.tsx` records: a
control that is only reachable-sized on the surface somebody remembered is not a floor.

**Two new BOX constants are declared, both in `src/lib/design/measurements.ts`** — never at a call site:

| Constant | Value | Why it is a constant and not a class string |
|----------|-------|---------------------------------------------|
| `OPS_QUEUE_SHELL` | `"mx-auto w-full max-w-5xl px-4 py-10"` | The page and `loading.tsx` must render the **same** box, and the 14-06 lesson is that two files agreeing "because somebody typed the same five utilities twice" is not agreement. `max-w-5xl` rather than `HOST_LIST_SHELL`'s `max-w-4xl`: a queue row carries a photo mosaic, and 896px squeezes the mosaic into a strip too small to judge a space by — which would defeat OPS-04's whole point. `max-w-5xl px-4 py-10` is the shipped `/host/listings` box, hand-typed in two files today; this declares it. |
| `OPS_QUEUE_ROW_HEIGHT` | **MEASURE BEFORE WRITING** — predicted `h-…  md:h-…`, see § The queue row | The `RowSkeletonHeight` union rejects an undeclared value at compile time. **The union widens 4 → 5 members** (`ROW_CARD_HEIGHT`, `HOST_AGENDA_ROW_HEIGHT`, `HOST_REQUEST_ROW_HEIGHT`, `HOST_BOOKING_ROW_HEIGHT`, + this). `measurements.ts:73-81` states the rule: the legal set is decided where the heights are derived, not at whichever `loading.tsx` needed a taller bar that afternoon. |

⚠ **`OPS_QUEUE_ROW_HEIGHT` must be MEASURED, not derived.** Every sibling constant in that file carries a
real number taken off a rendered route (`254.05px at 320`, `83.02px at 1280`), and the two nearest ladder
steps with the over-claim stated. Phase 18 owes the same. The **prediction** below exists so the planner can
size the task, and it is not a licence to write it down:

> at the 320px floor the row composes a 44px header line + a 16/9 hero at 288px content width (≈162px) +
> the `Show all N photos` control (≈36px) + a six-term description list (≈108px) + a touch-height actions
> row (44px) + card padding (32px) ≈ **~430px**, i.e. `h-108` is the likely step. Above `md:` the mosaic
> opens and the description list goes two-up, so the desktop figure is a *different* measurement, not a
> scaled one.

## Typography

Inherited unchanged. Four roles, declared in `src/app/globals.css` and pinned by `tests/design/type-scale.test.ts`
against `TYPE_ROLES` (`src/lib/utils.ts:40`).

| Role | court (default theme) | Where Phase 18 uses it |
|------|----------------------|------------------------|
| `text-display` | 28px / 1.15 / 600 | `PageHeader`'s `<h1>` on `/ops`. Nowhere else. |
| `text-heading` | 20px / 1.3 / 600 | The wait figure on each queue row (`emphasis="lead"`), and the `ResponsiveDialog` title. |
| `text-body` | 16px / 1.5 / 400 | The `EmptyState`/`ErrorState` titles (owned by the patterns), the badge explainer sentence. |
| `text-label` | 14px / 1.43 / 400 | **Everything else on `/ops`** — every `<dt>`, every `<dd>`, every reason sentence, every money figure (plus `tabular-nums`). |

**Three type rules this phase adds:**

1. **THE WAIT IS THE LOUDEST THING ON THE ROW, and "loudest" is scale and position, never a hue.** The
   `RowCard` `status` slot renders `Waiting {N} days` at the heading role — the largest type in the row, on
   the row's *first* line. This is 14-CONTEXT D-146's device applied to a second triage queue, and it is the
   same argument: an ops reviewer works the queue by age, so age leads. No colour is added to carry it.
2. **NOTHING ELSE ON THE ROW IS PROMOTED.** The listing title, the host name, the address, the capacity and
   the price all compute an **identical** size and weight (`text-label`). One shared constant per role, as
   `request-row.tsx:ROW_VALUE_CLASS` does, so the equality is a fact about one string and not an accident of
   two similar ones.
3. **MONEY IS `tabular-nums`, ALWAYS, AND PRE-FORMATTED SERVER-SIDE.** Every figure in the enforcement
   dialog arrives as a finished string from `formatMoney` (`src/lib/money.ts:14`). **The ops UI performs
   zero arithmetic on money** (PROJECT D-130 / GATE-05). A dialog that could compute a refund is a dialog
   that could compute it differently from the server that will move it.

## Color

Inherited unchanged. Every colour named below is an already-declared pair in
`src/lib/design/contrast-pairs.ts`. **Phase 18 adds ZERO pairs and ZERO tones.**

| Role | Token | Usage in Phase 18 |
|------|-------|-------------------|
| Dominant (~60%) | `--background` | The `/ops` page surface, under `<main>`. |
| Secondary (~30%) | `--card` (rows, dialogs) · `--muted` (the header bar via `surface="muted"`, every status chip surface, the no-photos plate) | Every `RowCard`, the `ResponsiveDialog` panel, the ops header. |
| Accent (10%) | `--brand` | **ZERO occurrences on `/ops`. ZERO occurrences on the badge.** See below. |
| Destructive | `--destructive` | **Exactly ONE new occurrence in the whole phase** — the escalation confirm button's *ink*. |

### The accent reserved-for list — Phase 18 appends ZERO entries. It stays at 10.

`src/lib/design/accent-uses.ts` holds ten entries and `AccentUseCountIsTen` is a **compile** constraint, so
an eleventh fails `next build`'s own type check. **Phase 18 does not touch it.**

- **No coral anywhere on `/ops`.** An internal triage console is not a conversion funnel — the same call
  `request-row.tsx` and `/host/earnings` already record. Approve is a **neutral solid** `<Button>` (default
  variant), never `variant="brand"`. An ops reviewer approving forty listings must not be nudged toward
  yes by a colour.
- **No coral on the check badge.** `DropInBadge`'s header states the rule this inherits verbatim: the chip
  is *"deliberately NOT accent — § Color lists the accent uses this phase allows and this is not one of
  them."* A trust chip painted in the brand colour is a marketing device wearing a fact's clothes.

### `--destructive` gains exactly ONE occurrence, and it is ink, never a fill

The escalation confirm button (`Reject and refund {N} bookings`) renders
`<Button variant="outline" className="text-destructive">` — the shipped destructive-**action** treatment at
`listing-card.tsx:367`, measured as `destructive on card` = **5.76:1**, already in the pair inventory.

- **NOT `variant="destructive"`.** A solid red button on a queue is a colour that shouts on every row it
  can reach, and DS-10's binding rule is that red is reserved for a genuine failure needing a human. An ops
  cancellation is a *deliberate act*, not a failure. Red marks the act, not the surface.
- **NOT the only signal.** The button's own *label names the count and the money*. Colour never carries the
  weight alone (the `payout-state-badge.tsx` rule).

### Status tones — unchanged at four

`STATUS_TONES` stays `["neutral","positive","attention","soft-accent"]`. Phase 18 uses two:

- **`positive`** — exactly one place: the empty queue's `CheckCircle2` glyph at `text-success`. One pixel of
  green in the whole phase.
- **`neutral`** — every review-state chip. **`In review` and `Not approved` are NEUTRAL, never red.** A
  listing awaiting a decision, and a listing that did not get one, are both normal lifecycle states of a
  working marketplace. `status-tones.ts`'s binding copy rule: *"occupancy and unavailability are NORMAL
  states — never errors, never red."*

### Page composition

```
<div className={OPS_QUEUE_SHELL}>
  <PageHeader title=… lede=… />
  <div className="mt-8">
     { rows.length === 0 ? <EmptyState …/> : <ol className="space-y-4"> … </ol> }
  </div>
</div>
```

- The `mt-8` data-region offset is the page's own and `loading.tsx` copies it, exactly as `/host/requests`
  and its plate do.
- **An `<ol>`, not a bare `<div>`.** The queue is an ordered list and its order is the product ("oldest
  first"). A screen reader announcing "list, 7 items" is telling an ops reviewer something true and useful.

| Slot | Copy |
|------|------|
| `title` | **Review queue** |
| `lede` | **Hosts and listings waiting on a decision, oldest first. Nothing new sells on FitOut until someone here has checked it.** |

⚠ "Nothing **new** sells" is load-bearing and is not a hedge. D-210 narrows the sell-gate to listings
created or materially edited after this phase; the pre-existing grandfathered catalogue is ungated. A lede
reading "nothing sells on FitOut until someone here has checked it" would be **false**, on the one screen
whose whole job is to be accurate about what has and has not been checked.

### The queue query, as a display contract

One list, both kinds interleaved, **`ORDER BY submitted_at ASC`** across the union — not two lists rendered
one after the other, not two tabs, not a kind filter. The oldest thing waiting is at the top whatever it is.
`schema.ts:379-399`'s partial-index device is the shipped way to make that cheap; `src/lib/ops/alerts.ts:12-24`
records the rule that the query's `ORDER BY` must byte-match the index's declared ordering.

### The queue row

**`RowCard` (`@/components/patterns/row-card.tsx`), one adopter file, one discriminated union.**

`src/components/ops/ops-queue-row.tsx` — a client island (it owns the action state), taking

```ts
type OpsQueueItem =
  | { kind: "host";    /* … */ }
  | { kind: "listing"; /* … */ };
```

…and branching on the **discriminant**, with any per-kind lookup keyed as a total `Record` over the union —
the `payout-state-badge.tsx:53-62` exhaustiveness lesson, so a third kind fails to compile rather than
throwing at runtime in front of an operator.

| `RowCard` slot | Host row | Listing row |
|---|---|---|
| `href` | **absent** | **absent** |
| `media` | **absent** | **absent** |
| `title` | The host's display name, or `A host` | The listing title, or `Untitled listing` |
| `meta` | `Host · {N} listings waiting` | `Listing · {Space type} · {City}` |
| `status` | `WaitedFor` at `emphasis="lead"` | same |
| `trailing` | **absent** | **absent** |
| `children` | the evidence `<dl>` | `<PhotoGallery>` **then** the evidence `<dl>` |
| `actions` | `<OpsDecisionActions kind="host" …>` | `<OpsDecisionActions kind="listing" …>` |

**`href` is absent, and that is a decision rather than an inheritance.** The row is **terminal**. This is
14-CONTEXT D-144 applied to a second queue, and here it is not merely a preference — a detail page you
click into to see the photos is precisely what D-246 and `<specifics>` forbid. Pin it the way the host
inbox pins it: `tests/ops/ops-queue-row.test.tsx` asserts **zero anchors and zero link-role elements inside
the card**, so a later plan that adds a destination fails there rather than in review.

**`media` is absent.** `RowCard`'s media box is a 48px square (`ROW_CARD_THUMB`). A 48px thumbnail is
useless as evidence of whether a space is real, and `RowCard` omits the box rather than drawing an empty
one. The photos go in the **body**, at a size a person can judge.

#### The evidence, per kind

**Listing** — `<PhotoGallery photos={…} title={…} />` **reused verbatim** from
`src/components/listing/photo-gallery.tsx`, then a `<dl>`:

| `<dt>` | `<dd>` | Why it is on the row |
|---|---|---|
| Address | the full street address | One of D-231's five material fields. |
| Space type | `SPACE_TYPE_LABELS[…]` | ditto |
| Capacity | `{N} people` | ditto |
| Price | pre-formatted, `tabular-nums` | ditto |
| Host | the host's name **+ their current verification state** | So the reviewer can see whether approving this listing actually makes it sellable — both terms of the gate are needed and one of them is not on this row's own record. |
| Submitted | `{date}` | The wait figure is relative; the date is what an operator quotes in a dispute. |

**Host** — a `<dl>` only:

| `<dt>` | `<dd>` |
|---|---|
| Account since | `formatMemberSince(createdAt)` |
| Email confirmed | `Yes` / `Not yet` |
| Listings waiting | `{N}` |
| Submitted | `{date}` |

⚠ **A host row shows NO document, NO image, NO ID number — because none exists.** HVER-02 forbids the
column, so there is nothing to render, and the row must not be designed with a placeholder that implies
something is coming. **Do not add a "documents" panel, an empty state for one, or a disabled control that
suggests it.** The ops-manual provider's check is a person looking at the account facts above; the surface
must say only that much. Fabricating the *affordance* for a document check is the same defect
`pending-copy.test.ts` exists for, one level up from copy.

#### The `<dl>` shape

`request-row.tsx`'s exact idiom, and for its exact reason:

```tsx
<dl className="space-y-1.5">
  <div className="flex items-baseline justify-between gap-4">
    <dt className="text-label text-muted-foreground">Address</dt>
    <dd className="text-label">{…}</dd>
  </div>
  …
</dl>
```

A `<dl>` and not a table: it goes in `RowCard`'s `children`, and the pattern's own docblock records that
this slot exists *"so the label↔value association survives linearisation on a narrow screen"*. It cannot go
through `meta` (a `<dl>` inside a `<p>` hydrates mismatched) or `actions` (lifted above the overlay link).

### The row at 320px — the hard case, answered concretely

**ONE component tree at every width. There is no desktop-table twin.**

This is a **deliberate departure** from `/host/requests`, which renders `hidden md:block` (table) beside
`md:hidden` (cards). Two reasons, and either alone is sufficient:

1. **A table twin renders every photo twice in one document.** The queue's whole subject is photographs;
   duplicating them for a tree that is `display:none` at that width doubles the image bytes on the one
   surface where the images are the point.
2. **A six-column table cannot carry a photo mosaic.** The shape that works at 1280 is the same shape that
   works at 320 — a card with a picture in it — so there is nothing for a second tree to say.

`tests/design/one-tree.test.ts` (RESP-04 AC#10/11) is satisfied by construction: no viewport-conditional
JSX, no `matchMedia`, no `useMediaQuery`. All responsiveness is CSS.

**What actually happens to the photo-bearing row as the viewport narrows:**

| Width | The mosaic | The rest of the row |
|-------|-----------|---------------------|
| ≥ `sm:` (640px) | `PhotoGallery` opens its declared `MOSAIC_SHAPES` template for the photo count — hero + stacked pair (3), hero + three (4), hero + 2×2 (5+). Up to `MOSAIC_MAX_CELLS = 5` cells; the surplus is reachable through the lightbox. | `<dl>` rows stay label-left / value-right; `RowCard`'s `status` column stays `shrink-0`. |
| < `sm:` (incl. **320px**) | `COLLAPSED_GRID` — **the hero alone**, at `MOSAIC_ASPECT` (16/9), every other cell `max-sm:hidden`. The `Show all {N} photos` control renders whenever N > 1 and opens `PhotoLightbox` **full-screen**. | Same `<dl>`, linearised by the flex rows above. Actions go full-width and stay 44px. |

**That collapse is the answer, and it is a better one than a shrunken mosaic.** At 320px an ops reviewer
gets ONE large photograph in the row and reaches the rest at *full screen*, which is a strictly better
inspection surface on a phone than five thumbnails would be. It costs **zero new photo code**: the
behaviour, the six templates, the alt strings and the lightbox are all shipped and already pinned by
`tests/listing/photo-gallery.test.tsx`.

**Three narrow-viewport hazards, named so the plan does not discover them:**

- **The `status` column squeeze.** `RowCard` renders `status` `shrink-0`, so it keeps its max-content width
  at every viewport and the title column beside it absorbs the whole squeeze — the defect
  `REQUEST_STATUS_CAP` was measured into existence for (title left **8.66px** at the 320px floor). The ops
  status slot holds only `Waiting {N} days`, which is much shorter than a countdown plus a reason line, so a
  cap **may** not be needed. **Measure it at 320 before deciding.** If it is needed, declare
  `OPS_QUEUE_STATUS_CAP` in `measurements.ts` with its own derivation — do **not** reuse
  `REQUEST_STATUS_CAP`, whose name would then be a lie about which surface it serves.
- **Horizontal scroll is forbidden.** No `overflow-x-auto` photo strip. `ScrollArea` is not an option
  either: `src/components/ui/scroll-area.tsx:63-68` records that it hardcodes a **vertical** `<ScrollBar />`
  and that a horizontal orientation *"is requested nowhere in `src/`"*. `e2e/overflow-320.spec.ts` gains a
  `/ops` row and is the instrument that proves this.
- **Every action stays reachable.** Approve and Reject are `size="touch"` (44px) and wrap onto two lines
  rather than shrinking. The `ResponsiveDialog` is the reason the reject flow is usable on a phone at all —
  below `sm:` it presents as a bottom sheet.

### Loading — `src/app/(ops)/ops/loading.tsx`

**Two jobs, and they are different jobs.** (1) The build gate requires it. (2) Its Suspense boundary is
what lets the layout's `assertStaff()` commit the 404 **status line** before any page body runs — the
`/listings/[id]/(detail)` fix, reused. Deleting it "to simplify" breaks both.

```tsx
<div className={OPS_QUEUE_SHELL}>
  <PageHeader title="Review queue" lede={/* the SAME expression the page carries */} />
  <div className="mt-8">
    <RowListSkeleton label="Loading the review queue" rows={2} height={OPS_QUEUE_ROW_HEIGHT} />
  </div>
</div>
```

- Composes **exactly one** of the three declared skeleton patterns (`RowListSkeleton`) and writes **no box
  measurement of its own** — `loading-coverage.test.ts` fails a `loading.tsx` that does.
- `rows={2}`, not the default 4. The ops row is roughly 430px at the floor; four of them promise ~1,700px
  of page. `/host/requests`' plate carries the same reasoning in the other direction (its 80px bar was
  *"promising less than a third of what arrives"*). A plate must promise the page that is coming.
- `label` is a full sentence, announced and never rendered visibly. `RowListSkeleton` supplies
  `role="status" aria-busy="true"`, the `aria-label` **name** and the `sr-only` **content** — two different
  mechanisms, both required (rule 4 + rule 5), and the bars are `aria-hidden`.
- The `PageHeader` strings are the **same expressions** the page carries, character for character. Not a
  fallback imitating a heading — the same component in the same container, rendered twice.

### Empty — "the queue is clear"

`EmptyState`, `tone="positive"`, `titleAs="h2"`, `actions={null}`.

| Slot | Copy |
|------|------|
| title | **The queue is clear** |
| body | **Nothing is waiting on FitOut right now. New hosts and new listings land here the moment they're submitted, oldest first.** |
| actions | `null` |

- **`tone="positive"` is the whole mechanism**, and it carries exactly one pixel of green: the glyph becomes
  `CheckCircle2` at `text-success` (4.00 court / 3.86 grove against a 3.0 non-text bar, already declared).

  review queue has no next step to offer: an ops reviewer cannot make a host submit a listing, and there is
  no second ops destination to point at. A CTA here would be a control that does not act on this state.

#### The reason is a taxonomy first, free text second

`18-RESEARCH` flags this as the phase's **highest-risk input field**: it is host-visible free text landing
in a durable column *and* an outbound email. The contract:

**A `<Select>` (vendored `ui/select.tsx`) of complete, host-readable sentences — not codes.** What is stored
is the **sentence**, not an id: `schema.ts:497-510`'s rule for notification payloads is *"STORE DISPLAY
STRINGS, NEVER IDS TO JOIN AT READ TIME"*, and a rejection the host reads must not silently re-render if a
taxonomy is later re-worded.

|---|---|

| The address or location doesn't match the space. | The account details don't match the space being listed. |

- The confirm is **disabled until a reason is chosen**, and `aria-disabled` alongside `disabled` (the
  shipped `RequestActions` idiom).

### The confirmation shape for cancel-and-refund

**The operator is told, in plain words and real numbers, before they commit — and the numbers are always on
screen, never revealed by the choice.**

The dialog body, in this order:

**(1) The impact block — ALWAYS rendered, for every listing rejection, whatever the operator has chosen.**

A `<dl>` of server-computed, pre-formatted figures. Rendering it unconditionally is the point: the operator
reads the money *before* choosing, so choosing changes nothing on screen, and **no live region is needed**
(nothing appears in response to an action).

| `<dt>` | `<dd>` |
|---|---|
| Bookings already made | **{N}** |
| Money that would go back | **{₱X}** — the space price, to {N} bookers |
| FitOut keeps | **{₱Y}** — the service fee |
| The host is paid | **Nothing** |
| Can't be undone here | **{M} — their payout has already left FitOut.** *(renders only when M > 0)* |

- Every figure is a finished string from `formatMoney`, computed in the RSC and passed down. **Zero client
  arithmetic** (PROJECT D-130 / GATE-05).
- The `Can't be undone here` row is D-241's requirement rendered: a booking whose payout has already left is
  *not cancellable here*, **and the console says so with the reason** — never a silent no-op, never a
  control that appears to work.
- **When N = 0** the block still renders, and the last four rows collapse to one plain sentence:
  **No bookings to undo — this listing has never been sold.** A statement of fact, not a disabled control.

**(2) The enforcement choice — a `RadioGroup`, rendered ONLY when N > 0.**

When there is nothing to cancel there is no choice to make, and a radio group offering an option that does
nothing is a trap. Legend: **What happens to bookings already made**

| | Label | Sub-label |
|---|---|---|
| ● **default** | **Block new bookings only** | Nobody can book this space again until it's approved. The {N} bookings already made go ahead as planned. |
| ○ | **Block new bookings and cancel what's already booked** | The {N} confirmed bookings are cancelled. Each booker gets {₱X} back — the space price. FitOut keeps the {₱Y} service fee. The host is paid nothing and is charged no cancellation fee. |

- The default is **always** the lighter lever (D-233). It is checked on mount, every time, and the dialog
  does not remember the last choice.
- The heavier option's sub-label states **all four** money consequences in the order they happen. The
  "charged no cancellation fee" clause is D-235 made visible: an operator must not believe a host-cancel fee
  is being applied.

**(3) The confirm button — its LABEL names the act and the number.**

| Selection | Label | Recipe |
|---|---|---|
| Block new only | **Reject listing** | `<Button variant="outline">` |
| Cancel and refund | **Reject and refund {N} bookings** | `<Button variant="outline" className="text-destructive">` |

**This is the anti-muscle-memory device, and it is the whole reason the label is dynamic.** The button an
operator presses to move money *says how many bookings it cancels*. A generic `Confirm` under a radio is
exactly the shape a tired reviewer clicks through; a button reading `Reject and refund 4 bookings` is not.
The variant never becomes a solid red fill — see § Color.

While in flight: `Rejecting…` / `Cancelling and refunding…`, `disabled` + `aria-disabled`.

⚠ **The impact numbers are a snapshot and the server is the authority.** Between paint and press a booking
can be cancelled by its booker or a payout can leave. The server action re-derives everything, and a
mismatch is a **calm typed refusal** carrying the server's own sentence — never a throw, and never a
partial apply. That refusal surfaces in the row's one status region.

### The refusal region — one per row, and exactly one

On **success** the action `revalidatePath("/ops")` and the row refreshes away, so a toast is the only
possible report: `toast.success(…)`. On **refusal** the row is still on screen, and the sentence belongs on
it — not in a dismissible, timed, unaddressable overlay. One outcome, one announcement (GATE-03 rule 6).

```tsx
{refusal ? (
  <p role="status" aria-label={OPS_REFUSAL_REGION_NAME} className="text-label">{refusal}</p>
) : null}
```

- **ONE** `refusal` state for approve *and* reject — a row can only ever have refused one thing.
- The **server action's own sentence, verbatim.** No client re-authoring: a second wording of a refusal is a
  second thing to keep in agreement with the action that refused.
- `OPS_REFUSAL_REGION_NAME = "Decision not recorded"` — three words that say *which* region this is. A
  **label, not a second copy of the sentence** (`share-link-box.tsx:109-121`'s measured reason: on the
  VoiceOver/Safari pairing a named live region can be announced by its name *instead of* its content).
- Ordinary ink, **no alarm colour**, no retry affordance — the row's own controls are the retry.

## Surface 2 — The check badge, and every state that is not it

### What the badge may say, and the fact it stands on

`host_verification.status = 'approved'` **and** `listing.review_state = 'approved'` — a real row, written by
a named, authenticated staff member (D-218), recording that **a person at FitOut looked at this account and
this listing**. That is the entire fact. There is no document in the product (HVER-02 forbids the column),
no vendor check (D-206 defers it), and nobody has been to the space.

**Therefore the badge may not say, and must not imply:**

| Forbidden | Why |
|---|---|
| that an ID or document was checked | **No document exists.** There is no upload surface and no column. A claim of a document check would be a sentence with no row behind it — the exact defect `pending-copy.test.ts` was written for. |
| that a third party checked anything | D-237: copy is written against the **manual** provider that actually ships. |
| that the space was inspected, visited, or is safe/insured | Success Criterion 6, verbatim. |
| any quality, tier, score or ranking word | `trust-signals.test.ts`'s twelve tokens. |

### The copy

| Element | Copy |
|---|---|

- The explainer's second sentence is a **deliberate negative**. Success Criterion 6 says the badge must

- **Why not the obvious one-word chip:** the obvious word is one of the twelve tokens, and unbanning it

### The component and the rule that makes D-212 structural

**`src/lib/listing/fitout-check.ts`** — one pure predicate, the `isPubliclyViewable` idiom:

```ts
export function isFitoutChecked(
  hostStatus: string | null | undefined,
  listingReviewState: string | null | undefined,
): boolean {
  return hostStatus === "approved" && listingReviewState === "approved";
}
```

⚠ **BOTH terms, and this is the sharpest reading of D-212 in the phase.** A grandfathered *listing* owned by
an approved *host* would wear the badge under a host-only rule — and nobody checked that listing. D-212's
own sentence is about the listing (*"A grandfathered listing MUST NOT show the verification badge"*) and
HVER-05's is about the row (*"never for a grandfathered row"*). One expression, positive literals only —
never `!== 'grandfathered'`, which would let `pending`, `rejected`, `unverified` and `suspended` through, the
same fail-closed discipline `booking.ts:193-195` records for `=== true`.

**`src/components/listing/fitout-check-badge.tsx`** — beside `drop-in-badge.tsx`, its exact analog:

```tsx
export const FITOUT_CHECK_LABEL = "Checked by FitOut";
export const FITOUT_CHECK_EXPLAINER = "Someone at FitOut checked …";

export function FitoutCheckBadge({ checked, className }: { checked: boolean; className?: string }) {
  if (!checked) return null;
  return <Badge variant="secondary" className={className}>{FITOUT_CHECK_LABEL}</Badge>;
}
```

- **Takes a BOOLEAN, reduced once by `isFitoutChecked` in the RSC.** This is F10's recommendation and it
  makes D-212 *structural*: a client component that never receives the distinction between `approved` and
  `grandfathered` cannot render the badge for the wrong one. `listing-card.tsx:11`'s precedent for
  `bookable` — *"derived upstream … and passed in — the card never re-derives it."*
- **`variant="secondary"`, no icon, no accent, no green.** `DropInBadge` is the exact analog (a booker-facing
  chip that names a fact) and its header carries both rules: **REAL TEXT, NEVER AN ICON-ONLY MARKER**, and
  deliberately not accent. A trust chip styled like a seal *is* a quality claim; a neutral chip that states
  what happened is not.
- **Returns `null`, never a placeholder.** There is no "unchecked" chip. A booker who sees nothing is being
  told nothing, which is correct — the alternative teaches bookers to read absence as a warning about the
  ungated grandfathered catalogue, which would be a claim FitOut cannot support.
- Both strings are **exported constants**, the `HOST_REQUEST_RULE` idiom, so specs import the copy instead
  of retyping it — and so the whole of the fifth signal's copy lives in **one scannable file** (see the gate
  edit below).

| Event | Heading / subject | Body |
|---|---|---|

| Listing rejected | **{Listing title} wasn't approved** | FitOut checked this listing and didn't approve it. *{the operator's sentence, verbatim}* It won't take bookings. |

### ⚠ Gap the planner must close explicitly: `rejected` has no route back

The `rejected` copy above offers **Edit this listing** as its way out, on the strength of D-213/D-232 —
material edit returns a listing to review. **But D-232 names `approved` OR `grandfathered` → `pending`
only. It says nothing about `rejected`.** As written, a rejected host edits their listing and it stays
rejected forever, and the surface has promised a route that does not exist.

Two honest resolutions, and the plan must pick one **explicitly**:

- **(a) Extend the flip to `rejected → pending` on material edit.** Recommended: it makes the copy true,
  it is the only self-serve route back that is not an appeal, and it costs one enum value in an existing
  predicate.
- **(b) Keep D-232 as written and delete the way out.** Then the `rejected` signal has a state and a reason
  and no way out — which `requests-signal.ts:56` explicitly calls a shape this product does not ship, and
  which reads as a permanent ban with no route, i.e. an appeal surface by another name.

## NOT COVERED — real blind spots, stated so the next reader under-trusts this document

- **`OPS_QUEUE_ROW_HEIGHT` is a PREDICTION here, not a measurement.** Every sibling constant in
  `measurements.ts` carries a real number off a rendered route. Writing the predicted step down without
  measuring would put a fabricated figure in the one module whose whole discipline is that its numbers were
  observed.
- **This document proves nothing about pixels.** It names tokens, patterns and recipes. Whether the queue
  row is legible at 320px in both themes is a picture, and it belongs to the e2e sweeps — which PROJECT D-24
  keeps out of CI.
- **The 404 status line is not assertable by Vitest.** AC#14 is a one-time manual audit. A structural test
  can prove the guard is *called*; only a real HTTP response can prove what it *returns*.
- **The reject taxonomy is copy, not a schema.** Nothing here constrains what an operator types into the
  free-text field beyond a length. The gate on that field is the server's Zod schema and the audit row, not
  this document.
- **`rejected` has no verified route back** until the D-232 gap above is closed one way or the other. The
  copy in this spec assumes resolution (a); if the plan takes (b), the way-out row must be deleted from the
  `rejected` signal in the same commit.
