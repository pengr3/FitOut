<objective>
Build the two ops components — the queue row that carries every fact a reviewer needs, and the
decision controls whose weights make a money-moving act impossible to reach by muscle memory.

Purpose: OPS-04 asks for one screen with everything needed to decide, and ENF-01 asks ops to choose
the enforcement level per case. Those two requirements pull against each other: the more power on the
row, the easier it is to hit the wrong thing forty listings into a session. The design answer is that
there is no control on the ROW that can cancel-and-refund at all — the escalation lives inside the
reject dialog, behind a radio whose default is always the lighter lever.

Output: three components under `src/components/ops/**`, two moved design inventories, and two
component test files.

**This plan ships NO route.** `src/app/(ops)/**` is plan 18-12, where the route and its three pinned
loading-coverage constants move in ONE commit.
</objective>

Create `src/components/ops/ops-reject-dialog.tsx`, composed through `ResponsiveDialog` — the app's one
overlay primitive — importing nothing from the vendored dialog module.

**The reason is a taxonomy first, free text second.** A `<Select>` of the COMPLETE, host-readable
SENTENCES from `src/lib/validation/ops.ts` (kind-appropriate list), never codes. What is stored is the
sentence. Selecting the "Something else (explain below)" member makes the `<Textarea maxLength={280}>`
REQUIRED; otherwise it is optional and appended. Beneath it a STATIC hint — *Up to 280 characters. The
host reads this exactly as you write it.* — not a live counter, because a counter is a live region and
a live region for a character count is noise on a surface that already has one announcement to make.
The confirm stays disabled until a reason is chosen, with `aria-disabled` alongside `disabled`. The
280 bound is re-validated server-side with Zod; the client bound is a courtesy, never the gate.

**The impact block — ALWAYS rendered, for every listing rejection, whatever the operator has chosen.**
A `<dl>` of server-computed, pre-formatted figures from `loadOpsCancelImpact`: bookings already made;
money that would go back (the space price, to N bookers); what FitOut keeps (the service fee); the
host is paid **Nothing**; and — only when it is non-zero — *Can't be undone here: {M} — their payout
has already left FitOut*, which is D-241 rendered: not cancellable here, WITH the reason, never a
silent no-op. Rendering it unconditionally is the point: the operator reads the money BEFORE choosing,
so choosing changes nothing on screen and NO live region is needed. When N = 0 the block still renders
and the last four rows collapse to one plain sentence — *No bookings to undo — this listing has never
been sold* — a statement of fact, not a disabled control.

**The enforcement choice — a `RadioGroup`, rendered ONLY when N > 0.** When there is nothing to cancel
there is no choice to make, and a radio group offering an option that does nothing is a trap. The
default is ALWAYS the lighter lever (block new bookings only), checked on mount every time; the dialog
does not remember the last choice. The heavier option's sub-label states all four money consequences
in the order they happen, including *the host is paid nothing and is charged no cancellation fee* —
D-235 made visible, so an operator cannot believe a host-cancel fee is being applied.

**The confirm button's LABEL names the act and the number.** `Reject listing` under the default;
`Reject and refund {N} bookings` under the escalation, rendered
`<Button variant="outline" className="text-destructive">` — ink, never a solid red fill. This is the
anti-muscle-memory device and it is the whole reason the label is dynamic. In flight: `Rejecting…` /
`Cancelling and refunding…`, `disabled` + `aria-disabled`. Dismissal is a ghost `Keep it` that closes
through the controlled state, never a vendored `DialogClose`.

⚠ The impact numbers are a SNAPSHOT and the server is the authority. Between paint and press a booking
can be cancelled by its booker or a payout can leave. The server action re-derives everything and a
mismatch is a calm typed refusal carrying the server's own sentence — never a throw, never a partial
apply — surfacing in the row's one status region (task 2).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator's hands → a money-moving control | The most likely failure here is a tired human, not an attacker; control weight is the mitigation |
| client dialog state → server action | Everything the dialog sends is re-parsed and re-derived server-side; the snapshot is never authoritative |
| operator free text → the durable column | Bounded in the client as a courtesy, gated by Zod on the server |

|-----------|----------|-----------|-------------|-----------------|
| T-18-1001 | Tampering | cancel-and-refund reached by muscle memory | mitigate | No row control can reach it; three deliberate acts required; the confirm label names the count. Default-lever assertion mutation-proved RED |
| T-18-1002 | Tampering | client-computed money disagreeing with the server that moves it | mitigate | Zero client arithmetic (PROJECT D-130 / GATE-05); every figure is a finished string from `formatMoney` in the RSC; grep-asserted |
| T-18-1003 | Tampering | a stale impact snapshot applied after the world changed | mitigate | The action re-derives everything server-side; a mismatch is a calm typed refusal carrying the server's own sentence into the row's one status region |
