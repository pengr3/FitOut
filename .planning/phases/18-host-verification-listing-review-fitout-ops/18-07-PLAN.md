<objective>
Freeze a suspended host's payouts in a place where the freeze cannot manufacture false operator alerts.

Purpose: ENF-02 has two clauses, and the second one — *"a frozen row does not read as a stuck row to
the reconciler and does not page an operator"* — is the one that decides where the code goes. The
obvious implementation (claim the row, then refuse to transfer) satisfies the first clause and breaks
the second, one false `[payout-alert]` per suspended booking, forever. `alertStuckHeld`'s own comment
already names that failure mode for a different case: *"operators who learn to ignore the channel will
miss a real transfer failure."*

Output: one `AND` on the due-payout predicate, one genuinely new join in the reconciler, and a test
that proves both halves plus the zero-write un-freeze.
</objective>

**`payout-sweep.ts`.** Add `LEFT JOIN host_verification hv ON hv.user_id = l.host_id` to
`queryDuePayouts`'s join set, beside the existing `JOIN host_payout hp`. Add
`AND COALESCE(hv.status::text, 'unverified') <> 'suspended'` to the WHERE, INSIDE the existing
predicate scope — never replacing any of it, and never touching the `kind = 'payout'` scoping the
neighbouring queries carry.

⚠ `<> 'suspended'` is the correct polarity here and it is NOT the sell-gate's shape. The sell-gate
asks "is this host approved?" and fails closed on a missing row; this asks "is this host suspended?"
and a missing row means NOT suspended. Getting it backwards would freeze every unverified host's
payouts. Write that distinction at the site — the two COALESCEs look alike and mean opposite things.

Write the placement argument as a comment at the predicate, because the placement IS the design:
filtering HERE means `payOne`'s claim INSERT never runs, so no ledger row is ever created, so there is
no row for the reconciler's stuck-`held` alert to page an operator about. Freezing AFTER the claim
would leave a `held` row per suspended booking and fire a FALSE `[payout-alert]` on every one — the
exact failure `alertStuckHeld`'s own comment warns about for `host_cancel_fee` debits. Also record
that un-suspension needs no write: the next sweep simply selects the row again (the D-14 auto-revert
property).

Add the freeze as a FOURTH numbered invariant in the file's header list at `:9-28`. It is a contract,
not a footnote.

**`payout-reconcile.ts`.** Add the mirror to `alertStuckHeld` — and budget for it being real new SQL,
because that query reads `host_payout_ledger` with no host join at all today. `host_payout_ledger`
carries `host_id` directly, so add `LEFT JOIN host_verification hv ON hv.user_id =
host_payout_ledger.host_id` (or the equivalent `NOT EXISTS`) plus the same
`COALESCE(...) <> 'suspended'` exclusion, INSIDE the existing `kind = 'payout' AND state = 'held'`
scope.

Comment it on the template of the `kind = 'payout'` scope comment above it: with a pre-claim freeze the
only `held` rows a suspended host can own are ones that were ALREADY held when the suspension landed —
the CR-01 crash window between claim and release — which would otherwise age past
`PAYOUT_RECONCILE_STUCK_HOURS` and page an operator about a payout that is deliberately frozen.

⚠ Do NOT touch the `processing` predicate. `reconcileOne` polls transfers that have already fired and
the money has left the platform wallet; a stuck `processing` row on a suspended host is a real
stranded transfer and must still page. Say so at the site so a later reader does not "complete" the
mirror.

Do NOT introduce a `frozen` ledger state. That would be an `ALTER TYPE` on a committed enum plus an
edit to every existing predicate, to express something a WHERE clause already expresses.
