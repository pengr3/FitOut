<objective>
Build the two pure foundations the email half of Phase 15 stands on: a directive-free owner for the
product-theme name, and `renderEmail` — the single function that turns one `EmailContent` value into
an HTML document and a plain-text twin that cannot drift from it.

Purpose: EMAIL-02 requires the emails to read the same generated token contract as the app. Today
`DEFAULT_THEME` lives inside a `"use client"` module that imports `next-themes` at top level and has
**zero server-side readers** — importing it from `src/lib/email.ts` would drag a React-context library
into every Inngest function's import graph and into the DB-free design test config. EMAIL-01 requires
one shell, not nineteen edits of markup, and the design vitest config loads **no `setupFiles`**, so the
gates that prove the shell must assert on a *pure exported renderer* rather than on a captured send.

Output: `src/lib/design/theme.ts`, `src/lib/email-shell.ts`, a re-exporting `theme-provider.tsx`, and
an `email.ts` that imports the one `escapeHtml` instead of declaring a second one.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied string → rendered HTML | Every `EmailContent` field originates outside the renderer: library-generated verify/reset URLs, `redirectTo`-influenced reset links, listing titles, and ~20 `recordAudit` free-text columns |
| rendered HTML → Resend (external) | Once content enters an email it is forwarded, archived and indexed outside anyone's control |
| generated token module → email markup | The one sanctioned path for a colour literal into `src/lib/**` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-01 | Tampering | `renderEmail` heading / paragraphs / cta.label / cta.href | mitigate | `escapeHtml` applied at the one choke point to all four, so no composition site can forget |
| T-15-02 | Tampering | `renderEmail` derived preheader `<div>` | mitigate | Newly identified sink: the preheader derives from raw content and is injected into HTML. Escape it with the same function before it enters the div |
| T-15-03 | Tampering | `content.tableHtml` pre-escaped slot | accept | Deliberately unescaped; its single producer (`renderOpsAlertDigest`) keeps per-field escaping. Documented in the type's own comment so a second caller cannot use it innocently |
| T-15-04 | Information disclosure | Reset/verification token in the `extractLink` path | mitigate | No absolute `http(s)` URL before the CTA href — no XHTML doctype, no `xmlns`, no linked wordmark. Prevents a bogus token being extracted three layers from its cause |
| T-15-05 | Spoofing | Phishing-shaped construction | mitigate | Zero images, zero external resources, zero tracking pixel, one CTA whose href is a caller-supplied absolute app URL |
| T-15-06 | Information disclosure | A fabricated support address in the footer | mitigate | `SUPPORT_EMAIL !== null` guard with no else-branch (15-CONTEXT D-161 / PROJECT D-64) |
| T-15-SC | Tampering | npm/pip/cargo installs | accept | **Zero installs in this phase** — 15-RESEARCH § Package Legitimacy Audit records the gate as not applicable and D-66 forbids the stack a plan would reach for. A plan containing an `npm install` line has misread the phase |
</threat_model>
