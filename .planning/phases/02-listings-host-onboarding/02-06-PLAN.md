<objective>
Build the architectural keystone of Phase 2: Stripe Connect Express onboarding (lazy account creation
+ Stripe-hosted Account Links) and the raw-body, signature-verified, idempotent `account.updated`
webhook that caches `payouts_enabled`/`charges_enabled` on the host — the single source of truth the
`deriveBookable` gate reads (PAY-04, D-14/D-15). Because bookability is DERIVED from this cached flag,
auto-revert (D-14) is free: when payouts later become disabled, every listing instantly becomes
not-bookable with zero per-listing writes. Adds the persistent payout-setup banner/checklist to the
host dashboard (D-12 — onboarding nudges but never blocks publish).

Per the security carry-forward gate (security_block_on=high): WR-06 (rate-limit + audit on
capability-activate actions) was CLOSED in Plan 02; this plan applies the same rate-limit/audit
treatment to the onboarding action before wiring payouts to the host/canHost flow, and surfaces WR-04
(email-send reliability) status since no host-onboarding email is in scope this phase.

Purpose: SC#4 — a host completes payout onboarding and a listing becomes bookable only once payouts
are enabled, tracked via the webhook. This gate, built here, can never be bypassed by Phases 3/4/6.
Output: stripe.ts + stripe-connect.ts + the webhook route + host_payout webhook writes + payout UI.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Stripe → webhook handler | The webhook is the trust boundary for payout state; only signature-verified events may write payoutsEnabled |
| client → payout state | payouts_enabled / stripeAccountId must never be settable from a client body |
| one host → another host's Stripe account | Onboarding must operate only on the caller's own host_payout row |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-SPOOF | Spoofing / Tampering | /api/stripe/webhook | mitigate | stripe.webhooks.constructEvent verifies the signature with STRIPE_WEBHOOK_SECRET; bad/forged sig → 400 (never trust an unverified body). |
| T-06-REPLAY | Tampering | webhook double-delivery | mitigate | Idempotency via the stripe_event table keyed by event.id; a duplicate is skipped and 200'd. |
| T-06-PRIV | Elevation of Privilege | payouts_enabled / stripeAccountId | mitigate | Webhook/server-set ONLY (single writer = the webhook); onboarding persists the account id server-side; mirrors Phase-1 input:false discipline; bookability is purely derived (Pitfall 4). |
| T-06-IDOR | Elevation of Privilege | startStripeOnboarding | mitigate | Operates on the session user's own host_payout row only; rate-limited + audited (WR-06). |
| T-06-SECRET | Information Disclosure | STRIPE_SECRET_KEY / STRIPE_WEBHOOK_SECRET | mitigate | Server-only env; stripe.ts fails closed in production if missing; webhook runtime=nodejs; no secret in the client bundle (only STRIPE_PUBLISHABLE_KEY is client-safe). |
| T-06-LINK | Information Disclosure / Tampering | Account Link URL | mitigate | Links are single-use + expiring; re-minted on every click and on the refresh_url page; never persisted (Pitfall 6). |
</threat_model>
