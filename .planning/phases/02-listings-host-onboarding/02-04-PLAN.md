<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Cloudinary (direct) | Bytes bypass our server; the only server involvement is minting a scoped, ownership-checked signature |
| client → sign endpoint | Untrusted; must prove session + listing ownership before a signature is minted |
| one host → another host's photos | persist/reorder/remove must be owner-scoped (IDOR) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-UPLOAD | Tampering / DoS | /api/cloudinary/sign | mitigate | Session required + listing-ownership check before signing; rate-limited (WR-06, 30/60s per user); signature scoped to `fitout/listings/<listingId>`. |
| T-04-IDOR | Elevation of Privilege | persist/reorder/remove + sign | mitigate | assertOwnership (`hostId === session.user.id`) on every action and before minting a signature. |
| T-04-SECRET | Information Disclosure | CLOUDINARY_API_SECRET | mitigate | Signed server-side only; never shipped to the client (cloudinary.ts invariant); only signature+apiKey+cloudName returned. |
| T-04-ORPHAN | Tampering (storage hygiene) | removed/abandoned assets | mitigate | removePhoto calls destroyListingPhoto({ invalidate:true }) so deleted photos don't linger or serve stale CDN copies. |
| T-04-SIGMATCH | Tampering | signed vs sent params | mitigate | Signed param set == client param set ({timestamp, folder}); no extra params on either side (Pitfall 3). |
</threat_model>
