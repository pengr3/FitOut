<objective>
Create the eleven image fixtures this phase's real-browser proofs need, and the committed generator that
makes them auditable.

Purpose: `find tests e2e -name "*.jpg" -o -name "*.png"` returns only VRT baselines. There is no
`e2e/fixtures/` directory, no binary fixture has ever been an INPUT to a spec here, and no script in
`scripts/` has ever written image bytes or an EXIF tag. This plan creates a convention rather than
following one, so it says out loud what it decided and why.

**The decision `16-PATTERNS.md` § No Analog Found demands be made explicitly.** Three options were on the
table: a hand-rolled zero-dependency encoder, `sharp` as a `devDependency`, or committing opaque bytes with
a README. **Chosen: the hand-rolled zero-dependency encoder.** Reasons, in order:
1. Phase 11 shipped "empty `package.json` diff" as an acceptance criterion and this phase's one argued
   dependency exception is already spent on `react-easy-crop` (D-167). A second exception for a build-time
   image library is not argued anywhere.
2. The stated goal is *"so the EXIF byte is auditable rather than magic"*. Bytes produced by a third-party
   encoder are exactly as magic as bytes committed by hand.
3. Determinism is a correctness requirement here — `scripts/generate-design-tokens.mjs:1-38` says so in as
   many words — and only an encoder we control gives byte-stable output across machines and versions.
The trick that makes it small: **every fixture is built from rectangles aligned to 8px**, so every 8x8 JPEG
block is a single flat colour, its DCT is DC-only, and the encoder needs no AC coefficients at all.

**One named substitution from `16-VALIDATION.md`'s list, raised rather than absorbed.** That list names
`e2e/fixtures/animated.webp`. An ANIMATED WebP cannot be produced without a VP8L encoder, which is far
larger than everything else here combined, and no installed tool emits one. The behaviour under test is
*"an animated source in the allow-list presents its still first frame"*. **APNG** satisfies it exactly:
its MIME type is `image/png`, which is inside `AVATAR_ALLOWED_TYPES`; browsers animate it in an `<img>`;
and `drawImage(HTMLImageElement)` draws the currently-presented frame, which at load is frame one. So the
fixture is `e2e/fixtures/animated.png`, built from the same PNG machinery, and the README records the
substitution and its reason. **If the PM wants a real animated WebP, that is a `devDependency` decision,
not an executor's.**

Output: `scripts/generate-image-fixtures.mjs`, eleven committed fixtures, a provenance README, a drift
gate, and one `package.json` script row.

**Scope-sanity note (recorded so a later pass does not re-flag it).** `files_modified` lists **15** files,
which is the nominal split threshold. **Eleven of them are generated binary fixtures** — written
mechanically by the one generator this plan authors, and verified as a set by one drift test. The authored
surface is **four** files: `scripts/generate-image-fixtures.mjs`, `e2e/fixtures/README.md`,
`tests/design/image-fixtures.test.ts`, `package.json`. Splitting would separate a generator from its own
output and give the drift gate nothing to compare against. **No split. The count is the exception, not the
complexity.**

Colour policy: use flat sRGB values whose channels are far apart (e.g. pure red / pure blue / pure white)

of +/- 8, because YCbCr conversion rounds; the tolerance belongs to the CONSUMER, not to the generator.

    Extend `scripts/generate-image-fixtures.mjs` with `renderJpeg({ width, height, blocks })`, a BASELINE
    (SOF0), 4:4:4 (no chroma subsampling), DC-only encoder. Its correctness argument, stated in a comment
    above it: every source rectangle is 8px-aligned, so every 8x8 block is one flat colour; the 2-D DCT of a
    flat block has a DC term and nothing else; so the encoder emits one DC coefficient per block and an EOB,
    and needs no AC path at all. That is why this is 150 lines and not 800.

    Emit, in order: `SOI`; the APP1 segment when an orientation is requested (see below); `DQT` with an
    ALL-ONES quantization table for all three components — legal, and it makes the DC quantization exact so
    the decoded colour is a pure function of the input; `SOF0` with three components at sampling factor 1x1;
    `DHT` carrying the four standard Annex-K Huffman tables (DC/AC x luma/chroma) verbatim; `SOS`; the
    entropy-coded scan; `EOI`. Convert RGB to YCbCr with the standard BT.601 full-range coefficients, round to
    integer, level-shift by -128, and write the per-block DC DIFFERENCE (the first block of each component
    carries the absolute value; every later block carries the delta from the previous block of the SAME
    component). Byte-stuff `0x00` after any `0xFF` in the entropy stream.

    Add `exifOrientationApp1(orientation)`: an APP1 segment whose payload is `Exif\0\0`, a little-endian TIFF
    header (`II*\0`, IFD offset 8), an IFD with exactly one entry — tag `0x0112` (Orientation), type 3
    (SHORT), count 1, value `orientation` — and a next-IFD offset of 0. A comment above it must spell out what
    Orientation = 6 MEANS: the stored raster is rotated 90 degrees clockwise from the intended view, so a
    480x320 stored image displays as 320x480, and a decoder that ignores the tag puts the corner block in the
    WRONG corner. That sentence is the whole reason the fixture is unmistakable.

    Add `truncate(bytes, keepRatio)` — take a valid JPEG and cut it mid-scan, keeping the SOI/DQT/SOF0/DHT/SOS
    prefix so the file is a plausible JPEG by extension and by header and undecodable in fact.
