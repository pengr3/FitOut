<objective>
Install the crop engine and author the one module that turns a crop rectangle into the bytes we store.

Purpose: `react-easy-crop` reports `croppedAreaPixels` and leaves the encode to us — which is a feature
here, because it keeps IC-06's decisions (JPEG, q0.9, white matte, 400x400) in FitOut's own code rather
than in a vendor's. Nothing in `src/` has ever touched a canvas, a decode or an EXIF tag, so this module
has no analog in this tree and is budgeted as real work.

Output: one dependency line and `src/lib/avatar-canvas.ts`.

**The decode decision, made and its alternatives named (RESEARCH §B5/§B6).** The encoder draws the SAME
`<img>` element the cropper measured, captured through the library's `setImageRef` prop.
`croppedAreaPixels` is computed by the library from `this.imageRef.current?.naturalWidth/naturalHeight`
— that exact element — and browsers apply EXIF orientation to `<img>` by default
(`image-orientation: from-image` is the CSS initial value), so those naturals are already in ORIENTED
space and the crop rectangle is an oriented-space rectangle. Drawing the same element makes the source
rectangle and the source bitmap one coordinate system by identity. **`createImageBitmap` is REJECTED for
the encode** — not because it is wrong, but because it is a second decoder path, and two independent EXIF
corrections that happen to agree today is exactly the "proven, not assumed" that IC-06 refuses.
`OffscreenCanvas` is unnecessary for a 400x400 draw.
</objective>

The encode contract (IC-06 / D-172), in the order it must happen:
