<objective>
Close the one real vulnerability in this phase's neighbourhood: `persistPhoto` currently accepts any
non-empty `publicId` and `url` from the client and inserts both, and that `url` is rendered as
`<img src>` on a PUBLIC listing page to every booker.

Purpose: D-165. The signed-upload pipeline in FRONT of this action is airtight — session gate, per-user
rate limit, ownership check, a fixed `ALLOWED_SIGN_KEYS`. The write BEHIND it trusts the client
completely (`listing-photo.ts:93-97` is a `.trim()` non-empty test). A host can skip the widget, call the
action directly, and serve arbitrary third-party content under FitOut's product surface.

Output: a pure validator, its wiring, and the twelve existing fixtures rewritten to shapes the real
pipeline could actually have produced.

**The single most likely way this ships as a no-op, named so it cannot happen quietly (R1).**
`.github/workflows/ci.yml` states at `:151` and `:875` that the test jobs hold no Cloudinary credential,
and `.env.local` is gitignored — so `process.env.CLOUDINARY_CLOUD_NAME` is `undefined` in every CI run.
A validator that SKIPS when the env is absent is dead in the only place it runs continuously, and every
test of it passes vacuously. That is the same defect shape as the `"use server"` incident
`tests/use-server-exports.test.ts` exists to prevent: a green suite over a feature that does not run.
The design that survives it: **a pure function taking `cloudName` as an argument, an action that fails
CLOSED when it is absent, and unit tests that inject rather than read.**
</objective>

in-repo fixture at `tests/listing/photos.test.ts:89`):

  upload option (photo-uploader.tsx:177):  folder: `fitout/listings/${listingId}`
  resulting public_id:                     `fitout/listings/<listingId>/<name>`   (no file extension)
  resulting secure_url:                    `https://res.cloudinary.com/<cloud>/image/upload/v<digits>/fitout/listings/<listingId>/<name>.<ext>`

The tightest honest test is a PARSE, never a substring match:

  const u = new URL(url);                        // throws on garbage -> reject
  u.protocol === "https:"
  u.hostname === "res.cloudinary.com"            // exact host — beats the suffix trick
  u.pathname.startsWith(`/${cloudName}/image/upload/`)

plus, on the public id: `publicId.startsWith(`fitout/listings/${listingId}/`)`, no `..` anywhere, no
leading `/`, no backslash, no `:` scheme, and strictly longer than the prefix itself.

The attacker set every one of which a naive `url.includes("res.cloudinary.com")` accepts:
  https://res.cloudinary.com.evil.tld/<cloud>/image/upload/x.jpg     suffix host
  https://evil.tld/?x=https://res.cloudinary.com/<cloud>/image/upload/   query-string host
  http://res.cloudinary.com/<cloud>/image/upload/x.jpg               mixed content on a public page
  javascript:alert(1)                                                opaque scheme
  fitout/listings/<other-listing-id>/one                             right shape, wrong listing
  fitout/listings/<id>/../../avatars/victim                          traversal inside a legitimate prefix
  fitout/listings/<id>/                                              prefix only, names no asset

The rejection literal is ALREADY in the file — `listing-photo.ts:97`
`"That photo didn't upload. Please try again."` — and needs no new export (Delta-15).

| Boundary | Description |

| client -> `persistPhoto` server action | a host-controlled `publicId` and `url` cross here and are stored |
| stored `url` -> public listing page | the stored string becomes `<img src>` for every booker |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-14 | Spoofing / Tampering | `persistPhoto` (`listing-photo.ts:93-108`) | mitigate | Parse the `url` with `new URL()` and require `https:` + exact host `res.cloudinary.com` + path prefix `/<cloudName>/image/upload/`; never a substring match |
| T-16-15 | Tampering | `publicId` prefix scope | mitigate | `startsWith("fitout/listings/<listingId>/")` PLUS an explicit `..` rejection, a leading-`/` rejection and a prefix-only rejection — a prefix check alone is not a scope check |
| T-16-16 | Elevation | validator fail-open when `CLOUDINARY_CLOUD_NAME` is unset | mitigate | Pure function takes `cloudName` as an argument and returns `false` when it is empty or undefined; the action never early-returns success; the absent-env case has its own test (R1) |
| T-16-17 | Elevation | signed-param widening | accept | Explicitly out of scope. `ALLOWED_SIGN_KEYS` (`sign/route.ts:35`) is untouched and `git diff --exit-code` over that file is in the verify command |
| T-16-18 | Denial of Service | oversized / SVG uploads on the listing path | accept | Phase 16.1 (D-164 / D-166). Named here so the residual risk is on the record rather than implied-fixed |
</threat_model>
