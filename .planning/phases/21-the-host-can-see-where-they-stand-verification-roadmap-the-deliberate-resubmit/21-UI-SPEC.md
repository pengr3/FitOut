# Phase 21 — UI Design Contract

> Visual and interaction contract for the host verification roadmap, deliberate listing resubmit,
> and bounded review-cycle history. Generated by gsd-ui-researcher for planner, executor, checker,
> and retrospective audit use.

---

## Contract Boundary

This phase makes existing server facts understandable and actionable. It does not create a new
verification, listing-review, appeal, or sell-gate authority.

The only three product surfaces changed are:

1. `/host`: a four-card roadmap, replaced by one compact readiness receipt after the first bookable
   listing exists.
2. `/host/listings`: a rejected-only `Fix and resubmit` entry and a per-listing `Review history`
   dialog.
3. `/host/listings/[id]/edit`: a persistent rejected-listing notice and a server-authorized,
   in-page re-review receipt.

The following are hard anti-features: a percentage or progress bar; a connecting roadmap line; a
countdown, duration, or verdict ETA; queue position; staff identity; internal reason codes; a canned
reason replacing stored host-readable text; a submit-without-edit control; appeal, dispute, or
contest wording; and any support or “get in touch” clause.

`src/lib/listing/re-review.ts` remains byte-unchanged. `deriveBookable` remains the sole final
readiness authority. No schema migration, dependency, new query round trip, or registry block is
authorized.

Sources: `21-CONTEXT.md` D-01…D-13, `REQUIREMENTS.md` HVER-09…HVER-14 and LVER-06…LVER-09,
`ROADMAP.md` Phase 21, and `21-RESEARCH.md`.

## Surface Contract 1 — `/host` Verification Roadmap

### Placement and ownership

Preserve the dashboard’s existing order and subject hierarchy:

```text
PageHeader — Your hosting{, name}
Hosting paused notice, when applicable
Today agenda OR No listings yet state
Get ready to take bookings roadmap OR Ready to take bookings receipt
Remaining HostSignals — requests owed, published listings missing hours
```

The roadmap occupies the former payout/verification responsibility on the dashboard. Remove the
legacy payout banner and the muted underlined verification row from `HostSignals`; leaving either
beside the roadmap is duplicate state, duplicate action ownership, and a failure.

When no listing exists, keep the existing `No listings yet` heading and body but remove its
create-listing action. Step 3 owns the one create action. When a listing exists, preserve the PageHeader
actions. The roadmap does not duplicate `Your listings` or `Create listing` unless its current state
requires that exact way forward.

Primary visual anchor by state:

- Roadmap state: the headed four-card roadmap grid is the primary focal point in this section; its
  numbered card sequence leads the eye before the remaining HostSignals below it.
- Ready-receipt state: the compact `Ready to take bookings` `PanelCard`, led by its success glyph and
  heading, is the primary focal point in the same section slot.

### Structure

- The roadmap is a headed `<section>` containing an `<ol>` of exactly four `<li>` elements.
- Each list item contains one `PanelCard` with `titleAs="h3"`; the section heading is `h2` under the
  page’s existing `h1`.
- The grid is one column at 320px and two equal columns from `sm` upward. Cards stretch to equal row
  height on desktop; action placement uses a local `mt-auto` region so card actions align without
  fixed heights.
- Step number and state label are visible. The sequence does not rely on DOM position, color, or a
  decorative connector.
- Explanations wrap naturally. No title, reason, absolute instant, or control label truncates.
- There is no line, percentage, fraction-as-progress, horizontal scroller, carousel, accordion, or
  viewport-dependent duplicate DOM tree.

### Server-backed state model

Each card reports its own authority. The four card booleans do not become a second readiness formula.
Only `listingRows.some(row => deriveBookable(...))` may replace the roadmap with the ready receipt.

| Step | Authority | State contract | Action contract |
|------|-----------|----------------|-----------------|
| 1 Identity | Existing single `loadHostVerification` result, `VERIFICATION_SIGNAL`, cooldown helper, and 30-minute Didit reconciliation grace | Explicitly map all six stored states. `unverified` = Current/not started; ordinary `pending` = Waiting; stale `pending` = Waiting with real rescue; `approved` = Done; `rejected` = Not passed; `suspended` = Paused; `grandfathered` = Done with capability-only copy. | Unverified: Start the check. Pending: no control until stale; stale uses Finish the check. Rejected: no control before the absolute retry instant, Ask for another check after it. Suspended and terminal states: no mutation control. |
| 2 Payouts | Existing `derivePayoutStatus` result | `enabled` = Done; `not_started` or `incomplete` becomes Current only when identity permits advancing; `paused` = Not passed; otherwise Next. | Reuse Set up payouts, Finish payout setup, or Review payout setup. The control mints a fresh hosted URL through the shipped action; no URL is stored or rendered optimistically. |
| 3 Listing | Owner-scoped non-deleted listing rows already replacing the count projection | Zero rows = Current; one or more rows = Done. The card does not call a draft “submitted” or “reviewed.” | Zero rows: relocated Create listing brand action. Existing rows: no card action; dashboard/listing navigation already owns editing. |
| 4 FitOut review | The same listing projection’s persisted review facts, with final completion authorized only by `deriveBookable` | Zero rows = Next. Any rejected row and no bookable row = Not passed. Otherwise any pending row = Waiting. Existing rows with no open/rejected review and no bookable row = Current. Any bookable row collapses the entire roadmap to the ready receipt. | Rejected: Review your listings. Current unfinished listing: Your listings. Waiting: no control. Never offer a queue refresh or resubmit action here. |

For mixed portfolios, `any bookable` wins only at account-roadmap level: render the compact ready
receipt even if a sibling is rejected. The sibling’s listing card remains `Not approved` and owns
`Fix and resubmit`. The receipt must not imply every listing is approved.

### Action and pending behavior

- At most one roadmap card has a button-shaped advancing action in a rendered snapshot.
- Roadmap actions that call Server Actions use 44px `size="touch"`, replace their label with the
  existing in-flight label, disable only themselves, and show one persistent in-card error on refusal.
- Link actions use normal Next links and retain visible keyboard focus. They do not masquerade as
  buttons unless the card owns the one advancing action.
- Waiting and Next states never draw disabled pseudo-actions. Absence is the contract.
- A stale pending control resumes/refetches the existing hosted session via the shipped action. It does
  not claim to refresh a verdict, move a queue place, restart a clock, or guarantee an outcome.

### Completed state

As soon as a server snapshot contains at least one truly bookable listing, replace the `<ol>` and its
four cards with one compact `PanelCard` in the same section slot:

- `CheckCircle2` success glyph plus heading `Ready to take bookings`;
- body `You have a listing that guests can book.`;
- no percentage, completed-step archive, confetti, CTA, or claim that every listing is ready;
- the existing account/listing maintenance signals remain elsewhere on the page.

## Surface Contract 2 — Rejected Listing Entry

Only a listing whose current review state is exactly `rejected` replaces the ordinary primary `Edit`
footer action with `Fix and resubmit`. Draft, pending, approved, grandfathered, withdrawn, unlisted,
and review-null listings retain their existing edit affordance.

The trigger remains a visible, neutral, `size="sm"` listing-footer button with `PencilIcon`. It opens
a controlled `Dialog`; it does not navigate or mutate on first press.

The dialog:

- has an accessible title and description matching the Copywriting Contract;
- displays the seven material labels as a semantic `<ul>` generated by
  `MATERIAL_FIELDS.map(field => MATERIAL_FIELD_LABELS[field])`;
- renders the current rejection reason as plain text exactly once when it helps connect the required
  edits to the decision;
- uses `sm:max-w-md`, the vendored `max-w-[calc(100%-2rem)]` mobile inset, and internal scrolling at
  `max-h-[calc(100dvh-2rem)]`;
- places initial focus on `Keep reviewing changes`; Escape, overlay press, close icon, and
  `Keep reviewing changes` close without side effect and restore focus to `Fix and resubmit`;
- uses neutral `Continue to edit` as a Next link to the existing owner-scoped wizard route;
- has no Submit, Resubmit now, Appeal, Dispute, Contest, Contact, or Support control.

The listing footer’s shipped `flex-wrap` behavior remains. Adding `Review history` and the longer
resubmit label may create another footer line; clipping, shrinking text, icon-only conversion, or
horizontal card overflow is not an acceptable substitute for wrapping.

## Surface Contract 3 — Review History

Any non-deleted, owner-owned listing with one or more review cycles renders one visible
`Review history` ghost/neutral `size="sm"` control in its card footer. A listing with zero cycles
renders no trigger and no dead dialog shell.

The controlled history dialog uses `sm:max-w-lg`, a dynamic viewport height cap, and internal
scrolling. It contains one semantic `<ol>` of at most five review-cycle `<li>` records, newest first.
The database query reads at most six per listing: five visible plus one older-data sentinel. Client
`.slice(0, 5)` is not the bound.

Each normal cycle is a bordered or divided record, not another Card. Inside it, render a nested
ordered lifecycle:

1. `Submitted {absolute date and time}`.
2. `Waiting`.
3. When decided, exactly one terminal event: `Approved`, `Not approved`, or `Review ended`, followed
   by the absolute decision time.

An open `pending` cycle stops at Waiting. A rejected terminal event renders the stored reason below it
as wrapping plain text. Approved cycles omit a reason. A legacy grandfathered row uses the dedicated
capability sentence and does not fabricate submitted, waiting, decision, check, or approval events.

`decidedByStaffId`, staff name, internal state/code, review id, host id, listing id, and deleted parent
data never enter the client DTO. Owner and `deletedAt IS NULL` constraints are applied inside the
query, not after serialization.

The dialog close button is visible and named. Focus enters at the Close control or first cycle heading,
is trapped by Radix, returns to `Review history` on close, and never falls to `<body>`. The list is
readable without icons or color. No pagination, load more, infinite feed, or link to an ops surface is
present.

## Surface Contract 4 — Edit-Wizard Notice and Receipt

### Persistent rejected notice

Whenever the authoritative current review state is `rejected`, the edit wizard renders the compact
notice from the Copywriting Contract above its editable content. This is state-derived, not authorized
by a query parameter, so direct URL entry and refresh cannot bypass it.

The notice:

- uses a flat neutral panel/notice, never destructive red;
- shows the current stored rejection reason as text;
- names all seven material changes from the exported tuple-backed label map;
- remains visible while the host moves through wizard sections;
- contains no standalone resubmit control.

### Server-confirmed receipt

Every field-save and photo add/remove action path that already invokes `markForReReview` propagates
only the existing `flipped` boolean needed by the client. The receipt appears if and only if:

1. the host is in the rejected-listing edit context derived by the server; and
2. the completed action returns `flipped: true` from the guarded transition.

Entering the route, carrying a query parameter, pressing Save, receiving a generic `ok`, or changing a
non-material field never authorizes the receipt. Photo reorder is non-material and never authorizes it.

On the first true result:

- latch the `Changes received` receipt in page state before any optional navigation;
- keep it visibly in-page for the remainder of the mounted wizard;
- suppress the generic success toast for the same outcome;
- move programmatic focus once to the receipt’s `tabIndex={-1}` heading/region and scroll it into view;
- do not also add a live region for that outcome.

Subsequent saves do not repeatedly move focus or re-announce the same receipt. A refresh may remove the
transient receipt; the persisted `pending` review state and newest open history cycle are then the
durable confirmation. Failed saves preserve input and the current rejection notice and never render
success.

## Loading, Error, Empty, and Partial States

- `/host/loading.tsx` keeps exactly one announced `RowListSkeleton`. Do not add a simultaneous roadmap
  skeleton or second `role="status"`; the roadmap is below the variable-height agenda and cannot claim
  a stable landing geometry before the server snapshot resolves.
- `/host/listings/loading.tsx` keeps the existing single `CardGridSkeleton`; history DTOs resolve with
  the cards and never load one dialog per card.
- Route read failures use the existing host `ErrorState`. The error boundary exposes only the opaque
  digest, not reason text, vendor reference, review row, staff identity, or SQL details.
- Dialogs receive resolved serializable data with the card. Opening history performs no fetch and has
  no spinner, flash, or empty intermediate state.
- If one listing has malformed/missing optional history data, render the truth that exists: a pending
  cycle may omit `decidedAt`; a rejected legacy row may omit a reason. Never fabricate an instant,
  reviewer, code, or cause.
- Required state mismatches that would make the lifecycle false fail the server composition and route
  to the boundary rather than displaying `Unknown` or a guessed terminal event.
- Long operator reasons, listing titles, dates, and material labels wrap. Nothing uses line clamp or
  ellipsis in these explanatory surfaces.

## Responsive and Accessibility Contract

- Acceptance widths are 320px and 1280px in both `court` and `grove` themes.
- The roadmap is one column at 320px and 2×2 at desktop/tablet width. The four-card DOM order remains
  identity, payouts, list a space, FitOut review at every width.
- No Phase 21 surface creates horizontal viewport overflow. Dialog content stays within 16px viewport
  insets and scrolls internally when taller than the dynamic viewport.
- Heading order is `h1` page → `h2` roadmap/ready section → `h3` step cards; dialog titles use Radix’s
  accessible title semantics rather than joining the document outline.
- State is always expressed by visible text and icon shape, never color alone. Decorative icons are
  hidden from assistive technology.
- Every action has a visible label. No new icon-only action is introduced.
- Roadmap touch actions are at least 44px high. Dense listing-footer actions retain the Phase 19 28px
  contract and wrap rather than shrink or clip.
