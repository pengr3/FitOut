# Phase 16.1: Upload Hardening & Storage Economy - Context

**Gathered:** 2026-08-26
**Status:** Ready for planning

<domain>
## Phase Boundary

**What a host uploads is bounded, is what it claims to be, and costs what it should to serve.**

Six things must become true (ROADMAP § Phase 16.1 Success Criteria). They are NOT six independent
work items — **one mechanism carries three of them**:

| Criterion | Carried by |
|---|---|
| 1. A declared, enforced size limit with truthful copy | the widget's `maxFileSize` + honest copy |
| 2. Only real raster formats; SVG refused | the widget's format allow-list |
| 3. Stored photo bounded in pixels and bytes, client cannot influence | **the incoming transformation** |
| 4. Backfill decided explicitly and recorded | **D-190 below — decided, no code** |
| 5. No GPS a host did not intend to publish | **the incoming transformation** (re-encode drops EXIF) |
| 6. Orphans accounted for | **D-187 / D-188 below** |

**The incoming transformation is the load-bearing deliverable.** Criteria 3 and 5 are entirely its
output, and criterion 1's honesty depends on it (see D-181). If the transformation can be omitted by a
caller, three criteria fail at once. **See `<research_questions>` R-1 — that is the phase's first
question and it may be a roadmap conversation rather than a planning detail.**

**This phase does NOT:**

- Rewrite the delivery pipeline. No render site changes, no per-surface resizing, no URL builder.
  Criterion 3 says *"no delivery URL changes"*; finding N2 stays out of scope, as does the stored
  focal-region work 999.2 § Source-of-truth finding 4 already ruled out.
- Add a schema migration. **GATE-06 binds: `drizzle/` stays at `0025`.** Nothing here needs a column.
- Re-open D-165. `persistPhoto` provenance validation SHIPPED in Phase 16
  (`src/lib/listing/cloudinary-provenance.ts`). The U-list's "arbitrary client url" gap is closed.

**Everything in this phase is PREVENTIVE, not remedial** — see D-190. Production holds zero real host
uploads, so there is no oversized asset to shrink, no orphan worth reaping and no leaked coordinate
today. That is the cheapest possible moment to fix all three, and it is why the disposition on each is
"stop it happening" rather than "clean it up".

</domain>

## Implementation Decisions

Numbering continues the project-global sequence; D-178 (16-09-PLAN) was the previous highest.

### Scope

- **D-179 — 16.1 is hardening and storage economy ONLY, and its user-visible surface is error copy.**
  ROADMAP's `UI hint: no` holds — no `/gsd-ui-phase` run. The one exception is that error copy IS the
  visible deliverable here (D-186), so it gets treated as a real surface rather than as an afterthought.

### The size ceiling *(PM, 2026-08-26)*

- **D-180 — FitOut declares 10 MB for a listing photo.**
  Chosen to make an EXISTING sentence true rather than to change a number under a host:
  `src/components/listing/photo-uploader.tsx:186` already promises *"an image under 10MB"* and nothing
  in our code enforces it — that is Cloudinary's own plan limit doing the work, i.e. **our copy
  describes a vendor default we neither control nor declare** (roadmap U1). 10 MB comfortably fits any
  phone photo and most DSLR JPEGs.
  ⚠ **The planner must verify 10 MB does not exceed what the account's actual Cloudinary plan
  accepts.** Declaring a limit the vendor refuses below would reproduce the exact defect this fixes.

- **D-181 — The 10 MB is ADVISORY client-side. The hard bound is the transformation.**
  The bytes go browser→Cloudinary directly; our server never sees them, so a caller who skips the
  widget and posts to `/api/cloudinary/sign` bypasses any client check by construction. The PM's
  explicit call: that is acceptable, **because the security boundary is not the byte limit — it is the
  transformation**, which bounds the STORED asset regardless of what arrived. The limit is honest about
  being a courtesy to hosts.
  ⚠ **DO NOT implement a server-side check of the widget's reported `info.bytes`.** It is
  client-supplied; a caller who bypassed the widget also lies about it. It would look like a guard and
  be theatre — the same defect shape `tests/use-server-exports.test.ts` and
  `cloudinary-provenance.ts:43-51` both exist to prevent.
  ⚠ **This decision is CONDITIONAL on R-1.** If the transformation turns out to be omittable, D-181's
  premise is false and the enforcement question must go back to the PM — the two rejected options were
  a server-fixed upload param and an Admin-API check on the write.

- **D-182 — Stored listing photos are capped at 2048px on the long edge**, with quality and format
  chosen by Cloudinary (`quality: auto`, `format: auto` or equivalent — the planner picks the exact
  spelling). Sized against the most demanding render site, the full-screen lightbox
  (`src/components/listing/photo-lightbox.tsx:353`); everything else is a thumbnail or a 16/9 mosaic
  cell. 2048 is sharp on a laptop and on most desktop monitors; only a retina 4K viewer at true
  full-screen would notice. **Bandwidth is the larger half of the win, not storage** — every render
  site serves this one file to every booker on every page view.

- **D-183 — Two ceilings stand: 5 MB avatar, 10 MB listing. `AVATAR_MAX_BYTES` is NOT touched.**
  PM's call: different surfaces, different jobs — an avatar becomes a 400×400 circle, so 5 MB is
  already absurdly generous there. `AVATAR_TOO_LARGE_MESSAGE` is pinned by 16-UI-SPEC and stays
  byte-unchanged.

### Formats *(PM, 2026-08-26)*

- **D-184 — The listing allow-list is JPEG, PNG, WebP, HEIC/HEIF. SVG and animated GIF are refused.**

  - **SVG out** — a scriptable document, not an image (roadmap U2).
    *Honest note for the planner, so the rationale is not overstated:* an SVG delivered through
    `<img src>` cannot execute script in any current browser, and it is served from
    `res.cloudinary.com` — a different origin from FitOut — so the practical risk in THIS architecture
    is low. It is refused because it is not a photo and refusing costs nothing, not because a live
    exploit was demonstrated.
  - **HEIC/HEIF IN** — a departure from `AVATAR_ALLOWED_TYPES`' three, made deliberately. It is what
    iPhones actually shoot; iOS Safari usually converts on pick, but a host with *Keep Originals* on,
    or on Android/desktop, sends real HEIC. Since the transformation re-encodes anyway, accepting it
    costs nothing and removes a refusal that would be baffling to a host looking at a normal photo.
    ⚠ Planner must verify HEIC ingest against the live account before pinning it in copy.
  - **Animated GIF out** — nobody asked for it, the mosaic and lightbox are built for stills, and a
    multi-frame asset is the one input where the re-encode can make the file BIGGER, which is the
    opposite of this phase's purpose.

- **D-185 — `sources: ["local"]`. Both `"url"` AND `"camera"` are dropped**
  (`photo-uploader.tsx:181` today reads `["local", "camera", "url"]`).
  `url` lets a client hand Cloudinary an arbitrary remote address and defeats every client-side check
  by construction, since no local file exists to measure (roadmap U3). The PM chose the tightest
  option and dropped `camera` too: on mobile, `local` already opens the photo picker, which offers the
  camera on both iOS and Android, so the practical loss is desktop-webcam capture only.

- **D-186 — One sentence per refusal reason, matching the avatar path.**
  Too-big, wrong-format and upload-failed each get their own message, mirroring the three the avatar
  flow already ships (`AVATAR_TOO_LARGE_MESSAGE`, `Only image files are allowed.`,
  `AVATAR_UPLOAD_FAILED_MESSAGE` — all in `src/lib/validation/profile.ts`). Today all three funnel into
  one generic toast at `photo-uploader.tsx:184-188`.
  Constraints: **rule F2 — two copies of a string are two strings.** Each sentence gets exactly one
  home in a directive-free module, as the avatar sentences did. The format sentence names what IS
  accepted (actionable) rather than what was refused.

### Orphaned and valueless assets *(PM, 2026-08-26)*

Measured, not assumed: **`destroyListingPhoto` has exactly ONE caller** — `removePhoto`
(`src/app/actions/listing-photo.ts:293`). Nothing else in the codebase ever deletes a Cloudinary asset.

- **D-187 — Close the SOURCES of new orphans. No sweep, no reaper, no Cloudinary Admin API.**
  The PM's call, and D-190 is why it is proportionate rather than a compromise: with zero real host
  uploads in production, everything currently orphaned is a dev/test artefact, so there is nothing
  worth the risk of a diff-driven irreversible delete.

  **The true orphan — bytes on Cloudinary with no DB row — has one reachable source, and it is
  bug-shaped:** the upload succeeds at Cloudinary, then `persistPhoto` refuses. Most reachable
  spelling: a listing holds 18 photos, the host selects 20 (the widget permits it —
  `photo-uploader.tsx:180`), all 20 upload, 2 persist and **18 are refused at the `MAX_PHOTOS` cap**
  (`listing-photo.ts:140`). `photo-uploader.tsx:113-121` toasts the error and returns; nothing
  destroys anything. 18 unreachable, permanently-billed assets from one click.

  **The fix: `persistPhoto` destroys the asset when IT is the one refusing.**

  ⚠⚠ **THE CONSTRAINT THAT MAKES THIS SAFE, AND IT IS NOT OPTIONAL. The destroy may run ONLY on a
  refusal that happens AFTER `isOwnCloudinaryAsset` has PASSED.** It must NEVER run when provenance
  REJECTED, and never on the session/ownership refusals that precede it, because in all of those cases
  we have **no proof the `publicId` names an asset that is ours to delete**. A destroy on the
  rejection path would hand any caller an arbitrary-delete primitive against our own Cloudinary
  account — another host's cover photo, or `fitout/avatars/<victim-userId>` — which is precisely the
  class of attack `cloudinary-provenance.ts` was written to stop. **The cleanup would introduce a
  destructive IDOR that the phase it lives in exists to prevent.**
  The existing order in `persistPhoto` already makes this natural: provenance at `:130`, `MAX_PHOTOS`
  at `:140`. The destroy belongs in the latter branch and nowhere above it. A test must pin it.

  **Best-effort, never user-facing:** the destroy follows the shape both existing call sites already
  use (`listing-photo.ts:292-296`, `avatar.ts`'s `removeAvatarAction`) — a Cloudinary hiccup must not
  change the result the host sees. Note `uploader.destroy` RESOLVES `{ result: "not found" }` rather
  than throwing, so a bare `catch` handles only one of its two failure shapes
  (`src/lib/cloudinary.ts:154-158`).

- **D-188 — Listing soft-delete destroys its photos IMMEDIATELY.**
  PM's call. `softDeleteListing` (`src/app/actions/listing.ts:416-435`) sets `deletedAt` and destroys
  nothing today, so a deleted listing's photos are billed forever.
  **The objection was raised and it does not survive contact with the code: there is no restore path.**
  Nothing anywhere sets `deletedAt` back to null; there is no undelete action and no UI. The soft
  delete exists for referential integrity — the comment at `:416` says *"forward-safe for when bookings
  FK to listings"* — not for host-facing undo. So destroying the photos costs nothing a host can reach.
  Record the consequence honestly anyway: **if a restore path is ever built, it restores a listing with
  no photos**, and whoever builds it inherits that from this decision.

- **D-189 — EXIF/GPS is stripped, silently. No copy, no toggle, no opt-out.**
  This is not a new privacy feature — **it closes a side channel around a guarantee FitOut already
  makes.** D-09 / T-05-PII are shipped and deliberate: `publicListing()` COARSENS the coordinates
  server-side so the precise point never reaches the browser, `listing-map.tsx` renders a fuzzed
  ~600m `<Circle>` instead of a pin, and the page tells the booker in as many words —
  *"Approximate area. The exact address is shared after booking."*
  (`src/app/listings/[id]/(detail)/page.tsx:314`).
  A photo carrying EXIF GPS is served publicly from `res.cloudinary.com` with the **exact** coordinates
  inside it, to anyone who downloads the file. For a host listing a home gym, that is their address.
  PM's call: strip silently. Nobody opts into their own privacy guarantee working, and a toggle whose
  OFF state publishes someone's home coordinates is a hazard dressed as a choice.
  ⚠ **Orientation trap for the planner:** EXIF also carries the rotation flag. Metadata stripped
  WITHOUT the rotation being applied first yields sideways photos. Confirm the transformation
  normalises orientation before stripping.
  ⚠ **R-2 must probe this before it is claimed as fixed** — see `<research_questions>`.

### The backfill decision *(criterion 4 requires this be explicit and recorded — here it is)*

- **D-190 — NO BACKFILL. Reason: there is nothing to backfill.**
  The PM confirmed on 2026-08-26 that **no real host has uploaded a photo in production** — v1.0
  shipped 2026-08-11 but nobody outside the team has listed a space. The local DB's 27 `listing_photo`
  rows are seeded **Unsplash** URLs, not uploads (verified directly). So:

  - there is no oversized stored asset to shrink,
  - the EXIF leak in D-189 has no victim today,
  - every asset currently orphaned is a dev/test artefact.

  **The condition that reverses this, stated so it is not forgotten:** if real host photos are
  uploaded BEFORE this phase ships, backfill stops being optional — not for bandwidth, but because
  D-189's leak would then be live on published listings, and criterion 5 would be retroactively false.
  Whoever plans this phase should re-confirm the production count rather than inherit this line.

  *Aside surfaced while verifying:* those seeded Unsplash URLs would now be **refused** by the D-165
  provenance guard, since they are not on our Cloudinary origin. Seeds write straight to the DB so
  nothing breaks, but the fixtures no longer represent anything the app can produce. Worth knowing
  before anyone reads a UAT result off them.

### Claude's Discretion

The PM delegated these; each was decided and is recorded with its reasoning.

- **D-191 — NO new pixel-dimension guard on the avatar path. The deferral pointed at from
  `src/lib/avatar.ts:22-25` and `src/lib/validation/profile.ts:74-77` is closed as UNNECESSARY, not
  as done.** Roadmap U4 frames a 40MP image inside 5 MB as "a decompression bomb against whatever
  decodes it" — but **FitOut has no decoder.** `uploadAvatarAction` does `arrayBuffer()` → `Buffer` →
  `upload_stream`; the bytes are never decoded server-side. The bomb, such as it is, detonates at
  Cloudinary, for whom 40MP is unremarkable. Storage is already bounded by D-171's retained 400×400
  `c_fill` transform. Adding a header-parsing dimension check would be new code defending against a
  threat this architecture does not have.
  **The condition that reverses it:** the day any server-side code decodes uploaded image bytes — to
  read dimensions, generate a blurhash, produce a thumbnail — the guard becomes necessary and this
  decision is void. Both source comments should be updated to say this rather than left pointing at a
  phase that decided not to.

- **D-192 — The e2e that performs a real Cloudinary upload cleans up after itself.**
  STATE records that Phase 16's verification pass orphaned 2 real assets (`e2e/avatar-crop.spec.ts`
  does one real upload per run, per D4). That is an ongoing bleed and it is exactly the "stop new
  ones" principle applied to our own tooling. It only bites on LOCAL runs — `.github/workflows/ci.yml`
  records at `:151` and `:875` that the test jobs hold no Cloudinary credential.
  Planner: confirm FIRST whether `overwrite: true` + `public_id: userId` (`src/lib/cloudinary.ts:53-55`)
  already makes repeat runs idempotent for a FIXED test user, in which case the fix is to pin the test
  user rather than to add teardown. Cheapest correct answer wins; do not add teardown that duplicates a
  property the upload already has.

- **D-193 — Copy wording is the planner's, within D-186's shape.** One home per sentence,
  directive-free module, format sentence names what IS accepted. The three shipped avatar sentences
  are the model and are NOT re-worded.

## Research Questions — R-1 gates the phase

- **R-1 (BLOCKING, answer before planning) — how does an incoming transformation reach the upload
  without the client being able to omit it?**
  Criterion 3's clause *"a transformation the client cannot influence"* is the whole phase. The
  constraint that makes it hard is deliberate and load-bearing: `ALLOWED_SIGN_KEYS`
  (`src/app/api/cloudinary/sign/route.ts:35`) signs ONLY `{folder, source, timestamp}` and rejects any
  other key with 400 before signing (T-04-SIGMATCH), and Cloudinary 401s if the signed set and the
  sent set differ — so the server cannot simply ADD a param the widget does not send.
  The roadmap names two candidate mechanisms: **a named Cloudinary upload preset**, or **a narrow
  server-fixed extension to the allow-list**. Evaluate both, plus anything else that holds.
  **The project's stated preference, and it is strong:** `cloudinary-provenance.ts:43-51` refuses to
  depend on ambient off-repo configuration by design, and gives the reason — CI holds no Cloudinary
  credential, so an ambient dependency is invisible to every test that runs continuously. **An upload
  preset is dashboard configuration no test can pin.** If it is the only mechanism that works, say so
  plainly and propose what pins it; do not adopt it silently.
  **If NEITHER mechanism holds, criteria 3 and 5 are not reachable as the roadmap words them, and
  D-181's premise collapses with them. That is an escalation to the PM, not a planning workaround.**

- **R-2 — probe EXIF/GPS end to end before D-189 is claimed as satisfied.**
  Push a real GPS-tagged photo through the live signed-upload path and read the delivered bytes back.
  Establish (a) whether an UNtransformed original currently retains EXIF GPS on delivery, and
  (b) that the transformation removes it while preserving correct orientation. This could not be
  verified from the repo — the seeded fixtures are Unsplash URLs, not uploads.

- **R-3 — verify the two vendor facts D-180 and D-184 rest on:** that the account's Cloudinary plan
  accepts 10 MB image uploads, and that HEIC/HEIF ingest works on it. Both are declared in host-facing
  copy, so being wrong about either reproduces the exact defect D-180 exists to fix.

- **R-4 — confirm the exact re-encode semantics** for the multi-frame (GIF) and vector (SVG) inputs
  D-184 refuses, so the client allow-list and whatever the transformation does cannot disagree about
  what happens to an input that slips past one of them.

</research_questions>
