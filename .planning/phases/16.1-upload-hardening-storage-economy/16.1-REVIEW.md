# Phase 16.1: Code Review Report

**Reviewed:** 2026-08-28
**Depth:** standard

## Summary

The four things the brief asked me to attack hardest hold up:

- **The equality gate (`sign/route.ts:129-157`) cannot be bypassed at the KEY level.** The extra-key
  test is identity-based (`ALLOWED_SIGN_KEYS.has(k)` over `Object.keys`), not a count, so case
  variants, `__proto__` (which `JSON.parse` makes an own enumerable property and `Object.keys`
  therefore reports), duplicate keys (last wins, still one key) and arrays (`typeof [] === "object"`,
  but `folder` is then `undefined` and the request 403s) all land on a refusal. `upload_preset` is
  compared with `!==` against the imported constant, so no non-string value and no near-miss spelling
  reaches `signUploadParams`. Path 5b never takes a client param at all.
- **Destroy ordering is correct on every path in both actions.** In `persistPhoto` the destroy is at
  `listing-photo.ts:182-197`, strictly below the provenance call at `:135`; no early return, catch or
  helper above it touches Cloudinary. In `softDeleteListing` (`listing.ts:472-503`) the publicIds come
  from a DB read scoped to the owned listing, never from client input, and the read is above the
  `deletedAt` write for the reason the docblock states.
- **The script's exit paths all set a code before returning.** I re-measured the three credential-free
  hard stops on this machine: `--bogus` → 1, no mode → 1, `--apply --verify` → 1. No `process.exit()`
  survives anywhere in the file, and the 404 branch pushes a failure onto `failures` before returning,
  so it can no longer fall through to 0.
- **No secret is printed.** `CLOUDINARY_API_SECRET` is read in exactly one place (the Basic header at
  `:776-778`); no error path echoes request headers, and the printed evidence is response bodies and
  drift lines only.
- **Declaration integrity holds.** `fitout_listing_v1`, `2048`, `10 * 1024 * 1024`, the six formats
  and `20` appear in exactly one non-test source file each (`upload-policy.ts`); every other consumer
  imports. The design suites pass (62 tests, 4 files) against the current tree.

What I found instead sits one layer out from those controls: the sign route validates *which* keys it
will sign but never *what is in them*; the new destroy at the photo cap can delete an asset a live row
still points at; two server actions can still reject instead of returning their `{ ok: false }` shape
(the exact defect `reorderPhotos` documents as fixed, left standing in its two siblings); and two of
the reconciler's own "never a skip / we could not tell must refuse" rules are applied inconsistently
inside the same file.

## Narrative Findings (AI reviewer)

### Warnings

#### WR-01: The sign route gates key IDENTITY but never validates key VALUES — smuggling is stopped only by a vendor default

**File:** `src/app/api/cloudinary/sign/route.ts:129-157` (with `src/lib/cloudinary.ts:102-109`)

**Issue:** `paramsToSign` is cast to `Record<string, string | number | boolean>` at `:90` and never
checked against that type. Only two of the four admitted keys have their *values* constrained —
`folder` (`:137`) and `upload_preset` (`:154`). `source` and `timestamp` are passed to
`signUploadParams` exactly as the client wrote them, including a value containing `&`.

The route's own security argument (`:148-153`) is that Cloudinary "validates the signature against
exactly the parameter set the upload carries, so a caller … cannot add one". That claim is not
enforced here; it is enforced by `cloudinary@2.10.0`'s `api_string_to_sign`, which since
signature version 2 runs `encode_param` (`node_modules/cloudinary/lib/utils/index.js:1081-1095`,
`&` → `%26`) precisely to stop parameter smuggling. Without that encoding, a body of

```json
{ "folder": "fitout/listings/<owned>", "source": "uw",
  "timestamp": "1700000000&transformation=c_scale,w_4000", "upload_preset": "fitout_listing_v1" }
```

passes all three gates (four allow-listed keys, exact folder, exact preset), and the string signed —
`folder=…&source=uw&timestamp=1700000000&transformation=c_scale,w_4000&upload_preset=…` — is
byte-identical to what Cloudinary canonicalises from a POST that carries `transformation` as a real
parameter (`t` sorts `timestamp` < `transformation` < `upload_preset`). That is the exact probe-E11
upscale-past-the-cap outcome this phase exists to prevent, obtained through the gate rather than
around it.

Today the SDK default closes it (`signature_version` is unset in `cloudinary.config()` at
`src/lib/cloudinary.ts:48-52`, so `config().signature_version || 2` yields 2, and `package.json`
pins `^2.10.0`). It is a Warning rather than a Blocker for that reason. It escalates if any of these
becomes true, none of which this repo would notice: a `CLOUDINARY_URL` carrying
`signature_version=1`, an explicit config change, a downgrade, or a Cloudinary account that still
accepts version-1 signatures for backwards compatibility. Secondary consequence of the same gap: the
route will sign any `timestamp` the client chooses, including a far-future one, so the validity
window of the token it mints is client-selected.

**Fix:** constrain the values, not just the key set — the widget's real set is fully known:

```ts
// after the extra-key check, before signing
const ts = paramsToSign.timestamp;
if (typeof ts !== "number" || !Number.isInteger(ts) || Math.abs(ts - Math.round(Date.now() / 1000)) > 3600) {
  return new Response("Bad Request — bad timestamp", { status: 400 });
}
if (paramsToSign.source !== undefined && paramsToSign.source !== "uw") {
  return new Response("Bad Request — unexpected source", { status: 400 });
}
```

(`folder` and `upload_preset` are already equality-checked, so those two need nothing.) Add a line to
the header recording that value validation — not only the key set — is what makes "cannot add one"
true on our side of the boundary.

#### WR-02: The D-187 cap destroy can delete an asset a live `listing_photo` row still points at

**File:** `src/app/actions/listing-photo.ts:144-197`

**Issue:** `isOwnCloudinaryAsset` proves the publicId is *ours and under this listing's folder*. It
does not prove the asset is **unreferenced**. When the listing is at the cap, any `{ publicId, url }`
pair that passes provenance is destroyed — including a pair that is already stored as a row. A host
calling their own server action with a pair copied from their own edit page (both values are rendered
there) gets: `position (20) >= LISTING_MAX_PHOTOS` → `destroyListingPhoto(publicId)` → `{ ok: false }`,
while the `listing_photo` row survives untouched. The public listing page then renders a 404 image
from an address the database still calls valid, and nothing in the product can repair it — `removePhoto`
will delete a row whose bytes are already gone.

The blast radius is owner-scoped (ownership and provenance both hold above it), which is why this is
not a Blocker. But it is silent, irreversible destruction of an asset the caller did not ask to remove,
introduced by this phase's new call site.

**Fix:** make the destroy conditional on the id being unreferenced — one indexed read, inside the
branch, below the provenance gate where it already sits:

```ts
const stillReferenced = await db
  .select({ id: listingPhoto.id })
  .from(listingPhoto)
  .where(and(eq(listingPhoto.listingId, listingId), eq(listingPhoto.publicId, publicId)));
if (stillReferenced.length === 0) {
  try { /* existing destroy + both failure shapes */ } catch { /* … */ }
}
```

and extend `tests/listing/photos.test.ts`'s D-187 describe with a sixth case: at the cap, re-submitting
an ALREADY-PERSISTED pair must leave `mockCloudinary.destroys()` empty.

#### WR-03: `persistPhoto`'s insert can reject instead of returning `{ ok: false }` — and the orphan it leaves is the class D-187 exists to close

**File:** `src/app/actions/listing-photo.ts:144, 204-205`; caller at
`src/components/listing/photo-uploader.tsx:126-134, 142`

**Issue:** `position` is read with a non-transactional `photoCount()` and used as the insert value,
under `uniqueIndex("listing_photo_position_uq").on(listingId, position)`
(`src/lib/db/schema.ts:252`). The widget runs with `multiple: true` and `maxFiles` up to 20, so
`onSuccess` fires once per file and `handleUploadSuccess` launches `void addPhoto(...)` without
awaiting the previous one — concurrent `persistPhoto` calls reading the same count are the normal
case, not an edge case. Two that collide make the second `db.insert` throw a unique-violation. There
is no `try` around it (contrast `reorderPhotos:267-295`, which documents this exact escape and fixes
it), so the action rejects rather than returning the refusal shape.

Consequences, in order of severity: the uploaded asset is already on Cloudinary and nothing destroys
it — a permanently billed orphan on a path D-187's cleanup does not cover; the client's `void
addPhoto(...)` has no `.catch`, so the rejection is an unhandled promise rejection and the host gets
no toast at all; the photo simply never appears.

**Fix:** wrap the insert and answer with the shipped sentence (and destroy the now-unreferenced asset
in the same place, since at that point provenance has passed and no row names the id):

```ts
try {
  await db.insert(listingPhoto).values({ id, listingId, publicId, url, position });
} catch (err) {
  console.warn(`[listing-photo] insert failed for listing ${listingId}`, err);
  try { await destroyListingPhoto(publicId); } catch { /* best-effort, both shapes */ }
  return { ok: false, error: LISTING_UPLOAD_FAILED_MESSAGE };
}
```

Serialising the client (`await` each `addPhoto` before the next) narrows the window but does not close
it — two tabs still collide — so the server-side `try` is the fix and the client change is optional.

#### WR-04: `removePhoto`'s transaction has no `catch`, so the optimistic grid keeps an order the database refused

**File:** `src/app/actions/listing-photo.ts:330-345`; caller at
`src/components/listing/photo-uploader.tsx:175-185`

**Issue:** This is the identical shape `reorderPhotos` documents at `:218-228` ("there was no `try`,
so the rejection ESCAPED the server action instead of returning the `{ ok: false, error }` shape
`photo-uploader.tsx` is written against — the optimistic UI never reverted"). The fix landed on
`reorderPhotos` only. In `removePhoto`, the delete + re-pack transaction can still throw — two
removals racing on one listing re-pack overlapping position ranges against the same non-deferrable
unique index, or a connection drop mid-transaction — and `handleRemove` has already removed the tile
optimistically at `:177`. The rejection escapes, `setPhotos(previous)` never runs, and the grid shows
a photo gone that the database still holds until the page is reloaded.

**Fix:** mirror `reorderPhotos` exactly:

```ts
try {
  await db.transaction(async (tx) => { /* unchanged */ });
} catch (err) {
  console.warn(`[listing-photo] remove failed for listing ${listingId}`, err);
  return { ok: false, error: "We couldn't remove that photo. Please try again." };
}
```

The same one-line omission exists on `softDeleteListing`'s update (`listing.ts:477-480`) and
`saveListingStep`'s transaction (`listing.ts:259-284`); worth the same treatment while the pattern is
in hand.

#### WR-05: `--apply` reports a REFUSED write as exit 3 — the code the contract reserves for "I could not look"

**File:** `scripts/cloudinary-preset.ts:682-687` (thrown), `:788-797` (classified), `:34-41`
(contract)

**Issue:** The documented contract is explicit: `3` means "THE TOOL COULD NOT RUN — no credential, a
rejected credential, or the Admin API did not answer. NOT a drift finding." A `POST`/`PUT` that comes
back 400/422/500 is the API *answering and refusing* — the preset was NOT reconciled and the account
is in whatever state it was in. `runApply` raises `CouldNotRunError` for it, so the operator (and any
CI wrapper that treats 3 as "no credential here, skip", which is exactly how the header tells them to
read it) gets a code that says "nothing was checked, this is expected in CI" for a failed
reconciliation of the phase's load-bearing security control. `runVerify` never runs afterwards, so
nothing else corrects the verdict.

**Fix:** give the write failure its own class and exit 1 (a hard stop, which is what it is):

```ts
class HardStopError extends Error {}
// in runApply
throw new HardStopError("THE PRESET COULD NOT BE WRITTEN.", …);
// in main's catch, before the CouldNotRunError arm
if (cause instanceof HardStopError) { /* print */ process.exitCode = 1; return; }
```

and add the row to the exit-code table in the header. Keep 3 for 401/403 and for the network-silence
path, which are correctly classified today.

#### WR-06: The account-wide unsigned scan fails OPEN, in the same file that argues the same property must fail closed

**File:** `scripts/cloudinary-preset.ts:641-653` (scan) vs `:318-326` (single-preset check)

**Issue:** `presetDrift` checks `remote.unsigned !== false` and states the rule out loud: "An absent
field, a string, or anything else the vendor might hand back is NOT a signed preset as far as this
check is concerned … 'we could not tell' must land on the refusing side." The account-wide scan,
whose subject is the *same* property and the *same* threat (T-16.1-08), inverts the polarity:
`entry?.unsigned === true`. If the list endpoint ever omits `unsigned`, or returns it as `"false"` /
`"true"`, every entry is treated as signed and the check prints `unsigned=[]` — a green that cannot
be distinguished from a real one, on the one control the file calls "a standing upload hole". The
printed evidence does not disambiguate either: it shows names and the (empty) unsigned list, never
the raw per-entry value.

Related and smaller, same call: `?max_results=500` with no `next_cursor` follow-up, so preset 501 on
a large account is never scanned and the omission is silent.

**Fix:** flag on the refusing side and print what was actually read:

```ts
const notProvablySigned = presets
  .filter((entry) => entry?.unsigned !== false)
  .map((entry) => `${String(entry?.name)}=${JSON.stringify(entry?.unsigned)}`);
reportCheck(failures, "every preset on the account is provably signed",
  notProvablySigned.length === 0,
  `presets=${JSON.stringify(presets.map((e) => [String(e?.name), e?.unsigned]))}`);
```

and either follow `next_cursor` or hard-stop when the response carries one.

#### WR-07: The D-192 e2e teardown only runs on the happy path, so a failing run still leaks the billed asset

**File:** `e2e/avatar-crop.spec.ts:970-1013` and `:2670-2707`

**Issue:** Both teardowns are the last statements of the test body, after every assertion. Playwright
aborts the body at the first failed `expect`, so any earlier failure — a flaky 30 s avatar-visible
wait, an axe regression in the a11y case, a dialog-focus assertion — skips the teardown entirely and
the real `fitout/avatars/<throwaway userId>` asset the case uploaded is abandoned again, with the
throwaway `user` row still referencing it (i.e. invisible to any diff sweep, which is the whole reason
D-192 exists). Failures are exactly when a run is repeated, so the leak multiplies precisely when the
mechanism is most needed. There is no `afterEach` in this file and no credential guard, so nothing
else catches it. UAT Check 7's 28→28 delta was measured across 33 GREEN cases and does not cover this.

**Fix:** hoist the removal into a fixture-scoped `test.afterEach` (guarded on "is the remove control
present?", so it is a no-op for the cases that never uploaded), or wrap each case's body in
`try { … } finally { await teardownAvatar(page); }`. Keep the two assertions that the removal landed —
they are the part that proves the teardown itself works — inside the helper.

### Info

#### IN-01: The sign endpoint does not fail closed when the Cloudinary credential is unconfigured

**File:** `src/lib/cloudinary.ts:102-109`, consumed at `src/app/api/cloudinary/sign/route.ts:157, 177`

**Issue:** `process.env.CLOUDINARY_API_SECRET!` is a non-null assertion over a value that can be
`undefined`. `api_sign_request` then computes `sha1(to_sign + undefined)` — no throw — so the route
answers **200 with a syntactically valid signature minted over the literal string `"undefined"`**,
and (at `:185`) an `apiKey` field that `JSON.stringify` silently drops. Uploads then fail at
Cloudinary with "Invalid Signature", which is a confusing place to discover a missing environment
variable. It is Info rather than Warning because the failure is loud at the vendor and not
exploitable — but it is the same shape `listing-photo.ts:116-134` writes six lines of comment about
refusing to allow.

**Fix:** guard inside `signUploadParams` (not at module scope — `upload-policy.ts:41-45` records that a
module-scope throw here breaks `next build`'s page-data collection): `if (!secret) throw new Error(…)`,
and let the route return 500, or check in the route and return 503.

#### IN-02: `presetDrift` compares two settings keys and is silent about every other one

**File:** `scripts/cloudinary-preset.ts:289-297, 378-401`

**Issue:** `RemotePreset.settings` is typed as `{ transformation?, allowed_formats? }` and only those
two are diffed. Inside the transformation component the file is uncompromising — an unrecognised long
key is a hard failure with the payload printed, "never a skip" (`:368-375`). One level up, a preset
that also carries `settings.eager`, `settings.raw_transformation`, `settings.format` or anything else
a dashboard edit can add is neither compared nor reported as unrecognised. The raw payload is printed
at `:562`, so a human reading carefully would see it; nothing in the exit code would.

**Fix:** apply the same rule one level up — iterate `Object.keys(remote.settings ?? {})` and push a
drift line for any key outside `{ transformation, allowed_formats }`, with the same "add the row with
the evidence in hand" wording the transformation loop already uses.

#### IN-03: The `normalisedAway` evidence line contradicts its own FAIL when the transformation is missing entirely

**File:** `scripts/cloudinary-preset.ts:587-602`

**Issue:** `normalisedAway` is computed as `have === undefined && VENDOR_NORMALISES_AWAY.has(key)`,
and `have` is `undefined` both when the vendor normalised the component away *and* when `component
=== null` (no transformation on the preset at all). In that second case the row correctly prints
`FAIL transformation.fetch_format` — and then prints, as its evidence, "NOT PERSISTED by the vendor,
and that is expected … It IS applied at upload … Do not restore a check here." On the one output that
means *the security control is absent*, the evidence tells the reader it is fine.

**Fix:** `const normalisedAway = component !== null && have === undefined && VENDOR_NORMALISES_AWAY.has(key);`

#### IN-04: An unexpected error in `main` falls back to Node's default exit classification

**File:** `scripts/cloudinary-preset.ts:804, 830-833`

**Issue:** The catch rethrows anything that is neither `CouldNotRunError` nor
`TransformationParseError`, into `void main(process.argv.slice(2))`. The rejection is unhandled, Node's
default `--unhandled-rejections=throw` turns it into an uncaught exception, and the process exits 1 —
i.e. an internal crash is reported as "drift or hard stop", which is the one reading the contract's
third code exists to prevent, and it is reached without any `process.exitCode` assignment of our own.

**Fix:** `void main(process.argv.slice(2)).catch((err) => { console.error("FATAL: unexpected internal
error. THIS IS *NOT* A DRIFT FINDING."); console.error(err); process.exitCode = 3; });`

#### IN-05: The credential-free hard stops are pinned only by a manual UAT table

**File:** `scripts/cloudinary-preset.ts:717-751`; `tests/design/cloudinary-preset-script.test.ts`

**Issue:** The argument block is deliberately ordered "BEFORE ANY CREDENTIAL WORK … which is what
makes them testable", `main` is exported, and every exit is `process.exitCode` rather than
`process.exit()` — every precondition for a unit test is in place, and no unit test exists. The only
record of the contract is the UAT's hand-run table. Given Finding 3 of that UAT was an exit-code
defect that the correct-looking output hid, this is the half of the contract CI could hold for free.
(I re-ran all three by hand during this review: `--bogus` → 1, no mode → 1, `--apply --verify` → 1.)

**Fix:** add to the existing design suite — no credential, no network:

```ts
it.each([[["--bogus"]], [[]], [["--apply", "--verify"]]])("hard-stops with exit 1 on %j", async (argv) => {
  process.exitCode = undefined;
  await main(argv);
  expect(process.exitCode).toBe(1);
});
```

(restoring `process.exitCode` in an `afterEach` so a passing suite still exits 0).
