## Accomplishments

- **`src/lib/listing/upload-policy.ts` exists and is the only place in the repo that spells any of the six values.** RESEARCH § R-1.6's layer 1 is in place: every other plan in this phase is now a consumer of this file rather than a second author of the same numbers.

## Decisions Made

- **`f_auto`, not `f_jpg`** (RESEARCH Open Question 4). Recorded in the constant's docblock with the measurement behind it. `f_jpg`'s deterministic-extension advantage is worthless here because `cloudinary-provenance.ts:22-23` already declines to require the url and the publicId to agree about the extension — an accepted residual this choice makes load-bearing, which the docblock says in as many words so nobody "tightens" it later.
- **Both new test files at `tests/design/`.** The trade is stated in both headers: they run inside `npm run build` and pay no Postgres preflight, at the cost that `npx vitest run tests/listing` does not collect them. Verified empirically — a full `npx vitest run tests/listing` (22 files, 245 tests) mentions neither file, and `vitest list --config vitest.design.config.ts` lists both.
- **Copy wording (D-193).** `Each photo must be 10 MB or smaller.` mirrors `AVATAR_TOO_LARGE_MESSAGE`'s "or smaller" phrasing — required here, not merely consistent, because the declared and vendor ceilings are now the same number and a file of exactly that size passes both sides. `Choose a JPG, PNG, WebP, or HEIC photo.` names what IS accepted; HEIF is not named separately because a host holding one calls it a HEIC photo.
- **The round decimal spelling of the ceiling is never typed out in `upload-policy.ts`.** See Deviations below — this resolves a direct conflict inside the plan.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The plan's Task 1 action text and its own acceptance criterion contradicted each other about the round decimal spelling of the byte ceiling**

- **Found during:** Task 1 (`upload-policy.ts`)
- **Issue:** The action text instructs the `LISTING_MAX_BYTES` docblock to carry *"the reason the arithmetic spelling is load-bearing: `10_000_000` renders identically to a reader…"*, while the acceptance criterion requires `grep -cE "10_000_000|10000000" src/lib/listing/upload-policy.ts` to return `0`. Both cannot hold: writing the token to explain why it is forbidden makes the prohibition report RED against a correct file. This is exactly the mirror failure the plan itself cites — `scripts/verify-workflows.mjs:24-32`, *"substring checks are wrong in both directions on a documented file: falsely green for requirements, falsely red for prohibitions."*
- **Fix:** Applied the repo's own existing resolution, recorded at `tests/design/avatar-zoom.test.ts:27-30` for the jsdom pragma: the docblock makes the full argument (the two numbers differ by 485,760 bytes, render identically to a reviewer, and would make the declared and enforced limits two different numbers again) using the phrase "a round decimal million", and adds an explicit ⚠ paragraph stating that the token is deliberately not typed out and why. Nothing about the argument is lost; only the literal token is.
- **Files modified:** `src/lib/listing/upload-policy.ts`
- **Verification:** `grep -cE "10_000_000|10000000" src/lib/listing/upload-policy.ts` → `0`; `grep -c "10 \* 1024 \* 1024"` → `2`. The reasoning survives in prose and, separately, in `tests/design/upload-policy.test.ts`, which asserts the prohibition over stripped source so the test can spell the token freely while the module does not.
- **Committed in:** `ab795ac` (part of the task commit)

**2. [Rule 2 - Missing critical coverage] The module's docblock claimed a test counted the forbidden token; no such assertion was in the plan's test list**

- **Found during:** Task 2 (`upload-policy.test.ts`)
- **Issue:** The `LISTING_MAX_BYTES` docblock states that the test file counts the round spelling. - **Fix:** Added `it("the ceiling is SPELLED as the arithmetic, never as a round decimal million")` — `expect(CODE).toContain("10 * 1024 * 1024")` and `expect(CODE).not.toMatch(/10_000_000|10000000/)`, both over `stripComments(SOURCE)`.
