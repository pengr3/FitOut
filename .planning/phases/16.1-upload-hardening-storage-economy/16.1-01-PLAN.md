<objective>
Build the one declaration everything else in this phase reads, and the error copy that is the phase's
only user-visible surface.

Purpose: RESEARCH § R-1.6 layer 1 — *"the declaration is the source of truth; nothing else in the repo
spells any of them."* Every other plan in this phase is a consumer of this file. It is the reason the
widget hint and the boundary gate cannot disagree about six formats, the reason the reconciler cannot
re-spell the transformation, and the reason a later "tidy" cannot quietly move `2048` or `10 MB`.

Output: `src/lib/listing/upload-policy.ts`, a shared comment-stripping test helper, and the two pure
test files that pin the module.

**Three decisions this plan makes explicitly, because PATTERNS.md says picking silently is what is not
defensible.**

1. **The two new pure test files live in `tests/design/`, not `tests/listing/`** (PATTERNS § C-2). The
   repo already litigated this at `tests/design/avatar-zoom.test.ts:13-20`: `vitest.config.ts:67`
   declares `globalSetup`, which hard-fails a run when Postgres is unreachable — even a single-file
   run — so a pure-arithmetic assertion about a module with no imports would pay a database preflight
   and would never block `npm run build` (`lint && test:design && next build`). Both new files are
   pure: constants, one array, one string matcher, one AST read. Neither mocks anything, so
   `tests/design/**`'s deliberate absence of `setupFiles` (and therefore of `mockCloudinary`) costs
   nothing. **The consequence, stated so no later plan is surprised:** `npx vitest run tests/listing`
   does NOT collect them; the command that does is `npm run test:design`.
2. **`f_auto`, not `f_jpg`** (RESEARCH Open Question 4). D-182 delegates the spelling and names
   *"format chosen by Cloudinary"*, which `f_auto` is literally. Measured across five inputs it never
   chose webp or avif, it turned HEIC into jpg, and it preserved alpha on a transparent PNG where
   `f_jpg` flattened it onto white. `f_jpg`'s only advantage — a deterministic stored extension — buys
   nothing here, because `cloudinary-provenance.ts:22-23` already declines to require the url and the
   publicId to agree about the extension.
3. **The `That photo didn't upload. Please try again.` sentence gets a home.** It ships as three inline
   copies in `listing-photo.ts` (`:101`, `:128`, `:136`) and is about to acquire a fourth consumer in
   the widget's `onError`. Rule F2: two copies of a string are two strings. Its VALUE does not change
   by one byte — `tests/listing/photos.test.ts:339` and `:385` assert it verbatim and must stay green
   untouched.

**What this plan deliberately does NOT do.**

- **No server-side check of the widget's reported `info.bytes`.** D-181 forbids it in as many words: the
  value is client-supplied, a caller who bypassed the widget also lies about it, and it would look like
  a guard while being theatre. The module carries the argument in prose so the next reader finds the
  reason rather than the omission.
- **No `process.env` read, no Zod, no Cloudinary SDK import, and no module-scope throw.** The last one
  is not style: `.github/workflows/ci.yml:608-635` records `Failed to collect page data for
  /api/cloudinary/sign` as a real failure — `next build` sets `NODE_ENV=production` and arms every
  module-scope boot guard, and this module is imported by that route.
- **It touches no render site.** Criterion 3 says no delivery URL changes.
</objective>
