### 5. How to read a **stored** asset back (Checks 4, 5)

Two routes; either is acceptable, and the second one pastes better.

**(a) The Cloudinary Media Library.** Open the asset under `fitout/listings/<listingId>/`, open the
info panel, read **Format** and **Dimensions**.

**(b) The Admin API.** From the project directory, in Git Bash:

```bash
set -a; . ./.env.local; set +a
curl -s -u "$CLOUDINARY_API_KEY:$CLOUDINARY_API_SECRET" \
  "https://api.cloudinary.com/v1_1/$CLOUDINARY_CLOUD_NAME/resources/image/upload/<public_id>" \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const r=JSON.parse(s);console.log({public_id:r.public_id,format:r.format,width:r.width,height:r.height,bytes:r.bytes});});"
```

The `<public_id>` is visible in the Media Library, or in the delivered URL. **The response carries no
secret** — it is safe to paste. The shell you ran it in now holds one; do not paste your environment.

### 6. How to read a **delivered** file back (Check 6)

This is the one that cannot be delegated to a dashboard summary — the point is **what a booker can
download**, not what the dashboard summarises.

```bash
# Right-click the photo in the listing gallery → "Copy image address". It is on res.cloudinary.com.
curl -sD headers.txt -o delivered.jpg "<the res.cloudinary.com url the listing renders>"
grep -i "^content-type" headers.txt
```

Then read its EXIF with Python + Pillow (**verified available on this machine: Python 3.13.14, Pillow
12.3.0**; `exiftool` and ImageMagick are **not** installed):

```bash
python -c "
from PIL import Image, ExifTags
im = Image.open('delivered.jpg')
ex = im.getexif()
print('size  ', im.size)
print('format', im.format)
print('exif  ', {ExifTags.TAGS.get(k, k): v for k, v in ex.items()})
print('gps   ', dict(ex.get_ifd(0x8825)))
"
```

Run the identical command against the **source** photo first, so the record carries a before and an
after. If the source prints an empty `gps`, the phone did not attach one — **fix that before
uploading**, or Check 6 proves nothing.

**The exit codes, quoted from the tool rather than paraphrased:**

```
Exit codes:  0 = every checked property holds   1 = drift or a hard stop   3 = could not run

  answer. **NOT a drift finding.** It prints `THIS IS *NOT* A DRIFT FINDING` and
  `Nothing about the preset has been checked, in either direction.` Never record an exit 3 as a FAIL of

### WHAT ACTUALLY HAPPENED — three findings from the 2026-08-27 run

*The expectation above was written before the run. This section is what the run produced. They are kept
apart on purpose: the section above is what we thought the `f_` row could do, this one is what it did.*

*Within each finding, the **measurements** come first and the **conclusion drawn from them** is marked
as a conclusion. A number and an inference are not the same kind of thing and this record does not blur
them.*

#### Finding 1 — `f_auto` is APPLIED but NOT PERSISTED. The verifier's row was a false alarm.

**The measurement that raised it.** `GET /upload_presets/fitout_listing_v1` returns a transformation
object with **four** keys — `width`, `height`, `quality`, `crop`. The declaration has **five**
components. `fetch_format` is absent. It is not present under a different long key: the fifth component
is simply not in the returned object, and the unrecognised-key hard stop stayed silent because there was
no extra key to be unrecognised.

**Why a rename could not be assumed away.** `presetDrift` cannot tell "the vendor dropped a key it still
honours" from "the transformation you think you applied was never applied". Those two have identical
GET output and opposite security consequences — the second one means every HEIC upload is stored as
`heic` and F-2 is silently false on all eight render sites. So the row was resolved by **experiment
against the account**, not by reading the absence charitably.

**The experiment.** Six probe uploads to `fitout/_probe_16_1`. Source for A–D: a generated **900×700
random-noise PNG, 174,117 B** — chosen because PNG stores noise badly and JPEG stores it well, so a
format optimiser has an unambiguous incentive to convert. E and F use a **real HEIC** (`200 image/heic`,
**448,047 B**, magic `ftypheic`), synthesised from the account's own probe asset via a `format: "heic"`
delivery URL — nothing was fetched from an untrusted source.

| Probe | Upload configuration | Stored `format` | dims | bytes |
|---|---|---|---|---|
| A | noise PNG through `upload_preset=fitout_listing_v1` | `png` | 900×700 | 2,613,840 |
| B | noise PNG, inline `raw_transformation: "c_limit,w_2048,h_2048,q_auto,f_auto"` | `png` | 900×700 | 2,613,840 |
| C | noise PNG, inline structured `[{crop,width,height,quality,fetch_format:"auto"}]` | `png` | 900×700 | 2,613,840 |
| D | noise PNG, inline `raw_transformation: "f_auto"` alone | `png` | 900×700 | 2,613,840 |
| **E** | **real HEIC** through `upload_preset=fitout_listing_v1` | **`png`** | 900×700 | 2,512,665 |
| **F** | **same HEIC**, NO transformation at all (control) | **`heic`** | 900×700 | 448,047 |

**All six probe assets were DESTROYED afterwards** — `destroy -> ok` ×6, and
`remaining under fitout/_probe_16_1: 0`. The account carries no residue from this experiment.

**CONCLUSION (an inference from E vs F, not a measurement).** E and F are the same bytes through the
same endpoint, differing only in whether the preset's transformation was applied. E stores `png`; the
untransformed control F stores `heic`. **Therefore the preset's transformation IS applied at upload and
DOES convert HEIC away from HEIC.** F-2 is in force. `transformation.fetch_format` missing from the GET
is a **verifier-only false alarm**: Cloudinary normalises `f_auto` out of the persisted preset
representation while still honouring it.

**The fix, and why it is not "relaxing the check".** The declared→account comparison stops treating the
**absence** of `fetch_format` as drift; a **present-but-wrong** `fetch_format` is still drift, and the
key stays in `KNOWN_LONG_KEYS` so it can never be reported as unrecognised. The canonicaliser still
parses `f_auto` — nothing about the declaration changed. The reason is stated in
`scripts/cloudinary-preset.ts` beside the code so that a later reader who sees a check that looks
missing finds the E-vs-F evidence instead of "restoring" it.

**What the fix costs, said out loud:** the verifier no longer proves that the format conversion is
present on the preset — because the vendor gives it no way to. What proves it is Check 4 (a real HEIC
uploads AND renders), which is a **product** check, on a **human's** screen. That is a weaker mechanism
than a scripted diff and it is recorded as such.

#### Finding 2 — `upload-policy.ts` states a measurement that does not reproduce.

**The claim, at `src/lib/listing/upload-policy.ts:176-178` before this run:** `f_auto` *"turns HEIC into
jpg, picks jpg for photographic input, preserves alpha on a transparent PNG … and never once chose webp
or avif"*, recorded as measured across five inputs on 2026-08-26.

**What today measured:** probe E turned HEIC into **`png`**, not `jpg`. Probes A–D show `f_auto` did not
change a PNG's format at all — including probe D, where `f_auto` was the *only* component.

**And the storage-economy consequence, in a phase named for storage economy:** the HEIC went in at
**448,047 B** and was stored at **2,512,665 B**. A **5.6× INFLATION**, on the exact input class D-184
and F-2 exist to handle.

**CONCLUSION.** The docblock's specific format predictions are false as written. `f_auto` is still
load-bearing — E vs F proves it does the one thing F-2 needs, which is to move HEIC off HEIC — but *what
it moves it to* is not what the docblock promises, and the byte direction is the opposite of what a
reader would infer. The docblock is corrected to today's measurement. 16.1-06's whole thesis was that a
comment describing something untrue is worse than no comment; leaving this one would have repudiated
that plan in the same phase that shipped it.

#### Finding 3 — an exit-code defect in `scripts/cloudinary-preset.ts` (now fixed).

**The measurement.** On the **404 branch only**, the script exits **127** instead of its documented `1`:

```
Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c, line 76
```

Confirmed twice via `npx tsx scripts/cloudinary-preset.ts --verify` directly (`RAW_EXIT=127`), on Node
**v24.13.0**, Windows. The `--apply` and post-apply `--verify` runs both exited a clean `1`. **The
verdict TEXT was correct on every run**; only the process exit status was clobbered.

**Why that branch and not the others.** The 404 branch `return`s from `runVerify` *before* the
account-wide scan, so exactly one undici socket is still closing when `process.exit()` fires
synchronously. libuv asserts on a handle closed twice and aborts the process; the shell reports 127,
which conventionally means *command not found*.

**Why it matters more here than in a normal script.** The entire purpose of this tool is a
machine-readable exit-code contract — `0` holds, `1` drift-or-hard-stop, `3` could-not-run. An exit code
the tool never emits on purpose, on the branch that fires when the security control is **missing**, is a
contract defect. **Fixed** by setting `process.exitCode` and letting the event loop drain instead of
calling `process.exit()` synchronously after a `fetch`.
