## Summary

Phase 16.1's load-bearing deliverable — an incoming transformation the client cannot influence — is
reachable, and the constraint that made it look hard (`ALLOWED_SIGN_KEYS`) turns out to be the thing
that makes it *safe*. Cloudinary verifies the signature against **exactly** the parameter set it
receives: a client that drops a signed parameter gets `401 Invalid Signature`, and a client that
substitutes one gets the same. So any parameter our server insists on signing is a parameter the
client is forced to send, verbatim. The server therefore does not need to *add* a parameter the
widget does not send — it needs to *refuse to mint a signature at all* unless the widget's own
parameter set already carries the one we require.

The Upload Widget sends exactly one parameter that can carry an incoming transformation:
`upload_preset`. I measured this in a real browser — with `uploadPreset` set, `paramsToSign` is
`{timestamp, folder, upload_preset, source}`; with `transformation` or `allowed_formats` set in the
widget options instead, both are dropped and `paramsToSign` is the unchanged
`{timestamp, folder, source}`. So the mechanism is: **the widget names a preset, the sign route
refuses to sign unless that name is byte-equal to a repo constant, and the preset carries the
incoming transformation and the format allow-list.** The preset's *name* is repo-pinned and
test-pinned; its *contents* are dashboard state, which is the honest cost and the subject of § R-1.6.

Everything else in the phase was measured rather than assumed. An untransformed original is
delivered from `res.cloudinary.com` **byte-identical, GPS IFD intact** — D-189's leak is live today.
The incoming transformation removes every EXIF tag *and* bakes the orientation in first, matching
`ImageOps.exif_transpose` pixel-for-pixel, with no `a_ignore` or explicit rotate needed. The
account's plan is **Free** and its hard image ceiling is **exactly 10,485,760 bytes (10 MiB)** — so
D-180's "10 MB" is true if and only if it is spelled `10 * 1024 * 1024`, with zero headroom. HEIC
ingests but must be converted. An animated GIF survives the transformation multi-frame *and gets
bigger*; an SVG survives it as an SVG — so neither is closed by the transformation, and both are
closed cleanly by `allowed_formats` instead.

**Primary recommendation:** one directive-free `upload-policy.ts` declaring the preset name, the byte
ceiling, the format list and the transformation string; a signed, Admin-API-reconciled upload preset
carrying that transformation and that format list; `ALLOWED_SIGN_KEYS` widened by exactly one key
(`upload_preset`) behind an **equality gate**, never an allow-list entry; path 5b closed; and
`transformation` kept permanently OUT of the signed set — because a client-supplied transformation
*chains after* the preset's and can upscale straight back past the 2048 ceiling (measured: 4000×6000).

**The size ceiling**

- **D-180 — FitOut declares 10 MB for a listing photo.** Chosen to make an EXISTING sentence true

- **D-183 — Two ceilings stand: 5 MB avatar, 10 MB listing. `AVATAR_MAX_BYTES` is NOT touched.**
  `AVATAR_TOO_LARGE_MESSAGE` is pinned by 16-UI-SPEC and stays byte-unchanged.

    ⚠ Planner must verify HEIC ingest against the live account before pinning it in copy.

- **D-186 — One sentence per refusal reason, matching the avatar path.** Too-big, wrong-format and

  Today all three funnel into one generic toast at `photo-uploader.tsx:184-188`.
  Constraints: **rule F2 — two copies of a string are two strings.** Each sentence gets exactly one
  home in a directive-free module. The format sentence names what IS accepted rather than what was
  refused. → **The three reasons ARE distinguishable, but only by matching vendor English. See § I-2.**

**Orphaned and valueless assets**

- **D-187 — Close the SOURCES of new orphans. No sweep, no reaper, no Cloudinary Admin API.**
  The true orphan — bytes on Cloudinary with no DB row — has one reachable source, and it is
  bug-shaped: the upload succeeds at Cloudinary, then `persistPhoto` refuses (18 of 20 refused at the

## R-1 (BLOCKING) — How does an incoming transformation reach the upload without the client being able to omit it?

### R-1.1 The answer in one paragraph

Cloudinary validates an upload signature against **exactly the parameter set it receives**. If the
server signed a parameter the client did not send, or the client sent a different value for one the
server signed, Cloudinary answers `401 Invalid Signature` and echoes the string it computed over. So
the direction of the problem is inverted from how CONTEXT.md frames it: the server does not need to
ADD a parameter to the client's request — it needs to **refuse to mint a signature at all** unless
the client's own parameter set already carries the one we require. Any parameter our route insists on
is therefore forced, verbatim, into the upload. `ALLOWED_SIGN_KEYS` is not the obstacle; converted
from a permissive allow-list into a **required-key equality gate**, it is the enforcement point.

The remaining question is purely mechanical: *which* parameter can carry an incoming transformation
AND actually be emitted by `<CldUploadWidget>`. Measured answer: **only `upload_preset`.**

### R-1.3 The two candidate mechanisms, evaluated as CONTEXT.md asks

#### Candidate T — a narrow server-fixed extension to the allow-list (`transformation` / `allowed_formats`)

| Question CONTEXT.md asks | Answer |
|---|---|
| Does Cloudinary apply it to a signed browser upload? | **Yes** (E1). It is an *incoming* transformation — the stored asset is rewritten and the original is not retained. |
| Can a caller who posts directly to `/api/cloudinary/sign` then to Cloudinary omit or override it? | **No**, provided the route requires it. Omit → 401 (E2). Override → 401 (E3). And the route must refuse to sign a set *lacking* it, or the caller simply asks for a signature over `{folder, source, timestamp}` and uploads unbounded. |
| What must change in `sign/route.ts`? | `ALLOWED_SIGN_KEYS` becomes a *required* set; `transformation` and `allowed_formats` compared with `===` against repo constants. |
| Does it widen the signed surface abusably? | Only if implemented as an allow-list rather than an equality gate — see E11. |
| Incoming or eager? | **Incoming** (`transformation`). `eager` would derive an extra asset and **leave the original stored**, which fails criteria 3 and 5 outright and would additionally produce a derived URL carrying transformation components that `isOwnCloudinaryAsset` **rejects** by design (`cloudinary-provenance.ts:162-200`). Do not use `eager`. |
| Survives the no-ambient-configuration preference? | **Perfectly.** Every value lives in repo source and is unit-testable in CI with no credential. |
| **Reachable through `<CldUploadWidget>`?** | **NO — measured E6.** The widget drops both parameters. |

**Verdict: correct in every respect except the only one that matters — it cannot be built without
replacing the widget.** Replacing `<CldUploadWidget>` with a hand-rolled `fetch` uploader would also
forfeit `maxFileSize`, `clientAllowedFormats`, `sources`, the multi-file queue and the entire UI that
D-180/D-184/D-185/D-186 are all expressed as options on. That is a rewrite of the host photo surface
inside a phase whose ROADMAP entry says `UI hint: no`. **Raise it as a scope alarm, do not absorb it.**

#### Candidate U — a named Cloudinary upload preset (RECOMMENDED)

| Question CONTEXT.md asks | Answer |
|---|---|
| Does Cloudinary apply it to a signed browser upload? | **Yes** (E8). Signed presets support all upload parameters, including an incoming `transformation` and `allowed_formats`. |
| Can a caller omit or override it? | **Cannot omit** — `upload_preset` is signed, so dropping it is a 401 (E10). **Cannot substitute** — the route compares the name to a repo constant and 400s before signing. **Cannot defeat the ceiling** — *provided* `transformation` stays out of `ALLOWED_SIGN_KEYS` (E11). |
| What must change in `sign/route.ts`? | `ALLOWED_SIGN_KEYS` gains **exactly** `"upload_preset"`, plus a new **required-and-equal** check on its value. Path 5b must also sign it (F-1). |
| Does it widen the signed surface abusably? | No. One extra key, whose only legal value is a compile-time constant. Every other key still 400s. |
| Incoming or eager? | **Incoming** — the preset's `transformation` setting is the incoming transformation (E8/E12 show it stored as `settings.transformation`). Do not set `eager` on the preset. |

#### Candidate D — Cloudinary's account-level *default* signed upload preset

Cloudinary lets you nominate a signed preset as the account default for images, applied *"whenever no
other upload preset is specified directly in an upload call"* [CITED: cloudinary.com/documentation/upload_presets].
This would apply the transformation with **no** code change at all and nothing for a client to omit.

**Rejected.** It is 100% ambient — not even the *name* appears in the repo, so the mechanism would be
invisible to `grep`, to every test, and to the next reader of `photo-uploader.tsx`. It is strictly
worse than Candidate U on the one axis the project already decided. Recorded so it is not
rediscovered as a clever shortcut.

### R-1.4 The recommended shape

### R-1.5 What does NOT change — criterion 3's "no delivery URL changes"

Measured across every probe: when an incoming transformation runs, the returned `secure_url` is a
**plain** delivery URL with no transformation components —
`https://res.cloudinary.com/<cloud>/image/upload/v<digits>/<folder>/<id>.<ext>`. The transformation
is baked into the stored bytes, not into the address.

Consequences, all verified against the shipped code rather than assumed:

- **`isOwnCloudinaryAsset` keeps accepting it.** The anchored pattern it requires
  (`/[v<digits>/]<publicId>[.<ext>]`, nothing else — `cloudinary-provenance.ts:170`) is exactly what
  the transformed upload returns. **No change to D-165 is needed or wanted.**
- **The extension may change** (`f_auto` can store `.png` where the source was `.jpg`, and does store
  `.jpg` for a `.heic` source). The provenance module already documents that it deliberately does not
  require the url and the `publicId` to agree about the extension
  (`cloudinary-provenance.ts:22-23`). **That accepted residual is now load-bearing** — say so in the
  plan so nobody "tightens" it later and breaks the pipeline.
- **The eight render sites are untouched.** They read `photo.url` verbatim; the URL shape is
  unchanged. Confirm, do not edit.
- **`eager` would break all of this** — the derived URL carries transformation components and
  `isOwnCloudinaryAsset` rejects it (it rejects even a benign `f_auto,q_auto`, per its own test at
  `tests/listing/cloudinary-provenance.test.ts:216`). One more reason `eager` is the wrong tool.

## R-2 — EXIF / GPS, end to end

Probed live on 2026-08-26 with a purpose-built fixture: a 3000×2000 JPEG carrying `Orientation = 6`
(rotate 90° CW), `Make`/`Model`, and a full GPS IFD (`GPSLatitudeRef N`, `14° 33′ 0″`,
`GPSLongitudeRef E`, `121° 1′ 0″`, `GPSAltitude 42`). Marker blocks were placed so orientation is
readable from pixels: red at the raster's top-left, white at its bottom-right.

### R-2.1 (a) Does an UNtransformed original retain EXIF GPS on delivery? — **YES. The leak is live.**

| | source file | delivered from `res.cloudinary.com` |
|---|---|---|
| bytes | 96,002 | **96,002** (byte-identical) |
| `Content-Type` | — | `image/jpeg` |
| EXIF | `{Make: FitOutProbe, Model: R2Probe, Orientation: 6, GPSInfo: …}` | **identical** |
| GPS IFD | `{Ref:N, 14°33′0″, Ref:E, 121°1′0″, Alt:42}` | **identical** |

Cloudinary stores and serves the original untouched when no incoming transformation runs. So today —
before this phase — a host photographing their home gym publishes their **exact** coordinates to
anyone who downloads the file, while `publicListing()` is busy rounding the listing's own coordinates
to 2 decimal places (`listing-public.ts:97`, `Math.round(value * 100) / 100`) and `listing-map.tsx`
draws a 600 m fuzz circle (`FUZZ_RADIUS_M = 600`). **D-189's premise is confirmed by measurement, not
by argument.**

### R-2.2 (b) Does the transformation remove it while preserving orientation? — **YES, and the orientation trap does not bite**

Uploaded the same fixture with `transformation=c_limit,w_2048,h_2048,q_auto`:

```
stored: 1365x2048, 11,892 bytes    (source 3000x2000, 96,002 bytes)
EXIF:   {}          GPS: {}
```

Corner sampling at 5%/95%, against the reference produced by `PIL.ImageOps.exif_transpose` — i.e.
what a correct viewer shows:

| | TL | TR | BL | BR |
|---|---|---|---|---|
| raw source (orientation NOT applied) | **red** | blue | blue | white |
| `exif_transpose` reference (2000×3000) | blue | **red** | white | blue |
| **Cloudinary output (1365×2048)** | blue | **red** | white | blue |

**Exact match.** Cloudinary applies the EXIF orientation *before* re-encoding and *before* the
metadata is dropped. No `a_ignore`, no `angle`, no explicit rotate parameter is needed — and none
should be added. A second, independent confirmation using the repo's **own committed fixture**:
`e2e/fixtures/exif-orientation-6.jpg` (480×320, `Orientation: 6`) came back **320×480**.

Two further measurements the planner needs:

- **Stripping does not depend on a resize.** An 800×600 GPS-tagged JPEG — well under the 2048 cap, so
  `c_limit` changes no dimension — came back `600×800`, `exif={}`, `gps={}`. The re-encode is what
  strips, not the scaling. Every accepted upload is covered, not just the big ones.
- **The saving is real.** A 10.23 MB / 3400×2270 photographic input stored as **1.61 MB / 2048×1367**
  — a 6.3× reduction, and D-182's bandwidth argument multiplies that by every booker on every page view.

**Could this be verified from the repo alone? No** — CONTEXT.md is right that the seeded fixtures are
Unsplash URLs. It was verified by live probe instead, which is stronger. The plan should still carry a
**UAT step** re-walking it through the real widget after the preset is applied, because everything
above went through the upload API directly; what remains unproven end-to-end is that
`<CldUploadWidget>` → our sign route → Cloudinary produces the same result in a browser.

## R-3 — The two vendor facts D-180 and D-184 rest on

### R-3.1 Does the account's plan accept 10 MB image uploads? — **EXACTLY, with zero headroom**

`GET /v1_1/<cloud>/usage` → `{"plan": "Free", "credits": {"usage": 0.23, "limit": 25}}`.

Boundary probed with three real files:

| file | bytes | MiB | MB | result |
|---|---|---|---|---|
| `s09_9.jpg` | 9,309,245 | 8.88 | 9.31 | `200` → stored 2048×1367, 1,612,234 B |
| `s10_6.jpg` | 10,225,256 | 9.75 | 10.23 | `200` → stored 2048×1367, 1,610,482 B |
| `c.jpg` | 10,797,728 | 10.30 | 10.80 | **`400 "File size too large. Got 10797728. Maximum is 10485760."`** |

**The ceiling is 10,485,760 bytes = 10 × 1024 × 1024 = 10 MiB.**

Therefore:

- **`maxFileSize` MUST be `10 * 1024 * 1024`.** Spelled `10_000_000`, the widget would refuse files
  between 10,000,000 and 10,485,760 that Cloudinary would have taken — merely conservative, not a lie,
  but it makes the declared limit and the enforced limit two different numbers, which is precisely the
  defect D-180 exists to end.
- **There is no headroom whatsoever.** 10,485,761 bytes is refused by the vendor. A declared limit
  even slightly above 10 MiB reproduces U1's defect in the opposite direction.
- The plan is **Free**. An upgrade only raises the vendor ceiling, leaving our declared 10 MB
  conservative and still true. Nothing below Free exists. So the copy is safe against plan movement.
- ⚠ Because the two numbers are now *equal*, a file of exactly 10,485,760 bytes passes both. Make sure
  the comparison in copy and in `maxFileSize` is "10 MB or smaller", matching
  `AVATAR_TOO_LARGE_MESSAGE`'s existing "5 MB or smaller" phrasing.

### R-3.2 Does HEIC/HEIF ingest work? — **YES, but D-184 is unsafe without a format conversion (F-2)**

Uploaded a real HEIC (`nokiatech/heif_conformance/C003.heic`, 224,452 B, 1280×720):

| transformation | HTTP | stored `format` | delivered `Content-Type` | renders in Chrome/Firefox? |
|---|---|---|---|---|
| *(none)* | `200` | **`heic`** | **`image/heic`** | ❌ **No** |
| `c_limit,w_2048,h_2048,q_auto` (preset) | `200` | **`heic`** | **`image/heic`** | ❌ **No** |
| `…,f_jpg` | `200` | `jpg` (116,735 B) | `image/jpeg` | ✅ |
| `…,f_auto` | `200` | `jpg` (116,735 B) | `image/jpeg` | ✅ |

So ingest is not the risk — **delivery** is. D-184's reasoning (*"since the transformation re-encodes
anyway, accepting it costs nothing"*) is true only if the transformation carries a format conversion.
Without one, a host with *Keep Originals* on uploads a perfectly good photo, `persistPhoto` accepts it,
and every booker sees a broken image icon on the public listing.

This does **not** re-open D-184 or D-182 — D-182 already delegates the exact spelling to the planner
and names `format: auto` as an option. It converts that delegation into a **requirement**.

**`f_auto` at upload time, measured across five inputs** (there is no `Accept` header at upload, so
Cloudinary chooses purely on content):

| input | chosen format |
|---|---|
| noisy 10 MB photographic JPEG | `jpg` |
| `panorama-4000x500.jpg` (flat synthetic) | `png` |
| `portrait-strip-500x4000.jpg` (flat synthetic) | `png` |
| `exif-orientation-6.jpg` (flat synthetic) | `png` |
| HEIC | `jpg` |
| PNG with a fully transparent quadrant | `png`, **alpha preserved** |

Never `webp`, never `avif`, in any probe. Every output is universally renderable.

**Recommend `f_auto`.** It satisfies D-182 literally, converts HEIC, and preserves transparency.
`f_jpg` is the zero-variance alternative — deterministic and universally renderable — but it flattens
alpha, measured onto **white** (a fully transparent pixel came back `(255,255,255)`). For photographs
of gyms and courts that is harmless; it is recorded so the choice is informed rather than accidental.

## R-4 — Re-encode semantics for the inputs D-184 refuses

The question CONTEXT.md asks is *"so the client allow-list and the transformation cannot disagree
about what happens to an input that slips past one of them."* The measured answer is that they **do**
disagree — and `allowed_formats` is what resolves it.

### R-4.1 Animated GIF

| probe | result |
|---|---|
| upload with no transformation | `format: gif`, `pages: 3`, **1,887 B** |
| upload with `c_limit,w_2048,h_2048,q_auto` | `format: gif`, **`pages: 3`**, **2,634 B** — *bigger* |
| upload with `…,f_auto` | `format: gif`, `pages: 3`, 2,634 B — *f_auto does not flatten it* |
| upload with `…,f_jpg` | `format: jpg`, no `pages`, 730 B — *flattened to frame 1* |
| upload with signed `allowed_formats=jpg,jpeg,png,webp,heic,heif` | **`400 "Image file format gif not allowed"`** |

**The transformation is not a backstop for GIF.** It preserves every frame and, exactly as D-184
predicted, made the file **40% larger**. Only `f_jpg` flattens it, and only `allowed_formats` refuses
it. Since D-184's allow-list contains no GIF at all — still or animated — `allowed_formats` is a clean
match: it refuses both, with no semantic gap to reason about.

### R-4.2 SVG

| probe | result |
|---|---|
| upload with no transformation | stored `format: svg`, served `Content-Type: image/svg+xml` |
| upload with `c_limit,w_2048,h_2048,q_auto` | **still `format: svg`**, 115 B → 110 B (an SVGO-style pass rewrote `<rect>` to `<path>`) — **not rasterised** |
| upload with `…,f_jpg` | `format: jpg`, 300×200 — rasterised |
| upload with `…,f_auto` | `format: png`, 300×200 — rasterised |
| **upload of an SVG carrying `onload="alert(1)"`, `<script>alert(2)</script>` and `href="javascript:alert(3)"`, no transformation** | `200` — **stored and delivered VERBATIM, script and handlers intact**, from `res.cloudinary.com` as `image/svg+xml` |
| same, **with** `c_limit,w_2048,h_2048,q_auto` | **`500 "General Error"`** — Cloudinary's SVG pass choked; nothing was stored |
| upload with signed `allowed_formats=…` (with or without a transformation) | **`400 "Raw file format svg not allowed"`** |

Two things follow:

1. **The incoming transformation does NOT close SVG.** With `f_auto` it rasterises (so a *slipped-past*
   SVG would at least become a PNG), but with no format conversion it stores an SVG. So SVG safety
   depends on which spelling is chosen — one more argument for including `f_auto`.
2. **D-184's honest note is confirmed and slightly sharpened.** An SVG on our cloud today really does
   retain its `<script>`, and it really is served from `res.cloudinary.com` — a different origin from
   FitOut, and inert inside an `<img src>`. It is not inert if the URL is opened directly, which is a
   thing a `Copy image address` away. Low risk, cheap to close, and `allowed_formats` closes it at the
   boundary rather than at the widget.

### R-4.3 The resolution

Put the format gate on **both** sides of the boundary, from **one** array:

- `clientAllowedFormats: [...LISTING_ALLOWED_FORMATS]` — the fast local refusal a host actually sees.
- `allowed_formats` inside the preset — the boundary. Un-omittable (E10 mechanics), un-substitutable
  (the equality gate on the preset name), and it answers `400` with a Cloudinary-authored reason.

They cannot disagree, because they are the same array.

### I-2 How the widget surfaces each refusal — D-186's three reasons, measured

`onError` is typed `(error: CloudinaryUploadWidgetError, widget) => void` where
`CloudinaryUploadWidgetError = { status: string; statusText: string } | string | null`. Measured in a
real browser by feeding files into the widget's own cross-origin iframe:

| Reason | `error` object actually delivered |
|---|---|
| **too big** (`maxFileSize: 1000`, 96 KB JPEG) | `{ status: "File size (93.75 KB) exceeds maximum allowed (1000 Bytes)", statusText: <same> }` |
| **wrong format** (`clientAllowedFormats: ["jpg","png","webp"]`, an SVG) | `{ status: "File format not allowed", statusText: <same> }` |
| **upload failed** (bad signature) | `{ status: "Invalid Signature deadbeef. String to sign - '…'", statusText: <same> }` |

**So the three reasons ARE distinguishable — but only by matching vendor English.** There is no error
code, no enum, no discriminant field. The planner needs to know this before writing copy:

- The discriminator must be a small pure function over `error` handling all three of the union's
  shapes (object / bare string / `null`), matching e.g. `/exceeds maximum allowed/i` → too-big,
  `/format not allowed/i` → wrong-format, everything else → upload-failed. Put it in the same
  directive-free module as the sentences and unit-test it against the three strings above, quoted as
  fixtures. **When the vendor changes its wording, the fallback is `upload-failed`** — a true-ish
  sentence, not a wrong one. Say that in the comment.
- The widget's `language` / `text` options can localise its own strings, which would break the match.
  Neither is set today; a source-assertion that they stay unset is a cheap guard.
- ⚠ **The widget renders its own error inside its iframe as well.** The host therefore sees Cloudinary's
  English sentence *and* our toast. D-186's sentences are a second surface, not the only one. Worth a
  UAT observation and possibly a line in the plan about whether the double message is acceptable.
- Measured sequencing: for both client-side refusals the widget **still requests a signature** from our
  endpoint (consuming one of the 30-per-60s budget) but makes **no** POST to `api.cloudinary.com`. So a
  refused file never reaches Cloudinary, and never reaches `persistPhoto`.

### I-3 D-192 — `overwrite: true` + `public_id: userId` does NOT make repeat runs idempotent, and "orphan" is the wrong word

**Answer to the question CONTEXT.md asks first: no, and pinning the test user is not the cheap fix.**

`e2e/helpers/avatar-session.ts:56` mints a **fresh randomised account every single run**:

the user is *expensive*, not cheap: the helper deliberately drives the real signup form with **no seed
and no DB fixture** (its header argues that at length), and a fixed email fails signup on the second
run against the unique constraint. Pinning would mean introducing a seeded user or a login path —
a bigger change than teardown, against a file that explicitly refuses fixtures.

**Measured on the live account and the live DB, 2026-08-26:**

| | count |
|---|---|
| assets under `fitout/avatars` | **28** |

### Pattern 1 — The equality gate, not the allow-list

**What:** for a parameter that must be *present and exactly one value*, an allow-list is the wrong
tool. An allow-list answers "may this key be signed?"; the question here is "will I sign anything at
all without it?"

**When to use:** any signed-upload parameter that carries a security property.

```ts
// WRONG — this is what makes the transformation omittable. A caller posting {folder,source,timestamp}
// still gets a signature, and uploads with no preset at all.
const ALLOWED_SIGN_KEYS = new Set(["folder", "source", "timestamp", "upload_preset"]);
const extraKey = Object.keys(paramsToSign).find((k) => !ALLOWED_SIGN_KEYS.has(k));
if (extraKey) return new Response("…", { status: 400 });

// RIGHT — the key is required AND its value is ours. No signature exists for any other request.
if (extraKey) return new Response("…", { status: 400 });
if (paramsToSign.upload_preset !== LISTING_UPLOAD_PRESET) {
  return new Response("Bad Request — upload preset out of scope", { status: 400 });
}
```

### Pattern 2 — One array, two sides of the boundary

**What:** the client hint and the server gate read the same exported constant, so "the picker offers
what the server refuses" is not expressible. This is the shipped `AVATAR_ALLOWED_TYPES` pattern
(`src/lib/avatar.ts:64`, imported by `validation/profile.ts:23`) applied to listing uploads.

**When to use:** every format/size list in this phase.

### Pattern 3 — Declared config + reconciler + drift check

**What:** when a value must live outside the repo, do not let the repo be silent about it. Declare it
in source, apply it with a committed script, verify it with the same script, and name the residual
window in prose. § R-1.6.

### Anti-patterns to avoid

- **`eager` instead of `transformation`.** Derives an extra asset and leaves the original stored —
  fails criteria 3 and 5, and the derived URL is rejected by `isOwnCloudinaryAsset` by design.
- **Admitting `transformation` to `ALLOWED_SIGN_KEYS` "for flexibility".** Measured: it chains after
  the preset's and upscaled a 2048-capped asset to 4000×6000.
- **A server-side check of `info.bytes`.** D-181 forbids it explicitly; it is client-supplied.
- **A destroy anywhere above `isOwnCloudinaryAsset`.** D-187's not-optional constraint; it would be a
  destructive IDOR.
- **Leaving path 5b as-is.** F-1.
- **Re-encoding "just the big ones".** The strip is a property of the re-encode, and `c_limit` on a
  small image still re-encodes — so every accepted upload is covered. Do not add a size condition.
- **Adding `a_ignore` / an explicit rotate to "fix" orientation.** Measured unnecessary; it would be a
  second, contradictory opinion about rotation.
- **Quoting the CDN-invalidation option token in a new comment inside `src/lib/cloudinary.ts`.** Plan
  16-12 counts its occurrences there (`cloudinary.ts:125-128`).

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---|---|---|---|
| Bounding stored pixels/bytes | A server-side resize (Sharp, canvas, a worker) | Cloudinary **incoming transformation** | The bytes never transit our server by design (D-04). Adding a decoder would also void D-191, whose whole argument is *"FitOut has no decoder."* |
| Stripping EXIF/GPS | An EXIF parser + rewriter | The same re-encode | Measured: it drops every tag and gets orientation right. A hand-rolled stripper is where the D-189 orientation trap actually lives. |
| Normalising rotation | Reading `Orientation` and rotating | The same re-encode | Measured pixel-identical to `exif_transpose`. |
| Refusing SVG / GIF at the boundary | A magic-byte sniffer in a server action | Preset `allowed_formats` | The bytes are not ours to sniff; Cloudinary already decoded the file and answers `400` with a reason. |
| Refusing oversized files at the boundary | Anything | Cloudinary's plan limit + widget `maxFileSize` | `400 "File size too large. Got X. Maximum is 10485760."` — the vendor already does it, exactly. |
| Finding orphans | An Admin-API diff sweep | Nothing — D-187 declines it | Measured: 3 true orphans, 0.15 MiB. Not worth an irreversible diff-driven delete. |
| Deleting an asset | A raw `fetch` to `/image/destroy` | `destroyListingPhoto` / `destroyAvatar` | Both exist, both set CDN invalidation. **New callers, not new helpers.** |
| A signature helper | A new signer | `signUploadParams` | Already signs an arbitrary exact param set — it needs no change for the extra key. |

**Key insight:** in this domain every "custom solution" requires putting a decoder on our server, and
this architecture's entire safety argument (D-04, D-181, D-191) is that there is not one.

## Common Pitfalls

### Pitfall 1 — Widening the allow-list instead of gating the value
**What goes wrong:** `upload_preset` is added to `ALLOWED_SIGN_KEYS` and nothing else. A caller posts
`paramsToSign = {folder, source, timestamp}`, gets a perfectly valid signature, and uploads unbounded.
**Why:** the allow-list answers "may this be signed", not "must this be present".
**Avoid:** the equality gate in Pattern 1.
**Warning sign:** a diff that touches only the `Set` literal.

### Pitfall 2 — Path 5b left behind
**What goes wrong:** 5a is hardened; 5b still mints `{signature, timestamp, apiKey, cloudName, folder}`
for any signed-in owner and criterion 3 is false.
**Avoid:** sign the preset in 5b too, or delete 5b. It has no production consumer.
**Warning sign:** `tests/listing/cloudinary-sign.test.ts` still green with no 5b change — its existing
cases assert the *old* 2-key signed set at `:126`, so it will need updating either way.

### Pitfall 3 — `eager` mistaken for `transformation`
**What goes wrong:** the original stays stored at full size with full EXIF; criteria 3 and 5 both fail
while the dashboard shows a nicely-sized derived asset.
**Avoid:** `transformation` only. [CITED: cloudinary.com/documentation/transformations_on_upload]
**Warning sign:** any URL with transformation components in it, or `isOwnCloudinaryAsset` rejecting.

### Pitfall 4 — `10 MB` spelled `10_000_000`
**What goes wrong:** the declared limit and the enforced limit are two different numbers again — U1's
defect, reintroduced by a rounding convention.
**Avoid:** `10 * 1024 * 1024`, with the measured vendor string in the comment.

### Pitfall 5 — HEIC accepted, HEIC delivered
**What goes wrong:** a host uploads a normal iPhone photo, everything reports success, and every
booker on Chrome sees a broken image.
**Avoid:** `f_auto` (or `f_jpg`) in the transformation. F-2.
**Warning sign:** any stored asset whose `format` is `heic`.

### Pitfall 6 — Destroying on the provenance-rejection path
**What goes wrong:** an arbitrary-delete primitive against our own account — another host's cover
photo, or `fitout/avatars/<victim>`.
**Avoid:** D-187's constraint, pinned by the ordering assertion in I-6.
**Warning sign:** `destroyListingPhoto` appearing above line ~137 of `listing-photo.ts`.

### Pitfall 7 — Two copies of the format list
**What goes wrong:** `clientAllowedFormats` and the preset's `allowed_formats` drift; the picker offers
what the boundary refuses, or vice versa.
**Avoid:** one exported array, read by the widget and by the reconciler. Rule F2.

### Pitfall 8 — Trusting the vendor's English forever
**What goes wrong:** Cloudinary rewords "File format not allowed" and D-186's wrong-format sentence
silently becomes the generic one.
**Avoid:** fall back to *upload-failed* (a true-ish sentence), unit-test the matcher against the three
measured strings, and say in the comment that the discriminator is vendor copy.

### Pitfall 9 — Assuming the e2e avatars are orphans
**What goes wrong:** teardown is designed around "delete assets with no DB row" and finds nothing,
because all 28 have rows.
**Avoid:** I-3 — delete the asset via the shipped removal path.

## State of the Art

| Old approach | Current approach | Impact here |
|---|---|---|
| Sign a fixed minimal param set and hope the client behaves | **Sign a required set and refuse to sign otherwise** — Cloudinary's signature check is exact in both directions | The whole of R-1. |
| Strip metadata with a server-side EXIF library | Let the CDN's incoming transformation re-encode | No decoder on our server; D-191 stays closed. |
| Deliver the original and resize at render time | Bound at **ingest** (`c_limit` incoming) *and* leave delivery URLs alone | Satisfies criterion 3 without the pipeline rewrite ruled out twice (999.2 finding 4). |

## Open Questions

1. **Does the double error message bother anyone?**
   - Known: the widget renders its own English error inside its iframe **and** fires `onError`, so the
     host sees the vendor sentence plus D-186's toast.
   - Unclear: whether D-186's sentences should replace the widget's (via the `text` option) or sit
     beside it.
   - Recommendation: ship beside it, observe in UAT, and record the observation. Do not spend the phase
     fighting the widget's chrome — D-179 says the visible surface is error copy, not widget skinning.

2. **Should `maxFiles` be `MAX_PHOTOS − photos.length` instead of a flat 20?**
   - Known: `maxFiles: 20` against `MAX_PHOTOS = 20` is exactly the 18-orphans-from-one-click shape
     D-187 describes.
   - Unclear: nobody decided it. It would *narrow* the window; it does not *close* it (the server count
     can change between render and upload), so it never replaces D-187's destroy.
   - Recommendation: **raise it to the PM as a one-line courtesy**, do not absorb it silently. If
     declined, the destroy alone is correct.

3. **Does the phase want a GPS-bearing e2e fixture?**
   - Known: `e2e/fixtures/exif-orientation-6.jpg` already exists and is byte-gated by
     `tests/design/image-fixtures.test.ts`; it carries orientation but **no GPS**.
   - Unclear: adding one means editing `scripts/generate-image-fixtures.mjs` and its byte gate — real
     work, for a fixture only a credential-holding local run can use.
   - Recommendation: **no new fixture.** Make R-2's GPS proof a **manual UAT step** with a photo from a
     real phone, which is more honest than a synthetic one anyway.

4. **Is `f_auto` or `f_jpg` the right spelling?**
   - Known: both convert HEIC; `f_auto` preserves alpha, `f_jpg` flattens onto white and is
     deterministic.
   - Recommendation: `f_auto`, on the grounds that D-182 names "format chosen by Cloudinary". If the
     planner prefers a deterministic stored extension, `f_jpg` is defensible — record which and why.

5. **Should the existing `removePhoto` destroy also learn the `{result:"not found"}` shape?**
   - Known: `listing-photo.ts:292-296` catches throws only; `avatar.ts:178` handles both.
   - Recommendation: planner's call. It is a log line, not a behaviour change, and D-187 does not ask
     for it. Cheap to include, easy to defer.
