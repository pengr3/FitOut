✅ **HEADCOUNT MODEL RESOLVED (2026-07-27).** The RSVP hard cap and its correctness are settled:

1. **Cap source = the listing's `maxOccupancy`.** It is ALREADY a required publish field (`publishSchema` requires `z.number().int().positive()` — [src/lib/validation/listing.ts:69](src/lib/validation/listing.ts:69)), so every group-bookable (published) listing has a positive capacity. **Q-06's "NULL capacity" premise is factually stale** — the NULL branch is a defensive guard for drafts/legacy rows only, never a product path. `maxOccupancy` has been a *required-but-dormant* field since Phase 2 (collected + displayed, never enforced in booking); **Phase 8 is its first consumer, Phase 9 makes it load-bearing.**

2. **SNAPSHOT the cap onto the group row at group-creation (`capacity_snapshot`).** The RSVP path reads ONLY the snapshot, never live `listing.maxOccupancy`. A host editing capacity down after attendees confirm cannot retroactively over-cap them — the retroactive-overflow bug is **structurally unrepresentable.** Mirrors the D-77 (cancellation tier) / WR-06 (`full_day`) snapshot pattern. Distinct from `declaredPax` (freezes at BOOKING time, drives price); `capacity_snapshot` freezes at GROUP-creation, drives RSVP.

3. **No-overflow (SC#4 "atomic, no overflow") via a `SELECT capacity_snapshot FROM group WHERE id=? FOR UPDATE` seat-claim** inside the RSVP txn — count current 'yes' rows under that lock, insert only if `count < snapshot`, else reject "full". **NOT** an unlocked count-then-insert (the CLAUDE.md anti-pattern); the row lock is the authority, analogous to the GiST exclusion constraint for the exclusive lock. Handles yes↔no toggles uniformly. **PROVEN by a two-connection boundary race test (`makeRacingClients`, like Phase 3 SC#4) = the plan's acceptance gate.** The denormalized-counter alternative is DEFERRED to Phase 9 (higher contention — a shared slot across many independent bookings, where a per-parent lock is too coarse).

4. **Organizer = attendee #1** (counted in cap AND `declaredPax`; pricing `included=1` = organizer's seat in base). Only confirmed 'yes' consumes a seat; 'no'/unanswered consume nothing; a partial RSVP leaves the booking valid (Q-07a/Q-08a/Q-09a).

5. **`declaredPax` vs RSVP:** RSVP-yes exceeding `declaredPax` = a corroboration flag + top-up nudge (a SIGNAL, never a block). This whole machinery only activates when `extraHeadFee > 0`; flat listings (the default) carry none of it — group booking there is just exclusive-lock + RSVP-capped-at-capacity.

**Why cap at capacity, not paid-pax:** RSVP is voluntary and unpaid, so it is NOT the leak-enforcement lever (a freeloader just shows up without RSVPing). Capping at paid-pax buys zero revenue protection and only frustrates honest friends + destroys the corroboration signal. The leak is caught at host check-in + top-up, never at the RSVP gate — so the cap is the loosest thing consistent with physical reality (`maxOccupancy`).

✅ **OCCUPANCY MODEL RESOLVED (2026-07-27) — occupancy type is a first-class HOST-SET, per-listing property; there are THREE modes, and the older "open play = GPAY-02" lump was too coarse.** The three modes add complexity in DIFFERENT subsystems, which is exactly why they belong in different phases:

| Mode | Availability | Payment | Examples | Status |
|---|---|---|---|---|
| **Exclusive** | GiST exclusion constraint (HAVE it) | single-payer (HAVE it) | basketball, exclusive pickleball court, gym/studio buyout | **Phase 8 — THIS phase** |
| **Drop-in / common-use** | capacity-counter (**NEW** — a count-then-insert seat race, the exact anti-pattern the exclusion constraint was built to avoid) | single-payer **per booking** (HAVE it — each visitor books their own head(s)) | common-use / drop-in gym, host-run open court | **its OWN future phase — NOT part of Phase 8** |
| **Open play / cost-split** | GiST exclusion constraint (HAVE it — organizer holds ONE exclusive lock) | multi-payer split (**NEW**) | organizer opens their own booked slot to others | **future GPAY-01, ORGANIZER-driven; builds on Phase 8's RSVP shell** |

**The load-bearing insight:** a drop-in gym is NOT open play. Drop-in stresses **availability** (needs the capacity-counter) but keeps payment simple — each visitor is an independent single-payer booking, no multi-payer, no RSVP, no ticketing money-machine. Open play stresses **payment** (cost-split among attendees) but keeps availability simple (still one exclusive lock). Different subsystems → different builds → different phases. This splits what the older notes called "open play (GPAY-02, breaks the exclusion constraint)" into (a) the **drop-in / host-run capacity-counter** and (b) **organizer-driven cost-split (GPAY-01, which PRESERVES the constraint)**.

**Decisions (2026-07-27):**
1. **Phase 8 stays EXCLUSIVE-ONLY** (unchanged). It records a host-set `occupancy_mode` on the listing, **DEFAULT `exclusive`** — the seam both future modes plug into. Phase 8 only ever writes `exclusive`; a host toggle with a real second option waits for the drop-in phase.
2. **Drop-in / common-use (per-head, host-run, capacity-counter) = its OWN dedicated roadmap phase**, parallel to Phase 8 — NOT folded in. Keeps gyms first-class (not deferred to a vague "paid future") without dragging the count-then-insert seat-claim onto the money path inside Phase 8. **ROADMAP FOLLOW-UP OWED: add this phase via `/gsd-phase`.**
3. **Open play's future = ORGANIZER-driven cost-split (GPAY-01, exclusion-preserving)**, NOT host-driven ticketing → the Phase 8 RSVP schema uses **per-attendee rows** (this answers **Q-18 = option a**: model each attendee/RSVP as its own row, payment-ready but unpriced).

✅ **PHASE 8 PAYMENT MODEL RESOLVED (2026-07-26).** This supersedes BOTH prior framings on record:
- It is **NOT "deferred entirely"** (the 2026-07-25 memory `phase8-deferred-defer-group-bookings` — now refreshed): the group-pricing model that was "unresolved / undesigned" is now designed.
- It is **NOT the "free-RSVP shell"** (the older `.continue-here` framing + `08-QUESTIONS.json` top matter): group size now affects price, so it no longer reads as "free."

**The resolved v1 design (exclusive group bookings):**

1. **Single payer.** The organizer pays for ALL pax — exactly one payment — so it reuses the existing **hold-until-session** rail unchanged (charge → hold on platform wallet → transfer to host minus commission after the session). No cost-splitting, no per-attendee collection, no partial-payment state machine. *This one payment is what makes it buildable* and is why it sidesteps the complexity that got cost-splitting rejected.

2. **Two independent axes** (earlier discussion conflated them):
   - **Pricing unit**: per-space (flat) vs per-head (pax-scaled)
   - **Occupancy**: exclusive (your crew only) vs open (strangers share the slot)

3. **v1 = EXCLUSIVE-ONLY.** A group booking is one exclusive lock on the space → the **GiST exclusion constraint stays untouched**. "Open court / open play" (strangers each buy a slot in one shared session, per head) is a **separate deferred product** = **GPAY-02 ticketing + a capacity-counter availability model** that would *break* the exclusion constraint. Its own future phase — do NOT build in v1.

4. **One unified exclusive pricing formula:**
   ```
   total = baseRate + max(0, pax − included) × extraHeadFee
   ```
   - `extraHeadFee = 0` → flat court rental, **zero leak**, backward-compatible **default** (existing listings behave exactly as today).
   - `included + extraHeadFee` set → group size affects price, leak **bounded** to the surcharge delta.
   - "Per-person" is just the **extreme setting** (`included = 1`, price pushed into the head fee) → **maximum** under-declaration exposure; the host's front desk *is* the enforcement there.
   - This is the **Airbnb extra-guest-fee** shape.

5. **Scope reach (acknowledged, bounded):** reaches into Phase 2 (host sets base + optional `included`/`extraHeadFee`) and Phase 4 (quote applies the formula), but shallow + backward-compatible because `extraHeadFee` defaults to 0.

**Money-leak crux (where we spent the most time):** per-person-exclusive is the **most-exposed cell** — organizer declares pax=1, pays for 1, brings 4 (court is already theirs, no stranger blocked, only the front desk forces honesty). Structural truth: **the leak is proportional to how much price depends on door-counted heads** — per-space = 0, surcharge = bounded, pure per-head = max. per-head-exclusive **cannot be made self-policing without becoming ticketing** (the deferred open-play model). So the leak is a *design choice*, not a patchable bug.

**Leak mitigations settled:** (a) structurally prefer per-space + surcharge; (b) **host check-in headcount confirmation** → creates a discrepancy RECORD (the v1 seam) + enables an in-app **top-up** charge to the organizer's saved card (top-up = fast-follow); (c) the **RSVP shell doubles as fraud corroboration** (RSVP count vs declared pax mismatch = flag) — this is invites' hard job beyond logistics; (d) align host incentives so they don't prefer cash (payout / ranking / dispute protection flow only from on-platform bookings); (e) accept the bounded remainder, priced into commission.

**Refund / no-show:** organizer bought the slots → no per-attendee refund on no-shows; pax-decrease follows the Phase-7 cancellation ladder; pax-increase = a capacity-checked top-up.
