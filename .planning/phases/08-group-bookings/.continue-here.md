<blockers>

🔴 **`confirmBooking` double-charges on a plain double-submit of "Confirm & pay".** BLOCKER-class, live, on the money path.

**Root cause — PayMongo does NOT honor `Idempotency-Key` on `POST /v1/checkout_sessions`.** Probed directly against `sk_test_`, two POSTs with a byte-identical body and key:

```
POST #1: HTTP 200  id=cs_ed60840548c9ccadc27ba6c3
POST #2 (same Idempotency-Key): HTTP 200  id=cs_6c4e54d253178994b94934b8
-> DIFFERENT ids
```

Every POST mints a separate, independently payable session. (`POST /v1/checkout_sessions/{id}/expire` **does** work — HTTP 200 on both probes — so expiry is the only real retirement mechanism.)

**Real consequence, observed:** booking `aff63acb-b6a5-45f7-8b47-6a01d589f765` was charged **twice** — `pay_YFn1jgMWyau46ECydfPR2LdN` (10:00:35Z) and `pay_iw2zsj3ehcRzgRYzgn7hkoUP` (10:08:29Z), ₱735.00 each. **₱1,470 collected against a ₱735 booking**, unrefundable via the API because both are `qrph` (`src/lib/paymongo.ts:257`).

**Scope — NOT a CR-02 regression, and WIDER than CR-02.** No re-price occurred: both charges were ₱735 at `declared_pax = 3`, so both calls built the same key `checkout:<holdId>:73500`. CR-02's expire gate lives in `updateDeclaredPax` and only fires on a re-price; `confirmBooking` expires nothing before creating. **Flat-priced bookings are equally exposed** — their `checkout:<bookingId>` key was believed to be the double-charge guard and is not one. **This predates Phase 8.**

**Downstream effects were contained:** the webhook handler deduped correctly — exactly ONE `booking_confirmed` notification, no duplicated `host_payout_ledger` row. `booking.payment_id` ended up naming the *later* payment because the second event overwrote the first (a lesser but real recording defect).

Logged at: `deferred-items.md` **item 5**, STATE.md Current Position + Blockers/Concerns.
