<objective>
Close `deferred-items.md` item 7 — a revenue-loss path, not polish.

`included` ("Base price covers") and `max_occupancy` are independent fields with no enforced relationship, and `declaredPax` is clamped to `max_occupancy` **before** the surcharge is computed (`src/lib/availability/units.ts:453-455`; `paxSurcharge` in `src/lib/booking/pricing.ts:70-80` then floors `extraHeads = max(0, pax − included)`). So on any listing where `included >= max_occupancy`, `extraHeads` is **always 0** — the host collects nothing extra forever and nothing warns them. This is the shape a host is **most likely** to configure: the operator's own example is a court rated for 8 that should surcharge above 8 → setting `included = 8, max_occupancy = 8` silently yields zero. For the surcharge to ever fire, `max_occupancy` must be **strictly greater** than `included`.

Two changes, both grounded in the existing coalescing defaults (`included ?? 1`, `extraHeadFee ?? 0`):
1. a cross-field `.superRefine` on **publishSchema** (the server-side publish gate, already run by `publishListing`) that rejects `included >= maxOccupancy` **only when `extraHeadFee > 0`** — a flat listing has no surcharge to lose and is deliberately untouched;
2. a line of explanatory copy in the wizard's Group-pricing block so the relationship is visible at configuration time (the two fields live in different wizard steps today, with no cross-reference).

**Independent of the money-path fix** — this plan touches no PayMongo code and shares no files with 08-18/08-19, so it runs in parallel (Wave 10).

Purpose: a host who sets a per-head fee cannot silently publish a listing that can never charge it.
Output: publish rejects an unreachable surcharge; the wizard explains the rule.
</objective>
