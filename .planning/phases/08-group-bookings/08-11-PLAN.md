<objective>
Close **CR-04 (BLOCKER)** — the app's one unauthenticated, publicly reachable write path grows an in-memory `Map` on attacker-chosen keys, without bound and without eviction.

`submitRsvp` shape-checks the invite token (`src/app/actions/group.ts:313-314`) and then charges `rateLimit(\`rsvp:${parsedToken.data}\`, RSVP_RATE_LIMIT)` at `:326` — **before** `getGroupByToken` resolves it at `:333`. `src/lib/rate-limit.ts:29` is a module-level `Map` whose entries are overwritten on a repeat hit but **never deleted**. Every previous caller keyed on an authenticated `userId`, so the key space was bounded by the user table; here it is `32^20` caller-selectable values, each buying a permanent ~150-200 byte entry with no session, no group and no database row behind it. On the container host CLAUDE.md prescribes, that is memory exhaustion against the whole app — and it takes the booking path (the core value) down with it.

Two changes, both small, both verifiable:
1. **Resolve before you budget.** Move the link budget after `getGroupByToken` and key it on the resolved `group.groupId`, so the key space is bounded by real `booking_group` rows. This leaks nothing: unknown, voided and regenerated tokens already collapse onto the identical `INVITE_INACTIVE` sentence (T-08-17).
2. **Bound the store itself**, so no future caller can reintroduce the class.

Purpose: keep the public RSVP surface (GROUP-03) available, which is what "the organizer sees a live headcount" (GROUP-05) depends on.
Output: a bounded limiter, a resolve-then-budget `submitRsvp`, and two tests that fail if either half is removed.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated internet → `submitRsvp` | the app's ONLY session-less server-action write; the invite token is the entire credential |
| caller-supplied string → module-level rate-limit `Map` | an unvalidated key becomes durable process memory |
| `submitRsvp` → `booking_group` token lookup | an unauthenticated request now reaches the database before any budget is charged |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-33 | Denial of Service | `src/lib/rate-limit.ts` module `Map`, via `src/app/actions/group.ts:326` | mitigate | Two independent bounds. (1) The RSVP key is derived from the RESOLVED `group.groupId`, so the key space is `booking_group` rows, not `32^20` caller-selectable tokens — an unknown token mints no bucket at all. (2) The store hard-caps at `RATE_LIMIT_MAX_BUCKETS = 50_000` via expired-sweep plus insertion-order eviction. Both are verified by test, not asserted: `tests/group/rsvp-rate-limit.test.ts` pins a bucket-count delta of 0 across 200 unknown tokens, and `tests/security/rate-limit-bound.test.ts` pins the ceiling under a 60,000-key flood. Both are mutation-checked. |
| T-08-34 | Denial of Service | `getGroupByToken` reached before the budget | accept | Resolving first lets an unauthenticated caller force one indexed unique-index lookup per request, no write, no transaction — the same cost profile as any unauthenticated `/listings/[id]` render the app already serves. The alternative (a global pre-resolution budget) is a strictly worse trade: one shared key on the only public write path is a global availability lever. Revisit with the distributed limiter the `rate-limit.ts` header already flags as the >1-instance hardening. |
| T-08-35 | Information Disclosure | resolve-before-budget ordering on the public path | accept | Unknown, voided and regenerated tokens already return one identical `INVITE_INACTIVE` sentence (T-08-17); resolving before budgeting adds no distinguishable response. If anything it reduces timing variance, because the lookup now happens for every caller rather than only for those under budget. |
| T-08-36 | Denial of Service | eviction of a live bucket under flood | accept | Under sustained pressure a still-live key can lose its window and get a fresh budget. Bounded memory beats an exact budget under attack; documented in the `rate-limit.ts` header so it is a stated tradeoff rather than a surprise. |
| T-08-SC | Tampering | npm/pip/cargo installs | accept | No packages added or upgraded in this plan; a `Map` with insertion-order eviction needs no LRU dependency. |
