<objective>
Close the first half of **CR-02 (BLOCKER)** — a re-priced hold mints a SECOND live, payable PayMongo checkout session and nothing can ever retire it.

`confirmBooking` discards `checkout.id` (`src/app/actions/booking.ts:553`), nothing persists it, and no expire call exists anywhere in the repository. Under D-108's amount-scoped key, the documented round trip — `Confirm & pay` → session A at ₱X → abandon → back on the reserve page via `cancelUrl` → step the headcount → `Confirm & pay` → session B at ₱Y — leaves BOTH sessions payable. The confirm webhook keys purely on `reference_number` with no amount check, so the first payment confirms the booking and **the second is captured, never refunded, and raises no alert**.

## Chosen remediation: persist the session id and expire the superseded one (08-REVIEW CR-02 option 1)

Stated explicitly, because the operator asked for the rationale:

- **The "revert to the stable `checkout:<bookingId>` key" option is not actually cheaper, and on its own it is a regression.** A pure revert re-opens exactly what D-108 closed: a re-priced hold replays the FIRST session and charges the OLD amount, so the total displayed by `price-breakdown.tsx` is not the total charged — the trust failure that component exists to prevent. The review's own wording of that option ("*and refuse `updateDeclaredPax` once a session exists*") requires knowing that a session exists, which requires the very persistence this option adds. So option 2 is option 1 minus the expire call, with a worse product outcome: a booker who steps their headcount is refused instead of re-quoted.
- `deferred-items.md` item 1 already names this as the close condition ("persist `checkout_session_id` on the booking and expire the old session on re-price").
- It stays inside D-107: one payer, one exclusive lock, the Phase-5 hold-until-session rail unchanged. This adds a nullable column and one REST call. It introduces no payment state machine, no split, no second payer.

This plan lands the **persistence and the client call**; plan `08-13` wires them into `confirmBooking` and `updateDeclaredPax`. Splitting there keeps the schema/migration/HTTP-client work in one context and the action-level money logic in another.

Purpose: make "exactly one live checkout session per booking" an enforceable statement.
Output: `booking.checkout_session_id` applied to the live database, and `expireCheckoutSession` in the one module allowed to talk to PayMongo.
</objective>
