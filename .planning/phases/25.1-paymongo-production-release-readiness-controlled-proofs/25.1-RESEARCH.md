## Architecture Patterns

### System Architecture Diagram

```text
Authorized product + PayMongo account authority
        │ records redacted, bounded authorization
        ▼
Evidence matrix + runbook ──missing field / mismatch──> HOLD (no external action)
        │ all applicable gates satisfied
        ▼
Server-owned hosted checkout ──provider signed event──> HMAC + event-ID dedupe
        │                                               │
        │ server-side Checkout Session probe            ▼
        └────────missed-event recovery──────────> sole confirmation writer
                                                        │
                                                        ▼
                                             durable booking/ledger state
                                                        │
                                     provider-derived payout status read-back
                                                        ▼
                                      paid / failed / still processing + alert
```

The normal control flow is already represented in code; Phase 25.1 should add release evidence and tests only, not another state transition. [VERIFIED: src/app/api/paymongo/webhook/route.ts:273-323] [VERIFIED: src/inngest/functions/payment-reconcile.ts:247-319] [VERIFIED: src/inngest/functions/payout-reconcile.ts:96-138]

### Pattern 1: Evidence is a gate, not a claim

**Use:** The planner should represent all external actions as `checkpoint:decision` or `checkpoint:human-verify` tasks. A failed precondition writes a redacted HOLD record and stops; it never falls through to a provider request. Phase 25 already used this authorization-or-HOLD model for controlled checkout and controlled payout. [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/25-02-PLAN.md:107-129] [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/25-04-PLAN.md:83-111]

### Pattern 2: Provider evidence converges on one confirmation writer

**Use:** Signed webhook and provider recovery may be separate sources, but both call `confirmPaidBooking`; no planner task may add a browser-return confirmation, direct booking update, or additional worker. [VERIFIED: src/app/api/paymongo/webhook/route.ts:273-323] [VERIFIED: src/inngest/functions/payment-reconcile.ts:247-319]

### Pattern 3: One-way money movement uses stop-on-first-mismatch

**Use:** A controlled checkout/refund/payout task must declare the exact operation, pre-authorized boundary, expected evidence, abort condition, and accountable human. Any mismatch stops further action and leaves state/release disposition at HOLD pending human resolution. The Phase 25 runbook requires this for payout before a provider call. [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/25-PRODUCTION-RUNBOOK.md:124-153]

### Anti-Patterns to Avoid

- **Treating configuration as proof:** Endpoint and function registration do not establish signed delivery, execution, or alert response. [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/COVERAGE.md:43-49]
- **Authorizing from a browser return:** Only signed provider delivery or server-side provider probe can confirm a payment. [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/25-PRODUCTION-RUNBOOK.md:5-11]
- **Broadening a rail because it appears in code:** The Checkout Session's supported list is not an account approval. [VERIFIED: src/lib/paymongo.ts:204-244] [ASSUMED]
- **Using a default wallet or recipient:** Payout code has guards, but provider entitlement and a correlated activated recipient remain human/provider evidence requirements. [VERIFIED: src/inngest/functions/payout-sweep.ts:238-357] [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/COVERAGE.md:76-80]
- **Converting unknown transfer status to paid:** Unknown/in-flight is deliberately retained as processing. [VERIFIED: src/inngest/functions/payout-reconcile.ts:67-70]

## Observability and Rollback Acceptance Criteria

### Minimum observability before any release decision

- A signed delivery is observed with only a redacted provider reference and its durable outcome recorded. [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/25-PRODUCTION-RUNBOOK.md:83-92]
- A registered `paymentReconcile` run is observed to probe provider state and emit the existing `webhook_missed` operator signal when it genuinely confirms a missed delivery. [VERIFIED: src/inngest/functions/payment-reconcile.ts:247-319]
- A payout read-back is observed to result in a durable terminal state or to remain processing; it must not be inferred from transfer creation. [VERIFIED: src/inngest/functions/payout-reconcile.ts:96-138]
- The monitored money-alert destination, responsible human, acknowledgement/escalation route, and response SLA are documented and exercised. This is not proven by a console registration record. [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/COVERAGE.md:79-80]

### Rollback acceptance criteria

- Before any live-money action, the authorized account owner must document the provider-side action that stops new checkout activity, the human authorized to invoke it, affected customer/host communication ownership, payout handling, and reconciliation follow-up. [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/25-PRODUCTION-RUNBOOK.md:109-113]
- A payout authorization must additionally specify cancellation before irreversible cutoff, and the return/escalation owner if a terminal transfer cannot be reversed. [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/25-PRODUCTION-RUNBOOK.md:124-153]
- A source-code change alone cannot satisfy rollback: Phase 25 records no evidenced provider-side kill-switch contract. [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/COVERAGE.md:25-26] [ASSUMED]

## Code Examples

No new runtime code pattern is recommended. A plan should use this decision rule in its task preconditions and evidence document rather than implementing it as a feature flag:

1. All required evidence fields present and independently observed by accountable humans → checkpoint may request explicit authorization.
2. Any missing, stale, contradictory, or unexpected field → HOLD, no provider action, record redacted discrepancy and owner.
3. Any live mismatch after authorization → stop-on-first-mismatch, invoke the pre-recorded provider-side boundary, reconcile durable state, and escalate to the named operations owner.

This keeps authorization out of client code and preserves the existing provider-evidence confirmation flow. [VERIFIED: .planning/phases/25-finalize-paymongo-production-payments/25-02-PLAN.md:107-129] [VERIFIED: src/app/api/paymongo/webhook/route.ts:273-323]
