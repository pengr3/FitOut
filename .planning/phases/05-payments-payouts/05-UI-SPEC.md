# Phase 5 — UI Design Contract

> Visual and interaction contract for the Payments & Payouts phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Phase surfaces (from 05-CONTEXT.md D-50..D-60 + 05-RESEARCH.md; ROADMAP Phase-5 prose is STALE/Stripe and ignored for mechanics):**
>
> Phase 5 is mostly payments plumbing. It has **exactly two real frontend surfaces plus two state-changes to existing pages**:
> 1. **HOST-03 — Host earnings/payouts page (NEW)** at `/host/earnings`, under the `(host)` route group (D-59). Per-booking rows: a payout **state badge** (`Held → Processing → Paid`, plus `Refunded`), the money breakdown `gross booking → −10% commission → net payout`, and the **expected payout date** — plus a **summary total** (upcoming/held vs paid). The host **does** see the commission line (unlike the booker).
> 2. **Checkout entry (MODIFIED)** — the Phase-4 reserve page's terminal `Confirm booking` button becomes **`Confirm & pay`** (D-57): it creates a PayMongo hosted Checkout Session and redirects **off-site** to PayMongo. The actual card/GCash/Maya/QR Ph payment UI is **PayMongo-hosted, NOT ours — do not design it.** On return the booker lands on a FitOut confirmation URL and sees a brief **"payment received, finalizing…" pending-payment state** until the `checkout_session.payment.paid` webhook confirms.
> 3. **Confirmation page (MODIFIED)** at `/bookings/[id]` — gains the **pending-payment interstitial** state (returned from checkout, not yet webhook-confirmed) that auto-resolves into the existing **confirmed** state.
> 4. **Reserve breakdown copy (MODIFIED)** — the `PriceBreakdown` atom's Total sub-line and the reassurance line change from "no charge yet" to "you'll pay this now". **The booker breakdown stays `subtotal = total` — there is NO booker-facing commission or fee line (D-50).**
>
> **Out of scope for this contract (later phases / not FitOut-rendered):** the PayMongo-hosted payment page itself (external), instant-book vs request-to-book fork + authorize→capture (Phase 6), booker-facing cancel/refund flow + refund-% tiers (Phase 7), My-Bookings management list (Phase 7), transactional emails (Phase 7). Phase 5 builds the refund **mechanism** only (D-60) — refunds are **system-initiated**, never a booker button here.

## Typography

Reuses the locked contract: single family (Geist), exactly **4 sizes**, exactly **2 weights** (400 regular, 600 semibold). No third weight, no italic.

| Role | Size | Weight | Line Height | Usage in this phase |
|------|------|--------|-------------|---------------------|
| Display | 28px | 600 | 1.2 | Earnings **summary totals** (the "Upcoming payouts" / "Paid out" figures, `tabular-nums`); the confirmation page's confirmed heading + reference (unchanged) |
| Heading | 20px | 600 | 1.25 | Earnings page title (`Earnings`); the pending-interstitial heading (`Payment received`); breakdown **Total** value (reserve) |
| Body | 16px | 400 | 1.5 | Interstitial reassurance copy, empty-state body, commission explainer prose |
| Label | 14px | 600 (row labels, summary captions, badge text) / 400 (meta: expected-date, tz note, helper, commission footnote) | 1.4 | Payout-row `gross/commission/net` labels (600) + values (`tabular-nums`), state-badge text (600), summary captions (600), expected-date meta (400 muted), commission explainer footnote (400) |

Rules:
- **Every money figure and every payout amount uses `tabular-nums`** (gross, −commission, net, summary totals, the charged Total) so columns align and digits don't jitter (Geist sans — never switch to mono).
- The commission line renders as a **negative** value (`−₱X`) in the same Label size, muted, so the deduction reads clearly against the gross.
- Headings stay weight 600 — never 700. Body reading copy stays 16px / 1.5 / 400.

**Accent (FitOut Coral) reserved for — EXPLICIT, exhaustive list this phase (one coral focal point per screen):**
1. **Reserve page:** the single terminal **`Confirm & pay`** CTA (the one primary action; disables → redirects to hosted checkout).
2. **Payment-reversed / failed edge state** (booker): the single **`Back to availability`** recovery CTA (coral primary), mirroring the Phase-4 hold-expiry recovery.
3. **Listing detail (existing seam):** the **`Book this space`** CTA — unchanged from Phase 2–4.
4. **Confirmation page (existing):** at most one optional coral forward action (`Find another space`) — unchanged from Phase 4.

Accent is **NOT** used for: the **Earnings page** (a read/status view — it has NO coral CTA), any payout state badge (Paid = `--success`; Held/Processing/Refunded = neutral), the earnings summary figures, the `Earnings` / `Your listings` host-nav links (neutral `outline`), the reused `Set up payouts` nudge button (neutral, per 02-UI-SPEC), or the **pending-payment interstitial** (neutral spinner — NOT coral, NOT success-green until confirmed). **"Held", "Processing", "Refunded", and "finalizing…" are NEVER rendered as red or as errors** — they are calm, expected states.

### Payout state badge recipes (the new visual vocabulary — built from existing tokens, a11y never color-only)

| Payout state | Badge treatment | Icon (lucide) | Meaning shown to host | Notes |
|--------------|-----------------|---------------|-----------------------|-------|
| **Held** | `secondary` (filled `--muted`) badge | `Clock` (or `Hourglass`) | Funds collected, held until after the session | The "scheduled" analog (Peerspace vocab). Pair with helper `Held until after the session`. |
| **Processing** | `outline` (bordered `--border`) badge | `ArrowLeftRight` (or `Loader`) | Payout released, on its way to the host's bank | Distinguished from Held by the bordered (not filled) treatment **and** the distinct icon/label. |
| **Paid** | `--success` badge (`bg-success text-success-foreground`) | `CheckCircle2` | Payout sent to the host wallet | The one semantic-success surface here — same treatment as the "Confirmed" booking badge. |
| **Refunded** | `secondary` muted badge, muted-foreground tone | `Undo2` (or `RotateCcw`) | Booking refunded — no payout for this row | Neutral/informational, **never red**. The net line renders muted/struck; helper `This booking was refunded — no payout.` |
| **(edge) Failed / Needs attention** | Reuse the existing destructive `Alert` pattern (icon + text), NOT a badge | `AlertTriangle` | A payout couldn't be sent and needs attention | Derived internal state (not in D-59's four). Mirrors the host "Bookings paused" banner; keep off the happy path. |

Because the four contract badges are visually close in a table, **every badge pairs its color with a distinct icon + text label** (never color-only) and, for the Held→Processing→Paid progression, the **expected/paid date meta** below the badge carries the nuance.

## Reserve price-breakdown contract (MODIFIED — D-50 booker view)

The Phase-4 `PriceBreakdown` atom already renders a **fee-extensible line-item list with a documented RESERVED Phase-5 fee slot**. **Phase 5 leaves the booker breakdown at `subtotal = total`** — the commission is a **host-side** deduction (D-50), so the reserved slot stays empty for the booker. Only two copy strings change:

```
{₱rate}/hr  ×  {N} hours                 {₱ subtotal}      ← hourly run (unchanged)
        — or —
{₱rate}/day ×  1 day                      {₱ subtotal}      ← full day (unchanged)

[ reserved fee slot — STILL renders nothing for the booker (commission is host-side, D-50) ]

──────────────────────────────────────────
Total                                     {₱ total}          ← == subtotal (no booker fee)
Final price — no added fees. You'll pay this now.            ← sub-line copy CHANGE
```

Rules:
- **Do NOT add a commission/"service fee" line to the booker's breakdown** (D-50/Pitfall 6). The `FitOut service fee (10%)` line appears **only** on the host `/host/earnings` rows.
- The displayed Total is the server-frozen `quotedTotalCents` (D-49) — the exact amount charged. Never a client recompute.
- `Total` value stays Heading-600, `tabular-nums`.

**Visual hierarchy / focal point (locked, per surface):**
- **Earnings page:** the **two summary totals are the entry focal point** (what's coming, what's landed), then the eye travels down the **payout history** (the working area). Rows are uniform and neutral; the only color pop is the `--success` **Paid** badge and the occasional attention `Alert`. **No coral** — this is a status view, not an action surface.
- **Pending interstitial:** the **neutral spinner + `Payment received` reassurance is the whole focal point** — calm, single-purpose, auto-resolving. No competing actions.
- **Reserve page:** unchanged — summary → breakdown → the one coral **`Confirm & pay`** terminal action.

**Interaction rules (locked):**
- **The webhook is the confirm authority (D-57)** — the browser return to `?paid=1` only renders "finalizing…"; the page must **never** claim "Booking confirmed" until `status==='confirmed'` in the DB (truthfulness, same rule as the Phase-4 confirmation page's pending guard).
- **Booker breakdown stays `subtotal = total` (D-50)** — no commission/fee line ever leaks into the booker view; the commission line lives only on `/host/earnings`.
- **Payout states are calm, expected states** — Held/Processing/Refunded are never red; only genuine failures use the destructive `Alert`. Paid is the one success signal.
- **The host always sees a fixed, explainable payout** = `gross − 10%` (D-52 — the platform absorbs processing costs; never surface a gateway-fee line to the host).
- **Every displayed date names / respects the venue timezone** (SC#2), on expected-payout dates and the confirmation.
- **All money is server-frozen** (D-49/D-51) — the UI renders `quotedTotalCents`, the frozen `commission_cents`, and `net_cents`; it never recomputes.

**Accessibility (non-negotiable):**
- Payout state badges are **icon + text, never color-only** (Held/Processing/Refunded are neutral and would be indistinguishable by hue alone).
- The `PendingPaymentState` spinner exposes a text status (`aria-live="polite"` on the "finalizing…" copy) so screen-reader users hear the resolution; do not rely on the visual spinner alone.
- The earnings `table` uses real `<th>` headers with scope; the mobile card fallback keeps label↔value pairs associated.
- The `Earnings` nav link, `Set up payouts`, and every recovery/`Refresh` control are keyboard-operable with ≥44px hit area.
- `--success` (Paid) and `--brand` (Confirm & pay) contrast ≥4.5:1 with their declared foregrounds (verified Phase 2); success/attention never the sole signal (icon + text always).
