## Decisions Made

- **`React.useId()`, not an `idPrefix` prop.** The prop route would have required editing `BookingPanel` and the listing route, both outside this plan's files, and would have put the uniqueness guarantee at the mount site where the next mount can forget it. The hook keeps it in the component that owns the id. Applied identically in both files: two spellings of one convention in one directory is a second source of truth in costume.
- **DEFECT 2 is a missing settle, and the spec's own record is the control.** The failure carried the stale-grid message but `found: false` on both chips — the buttons were **absent**, not present-and-still-selectable. This spec's watched red R1 (produced deliberately by deleting `refreshDay()` from `book-cta.tsx`) carries `"found": true` **unchanged on both sides of its diff**: a stale grid mounts its chips and reports them free. The observed state is a loading frame after `router.refresh()` remounts the picker, not a claim about availability.
- **The post-condition asserts PRESENCE ONLY.** A grid that comes back still offering the lost hours mounts its chips, satisfies it, and is then failed by the one synchronous evaluate exactly as before. AC#34 is not weakened by one byte; only the race against an empty intermediate frame is removed. Proved able to fail with its own sentence under a watched red, and reverted with matching content checksums.
- **The unit test that pinned the literal was the defect in miniature.** `expect(note.id).toBe("availability-tz-note")` would have been asserting the bug. It now reads the id off the note and requires the describedby to target **that** — false for an unlinked grid *and* for a describedby left pointing at a stale id, which is the stronger claim.
- **CI-01 stays unticked**, following 19.1-03's convention and reason: it is a phase-level requirement spanning all fifteen plans, and ticking it while twelve plans are unexecuted is exactly the fake-green this phase exists to eliminate.

**1. [Rule 4 — cross-plan ownership] DEFECT 3: `pickWindow`'s tz-note assertion is ambiguous on TEXT, and an id-only repair cannot close it**

- **Found during:** Task 3, on the canonical post-repair run.
- **Issue:** the grove variant failed at `e2e/helpers/booker-seed.ts:180` with `strict mode violation: getByText(/Times shown in .*Makati.*\(GMT\+8\)/i) resolved to 2 elements` — the two elements now carrying **different** ids (`_r_c_-tz-note` visible, `_R_16b9bnabn5ritulb_-tz-note` hidden). - **What it falsifies:** the plan's key-link states "the strict-mode ambiguity this plan removes is what would otherwise make that assertion nondeterministic." That is wrong, and the transcript says so. The id repair closes the HTML-validity and `aria-describedby` half; the locator half is a separate defect in a separate file.
- **What it revealed:** the duplicate had **two** producers, not one. Beside the responsive sheet, the served shell and the resolved content overlap while `/listings/[id]` streams — the two ids above are React's server and client forms. This is the mechanism `booker-seed.ts:363-373` already records for `#search-category`. Both were served by the same module-level literal, so the repair closes both *as ids*.
- **Why not repaired here:** `e2e/helpers/booker-seed.ts` is outside this plan's `files_modified`, is shared by many specs, and **19.1-PATTERNS section 7 charters plan 08 to harden that exact helper** — noting there that "the two repairs interact". A second, uncoordinated edit to plan 08's file is not a fix, it is a merge conflict with a plan that has more of that file in view.
- **Severity:** a flake, not a hard failure. It passed on retry; under CI's `--retries=2` the spec is green overall (`1 flaky / 1 passed`, exit 0).
- **Handling:** triaged in `evidence/triage-collision-in-place.txt` section 7 and VERDICT DEFECT 3, with an explicit brief for plan 08 (scope or settle it the way `selectTargetDayIn` already takes a scope — **do not** weaken it to `.first()`, which goes green against a page rendering only the pending shell).
