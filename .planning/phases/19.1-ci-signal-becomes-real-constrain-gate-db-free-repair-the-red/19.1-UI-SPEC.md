# Phase 19.1 — UI Design Contract

> Visual and interaction contract for the host-listing wizard route-resolution repair. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope: preserve the wizard, repair how the route reaches it

This gap-planning slice authors **no redesign and no new product surface**. Run `34008844133` leaves
seven functional failures, but all seven stop at the same boundary: `/host/listings/[id]/edit` does
not reach the resolved wizard on the GitHub runner. The failures therefore cannot be evidence that
the wizard's colors, layout, copy, headings, keyboard order, document tree, or overflow behavior are
wrong. Those properties have not been reached.

The only permitted visible outcome is **no visible change**: once the route resolves, the existing
wizard must render and behave exactly as it does on the current green local and pinned-container
readings. This specification makes that no-change requirement measurable rather than implicit.

Sources: `19.1-CONTEXT.md` D-01/D-02 and Phase Boundary; `19.1-18-SUMMARY.md`; and
`evidence/ci-run-after-18.txt`. The checkout-path defect is closed and outside this contract.

## Route Resolution Contract

### R1. Prove the module is reachable before measuring the wizard

The first discriminator remains the DB-free anonymous request in
`e2e/host-route-reachability.spec.ts`:

| Request | Required status | Meaning |
|---------|-----------------|---------|
| `GET /host/listings` | 307 | Route module reached its pre-data auth redirect |
| `GET /host/listings/new` | 307 | Route module reached its pre-data auth redirect |
| `GET /host/listings/route-reachability/edit` | 307 | Dynamic edit module resolved before any DB read |
| `GET /host/listings/route-reachability/availability` | 307 | Sibling dynamic route resolves as control |

Use Playwright's API `request` context with `maxRedirects: 0`; a followed redirect returning 200 is a
vacuous guard. The edit route's 404 means the router never reached the module. It does **not** mean a
listing is missing, ownership failed, or the wizard needs a fallback.

Before any repair, capture both running-server route manifests and distinguish clean dev from
production build behavior. The cause remains unasserted until that probe names it. Do not increase a
timeout, retry navigation, or touch product presentation to hide a missing module.

### R2. Preserve the security order

`src/app/(host)/host/listings/[id]/edit/page.tsx` keeps this order:

1. resolve the async `params`;
2. read the session;
3. anonymous user redirects to `/login`;
4. signed-in non-host redirects to `/`;
5. only then query the listing;
6. missing, deleted, or non-owned listing calls `notFound()`.

The `notFound()` is an IDOR guard and is immutable in this phase. Do not soften it, move it ahead of
the anonymous redirect, replace it with a rendered explanation, or leak whether another host's listing
exists. Nothing under `src/app/(host)/host/listings/[id]/edit/` is a permitted route-resolution repair
site unless a new measurement directly contradicts this contract and is escalated before editing.

### R3. The authenticated arrival tell is the wizard rail

After an owner-authenticated navigation, the resolved-route tell is exactly one
`[data-testid="wizard-step-rail"]`, followed by the step-one action named `Get started`. A page heading,
loading plate, 404 body, or host chrome is not an arrival tell: all can exist without the wizard.

The tell must resolve within the existing measured budgets. Do not widen the 60-second or 120-second
route compile allowances. On a clean server, a timeout remains a failure that must retain the route,
viewport, theme, and missing tell in its message.

### R4. Downstream gates run only after arrival and keep their own properties

Once R1 and R3 pass, the seven red cases retain their independent meanings:

- axe sweep: zero violations at 320 and 1280 in `court`, with non-zero scanned nodes and passed rules;
- heading walk: one `<h1>` per step and one computed heading size across host surfaces;
- keyboard composite: the existing 14 stops at 320, in order, with the checklist disclosure,
  advance action, and visited-step return control reachable and operable;
- one-tree: one wizard rail and one publish checklist in the **document**, not merely one visible;
- overflow: no horizontal overflow at 320, existing controls keep their target floors and focus;
- route reachability: anonymous edit route returns 307, not 404.

No downstream assertion may be weakened, skipped, allowlisted, given a retry, or changed to accept the
loading/not-found document. A single route repair is allowed to release several cases; it does not merge
their contracts.

## Verification Contract

The planner must produce evidence in this order:

1. Reproduce or capture the runner's edit-route failure before the repair, including HTTP status and
   the running server's relevant route-manifest entry.
2. Show the anonymous edit-route discriminator red for the same reason, or record why a lower-level
   manifest/module probe is the first red when the failure cannot be reproduced locally.
3. Apply the narrow route-resolution repair outside the frozen wizard surface.
4. Watch the route discriminator green: anonymous edit returns 307 with `maxRedirects: 0`.
5. Run an owner-authenticated arrival proof: one rail, step-one `Get started`, no loading or not-found body.
6. Run all six downstream property groups without weakening them.
7. Read a SHA-matched, push-triggered real CI run. All seven host-wizard failures must be absent from
   failed and flaky lists; `gate-e2e` must conclude `success`. Local and container green alone do not close it.

The repair must leave `gate-db-free`, `gate-db`, and `gate-price-parity` green. Functional closure does
not claim visual closure; Plan `19.1-19` remains the owner of the visual job.
