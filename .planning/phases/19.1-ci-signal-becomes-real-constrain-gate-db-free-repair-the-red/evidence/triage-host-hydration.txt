That is precisely what React's + meant, and what this plan's Step 1 wrote down without yet knowing
why: CLIENT-ONLY. The client renders <button aria-label="Menu"> into a div the server left empty.

WHY THE SERVER LEFT IT EMPTY. ResponsiveDialog forwards its `trigger` prop into
`DialogTrigger asChild`, and `asChild` is Radix's `Slot` — which CLONES an element rather than
rendering one. `patterns/site-chrome.tsx` is a SERVER COMPONENT (its own header says so, of every
export in it), so `NavDrawer` created the trigger element on the server and handed it across the RSC
boundary into a client component, where it could not be cloned during the SSR pass.

with the first line of its module:

STEP 2 · THE CHOSEN SHAPE, AND THE SHAPES REJECTED WITH THE CONSTRAINT THAT DECIDED EACH
------------------------------------------------------------------------------------------------

CHOSEN — move the CLONED ELEMENT, and only it, to the client side of the boundary.
  `src/components/patterns/nav-drawer-shell.tsx`, a new "use client" module holding the
  <Button aria-label="Menu"> trigger and composing the same ResponsiveDialog. `NavDrawer` stays in
  `site-chrome.tsx`, stays a Server Component, and passes `NavLinks` down as ordinary children —
  children cross the boundary unchanged and are never cloned, so only the trigger had to move.
  Constraint (e) holds exactly: ONE overlay mechanism, ONE focus trap, `ui/sheet.tsx` still absent,
  the vendored dialog untouched. Constraint (f) holds: no composition merged.

REJECTED — a placeholder fallback ALONE.  Decided by: THE MEASUREMENT ABOVE. It leaves
  HYDRATION-COUNT at 1. It is KEPT as a second, smaller change (below) but it is not the repair.

REJECTED — turn `asChild` off and let Radix render its own trigger button.  Decided by: the drawer's
  accessible name and its AUTH_SLOT_ICON box are the caller's, and Radix's own button carries
  neither. That trades a hydration failure for a WCAG 4.1.2 failure and a reflow.

REJECTED — wrap the trigger in a <span class="contents"> so Slot has something real to clone.
  Decided by: the aria wiring (aria-haspopup, aria-expanded, aria-controls) would land on the span
  rather than on the button. Same category of trade as above.

REJECTED — make `site-chrome.tsx` itself a client module.  Decided by: `SiteChrome` and `NavLinks`
  are Server Components by design and the file's header states it; converting them would ship the
  whole header inventory to the browser to fix one cloned element.

REJECTED — edit the vendored `ui/dialog.tsx`.  Decided by: the plan's prohibition, and RESP-01's own
  record that nothing under src/components/ui/** is edited by this layer.

KEPT ALONGSIDE — `NavSlotSkeleton`. It is not the repair and is not claimed to be. It is kept on its
own merits, stated narrowly: while the boundary is pending there is now NO button[aria-label="Menu"]
in the document at all, where before there was one that React then replaced — and a control that is
absent and then appears is one Playwright's auto-waiting handles, whereas a control that is present
and then swapped is the LOST-CLICK shape `e2e/helpers/booker-seed.ts:118-160` records.

STEP 3 · THE END-TO-END ASSERTION, AND THE RACE THAT MADE IT TWO CLAUSES
------------------------------------------------------------------------------------------------

One case added to `e2e/shell.spec.ts`, in a NON-SERIAL describe beside the other host-composition
cases: listeners armed before the navigation, a presence assertion, an interactive hydration proof
(open and close the nav drawer below md: — the very subtree under suspicion), then the absence.

WARNING: ONE THING THE PLAN DID NOT ANTICIPATE, MEASURED HERE RATHER THAN ASSUMED. The message
clause ALONE IS RACED. React does not hydrate a Suspense boundary that is still pending when
hydration begins — it client-renders the contents when they arrive, and a client render has nothing
to disagree with. So on a cold compile cache the same broken tree reports ZERO mismatches:

  reverted tree, rm -rf .next, message clause only     -> PASSED   (a green for the wrong reason)
  reverted tree, route already compiled                -> FAILED   1 mismatch
  a warm-up navigation added before the measured load  -> still PASSED cold; NOT deterministic

So the case carries a SECOND clause, on the served bytes, which reads the CAUSE rather than the
symptom: the served document must contain no EMPTY drawer placement <div class="md:hidden"></div>.
Pre-repair that string is present whether the boundary resolved or not (the fallback and the resolved
child are both served empty); post-repair neither is (the fallback holds the reserved box, the
resolved child holds the button). Both clauses ship; the deterministic one is what makes the red
reliable and the symptom clause is what names what a user would see.
