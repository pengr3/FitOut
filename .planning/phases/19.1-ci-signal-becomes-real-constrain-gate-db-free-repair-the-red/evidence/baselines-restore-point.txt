THE RESTORE COMMAND IS PROVEN, NOT ASSUMED — and it was worth proving.
================================================================================

A restore command that silently matches nothing is worse than no restore file: it
reads as a reversal that has been thought about, and it is a no-op. So it was tested
here rather than written and trusted.

  NEGATIVE CONTROL — a pathspec matching nothing is LOUD, so a silent success means
  something really matched:

    $ git checkout fe99817 -- 'e2e/**/*-NOSUCHTHING.png'
    error: pathspec 'e2e/**/*-NOSUCHTHING.png' did not match any file(s) known to git

  POSITIVE PROOF — a real baseline was corrupted and restored by the exact command
  above, and the bytes came back identical:

    before    md5 38ac2012a4d9   (dev-theme-320-court-visual-linux.png)
    corrupted md5 11ce7a200230
    restored  md5 38ac2012a4d9   <- byte-identical to `before`

  ⚠ AND ONE TRAP THAT LOOKS EXACTLY LIKE A FAILURE, RECORDED SO THE NEXT READER DOES
  NOT "FIX" A WORKING COMMAND. `git ls-tree -r --name-only fe99817 -- 'e2e/**/*-visual
  -linux.png'` reports 0 for this same glob, because ls-tree does prefix matching and
  not full pathspec globbing. `git ls-files` reports 36 and `git checkout` restores 36.
  The 0 is a property of ls-tree, not of the pathspec. Do not use ls-tree to verify
  this file.
