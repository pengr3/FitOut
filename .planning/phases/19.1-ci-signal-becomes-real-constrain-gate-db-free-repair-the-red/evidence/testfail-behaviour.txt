=====================================================================

WHY THIS FILE EXISTS
  19.1-RESEARCH.md § "D-03 — the known-failures allowlist" recommends option A
  (`test.fail(cond, reason)` in-file, paired with a build-blocking design test) and lists TWO
  behaviours beneath the recommendation as ASSUMED — Assumptions Log rows A1 and A2. Neither is
  documented clearly enough to assume, and both change the allowlist design if wrong. This file
  settles them by measurement, not by reading.

WHAT WAS RUN
  A throwaway spec `e2e/__scratch-known-failure.spec.ts` with SIX tests in four constructs and NO
  product interaction — no navigation, no fixtures, no database access:
    (1) a standalone expected failure whose body THROWS               → measures A1 (retries)
    (2) a standalone expected failure whose body PASSES               → measures the stale-entry guard
    (3) a `describe.serial` group of three, the FIRST an expected
        failure whose body throws, the other two ordinary passes      → measures A2 (serial tail)
    (4) one plain passing test outside both                           → the NON-VACUITY ANCHOR

Q1. DOES AN EXPECTED FAILURE CONSUME ITS CONFIGURED RETRIES?
    ANSWER: NO. It runs exactly once even at --retries=2.

    Read from RUN 2 (`--retries=2`). The two expected-failure tests each appear ONCE in the
    attempt list, with no `(retry #N)` line anywhere for either:

        x  1 [chromium] › e2e\__scratch-known-failure.spec.ts:14:5 › A1 · standalone expected failure whose body throws (7ms)
        x  4 [chromium] › e2e\__scratch-known-failure.spec.ts:35:7 › A2 · serial group whose FIRST test is an expected failure › serial 1 · expected failure whose body throws (9ms)

    The ONLY test that consumed retries in that run was the UNEXPECTED PASS:

        ok 7 [chromium] › e2e\__scratch-known-failure.spec.ts:24:5 › stale-entry guard · standalone expected failure whose body PASSES (retry #1) (8ms)
        ok 8 [chromium] › e2e\__scratch-known-failure.spec.ts:24:5 › stale-entry guard · standalone expected failure whose body PASSES (retry #2) (7ms)

    → 19.1-RESEARCH.md Assumptions Log A1 is CONFIRMED. An annotated `hold-countdown.spec.ts:443`
      would burn ONE 3-minute timeout in CI instead of three, so the ~6-minute wall-clock saving
      RESEARCH.md attributes to it is REAL and plan 13 may assume it.

Q2. DOES AN UNEXPECTED PASS FAIL THE RUN?
    ANSWER: YES — with a named error and a non-zero exit, in BOTH runs.

        1) [chromium] › e2e\__scratch-known-failure.spec.ts:24:5 › stale-entry guard · standalone expected failure whose body PASSES

            Expected to fail, but passed.

        1 failed
          [chromium] › e2e\__scratch-known-failure.spec.ts:24:5 › stale-entry guard · standalone expected failure whose body PASSES
        5 passed (15.0s)

    and the shell reported `RUN1 EXIT=1` / `RUN2 EXIT=1`.

    → The stale-entry guard that D-03 option A rests on EXISTS and is loud. An allowlist entry whose
      test starts passing turns `gate-e2e` red by name, without any custom reporter.

    ⚠ AND THE COST IS NAMED: an unexpected pass DOES consume its retries (the `retry #1` / `retry #2`
      lines above, plus a trace attachment written on retry #1). A stale entry therefore costs THREE
      attempts in CI, not one — the opposite of Q1's saving. Cheap here (8ms); not cheap on a spec
      that times out.

Q3. DOES AN EXPECTED FAILURE STOP THE REMAINDER OF ITS `describe.serial` GROUP?
    ANSWER: NO. Both following tests in the group ran and passed, in both runs.

    Read from RUN 2:

        x  4 [chromium] › ... › serial 1 · expected failure whose body throws (9ms)
        ok 5 [chromium] › ... › serial 2 · ordinary passing test (16ms)
        ok 6 [chromium] › ... › serial 3 · ordinary passing test (4ms)

    and the summary reports no "did not run" bucket at all:

        5 passed (10.0s)

    → 19.1-RESEARCH.md Assumptions Log A2 is CONFIRMED. An allowlisted entry does NOT keep hiding the
      tail of its serial group, so an in-file annotation does not mask more than it declares. This is
      the behaviour D-03 option A needed, and it is why the in-file annotation stays the right
      mechanism rather than the reporter (option D).

TWO MEASURED DELTAS AGAINST WHAT RESEARCH.md ASSUMED — recorded because the measurement wins
────────────────────────────────────────────────────────────────────────────────────────────

D1. AN EXPECTED FAILURE IS COUNTED UNDER `passed`, NOT UNDER A SEPARATE BUCKET.
    Run 1 collected 6 tests: 1 unexpected pass (`1 failed`) and `5 passed` — and those five include
    the TWO expected failures. Playwright's list summary has no "expected failure" line. Plan 11
    must therefore NOT expect the `gate-e2e` summary to name its allowlisted entries; the pinned
    count in `tests/design/e2e-known-failures.test.ts` is the only place the list is visible, which
    strengthens rather than weakens the case for that design test.

D2. LOCAL WORKER COUNT IS 4, NOT 1.
        Running 6 tests using 4 workers
    19.1-RESEARCH.md § Cause F states "the suite runs on 1 worker" — true of the 2-core CI runner
    (`workers` is unset, so Playwright derives it from cores), but NOT of this laptop. A local
    reproduction of any ordering-dependent failure (Cause F live hypothesis 2, "a hold placed by an
    earlier spec still occupies 2:00 PM") therefore does NOT reproduce CI's ordering by default.
    `--workers=1` is what reproduces it; this is carried into `evidence/triage-harness.md`.
