19.1-17 — THE "ONE ELEMENT RESOLVES TO TWO" DEFECT ON THE TWO BOOKER SURFACES, READ RATHER THAN INFERRED
=======================================================================================================

Convention: `19.1-PATTERNS.md` §A — the command line above its own unedited output, line-anchored
markers at column zero. Raw excerpts from the throwaway probe are INDENTED by two spaces so that a
grep over a marker cannot be satisfied by a block that merely quotes one; the markers this plan's
acceptance criteria count are the un-indented ones.

MARKER BUDGET, STATED SO A LATER READER IS NOT SURPRISED. Task 1 writes exactly one `ARRIVAL-MS=` and
exactly one `PERSISTS=` (the confirmation surface). Task 2 writes one more of each under its own
heading, because its acceptance criterion requires them for the profile surface. So the finished file
carries two of each, one per surface, and that is by design rather than a duplicate answer. There is
exactly ONE `SHARED-CAUSE=` and exactly ONE `SAME-BRANCH=` in the whole file, and those two are the
questions that may only be answered once.

TASK 1 — STEP 2. BOTH MATCHES' PROVENANCE. THIS IS THE MEASUREMENT THE WHOLE PLAN TURNS ON.
-------------------------------------------------------------------------------------------------

Instrument: a throwaway probe (`e2e/zz-probe-dup-mount.spec.ts`, deleted in Task 3, never committed)
that installs a document-start script before navigation. The script observes the whole document with a
MutationObserver plus a 4ms interval, records one sample per count change, and — the first time the
count exceeds one — walks BOTH matches to `<html>`, one ancestor per line, recording each ancestor's
tag, identifier, class list, whether it declares the `hidden` attribute ITSELF (the attribute's
presence, never a computed style, because a node inside a hidden container computes as hidden without
carrying the attribute), and whether it is the page's main landmark. It also records the comment-node
siblings of the outermost DIVERGING ancestor.

THE READING, IN THE WALK'S OWN TERMS.

The two chains are identical for two levels — `section[data-testid=confirmation-moment]` inside
`div.mx-auto.w-full.max-w-2xl` — and then diverge at `<body>`:

    match 1 :  … → MAIN.flex.flex-1.flex-col → div.flex.min-h-full.flex-col → body
    match 2 :  … → DIV#S:1[hidden]                                          → body

`div#S:1[hidden]` is React's OUT-OF-ORDER STREAMING STAGING AREA. Content for a Suspense boundary that
resolves after the shell has been flushed is written at the END of `<body>` inside a hidden div with a
generated `S:n` identifier, and an inline script then commits those children into the boundary and
drops the staging div. The two "copies" are therefore ONE section in two places for one frame: staged
and committed.

THE BRANCH THIS SELECTS, from the three this plan stated in advance:
  • the second copy goes away on its own — `PERSISTS=no`, measured on every load, gone within ~150ms
    of arriving (193ms → 338ms in the samples above);
  • its ancestor chain carries the delivery mechanism's own marker — `div#S:1`, `hidden`, a direct
    child of `<body>`, which no page composition in this repository produces;
  • the browser reported NOTHING about regenerating the tree on this route — `HYDRATION-MSGS=0` on
    both trees (see Step 3), so the third branch is excluded by measurement and not by argument.

→ IT IS A COMMIT-WINDOW ARTEFACT. It is NOT a duplicated mount, and it is NOT a regenerated tree. The
defect is that the measurement runs before the surface has committed.

AND IT EXPLAINS THE ONE THING NO DUPLICATE-MOUNT THEORY EVER DID — the original `0px tall` reports.
While only the STAGED copy exists the count really is one, `boxOf`'s `document.querySelector` takes it,
and a node inside a `hidden` container has a zero rect. The case's note read that as "the box of the
WRONG section", which was right about the section and wrong about why there were two. Both readings
are kept at the site; see Task 3.

WHY THE COUNT ASSERTION PASSES AND THE VISIBILITY ASSERTION THEN FINDS TWO — the window, named. The
samples say the count is 0 → 1 → 2 → 1. `toHaveCount(1)` retries until it sees ONE, and one is exactly
what the document holds while the staged copy is present and the committed one is not. Two statements
later the commit lands, the staged div has not yet been dropped, and the strict-mode resolution reports
both. The window is not between two renders; it is between the flush and the commit.

TASK 1 — STEP 4. THE REPAIR THE READING SELECTED, AND THE CONSTRAINT SET IT SATISFIES.
-------------------------------------------------------------------------------------------------

CHOSEN: a precondition in `e2e/confirmation-decay.spec.ts` that ASSERTS THE COMMIT — a new helper
`expectStreamCommitted(page, testId, where)` that polls a CLASSIFICATION of every match: a match with a
`[hidden]` ancestor is STAGED, one without is COMMITTED, and the precondition is *zero staged and at
least one committed*. It runs on the default expect budget and is called immediately after each
`page.goto` on this surface, ahead of the count assertion.

  This is a repair to the INSTRUMENT and not to the product, and the reading is why: nothing in the
  delivered page is wrong. A booker never sees two confirmation sections; the staged copy is hidden,
  belongs to the framework's delivery mechanism, and is gone within ~150ms. What was wrong is that the
  measurement started before the surface had committed.

REJECTED, each with the constraint that decided it:

  1. Scope the locator to the main landmark — PROHIBITED at the case's own site, and rightly: it
     deletes the only instrument that has ever named this defect. Also wrong on the reading: it would
     hide a genuine duplicate outside `main` forever.
  2. Hand `boxOf` the visible match — PROHIBITED at the same site, and it would silently pass over a
     staged copy rather than notice one.
  3. Widen the expect budget, or the case's own budget — forbidden by this plan, and it would not have
     worked: the count is ONE during the window, so a longer wait on `toHaveCount(1)` returns sooner,
     not later.
  4. `waitForTimeout` past the window — the constraint that kills it is (d). A sleep long enough to
     outlast the commit also outlasts a genuine duplicate injected afterwards, and the case stops being
     able to see the thing it exists to see. This is the difference between asserting the commit and
     waiting it out, and it is why Task 3's second control exists.
  5. Change the route's streaming structure so the moment is never streamed — this is production
     source, it moves a surface above a gate for a test's convenience, and the measurement names no
     product defect to justify it. Constraint (e) and the plan's own prohibition on crediting a repair
     to the wrong change.

THE CONSTRAINT SET, EACH SATISFIED AND HOW:

  (a) The case's locator is untouched and unscoped; `boxOf` still takes `document.querySelector`'s
      first match. The helper classifies matches, it does not select one for the case.
        $ git diff -- e2e/confirmation-decay.spec.ts | grep -cE '^\+.*getByRole\(.main.\)'   ->  0
  (b) No timeout widened. The helper takes no explicit budget; `expect.poll` uses the configured
      expect default, the same one `toBeVisible()` above it already used.
        $ git diff -U0 -- e2e/confirmation-decay.spec.ts | grep -E '^\+' | grep -cE 'timeout: *[0-9_]+'  ->  0
  (c) The height floor (`height - 64`) and the fold position (`>= height`) are byte-unchanged.
  (d) The case still fails against a genuine second copy present after the surface has settled: the
      precondition passes (`staged=0`, `committed=2`) and `toHaveCount(1)` then reddens. Watched in
      Task 3.
  (e) No production source changed in this task. The confirmation component's single mount site is
      still single and nothing in the route's streaming structure moved.
