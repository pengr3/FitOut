(e2e/helpers/booker-seed.ts:175) asserts on the tz note with an UNSCOPED text
locator, and `collision-in-place.spec.ts` runs at the config's default 1280px

Read three things off that transcript:

  * BEFORE the sheet opens: `#availability-tz-note=1`. AFTER: `=2`. The id is
    duplicated by the act of opening the sheet, and by nothing else.
  * The two resolved elements are quoted by Playwright itself, and BOTH carry
    `id="availability-tz-note"`:
      1) <p aria-hidden="true" data-aria-hidden="true" id="availability-tz-note" ...>
         aka getByRole('main').getByText('Times shown in Makati time (')
      2) <p id="availability-tz-note" ...>Times shown in Makati time (GMT+8)</p>
         aka getByTestId('responsive-dialog').getByText('Times shown in Makati time (')
    One is the main column's `AvailabilityCalendar`; the other is the SAME
    component mounted a second time inside the sheet. Radix has marked the
    outside copy `aria-hidden="true"` — which is exactly why the ROLE queries in
    `selectTargetDayIn` are unambiguous and this TEXT query is not.
  * The failure is the shape RESEARCH.md quotes, to the character:
      "strict mode violation: getByText(/Times shown in .*Makati.*\(GMT\+8\)/i)
       resolved to 2 elements"

The declaration sites, read at HEAD:

  src/components/availability/availability-calendar.tsx:470
      const TZ_NOTE_ID = "availability-tz-note";
  src/components/availability/date-pass-picker.tsx:73
      const TZ_NOTE_ID = "availability-tz-note";

and `date-pass-picker.tsx:71-72` carries the claim the measurement falsifies:

    // The same id the hourly calendar uses for its tz note. Exactly one of the
    // two surfaces renders per listing (a listing is exactly one mode), so the
    // id can never appear twice in one document.

THE COMMENT IS FALSIFIED, AND NOT ONLY IN THE WAY IT ANTICIPATES. Its premise —
one surface per listing — is a claim about the two COMPONENTS. The measurement
above duplicates the id WITHOUT the second component being involved at all: the
same component is mounted twice, once in the main column and once in the sheet.
So the comment is wrong twice over, and the mechanism that makes it wrong is the
one `e2e/helpers/booker-seed.ts:86-88` already records. A module-level id literal
is unsafe in ANY component that can be mounted more than once in a document,
which on this route is every client component.

# 4. DEFECT 2 — the court variant's stale grid
################################################################################

NOT REPRODUCED. 8 invocations of the court variant across the two runs in
section 1 (1 run + 3 repeats, up to 3 attempts each, --workers=1 matching CI's
serialisation), all green, with the stale-grid message absent from every
transcript.

That is consistent with what is recorded about it: RESEARCH.md section Cause D1
notes the court variant "was flaky (passed on retry)". A message that appears on
one attempt and not the next is a RACE, and the spec's own header already names
the race it is exposed to — `router.refresh()` merges the RSC payload without
losing client `useState`, and the day's slots ARE that state (12-RESEARCH
Pitfall 3, watched red R1). The spec asserts against it deliberately, in ONE
`page.evaluate` at :319, precisely so a notice arriving a beat before the grid
cannot be papered over by a retrying expectation.

An absence over 8 attempts is not proof the race cannot occur; it is proof it
does not occur on this box under this ordering. It is recorded as such and NOT
as a closure. It is not eligible for the known-failures allowlist either: D-01
makes eligibility conditional on genuine drift or flake that is not repairable
here, and this one has no failing transcript on this machine to attach an
annotation's reason to.
