2. THE DECISION, AND THE CONDITION THAT CAME WITH IT
═══════════════════════════════════════════════════════════════════════════════════════════════════

The operator chose DERIVE THE PLATE'S ROW COUNT. `fixedWeeks` on the DayPicker call site was
considered and REJECTED: it renders a trailing week of the next month EVERY month, a permanent
visible UX change.

The condition attached to the choice was the hard part:

  the plate is the PRE-HYDRATION paint, so its row count is computed server-side; if the server and
  the client disagree about which month it is — which they can, across a timezone boundary near
  midnight — that is a hydration mismatch, and the repair would have traded a layout shift for a
  React error. The month must come from a SINGLE source both sides agree on, and must NOT be
  re-derived from `new Date()` independently on each side.

HOW IT IS SATISFIED (and it is satisfied by CONSTRUCTION, not by care):

  `src/app/listings/[id]/(detail)/loading.tsx` is a Server Component. It reads the clock ONCE, binds
  it to one `const`, and passes `{ year, month }` to `CalendarMonthSkeleton` as a prop. The component
  is `"use client"`, so React renders it again during hydration — but with the SAME SERIALIZED PROP.
  The client derives nothing. There is no second derivation to disagree with the first.

  `weekRowsForMonth` and `CalendarMonthSkeleton` contain no clock access of any kind. The `month`
  prop is REQUIRED rather than defaulted, deliberately: a default would have to read a clock.

4. TWO HARNESS DEFECTS THE CONTROL CAUGHT (both would have been a green that measured nothing)
═══════════════════════════════════════════════════════════════════════════════════════════════════

DEFECT H1 — `vi.useFakeTimers()` stalls React's scheduler.
  First run: control reported ZERO recoverable errors. Faking the whole timer suite also fakes the
  timers React's scheduler uses, so the hydration work never flushed. Narrowed to
  `vi.useFakeTimers({ toFake: ["Date"] })`; the same narrowing was applied to the purity test.

DEFECT H2 — the control was a function of the RUNNER's timezone.
  Second run: control still reported ZERO. The instants were chosen as 2027-01-31T20:00Z and
  2027-02-01T04:00Z and the control read the LOCAL month. This box is Asia/Manila (+08), so BOTH
  instants are already 1 February locally — the two renders agreed and there was nothing to mismatch.
  Verified directly:

    $ node -e "console.log(Intl.DateTimeFormat().resolvedOptions().timeZone,
                           new Date('2027-01-31T20:00:00.000Z').toString())"
    Asia/Manila Mon Feb 01 2027 04:00:00 GMT+0800 (Philippine Standard Time)

  Fixed by having the control read UTC, which pins the boundary to the instants rather than to the
  machine. A non-vacuity assertion on the SERVER row count (must be January's six) was added so the
  same class of silent agreement cannot return.

BOTH DEFECTS WERE FOUND BY THE CONTROL, IN A FILE WHOSE SUBJECT IS TESTS THAT CANNOT FAIL. Recorded
because the obvious reading of the first run — "no mismatch, the property holds" — is exactly the
false green this phase exists to eliminate.

10. RESIDUALS — stated, not closed
═══════════════════════════════════════════════════════════════════════════════════════════════════

R1. THE LISTING'S OWN ZONE. `loading.tsx` gets neither params nor a database, so it cannot know which
    zone the listing renders in. It uses the launch region (`schema.ts:223`'s `Asia/Manila` default).
    For a listing in another zone, during the hours when its calendar date differs from Manila's AND
    the two dates fall in different months AND those months fold into a different row count, the plate
    is one row out. A handful of hours a year against ten months in twelve.

R2. THE SEARCHED MONTH. `/listings/[id]?date=...` can open the resolved grid on a month that is not
    the current one (D-59 #1). A `loading.tsx` cannot read search params, so the plate reserves the
    current month's rows for another month's grid. UNCHANGED by this repair — it was equally wrong
    before — and unfixable from a `loading.tsx`, which is defined not to see the request. Closing it
    would mean moving the plate inside the page's own `<Suspense>`, which is a different change on a
    different surface.

R3. NO REAL-BROWSER HYDRATION TEST ACROSS A MONTH BOUNDARY. See section 3. The property is proved at
    the jsdom layer with a control; it is not proved through Next.js.

Neither R1 nor R2 is a regression, and neither reintroduces the hydration hazard: both are about WHICH
month the single source names, never about the two sides naming different ones.
