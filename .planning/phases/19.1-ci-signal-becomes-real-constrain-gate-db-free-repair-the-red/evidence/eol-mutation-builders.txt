And one primitive they all share:

  :825  insertAfterLineContaining   const lineEnd = ci.indexOf(eol, at);      ← DEFECT

That search begins AT the anchor's own first byte. For an anchor whose first character is
a line terminator, `at` IS the offset of a terminator, so on an LF tree the search returns
`at` itself: `cut` becomes the START of the anchored line and the insertion lands one line
early. On CRLF the same search skips the `\r` and stops at the `\n` one byte later —
inside the SAME terminator — so `cut` comes out correct. The defect is invisible on a CRLF
checkout by one byte.

SECTION 3 — WHICH EDIT IS THE FIX. THREE CONTROLS, RUN AGAINST AN LF TREE.
================================================================================

The deferred item attributes the failure to the hardcoded anchors. That was tested rather
than assumed, by reverting each half of the repair independently.

  CONTROL A — both the primitive and the two `\n` anchors reverted (i.e. HEAD's behaviour)
    → 7 failed | 31 passed.  The six, plus the new case 37.
    case 37's message: withJobKey (string form): mutated ci.yml DIFFERENTLY depending on
      the checkout's line endings … first divergence at line 1569 — LF tree produced
      "    continue-on-error: true", CRLF tree produced "  gate-e2e:"

  CONTROL B — ONLY the two `\n` anchors reverted; the primitive repaired
    → 39 passed (39).
    ⇒ THE HARDCODED ANCHORS ARE NOT THE DEFECT. With the primitive correct, a `\n` anchor
      is harmless on both checkouts, because the search no longer starts inside it.

  CONTROL C — ONLY the primitive reverted; both anchors composed from `eolOf`
    → the SAME SIX cases fail … and they fail on a CRLF checkout too.
    ⇒ THE PRIMITIVE IS THE DEFECT. Composing the anchor from `eolOf` does not make the
      builder correct; it makes it EOL-SYMMETRIC — wrong on both checkouts instead of
      wrong on one. That is the fail-closed direction (a red everywhere is a red the
      author sees), but it is not correctness.

Both edits ship, each for its own measured reason:
  • `indexOf(eol, at + anchor.length)`  — this is the repair. It makes the builders right.
  • anchors composed from `eolOf(ci)`   — this is the insurance. It makes any FUTURE
    anchor-arithmetic error red on this laptop as well as on the runner, which is the one
    property whose absence let this survive eleven plans.

Case 37 alone would NOT have caught control C — it measures the split, and control C is
symmetric. That gap is why case 39 exists (section 4).

================================================================================
VERDICT
================================================================================

The six cases were red on the runner because `insertAfterLineContaining` searched for the
end of the anchored line starting AT the anchor, and two builders anchor on a string whose
first character is a line terminator. On CRLF the search lands one byte into the same
terminator and comes out right; on LF it returns the terminator itself and the insertion
goes one line early. Two of the six then measured a job no invariant watches and the
checker exited 0 — a false green inside a case whose whole purpose is to prove a red.

Repaired at the primitive, with the anchors composed from `eolOf` so a future arithmetic
error is red on both checkouts rather than only on the one that gates the repository.
Three new cases hold the class closed: equivalence, census, placement. Each was proved to
catch the defect it exists for by putting the defect back.
