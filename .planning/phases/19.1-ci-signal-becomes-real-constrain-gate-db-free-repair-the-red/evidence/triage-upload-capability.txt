§ 2 — THE MEASUREMENT MATRIX (six runs, three environments × two specs)
================================================================================================

THE INSTRUMENT, AND WHY IT IS NOT THE CONTAINER. Plan 09 settled its "green here, red in CI" case by
reproducing inside `mcr.microsoft.com/playwright:v1.60.0-noble`, because its cause was a RASTERISER
difference that only that image has. This plan's hypothesised cause is an ABSENT ENVIRONMENT VARIABLE,
which is reproducible on any machine by absenting it — and absenting it is a sharper instrument than
the container, because the container would vary the rasteriser as well and could not tell the two
apart. Each variable is set to the EMPTY STRING rather than deleted, for the reason
`playwright.config.ts` records for `RESEND_API_KEY`: `webServer.env` merges over `process.env`, and
`@next/env` re-supplies a `.env.local` value only when the key is `undefined`, so a DELETED variable
would be silently re-supplied from this box's live `.env.local` and the run would measure nothing.

Three environments:

  AS IT STANDS  — this box's `.env.local`, untouched. The control.
  CI's SHAPE    — every Cloudinary variable emptied. `gate-e2e`'s job-level `env:` in
                  `.github/workflows/ci.yml:1526` declares exactly one key, `DATABASE_URL`; a grep of
                  the whole file for `CLOUDINARY` returns nothing. So this is the state the gate runs in.
  DISCRIMINATOR — the PUBLIC identifier `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME` supplied as the invented
                  literal `fitout-ci-placeholder`, with both SECRETS still absent. This is the run
                  that separates "needs a credential" from "needs a name".

§ 4 — THE FOUR ROUTES
================================================================================================

Permitted routes in preference order: REPAIR > SEED > INTERCEPT > ANNOTATE. One line per case.

ROUTE e2e/avatar-crop.spec.ts:974 — ANNOTATE — Delta-3's subject is a save that really lands: the case holds the server action open to make the pending window, then releases it and asserts at :1072-1075 that the round trip stored an avatar. That needs `CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` in the Next process (`src/lib/cloudinary.ts`), which is a credential and is closed by § 5. SEED is unavailable because the subject is the save itself, not a state a save leaves behind. INTERCEPT is unavailable because there is nothing browser-visible to intercept: the provider call is made by `upload_stream` from the SERVER, so `page.route` — which sees only the browser's own requests — can never reach it, and the only browser-visible request is the `next-action` POST, whose fabrication the file's own header refuses as "asserting against our own forgery" and which would run none of the product's upload path. R3 measured that everything except :1072-1075 passes without a credential, so the reason string names that one assertion rather than the whole case.

ROUTE e2e/avatar-crop.spec.ts:2675 — SEED — the case needs an avatar to exist, not an upload to happen: it audits the removal confirm's open-time focus, axe and tab walk, and reaches that overlay only because `avatar-field.tsx` renders the removal affordance when the row carries a photo. § 3a measured that writing that row directly, pointed at the committed local asset `public/vrt/photo-0.svg`, renders the circle and the affordance with every Cloudinary variable empty. SEED outranks INTERCEPT and ANNOTATE, so it is taken.

ROUTE e2e/avatar-crop.spec.ts:2747 — SEED — same state, same asset, one step further: it presses `Remove photo` and reads where focus lands. § 3a measured that the removal lands with a `public_id` that names no asset and no credential to destroy with, because `removeAvatarAction` nulls the columns first and treats the destroy as best-effort. The focus behaviour this case exists for is downstream of the removal's RESULT, which the absent destroy cannot change.

ROUTE e2e/overflow-320.spec.ts:3400 — REPAIR — NOT the seed this plan prescribed, and not an annotation. The fixture already seeds the photo (`:2731-2755`); the walk fails because `<CldUploadWidget>` throws at render when `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME` is absent, taking the photos step down through the route's error boundary. § 5 — WHY THE CREDENTIAL ROUTE IS CLOSED
================================================================================================

The fastest way to make the avatar three pass is to give `gate-e2e` a live Cloudinary credential.
It is closed on two grounds, and THE SECOND IS THE ONE THAT MATTERS.

GROUND 1 — IT WOULD TURN THIS PHASE'S OWN CHECKER RED BY DESIGN.
A real credential can only reach a workflow as `${{ secrets.X }}`, and `scripts/verify-workflows.mjs`
asserts, over `.github/workflows/ci.yml`:

    scripts/verify-workflows.mjs:813-819
      check(
        "zero `secrets.` references in any env / run / with VALUE, across every job",
        ciSecretHits.length === 0,
        …"scanned workflow env, every job env, every container env, every service env, and every step
          run/env/with — 0 hits"…
      );

with the same assertion made a second time over `baselines.yml` at `:596-603`. `secretHitsIn(doc)`
(`:439`) walks every one of those surfaces, so there is no corner of the file a credential could be
written into that the check does not see. The comment directly above it states the intent this plan
must not defeat: "The build step's three visibly-fake literals are LITERALS, so this passes today and
fires the day somebody 'promotes them to secrets'." Plans 19.1-01 and 19.1-05 spent this phase
strengthening the job that runs that checker; adding a credential now would redden the instrument the
phase exists to make trustworthy.

⚠ THE CITATION EVERY EARLIER DOCUMENT USES IS STALE, AND IT IS RECORDED HERE SO NOBODY RE-DERIVES IT.
RESEARCH.md § Cause B cites this invariant as `verify-workflows.mjs:538`. That was true when
RESEARCH.md was written; it is not true now. Plans 01, 05 and 06 added invariants above it and the
check moved to `:813`. What lives at `scripts/verify-workflows.mjs:538` TODAY is part of
`baselines.yml`'s trigger/permissions block ("workflow-level permissions.contents is 'read'"). Any
reason string that must survive this drift should quote the invariant's PRINTED NAME — "zero
`secrets.` references in any env / run / with VALUE, across every job" — which is stable, alongside
the line.

GROUND 2, AND THE ONE THAT MATTERS — THE REPOSITORY IS ABOUT TO BE PUBLISHED.
D-07 and D-08 take this repository public within this phase. A credential added to a workflow now is a
credential published, in a file whose history is published with it — and unlike a red checker, that
cannot be undone by reverting the commit. The first ground says the fix would fail; the second says it
would be a disclosure. A phase whose subject is making CI signal REAL does not buy a green by shipping
a live third-party key into a repository it is opening.

WHAT IS PERMITTED AND WHAT IS NOT, so the distinction survives:
  • FORBIDDEN — any `secrets.` reference, and any real `CLOUDINARY_API_KEY` / `CLOUDINARY_API_SECRET`
    value, anywhere in either workflow file. Neither is added by this plan; § 6 re-runs the checker.
  • PERMITTED — a visibly-invented literal for the PUBLIC identifier
    `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME`, which is served to every browser by construction and is not a
    credential. This plan supplies it from the test harness rather than from a workflow, so not even a
    workflow edit is needed; the precedent for the shape is `ci.yml:1076-1078`'s three
    `ci-build-only-placeholder-not-a-real-*` literals, which exist precisely so that promoting them to
    secrets goes red.
