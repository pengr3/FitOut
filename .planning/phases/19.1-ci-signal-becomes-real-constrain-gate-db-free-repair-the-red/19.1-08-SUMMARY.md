## Accomplishments

**Task 1 (inherited) — Cause F: the discriminator was the wrong instrument.**
The canonical run (CI's `--retries=2 --workers=1`, `--trace on`) was **4 passed / 2.4m**, with `:443`
green in 15.8s. No local DOM-at-the-timeout existed, so the four required observations were measured
from the mechanism with throwaway probes instead. That produced the plan's most consequential finding:
**the observation RESEARCH.md and `triage-harness.md` both nominate to separate the two live
hypotheses — "is the 2:00 PM button absent, or present-but-disabled?" — cannot separate them.** A held
hour IS in the document, `disabled` and `aria-disabled`, but its accessible name is
`"2:00 PM — Unavailable"` (`slot-picker.tsx:336-341` composes `${timeLabel} — ${tooltipFor(...)}`), so
the caller's `{ name: "2:00 PM", exact: true }` reports **ABSENT in both hypotheses**, and the two call
logs are byte-identical to the one CI recorded. Live hypothesis 2 (an earlier spec's hold on a shared
slot) was then **refuted on three independent grounds** — per-run UUID listings, the disjoint `WINDOWS`
map at `hold-countdown.spec.ts:117-122`, and a first attempt that timed out before placing any hold —
leaving the unguarded day click as the only cause the evidence still supports, with its precondition
measured: `selectTargetDayIn` returns **683ms before its own effect is observable** and asserts nothing
about it.

**Task 2 (inherited) — the day helper now asserts its own effect, and the hour message tells four
states apart.** The post-condition asserts `data-selected-single="true"` — read off the live document
(33 day buttons dumped, exactly one carrying it) and off `availability-calendar.tsx:690`, **not** the
`aria-selected` RESEARCH.md guessed; react-day-picker v9 emits no such attribute here. `pickWindow`'s
hour click now reports `present` / `present-but-disabled` / `absent-while-other-hours-render` /
`absent-with-no-hours-at-all`, each naming its likely cause and the file that owns it. **DEFECT 3, handed
over by plan 04 with a transcript, is settled** with `openSeededListing`'s own count-settle idiom — wait
for the streamed boundary to resolve to 1 — and explicitly **not** with `.first()`, which goes green
against a page rendering only the pending shell.

**Task 3 (executed) — the wizard walk was accusing the server of a refusal it never asked for.**
CI failed this **six for six** (two runs × three attempts; it is on `gate-e2e-wallclock.txt`'s
fourteen-failure list, not its two-line flaky list). It does not reproduce here — 14/14 green, the
whole-space walk finishing all nine steps in 13.3s. Three observations, all measured:

1. **The location step's server action returns HTTP 200 in 350ms.** Eight advances, eight
   `POST …/edit`, all 200, 270–452ms, one `next-action` id.
2. **The save-state region reads `""` at step 1 and `Saving…` → `Saved` at every advance** — and it is a
   trace *reference* (unchanged) from arriving at "Where is it?" through its own press, so locally it
   reads **`Saved`** exactly where CI read **`(nothing)`**.
3. **The draft row's `updated_at` moves once per press, eight times**, with `address_line1`/`city`/

**`(nothing)` is the whole finding**, because it is a state a refusal *cannot* produce: `saveAndContinue`
writes `Saving…` into that region synchronously before it awaits, and a refusal replaces it with
`Couldn't save — …`. An empty region means the handler never ran. **The walk clicked and then waited 30s
on the heading — which cannot tell a refusal from a press that was never received — and reported the
first.**

## Decisions Made

- **The Cause F discriminator is falsified, so the distinction moved into the helper.** When the one
  observation that was supposed to separate two hypotheses turns out to be blind to the difference, a
  better trace cannot help; the code under test has to start reporting the difference. That is what
  `clickHourChip`'s four states are.
- **Neither new post-condition retries.** `openBookingSheet` retries because its lost click was
  *observed*, with Playwright's own call log naming the detachment. Neither of this plan's was. For
  `pressAdvance` there is a second, harder reason: if the first press *was* received and merely slow, a
  retry saves and advances twice, the walk ends a step early, and `EXPECTED_MEASUREMENTS` goes red for
  a reason that has nothing to do with the wizard.
- **The press-received signal is the REQUEST, not the UI state.** `Saving…` and the button's disabled
  state are both gone again in under half a second and cannot be asserted without a race; and the
  region already reads `Saved` at press time on steps 2–9, which would have made a
  "region is non-empty" post-condition *vacuous on exactly the step that fails*. The outgoing server
  action is durable and unambiguous.
- **ENVIRONMENT-DEPENDENT was actively looked for before being rejected**, because the plan forbids
  "CI is different" as a verdict — and a verdict of *environment* with no named capability is that
  sentence in better clothes.
