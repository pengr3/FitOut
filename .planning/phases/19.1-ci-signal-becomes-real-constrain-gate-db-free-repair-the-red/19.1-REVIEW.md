**Issue:**
The invariant's printed name is
`"gate-db-free" is unconditional — no if:, no continue-on-error: AT ALL, on the JOB or on ANY STEP`,
and the neighbouring display-name invariant (`:1445`) prints
*"a required status check is matched by this string; changing it silently unbinds the job that runs
`scripts/verify-workflows.mjs`, lint, the design suite and the build"*. The predicate behind both is
an **enumeration of two keys** (`checker?.if`, `checker?.["continue-on-error"]`) with no job-level

```
# vector 1 — the job never runs on any push whose gate-e2e is red (gate-e2e IS red today)

# vector 2 — the reported check context becomes "…(1)" / "…(2)", never the pinned string
  gate-db-free:
    name: gate-db-free (lint + design + build + workflow parse)
    strategy:
      matrix:
        shard: [1, 2]
→ All 55 invariants hold across 3 section(s) (baselines=11, ci=36, cross=8).   exit 0
```

Why it matters, and the two consequences differ:

- **`needs:` is the false-green one.** A job skipped because a needed job failed reports a check run
  with conclusion `skipped`, and GitHub's required-status-check evaluation treats a skipped job as
  passing (this is the documented reason the `always()` aggregator-job idiom exists). So plan
  19.1-15's required check would go **green over a job that ran neither lint, nor the design suite,
  nor the build, nor this checker** — the exact defect class this phase's subject is. Even under the
  more conservative reading (the check stays pending and blocks the merge), the outcome is a
  required gate that has stopped executing.
- **`strategy:` is the fail-closed one**, but it still breaks the binding the sibling invariant
  exists to protect: `name:` is byte-unchanged, so that invariant stays green while the string
  branch protection matches on no longer exists at runtime.

The file's own reasoning already rejects enumerating against an open set — `MAIL_STEP_ALLOWED_KEYS`,
`CHECKER_STEP_ALLOWED_KEYS` and `BUILD_STEP_ALLOWED_KEYS` are all allow-lists, and
`PUSH_FILTER_ALLOWED_KEYS` was introduced in this very phase for the same reason ("the modifier
surface is an open set"). The job level is the one place that rule was not applied.

**Fix:** give the job the same allow-list treatment its steps already have, and let the printed name
state the property rather than two key names.

```js
// scripts/verify-workflows.mjs — beside the "is unconditional" check
const CHECKER_JOB_ALLOWED_KEYS = ["container", "env", "name", "runs-on", "services", "steps"];
const checkerJobKeys = Object.keys(checker ?? {}).sort();
const checkerJobExtraKeys = checkerJobKeys.filter((k) => !CHECKER_JOB_ALLOWED_KEYS.includes(k));
check(
  `"${CI_CHECKER_JOB}" carries NO KEY OUTSIDE [${CHECKER_JOB_ALLOWED_KEYS.join(", ")}] — ` +
    `if:, continue-on-error:, needs: and strategy: each stop this job from running (or rename ` +
    `the check context) while its name: stays byte-identical`,
  checkerJobExtraKeys.length === 0,
  `keys=[${checkerJobKeys.join(", ")}]  unexpected=[${checkerJobExtraKeys.join(", ") || "(none)"}]`,
);
```

Add two standing cases to `tests/design/workflow-invariants.test.ts` using the existing
`withJobKey(CHECKER_JOB, "needs: [gate-e2e]")` / `withJobKey(CHECKER_JOB, ["strategy:", "  matrix:", "    shard: [1, 2]"])`

**File:** `e2e/cancel.spec.ts:295-296`

**Issue:**
`locator.count()` is a point-in-time read with **no auto-wait and no retry** — unlike the
`await expect(...).toBeVisible()` it replaced, which polled. The three assertions preceding it do not
settle the page either: `waitForURL` resolves on navigation commit, and the two
`await expect(...).toHaveCount(0)` checks at `:250-256` are satisfied *immediately* by a
still-streaming pending shell (a locator that has not rendered yet also has count 0). So both counts
can be read at zero on a slow render, and the test then throws the hard error whose text is

> `NEITHER money sentence rendered … the booker was told nothing about their money.`

That is a timing flake wearing the costume of a money defect, and its message sends the next reader
into `src/app/(app)/bookings/[id]/page.tsx` and `manual-return-notice.tsx` to find a bug that is not
there. It is the same "the failure names the wrong file" pattern that `clickHourChip` and
`pressAdvance` were written in this phase to delete — and the idiom that fixes it already exists in
`e2e/helpers/booker-seed.ts:229-256`.

**Fix:** poll the pair to a settled state before forking, so a slow render waits and a genuinely
absent statement still fails by name.

```ts
const state = await expect
  .poll(
    async () => {
      const manual = await manualReturnSentence.count();
      const inTransit = await inTransitSentence.count();
      if (manual === 1 && inTransit === 0) return "manual-return";
      if (manual === 0 && inTransit === 1) return "in-transit";
      if (manual === 0 && inTransit === 0) return "neither-yet";
      return `both (${manual} manual, ${inTransit} in-transit)`;
    },
    { timeout: 15_000, message: /* the existing NEITHER / BOTH prose */ },
  )
  .toMatch(/^(manual-return|in-transit)$/);
```

(This also subsumes WR-01: `both` can never poll to a pass.)
