## Summary

This phase has one theme with two halves. The first half is a **specification-discipline** problem in a
1,288-line parse-based checker: the checker's predicates were each written along the axis that was last
measured (a deleted key, a named attribute, a job that was in scope) rather than along the property the
prose beside them claims. Four rounds of Phase 19 closed four measured mutations; a fifth class remains
open in three places (CR-01, CR-02, CR-03) plus one coverage gap (WR-01). All four are mechanical, all
four have fix sketches already written in `19-REVIEW.md`, and all four were independently reproduced by
the verifier. **This half is low-risk, high-precision work** — the real hazard is that the fixes are
themselves written along a new single axis, which is what produced rounds 2, 3 and 4.

The second half is **triage of a suite that had never once executed on a real runner before 2026-09-04**.
This research pulled the actual `gate-e2e` job log for run `33848750657` and read every failure message
verbatim. The 14 failures are **not fourteen independent defects**: they collapse into six root causes,
and the largest single cause — four of the fourteen — is a **calendar-shape time bomb** that has nothing
to do with CI and would have gone red on a laptop in any five-row month. Two more are real product bugs
(a duplicated DOM `id`, and a table row that grew ~20px past its declared shape). Three are blocked on a
capability CI structurally cannot have (a live Cloudinary credential — and `ci.yml` is *forbidden by an
existing invariant* from carrying any `secrets.` reference). One (`tabular-figures.spec.ts:361`) is a
spec that asserts a condition its own error message declares to be a **known open finding handed to
Phase 17**. And one (`cancel.spec.ts:232` — the test D-01 forbids quarantining) fails because the product
does exactly the right thing in an environment with no PayMongo credential: it renders the manual-return
notice instead of "refund on its way".

**Primary recommendation:** Split the phase into two independent tracks that can run in parallel waves —
a **checker track** (SC1/SC2/SC3, ~4 plans, each proved by a watched-red mutation and a standing case in
`tests/design/workflow-invariants.test.ts`) and a **suite track** (SC4, ~6–8 plans grouped by *root cause*
not by spec file). Sequence SC5 last, as D-08 requires. For the allowlist (D-03), use
**in-file `test.fail(IS_CI, "<written reason>")` annotations plus a build-blocking design test that pins
the entry count and enforces the reason and the forbidden-file list** — this gets fail-closed behaviour
in both directions from mechanisms already documented and already idiomatic in this repository.

### SC2 — The axis-vs-property audit

The defect class in one sentence: **a predicate that LOCATES its subject by substring, or asserts a key's
PRESENCE without denying the modifiers that neuter it, is measuring the axis that was last defeated
rather than the property its own printed name claims.**

There is a crucial asymmetry the audit must preserve, or it will "fix" correct code:

> Substring matching is **safe** when it makes a check MORE likely to fire (a deny-direction count that
> must be zero), and **dangerous** when it is used to LOCATE the subject of a positive assertion.

The `--update-snapshots` counter at `:527-532` is the safe direction — an over-matching substring there
produces a false red, which fails closed. Every anchor below is the dangerous direction.

### Rulesets vs. classic branch protection

Both become available the moment the repo is public. **Use a repository ruleset**, for three reasons:

- Rulesets are the actively-developed surface; classic branch protection is the legacy one. Multiple
  rulesets can apply to one branch, while only one classic rule can. `[CITED: docs.github.com/…/managing-rulesets/about-rulesets]`
- A ruleset is **declarative JSON** — it can be checked into `.planning/` as the exact payload that was
  applied, which matches this repository's "the artefact is the record" habit.
- Ruleset bypass is explicit: *"organization owners or repository administrators will be unable to change
  or rename the default branch unless they are authorized to bypass the ruleset"* — i.e. admin status
  alone does not grant bypass, unlike classic protection's opt-in "include administrators" toggle.
  `[CITED: docs.github.com/…/managing-rulesets/available-rules-for-rulesets]`

## Common Pitfalls

### Pitfall 1: Fixing the axis that was measured
**What goes wrong:** the new predicate closes exactly the mutation in the review and nothing one token further out.
**Why it happens:** the fix is written from the reproduction rather than from the property in the predicate's own printed name.
**How to avoid:** for each fix, write down the *property* first, then enumerate at least three distinct mutations that violate it, and add a standing case for each. If only one mutation exists, the property was written too narrowly.
**Warning signs:** a new `check()` whose printed name is broader than its conjunct list.

### Pitfall 2: A green that means nothing because the mutation did not apply
**What goes wrong:** a `.replace()` anchor drifts, the copy is unmutated, and every red case turns into a meaningless green.
**How to avoid:** `withMutatedWorkflows` already asserts differs-from-input — do not bypass it, and do not add a mutation helper that returns the input on a missing anchor without routing through it.

### Pitfall 3: Blessing a real visual regression into a new baseline
**What goes wrong:** `baselines.yml` regenerates and commits; nobody looks at the pixels; a real defect becomes the reference.
**How to avoid:** upload the diffs from `gate-visual` **before** dispatching regeneration; review all 12; explain the +28px once.
**Warning signs:** a diff whose *dimensions* are unchanged but whose pixel ratio is high — that is a content change, not a reflow, and is the most likely real regression.

### Pitfall 4: Moving the tolerance instead of the constant
**What goes wrong:** `skeleton-geometry.spec.ts:1807` is red; someone raises `HOST_TOLERANCE_PX` from 4 to 20.
**How to avoid:** the spec says it in its own error message — *"Re-measure and move the constant, never the tolerance."* Reproduce, identify which cell wrapped, then decide.

### Pitfall 5: Allowlisting the money path
**What goes wrong:** `cancel.spec.ts:232` is the fastest of the 14 to "fix" by annotation.
**How to avoid:** D-01 forbids it, and the design test's forbidden-file list should encode that so the prohibition survives this phase.

### Pitfall 6: Updating the invariant count in one place
**What goes wrong:** the checker prints 55, `ci.yml:362` says 50, `EXPECTED_GREEN` says 50 → case 1 (the control) goes red for a bookkeeping reason and the real signal is lost.
**How to avoid:** all three move in the same commit. The control case is what enforces it; that is by design.

### Pitfall 7: Assuming a stale `.next` is a product bug
**What goes wrong:** local reproduction of a "route 404s" or "hydration mismatch" failure against a week-old dev server.
**How to avoid:** `rm -rf .next` and restart before any local triage run. `[CITED: memory local-env-and-uat-seed.md; memory fitout-long-agent-run-ops.md]`
