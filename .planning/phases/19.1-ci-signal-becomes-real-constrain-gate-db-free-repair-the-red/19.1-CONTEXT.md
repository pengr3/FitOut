# Phase 19.1: CI signal becomes real — constrain gate-db-free, repair the red e2e baseline, and close the checker's own coverage holes - Context

**Gathered:** 2026-09-05
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase makes a `ci` run mean something. Five things must become true:

1. `gate-db-free` — the job that actually executes `verify-workflows.mjs`, `lint`, `test:design` and
   `next build` — is itself constrained, so deleting or softening its checker step turns the checker RED.
2. Every existing predicate is audited for the **axis-vs-property error**: presence checks must also
   assert the absence of the modifiers that neuter them, and every step anchor must identify its step
   the same way (exact `name:`, never a `run` substring a decoy can capture).
3. The standing test (`tests/design/workflow-invariants.test.ts`) covers the predicates it was built
   for — reverting round 2's own load-bearing fix must turn it red.
4. The `ci` run stops being red on every push.
5. The repository is public and the agreed status checks are required on `main`.

**Out of scope.** No new product features, no new CI jobs beyond what the five criteria require, no
sharding of the Playwright suite (D-13 defers that, and the 90-minute cap must not be raised again),
and no host/ops/booker surface work. Repairing a failing spec is in scope **only** as the means to
SC4 — it is a repair of existing behaviour, never a redesign.

</domain>

<decisions>
## Implementation Decisions

### The red e2e baseline (SC4)

- **D-01:** The 14 failures are **triaged before anything is written off**. Each of the 14 is diagnosed
  first; anything that turns out to be a real product bug is **repaired**, and only genuine test drift
  or flake is eligible for the known-failures allowlist. Every allowlist entry carries a written reason
  naming why it is not a product bug. Blanket quarantine was explicitly rejected: `cancel.spec.ts:232`
  ("re-opening the review screen for an already-cancelled booking redirects, never re-refunds") sits on
  the refund path, and a green `ci` badge sitting on top of an unverified money-path behaviour is the
  exact failure mode this phase exists to prevent.
  — **Reversibility:** reversible — a triage verdict can be revisited per test; nothing is published or migrated.

- **D-02:** If triage finds that most of the 14 are real product bugs, **they all get fixed in this
  phase**. The phase grows rather than the allowlist. SC4 is the criterion that makes every other gate
  in this phase worth having, so the phase is allowed to run to 10–15 plans rather than push real bugs
  behind a green check. Explicitly rejected: capping 19.1 and spinning the remainder into a "Phase 19.2"
  owned by the roadmap.
  — **Reversibility:** reversible — a scope call, revisitable at any wave boundary.

- **D-03:** The allowlist, if it has any entries at all, is **checked in and asserted** so it cannot
  silently grow. The assertion mechanism is Claude's discretion (see below); the property is not.

### The visual gate (SC4 boundary)

- **D-04:** `gate-visual` is **in scope for SC4**, not excluded from it. Its ~36 tracked
  `*-visual-linux.png` baselines have been stale since 2026-08-30 and the job is red on every push
  alongside `gate-e2e`. The baselines are regenerated in this phase so the whole workflow goes green —
  "not red on every push" is a property of the run, not of one job. **If a regenerated diff turns out
  to be a real visual regression, it is fixed, not blessed into a new baseline.** Rejected: scoping SC4
  to `gate-e2e` and recording `gate-visual` as permanently known-red, because a standing red X trains
  everyone to ignore red — the habit SC4 exists to break.
  — **Reversibility:** costly — regenerated baselines overwrite the committed reference set; restoring the
  old ones means reverting binary files across ~36 paths and re-establishing which diffs were intentional.

### Branch protection (SC5)

- **D-05:** The required status checks on `main` are the **four behaviour jobs**: `gate-e2e`,
  `gate-db-free`, `gate-db` and `gate-price-parity`. **`gate-visual` reports but does not block.**
  Rationale: the four that assert behaviour guard `main`, while the one that compares pixels cannot
  wedge a merge over antialiasing or a legitimate one-pixel design change. `gate-db-free` being required
  matters specifically — it holds lint, the design suite, the build and the workflow checker that SC1
  spends this phase hardening, so leaving it non-required would undo SC1 at the branch level. Rejected:
  `gate-e2e` alone (the ROADMAP's literal SC5 text) and all-five-required.
  — **Reversibility:** reversible — a repository setting, changeable in the GitHub UI at any time.

- **D-06:** Branch protection applies to **`main` only**. `dev` stays unprotected: GSD keeps committing
  directly to it, `ci` still runs on every `dev` push so the result is visible, and only the merge into
  `main` has to pass the four checks. Protecting `dev` too was rejected — it would force a pull request
  and a ~45-minute wait on every GSD commit and roughly halve execution pace.
  — **Reversibility:** reversible — a repository setting.

### Disclosure and the public flip (SC5)

- **D-07:** `.planning/` is **published as-is** once SC1–SC3 have closed the vectors. No redaction pass
  over `19-REVIEW.md` / `19-VERIFICATION.md`. Once the vectors are closed those documents describe
  defeated attacks, which is ordinary security writing, and the planning trail is most of what makes
  this repository worth reading in public. Redaction was rejected as theatre: the original payload text
  stays in git history across 2,157 commits unless the history is rewritten, so it buys the appearance
  of caution at the cost of damaging the record. Moving `.planning/` to a private mirror was also
  rejected — it breaks every in-repo link into it.
  — **Reversibility:** one-way — publishing the repository puts `.planning/` and its full history in front
  of crawlers and mirrors; un-publishing does not retract what was fetched or indexed.

- **D-08:** The public flip happens **at the end of the phase**, after every criterion has landed —
  vectors closed, suite green, baselines fresh — and **the user runs it, not Claude**. Claude's last
  step is a pre-flight checklist plus a final full-history secret scan, then it stops and hands over the
  exact command. Two consequences: the first thing anyone sees is a green badge rather than a red one,
  and the irreversible outward-facing click stays with the PM. Rejected: flipping right after SC1–SC3
  (ROADMAP's literal sequencing — it would publish a red badge for the rest of the phase), and
  pre-authorising Claude to run `gh repo edit --visibility public` itself.
  — **Reversibility:** one-way — see D-07. The flip is the act that makes D-07 irreversible, which is why
  it is sequenced last and held by a human.

### Claude's Discretion

The PM is FitOut's product manager, not an engineer. Everything below is Claude's to decide and must
not be escalated:

- How the known-failures allowlist is represented and asserted (external manifest vs. in-file
  annotations, and the mechanism that makes it fail closed when it grows).
- The triage method and ordering for the 14 failures, and how many plans/waves the phase splits into.
- How the axis-vs-property audit (SC2) is carried out and how each repaired predicate is watched red.
- The shape of the SC3 regression case that reverts `e2eMailRun.trim() === MAIL_REFUSAL_RUN` to
  `.includes(...)` and proves the standing suite goes red.
- How `gate-db-free` is constrained (SC1) — the invariant's shape, its anchor rule, and its mutation
  coverage.
- Whether repairing a given failing spec means changing product code, the spec, or a fixture.
- The exact `gh` / API calls and ruleset shape used to configure the required checks, and whether the
  ruleset additionally requires branches to be up to date.

## Existing Code Insights

### Reusable Assets
- `scripts/verify-workflows.mjs`: already sectioned and already holds a positive allow-list, presence
  tests and a `cross` section spanning both workflow files. SC1's `gate-db-free` invariant and SC2's
  audited predicates extend this file rather than starting a new checker.
- `tests/design/workflow-invariants.test.ts`: the round-4 standing mutation suite (12 cases at last
  count) is the established place to prove a predicate goes red under a named mutation. SC3's
  regression case is one more case in it, in the same shape.
- `e2e/helpers/` (e.g. `booker-seed.ts`, the overflow helpers used by `host-listing-grid.spec.ts`):
  fixture and measurement helpers exist; repairs should reuse them rather than inline new seeding.
- Phase 19's own evidence convention —
  `.planning/phases/19-.../evidence/guards-pre-fix.txt` / `guards-post-fix.txt` — is the established
  way to record a watched-red then watched-green pair. Reuse it for every SC1–SC3 mutation.

### Established Patterns
- **Watch it red before you trust it green.** Every invariant this project has shipped was proved by
  reverting the fix and observing the checker fail, with `md5sum` / `git status --porcelain` confirming
  the revert. Phase 19 rounds 2–4 were each defeated precisely where this was skipped.
- **Anchor a step by exact `name:`, never by a `run` substring.** CR-02 is the standing counter-example.
- **A presence check must also deny its neutering modifiers.** CR-01 is the standing counter-example:
  `pull_request: branches: [does-not-exist]` and `paths-ignore:` must both go red.
- One spelling of a value, read rather than copied (D-14's `MAIL_KEY_PREFIX`), with an invariant that
  fires the moment the declaration stops matching the pattern the reader uses.

### Integration Points
- `gate-db-free` (`ci.yml:675`) executes `verify-workflows.mjs` — SC1 constrains this job, and SC5 makes
  it a required check, so the two criteria reinforce each other.
- `gate-e2e` (`ci.yml:1372`) runs `npx playwright test --project=chromium` with no allowlist and no
  `continue-on-error` today. SC4's allowlist, if any, plugs in here; note that adding
  `continue-on-error:` would turn 19-11's unconditional invariant red, by design.
- `gate-visual` (`ci.yml:1172`) already guards against a zero-baseline checkout with an `::error::`
  line; regeneration must keep that guard true.
- Branch protection is a repository setting reached with `gh`/the API, gated on the repo being public
  (currently `PRIVATE`, owner `pengr3`, default branch `main`).

## Specific Ideas

- The PM's framing of SC4: a gate that is red unconditionally carries zero signal, and it is the item
  that makes every other gate in this phase worth having.
- `cancel.spec.ts:232` is named explicitly as the test that must never be quarantined — it is the
  reason blanket quarantine was rejected.
- The pre-flight handover for D-08 should include a fresh full-history secret scan, not a reference to
  the earlier one (2,157 commits, zero credential hits, only `.env.example` ever committed).
- The 90-minute `gate-e2e` cap has already been raised once and must not be raised again; an expiry
  once the job is required is a RED and the correct response is D-13's sharding conversation.

  baseline drift has no forcing function. Worth a follow-up; not in this phase.

  thirds of Invariant B, `withJobKey`'s hard-coded fallback, cases 4/5/6/8 not isolating the predicate

  absorb some; any it does not are carried, not dropped.
