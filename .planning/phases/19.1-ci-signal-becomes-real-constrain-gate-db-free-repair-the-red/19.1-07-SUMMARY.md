## Decisions Made

- **The disjunction identifies the branch before asserting anything.** A bare "one of these two strings is
  on the page" check would pass on a page rendering the wrong sentence for its audit state, which is a
  weakening dressed as a repair. The `count()`-then-branch shape is what buys the per-branch consequence.
- **`.first()` on both visibility assertions.** `getByText` with a regex can match more than one node
  (the `MoneyStatement` sentence and any ancestor carrying the same text), and a strict-mode violation
  there would be a locator failure masquerading as a product failure. The branch has already been
  established by the count, so `.first()` narrows a locator, not an assertion.
- **`expect(alert.n).toBeGreaterThan(0)` rather than a boolean existence check**, with the four actions
  interpolated into the message. The failure text then names the exact predicate that did not match, so
  the reader is told which write was lost rather than that something was absent.
- **The checksum baseline for the watched-red pairs is the post-`git checkout` form of the file, not the
  editor's.** Under `core.autocrlf=true` and `.gitattributes`' `* text=auto`, a `git checkout --` rewrites
  the working tree with CRLF, so a checksum taken before that normalisation cannot match one taken after
  it. Narrowing (a) was therefore re-run from the canonical checked-out form so the pair is genuinely
  equal rather than explained away. `git status --porcelain` is the authoritative proof in both cases.
