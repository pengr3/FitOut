<objective>
Build the signed-in identity surface: a basic profile (Airbnb-style public/private split with optional Cloudinary avatar), the explicit "activate the other capability later" flow (Start hosting / Start booking), and the Airbnb-style mode switch with a distinct host-dashboard route group gated on `canHost`. All writes re-validate server-side, and capability flags are flipped server-side (input:false guard).

Purpose: This completes AUTH-04 (single account acts as both booker and host, via explicit activation + mode switch — D-03/D-04) and AUTH-05 (create/edit basic profile with optional photo — D-09/D-10/D-11). It builds on the Plan-02 schema columns and the Cloudinary helper, and complements Plan 03's signup-time capability choice with the "add it later" half of the model.

Output: Profile view/edit + avatar upload, capability-activation server actions, the mode switch, a gated host dashboard, and green tests for profile persistence, public/private projection, avatar storage, capability activation, and the mode-switch routing.

<!-- Contracts produced by Plan 02 that this plan consumes. See 01-02-SUMMARY.md for exact signatures. -->

From src/lib/auth.ts (server):
- auth.api.getSession({ headers: await headers() }) → { user, session } | null
  user includes: id, email, emailVerified, createdAt (member-since),
  canBook, canHost, role, firstName, lastName, phone, bio, city, avatarUrl, avatarPublicId
- auth.api.updateUser({ body: {...}, headers }) → updates user (NOTE: canBook/canHost/role are input:false,
  so they CANNOT be set through updateUser from client input — flip them via the server-side privileged
  mechanism documented in 01-02-SUMMARY, e.g. a direct Drizzle update on the user row inside a server action).

From src/lib/cloudinary.ts:
- uploadAvatar(buffer: Buffer, userId: string) → Promise<{ secure_url: string; public_id: string }>

From src/lib/validation/profile.ts (Plan 02):
- profileSchema { firstName: min1, lastName?: , bio?: , city?: , phone?: }

Public vs Private split (D-09/D-10) — to implement in src/lib/profile.ts:
- PUBLIC (visible to other users): avatarUrl, firstName, bio, city, createdAt ("member since")
- PRIVATE (account settings only, NEVER public): lastName, email, phone, role, connected accounts
- export function publicProfile(user) → returns ONLY the public subset.

Capability activation (D-03): canBook/canHost are input:false. activateHosting()/activateBooking()
server actions must read the session, then perform a server-side privileged update setting the flag true.
Per D-05, activating hosting only sets the flag + routes toward listing creation — NO Stripe onboarding (Phase 2).

Host route gate (D-04): host pages MUST call auth.api.getSession() and redirect to / (or a "start hosting"
prompt) if !user.canHost. Middleware is optimistic only — the real gate is here (RESEARCH Anti-Patterns).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → profile/avatar server actions | Untrusted profile fields + uploaded file; re-validated + type/size-checked server-side |
| Browser → capability activation | Capability flip must be server-authorized; flags are input:false |
| Browser → /host routes | Host surface must be gated server-side on canHost, not just hidden in UI |
| Server → Cloudinary | api_secret server-only; only the resulting URL/public_id stored |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Elevation of Privilege | User self-grants canHost/canBook/role by tampering the activation or profile request | mitigate | canBook/canHost/role are input:false (Plan 02); activation actions flip the flag via a server-side privileged update after authorizing the session — never from client input. Tested by capability-activate.test.ts. |
| T-04-02 | Elevation of Privilege | Accessing the host dashboard without canHost (UI-only hiding bypassed via direct URL) | mitigate | (host)/host/layout.tsx calls auth.api.getSession() and redirects when !canHost — the per-page server check is the real gate (middleware is optimistic only). Tested by e2e/mode-switch.spec.ts. |
| T-04-03 | Information Disclosure | Private profile fields (lastName, email, phone) leaked in a public profile view | mitigate | publicProfile() projects ONLY public fields; tests assert lastName/email/phone are excluded (D-09/D-10). |
| T-04-04 | Tampering / DoS | Malicious or oversized file upload to the avatar endpoint | mitigate | avatar action validates content-type (image/*) and size (<=5MB) with Zod before uploading; Cloudinary transformation normalizes to 400x400. |
| T-04-05 | Information Disclosure | Cloudinary api_secret exposed to the client | mitigate | Upload runs server-side (server action → uploadAvatar); secret stays in server env; only secure_url/public_id returned to client. |
| T-04-06 | Spoofing | Unauthenticated access to profile edit / capability actions | mitigate | Every server action + (app)/(host) layout reads the session first and redirects/rejects when absent. |
</threat_model>
