`baseline-evidence.md` §7a measured the app's own stylesheet at seven widths (an element carrying each

| class string | 320 | 639 | **640** | 768 | 1023 | **1024** | 1280 |
|---|---|---|---|---|---|---|---|
| `…px-4 py-8 sm:py-12 pb-20` — the listing's OLD `<main>` | 80px | 80px | **48px** | 48px | 48px | 48px | 48px |
| `…px-4 py-8 sm:py-12 pb-20` — **the checkout's `<main>`, shipped today** | 80px | 80px | **48px** | 48px | 48px | 48px | 48px |
| `flex min-h-dvh flex-col pb-20 lg:pb-0` — the NEW layout wrapper | 80px | 80px | 80px | 80px | 80px | **0px** | 0px |

**Confirmed independently in this session against the repo's own generated stylesheet**
(`.next/dev/static/chunks/src_app_globals_css_1igg3k2._.single.css`, Tailwind 4.3.0), by byte offset in the
base layer:

```
.py-8   @ 38496      padding-block: calc(var(--spacing) * 8)
.py-12  @ 38618      padding-block: calc(var(--spacing) * 12)
.pb-0   @ 39272      padding-bottom: calc(var(--spacing) * 0)
.pb-20  @ 39455      padding-bottom: calc(var(--spacing) * 20)
```

`pb-*` is emitted **after** `py-*` within a layer (Tailwind's canonical property sort), so unvariant `pb-20`
beats unvariant `py-8`. But `sm:py-12` lives in its own `@media (min-width: 40rem)` block emitted **after**
the whole base layer, so from 640px up `sm:py-12` wins. **`STICKY_BAR_CLEARANCE` has therefore never been in
effect at or above 640px on either route.** `[VERIFIED: repo's generated CSS + baseline-evidence.md §7a]`

### Pattern 1 — the dev-only server seam (item 3's template)

**What:** a behaviour override that exists only outside production, guarded by a **build-time constant**
rather than an operator-settable env var, with the value parsed and never cast.

**When to use:** whenever a test needs to change what the **server** does. It is the only shape that works
when the computation is in the RSC or a server action.

```ts
// Source: src/lib/dev/today-override.ts (commit c7f1a1a, plan 17-14) — the shipped precedent.
//
//   1. THE PRODUCTION GUARD IS FIRST AND IT IS A BUILD-TIME CONSTANT. `process.env.NODE_ENV` is
//      inlined by the bundler, so in a production build this function is `return null` and the parse
//      below is dead code — pruned, not merely skipped at runtime. It is deliberately NOT an
//      operator-settable env var: an env var can be flipped on a live deploy, a build-time constant
//      cannot.
//   2. THE VALUE IS PARSED, NEVER CAST. [… the shared strict parser, regex-anchored, range-checked …]
```

Its test file pins, among 17 assertions: production inertness **with a positive control** (the same value
honoured outside production), that the guard is *"a build-time constant, as its FIRST statement"*, that the
module *"reads NO other environment variable — the guard cannot be widened by configuration"*, and a
**blast-radius** walk asserting it is referenced by exactly one file. **Any item-3 seam should be held to
this bar**, and the bar is higher here because the guarded path is money-adjacent.

### Pattern 2 — the pre-dispatch prediction

**What:** write the predicted baseline diff **before** dispatching; read the actual diff against it file by
file; an unpredicted changed row or a newly minted PNG is a **finding**, investigated and written up before
close. Never absorbed by widening a threshold and never re-dispatched until green.

**When to use:** every `baselines.yml` dispatch. `baseline-evidence.md` is the shipped instance, including
the part where the prediction was **wrong** and was left standing with a pointer to the correction — because
*"a prediction written after reading a diff is not a prediction, it is a description."*

### Pattern 3 — deletion coupled to its inventory

**What:** a route file's deletion is coupled to four instruments by **disk-walking assertions** that fail in
the intermediate state. Delete file and rows in one commit; watch the intermediate red first.

**When to use:** item 4, and any future route-file removal.

### Anti-patterns to avoid

- **Asserting on the class list instead of on pixels.** `mobile-booker-path.spec.ts`'s header:
  *"⚠ THE ASSERTIONS ARE ON PIXELS, NEVER ON THE CLASS LIST."* Item 1b exists precisely because a class was
  present and had no effect. A class-list assertion would have been green throughout.
- **Verifying a workflow edit by grepping it.** `baselines.yml`'s vacuity table is **six of six green**
  against six real mutations, *including an added `push:` trigger*. Parse it —
  `node scripts/verify-workflows.mjs`. And the mirror failure: a *prohibition* checked by substring goes
  falsely **RED** on the paragraph that forbids the thing.
- **Treating the generation run as evidence.** It wrote the PNGs. Nothing has compared against them.
- **Adding a row to `e2e-baseline-reds.md` to make a run read green.** Forbidden outright. That file is
  amended in exactly one way: re-measured at a named commit, with the SHA at the top replaced in the same edit.
- **Landing anything after the recorded comparison run.**
- **Folding `[17-D19]` in because item 4 opens `overflow-320.spec.ts`.** It is 42 newly-asserting cases and
  it is explicitly parked.
- **Running `npm test` concurrently with anything.** `tests/global-setup.ts` TRUNCATEs shared tables;
  a collision manufactures convincing failures in files nothing touched. Build first, then `npm test` ALONE.
- **Trusting the first red immediately after a build.** Re-run the failing file alone before reading it as a
  defect. And clear a stale `.next/` before trusting `tsc` (stale `.next/dev/types`).

## Common Pitfalls

### Pitfall 1 — Assigning a browser-side instrument to a server-side computation
**What goes wrong:** `page.route` / `page.clock` applied to something the Node process computes. The
instrument runs, reports green, and measures nothing.
**Why it happens:** the surface under test *is* a browser document, so the tier of the *document* gets
confused with the tier of the *computation*.
**How to avoid:** consult § Architectural Responsibility Map before writing the task. Ask "which process
executes this line?"
**Warning signs:** a probe that changes an input and produces no change in the output —
`[17-D26]`'s `data-today` stayed 30, the caption stayed August 2026, the disabled count stayed 29.

### Pitfall 2 — Trusting a ledger row's inference instead of its measurement
**What goes wrong:** the measurement is real and the inference around it is stale. `[17-D1]`'s `git log`
claim (C1) and its `loading-coverage` claim (C2) are both wrong; `[17-D3]` repeats the second.
**Why it happens:** the ledger is assembled at phase end from twelve summaries; a pointer that was right
when written outlives the tree.
**How to avoid:** re-run every command a ledger row quotes. They are all cheap.
**Warning signs:** a row asserting a negative ("is empty", "moves the pins") without a transcript.

### Pitfall 3 — Reading the generation run as the evidence
**What goes wrong:** `baselines.yml` goes green, the PNGs land, everybody stops. Nothing has compared.
**Why it happens:** the recursion-prevention property (`GITHUB_TOKEN` pushes trigger no workflow) and the
"nobody has verified these" property are **the same sentence**, and only the first half is memorable.
**How to avoid:** §7d. Record the comparison run's `headSha` and assert it equals `git rev-parse HEAD`.
**Warning signs:** a recorded run id whose workflow name is `baselines`, not `ci`.

### Pitfall 4 — A `next start` probe poisoning every later Playwright run
**What goes wrong:** a production server left on :3000 is **adopted** by `reuseExistingServer: !CI`. Later
e2e runs measure a production build while believing they measure `next dev`.
**Why it happens:** the reuse is silent and is normally a convenience.
**How to avoid:** `-p 3100`. Kill the real PID, not the `npm` wrapper (which leaves the child holding the port).
**Warning signs:** `EADDRINUSE` on the next `npm run dev` while a stale server still answers 200; or e2e
results that change with no code change. (`[17-D24]`.)

### Pitfall 5 — A production probe failing on a boot guard and being read as the defect
**What goes wrong:** `npx next start` 500s on every page importing the booking actions because
`PLATFORM_WALLET_NUMBER` / `PLATFORM_WALLET_NAME` are absent from `.env.local` — and the probe records "500"
as if it were a status-line finding.
**Why it happens:** `npm run build` passes bare (the guard is exempted for
`NEXT_PHASE=phase-production-build`), so the build being green implies nothing about runtime.
**How to avoid:** pass both inline for that process only, and always read a **published-listing control**
alongside the draft.
**Warning signs:** every route returns the same non-2xx.

### Pitfall 6 — Deleting a route file and leaving its inventory rows
**What goes wrong:** four instruments go red in four different places, two of them build-blocking, and the
run looks like four unrelated failures.
**How to avoid:** one commit, five edits (file + 4 instruments) + 2 prose corrections. Watch the
intermediate red on purpose — it is a free proof that the coupling is enforced.
**Warning signs:** `extra: [...]` from `axe-sweep` AC#2, or `"inventory to disk"` naming a stale entry.

### Pitfall 7 — Absorbing an unpredicted baseline row
**What goes wrong:** the diff contains a row the prediction did not name (`dev-theme-1280` is the live
candidate — it was flaky one run ago), and it is waved through because "the rest is right".
**How to avoid:** an unpredicted changed row is a **finding**, investigated and written into
`baseline-evidence.md` before close. Not a threshold change, not a re-dispatch.

### Pitfall 8 — Reading a shared-fixture race as a phase regression
**What goes wrong:** rows 4–10 of `e2e-baseline-reds.md` are contention-class and pass alone. A multi-worker
run meets them and costs an investigation.
**How to avoid:** run **per file**, `--project=chromium --workers=1`, against one long-lived dev server,
with `npm run db:up` first and a stale `.next/` cleared. Compare every failure against the 10 declared rows.
A failure not on that list is this phase's to explain — **and no row may be added to make a run read green.**
