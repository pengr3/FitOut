## § P1 — `/listings/[id]` under `next build && next start` (item 2, assumption `[A6]`)

**Driven by:** plan **17.1-01**, Task 1, on **2026-08-30**. Manual-only by design — no harness in this
repo boots `next start` (17.1-RESEARCH § Validation Architecture). The three `curl` codes below **are**
the deliverable.

### The question, and why it had to be asked in production

Every reading of `/listings/[id]`'s soft-404 to date is a `next dev` reading. `[17-D2]` measured the
identical mechanism in a **production** build, but on `(host)` — a different segment. So `[A6]` — *that
the soft-404 behaves the same in a production build as in `next dev`* — was never driven on this route.

### The prediction, written before the drive

**404 / 404 / 200** (draft / nonexistent / published control), per 17.1-RESEARCH **C1**.

C1's argument, restated so this section stands alone: `[17-D1]` claims
`git log d24b212..HEAD -- 'src/app/listings/[id]/(detail)/'` is empty. It is not — it contains
`89fb451 fix(260826-l1o): /listings/[id] answers a real 404 again`, which landed **72 minutes after**
`[16-D6]` measured the 200. The question therefore **inverted**: this probe asks *does the shipped
layout-assert hold under a production build?*, and

> **a 200 on the draft is a REGRESSION of `89fb451`, not a reproduction of a known defect.**

**The published control is mandatory.** A probe that only reads 404 cannot distinguish "the guard
works" from "the whole app is 500ing". A 5xx on any of the three would be the `src/lib/paymongo.ts`
boot guard or a build failure — Pitfall 5 — and **not** a status-line finding.

### The mechanism under test (already shipped)

`src/app/listings/[id]/(detail)/layout.tsx` awaits `assertPublicListing(id)`. `loading.tsx` creates an
implicit `<Suspense>` boundary and Next flushes the shell — committing `200` — before the page body
reaches `notFound()`. A **layout** renders in that shell, above the boundary, so awaiting there blocks
the flush and the status line is still settable. `assertPublicListing` is `cache()`d, so the layout's
lookup and the page's are one query.

### The exact `next start` invocation

```
PLATFORM_WALLET_NUMBER=09170000000 PLATFORM_WALLET_NAME="local" \
  node ./node_modules/next/dist/bin/next start -p 3100
```

Three operational facts carried, each with the reason it is not cosmetic:

- **The wallet values are throwaway literals** (`09170000000` / `local`), passed **inline on that one
  process**. `src/lib/paymongo.ts:39-48` refuses to boot in production without them and is exempted
  only for `NEXT_PHASE=phase-production-build` — which is exactly why `npm run build` is green while
  `npm start` is not. Both vars are **absent from `.env.local` and stayed absent**
  (`grep -c "PLATFORM_WALLET" .env.local` → **0**; `git diff --name-only -- .env.local .env.example`
  → empty). No payout path is exercised by a status-line read.
- **Port 3100, never 3000.** `playwright.config.ts:113` sets `reuseExistingServer: !process.env.CI`,
  so a production server left on :3000 is adopted by every later Playwright run — the `[17-D24]` trap.
  3100 is the port `[17-D2]` used.
- **`node ./node_modules/next/dist/bin/next` rather than `npx next`,** so the shell owns the real
  server PID directly. Killing an `npm`/`npx` wrapper leaves `next start` alive holding the port.

### One operational finding, recorded because it is the same trap from the other side

Clearing `.next/` before the build broke a **pre-existing, long-running `next dev` server on :3000**
(Windows PID `11696`, `next/dist/server/lib/start-server.js`, ~2.1 GB RSS, started before this
session). It began answering **500 on every route**, and because `reuseExistingServer: !process.env.CI`
makes Playwright **adopt** whatever is on :3000 rather than start its own, the acceptance-criterion e2e
run would have read as a wall of false reds attributable to nothing in this phase.

It was terminated (`taskkill /PID 11696 /T /F`) so Playwright would boot a clean `next dev`. Recorded
because it is `[17-D24]` arriving from the *dev* side: **any drive that clears `.next/` must also
account for a dev server already running against it.** The stale server's own state was already
unrecoverable — it was 500ing — so nothing was lost by killing it.
