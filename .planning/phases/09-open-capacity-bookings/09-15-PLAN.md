<interfaces>
The shipped e2e idiom (`e2e/availability.spec.ts:1-40, 66-120`): seed DIRECTLY into the dev Postgres
`public` schema (the same database the Playwright `webServer` dev app reads) using `postgres` with
`DATABASE_URL ?? "postgresql://fitout:fitout@localhost:5432/fitout"`; unique ids per run
(`` `e2e_open_host_${randomUUID()}` ``); a bookable listing needs the host `email_verified = true` AND a
`host_payout` row with `payouts_enabled = true`; tear everything down in `afterAll`.

For an open-capacity listing also set: `occupancy_mode = 'open_capacity'`, `per_head_price_cents`,
`max_occupancy` (the cap), `unit_count = 1`, `booking_mode = 'instant'`, `cancellation_policy = 'standard'`,
`status = 'published'`, `timezone = 'Asia/Manila'`, plus `operating_hours` rows for the tested weekday.

Occupancy can be simulated by INSERTing `booking` rows directly with
`open_capacity = true, status = 'confirmed', declared_pax = N, unit = 1` and `starts_at`/`ends_at` set to the
date's opening/closing instants — that is exactly what the claim writes.
</interfaces>

Create `e2e/open-capacity.spec.ts` with a header stating what it proves and why a browser is required (the
decrement is only observable across two independent bookers' views).

Seed: one host (verified + `host_payout.payouts_enabled = true`), one open-capacity listing with
`max_occupancy = 3`, `per_head_price_cents = 35000`, hours 06:00–22:00 on the tested weekday, timezone
`Asia/Manila`, and a second EXCLUSIVE listing as the control. Pick a target date a few days ahead so it is
inside the 90-day horizon and unambiguously in the future.

Cases (assert on rendered text and ARIA, never on internal state):
1. **The public drop-in page is day-shaped.** Visit `/listings/{openId}` unauthenticated:
   - the `Availability` heading carries the `Drop-in` badge and the framing line
     `Pick a day — your pass is good any time they're open.`
   - **no hour chips render** — assert the SlotPicker's chip container / any `toggle` group is absent
   - pick the target date ⇒ the day panel shows the date heading, a scarcity chip, the
     `Open 6:00 AM – 10:00 PM · …` line and `Your pass covers the whole day — come any time while they're open.`
   - the rendered page text contains **no clock-time range presented as a booking** (assert the absence of
     the exclusive-page duration copy)
2. **Spots decrement when someone else books.** With cap 3 and the date empty, the chip reads
   `Only 1 left` after seeding 2 occupying heads (cap 3 ⇒ threshold `clamp(floor(3/2),1,5) = 1`). Seed the
   heads via direct INSERT between two page loads and assert the chip text CHANGES on reload — this is the
   two-booker decrement, observed from the second booker's browser.
3. **Sold out is calm and unselectable.** Seed the third head ⇒ reload ⇒ the day panel reads `Fully booked`
   and `All 3 passes for this day are taken. Try another day.`, and the date cell in the month grid carries
   `aria-disabled="true"` (or is `disabled`) with an `aria-label` containing `fully booked`. Assert the grid
   is still interactive (another date is selectable) — never a dead end.
4. **Search shows the drop-in card without a time range.** Visit the search page with `?date={target}` AND
   `&start=09:00&end=11:00`: the drop-in card renders the `Drop-in` badge, a `/person` price,
   `Service fee included`, and its rendered text contains **no `:` clock time**. Its link `href` contains
   `date=` and neither `start=` nor `end=`.
5. **Sold-out dates leave search.** With the date fully booked, the drop-in listing is ABSENT from the
   `?date={target}` results while the exclusive control is still present.

Keep the money path out of this spec — the real PayMongo checkout is the human walkthrough's job (09-16).
Tear down every seeded row in `afterAll`.
