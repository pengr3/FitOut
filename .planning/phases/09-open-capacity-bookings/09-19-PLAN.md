<objective>
Close **CR-03 layer 2**: `saveOperatingHours` deletes and reinserts every window for a listing with **zero**
booking, occupancy or lock awareness (`src/app/actions/operating-hours.ts:80-94`), and `getModeLockState`
guards only a change of `occupancy_mode`, never the hours.

Purpose: 09-18 makes the counter immune to an hours edit, so the *overbook* is gone. What remains is a real
second harm the re-anchor does not touch — an hours edit **strands passes already sold**. A pass persists
concrete `starts_at`/`ends_at` at hold time (OC-03), and those instants are what the Phase-7 refund ladder,
the payout sweep (`ends_at + delay`), reminders and expiry all key on. Move Monday's opening 06:00 → 07:00
and every pass already sold for a future Monday now claims an entry window the venue will not honour, with a
refund deadline computed from an opening time that no longer exists. Deleting a weekday's hours outright is
worse: `loadOpenDayWindow` returns null, `getOpenDay` renders "Closed on {day}", and the sold passes become
invisible in every read model while still occupying admissions.

The guard is OC-17's shape, one level down: a host may change **how** a space is sold only while nothing is
still to come; they may now also change **when** it is open only for weekdays nothing is still to come on.
Scoped to `open_capacity` listings and to weekdays that actually carry live passes, and — mirroring
`saveListingStep`'s OC-17 idiom — **only a genuine change is refused**, so an unrelated autosave never
freezes the editor.

Output: a new lock module, a shared refusal sentence, the server-side refusal, a host-facing advisory on the
availability page, and a DB-backed mutation-measured test.
</objective>

**(a) Create `src/lib/listing/hours-lock.ts`** exporting

`getOpenHoursLockState(dbConn: DbConn, listingId: string): Promise<OpenHoursLockState>`

where `OpenHoursLockState` is `{ lockedWeekdays: number[]; lockedByCount: number; unlocksAt: Date | null }`.

ONE raw-SQL statement, `booking b` joined to `listing l` on `l.id = b.listing_id`, filtered to
`b.listing_id = $1`, `b.open_capacity = true`, `b.ends_at > now()`, and the imported
`OPEN_OCCUPYING_STATUS_SQL`. Group by
`EXTRACT(DOW FROM (b.starts_at AT TIME ZONE l.timezone))::int` and return that weekday, a `count(*)::int` and
`MAX(b.ends_at)`. Sum the counts and take the maximum `ends_at` in TS to fill `lockedByCount` and
`unlocksAt`; `lockedWeekdays` is the sorted distinct weekday list.

Three rules to state in the header, each with its reason:
- **`starts_at`, not `ends_at`, decides the weekday.** A split-shift or overnight venue's `ends_at` can land
  on the next calendar day; the pass belongs to the day it was bought for.
- **`ends_at > now()` is what makes it "upcoming OR active"** — a finished pass cannot be stranded by an
  hours edit, so a host is never frozen out by their own back catalogue. Same rule as `mode-lock.ts`.
- **The DB clock is the only clock** — SQL `now()`, no injectable `now`, no JS wall-clock read anywhere in
  the module. Phrase this WITHOUT naming the JS date constructors, exactly as `mode-lock.ts:51-53` does, so
  the existing grep tripwire idiom stays usable.

Also state that `lockedWeekdays` is empty for an EXCLUSIVE listing by construction (`open_capacity = true`
filters every exclusive row out), so the caller needs no separate mode branch to stay safe — but the caller
should still branch on the persisted `occupancy_mode` to avoid the query entirely on the exclusive path.

**(b) Add `HOURS_LOCKED_MESSAGE` to `src/lib/validation/availability.ts`.** One exported constant, the O3
grammar the phase uses everywhere (statement + imperative next step, no exclamation, never rendered red):

`"You can't change these hours while drop-in passes are still to come for that day."`

It lives in the validation module for the same reason `MODE_LOCKED_MESSAGE` lives in
