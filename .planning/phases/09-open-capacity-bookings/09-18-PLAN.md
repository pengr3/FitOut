<objective>
Close **CR-03 layer 1** (orchestrator-verified): the admissions counter's identity for a date is the venue's
**opening instant**, re-derived at request time from the listing's *current* operating hours. A host shifting
Monday's opening 06:00 → 07:00 re-keys the advisory lock, empties the counted set, and makes a **second full
cap** sellable for the same date — up to 2× cap paid admissions with no constraint violation, no error, and
nothing in the month grid showing the date as full.

Purpose: this is an overbook path around the exact guarantee the phase exists to provide (OPEN-03). The
exclusive path is immune because the GiST EXCLUDE keys on the booking's **own stored range**; Phase 9
introduced a key re-derived from mutable host config and no guard with it.

The fix is the reviewer's layer 1, in its cheapest correct form: **anchor the counter on the venue-local
calendar day** — a half-open `[dayStartUtc, dayEndUtc)` range over the *stored* `booking.starts_at` — and key
the advisory lock on `listing_id || ':' || YYYY-MM-DD`. An opening instant built for venue-local date D
always falls inside venue-local day D, so the day ranges are disjoint by construction and an hours edit can
move `starts_at` anywhere inside the day without changing which rows count. Layer 2 (refusing the edit
itself) is **09-19**.

**No schema change and no migration.** `booking.starts_at` is already the stored anchor; only the predicate
that reads it changes. The next migration number stays **0023** — do not create one.

Output: one new shared bounds helper, a signature change on `openTakenSql` that forces a compiler census of
every caller, the re-keyed claim, the fixed month `GROUP BY`, and a DB-backed mutation-measured overbook gate.
</objective>
