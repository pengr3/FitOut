<objective>
Close **CR-06** (reported, NOT independently verified) and **WR-01** (warning) — two defects in one `WHERE`
clause.

**CR-06.** `findOwnOpenHold` matches "the booker's own active open hold" as
`open_capacity = true AND (status = 'confirmed' OR (status = 'pending' AND expires_at > now()))
AND booker_id = … AND starts_at = …`. For an open row `starts_at` **is the whole date**, so this matches any
prior booking that booker has for that day — including a fully **confirmed and paid** one. On the exclusive
path the equivalent match is on the exact `(starts_at, ends_at)` window, so booking a different slot is
unaffected; on the open path there is only one "window" per date, so **all** purchases for a date collapse
into the first. A booker who bought 2 passes for Saturday and returns to buy 2 more is redirected to the
booking they already had, with no message of any kind — while the app's own copy for this situation,
`PASSES_FIXED_MESSAGE = "To add more passes, book them separately."`, is what told them to try. OC-18 says
there is deliberately no per-booker head cap, so this is idempotency machinery producing a policy nobody chose.

**WR-01.** The key branch is `idempotency_key = ${key}` with **no `booker_id`**. `openHoldSchema` accepts a
client-supplied key up to 200 chars and `booking_idem_uq` is a **global** unique index, so keys are not
namespaced per user. Mallory posting Alice's key gets `{ ok: true, replayed: true }` carrying **Alice's**
booking id and a redirect to it — an existence oracle, and her own purchase silently swallowed. The exclusive
`findOwnActiveHold` (`units.ts:265`) has the identical shape and is fixed in the same pass.

**This plan is CONFIRM-THEN-FIX.** Task 1 must independently reproduce both defects against the current code
before Task 2 changes a line of `src/`.

Output: a booker-scoped key branch on both functions, a tokenless branch narrowed to a live pending hold, a
per-selection token from `BookCta`, and a test file that begins as the confirmation and ends as the guard.
</objective>

<design_decision>
**The key branch must stay status-agnostic. This is load-bearing and easy to get wrong.**

The reviewer proposes dropping `status = 'confirmed'` from `findOwnOpenHold` entirely. Applied to the
**tokenless** branch that is exactly right — a confirmed pass is not a hold being re-entered. Applied to the
**key** branch it would introduce a new bug: `booking_idem_uq` is a GLOBAL unique index on
`idempotency_key`, so a key whose row exists but no longer matches the status filter would fall through to the
INSERT and raise a **23505**, which `mapBookingError` re-throws (it maps only `NoUnitAvailableError` / 23P01 /
40P01) — a raw 500 on the money path, the same `T-03-500` class as CR-04.

So: the key branch matches **any** row carrying that key **for this booker**, whatever its status, because a
key that already exists can never legally be re-inserted. A replay that hands back a lapsed or cancelled row
is honest — the reserve page already renders `HoldExpiredState` for one — and it is strictly better than a
500. The tokenless branch is where the narrowing happens.
</design_decision>
