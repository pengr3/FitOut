Purpose: a gym host closed for a public holiday adds a whole-day block, sees it listed, and stops worrying —
while the public calendar keeps showing `Spots available`, search keeps returning the listing for that date,
and the claim keeps granting and charging passes. The host then either honours a day they closed or cancels
every pass and pays the D-71 host-cancel fee on each one. This is precisely the "stale-availability is an
unacceptable failure mode" case CLAUDE.md names, and it is an implementation gap against the phase's own UI
spec, not a recorded deferral.

**This plan is CONFIRM-THEN-FIX.** Task 1 must independently reproduce the defect against the current code

<interfaces>
The only `availability_block` read in `src/` — `read-model.ts:220-224`, in the EXCLUSIVE branch, verbatim:

```ts
    dbConn.execute(sql`
      SELECT unit, starts_at, ends_at FROM availability_block
      WHERE listing_id = ${listingId}
        AND tstzrange(starts_at, ends_at, '[)') && tstzrange(${dayStartIso}, ${dayEndIso}, '[)')
    `),
```

Block shape: `availability_block.unit` is `NULL` for a whole-listing block and an integer ≥ 1 for one unit
(`src/lib/db/schema.ts:624`, D-24). An open-capacity listing is publish-enforced `unitCount = 1` and every
open row uses the sentinel `unit = 1`, so the scope that can zero a drop-in date is
`unit IS NULL OR unit = 1`.

Host entry points: `addBlock` / `removeBlock` in `src/app/actions/blocks.ts:81` / `:172`.
`removeBlock` refuses to delete a block whose `reason` is `"host_cancellation"`
(`src/lib/availability/block-reason.ts:9`) — which is exactly why 09-09 stopped drop-in host cancels from
writing one. A host-created block carries no such reason and stays removable; case 4 pins that.

09-18 added `dayStartUtc` / `dayEndUtc` / `dateKey` to `OpenDayWindow` and `venueDayBoundsUtc` to
`open-capacity.ts`. Those venue-local day bounds are the range this plan checks blocks against — see the
design note in Task 2(a).

**(a) The RANGE decision, stated once and applied everywhere.** Check blocks against the **venue-local day**
`[dayStartUtc, dayEndUtc)` (09-18's `venueDayBoundsUtc`), not against the pass window
`[dayOpenUtc, dayCloseUtc)`. Record the reasoning in the predicate's docblock:
- OC-02 makes a date ONE pass — there is no sub-day inventory to withhold, so a host blocking any part of a

- the reviewer's suggested pass-window form is therefore the **rejected alternative**, and it is rejected for
  drift, not for difficulty.

Also record the accepted consequence: a partial block (say 10:00–12:00) closes the whole date for a drop-in
