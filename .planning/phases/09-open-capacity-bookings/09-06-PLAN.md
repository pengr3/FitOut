```typescript
/**
 * OC-17 — the occupancy-mode lock. A host may change how their space is sold only while NOTHING is still
 * to come: switching mode under a live booking would strand it between two arbiters (an exclusive booking
 * on a listing whose capacity is now counted, or an open admission on a listing whose EXCLUDE now governs).
 *
 * ONE authority, TWO consumers: the wizard RENDERS this (the lock alert, 09-UI-SPEC § 1f) and
 * saveListingStep ENFORCES it. The render is a courtesy; the action is the gate (Security V4).
 */
export type ModeLockState = {
  locked: boolean;
  /** how many bookings are still ahead — the alert says "{N} booking{s} … still ahead" (O7). */
  lockedByCount: number;
  /** the LAST of those bookings' ends_at, so the alert can say WHEN it unlocks. Null when not locked. */
  unlocksAt: Date | null;
};

export async function getModeLockState(dbConn: DbConn, listingId: string): Promise<ModeLockState>;
```
One query, mirroring the shipped occupying predicate plus a future bound:
```sql
SELECT count(*)::int AS n, MAX(ends_at) AS unlocks_at
FROM booking
WHERE listing_id = ${listingId}
  AND ends_at > now()
  AND (status = 'confirmed' OR (status IN ('pending','requested','approved') AND expires_at > now()))
```
Comment that `ends_at > now()` is what makes "upcoming or active" true (a session already finished cannot be
stranded), that a lapsed hold does not lock (lazy expiry, same rule as everywhere else), and that the DB
clock is the only clock.
