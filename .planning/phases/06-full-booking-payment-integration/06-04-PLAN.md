<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → placeHold | The booking mode + amount are server-authoritative; a client flag is never trusted. |
| client countdown → confirmBooking | The DB clock (now() vs expires_at) is the sole expiry authority. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-09 | Elevation | placeHold mode fork | mitigate | bookingMode is read SERVER-SIDE from the listing row inside the existing deriveBookable join; the client never selects the mode. The booker-capability + deriveBookable re-check (Security V4) is unchanged. |
| T-06-10 | Tampering | confirmBooking extend-hold on approved | mitigate | Scope the extend to `status IN ('pending','approved') AND booker_id = $userId`; use GREATEST so paying an approved request never shrinks its 24h window (Pitfall 6). The owner-gate (bookerId===userId) is unchanged. |
| T-06-11 | Spoofing | request branch charges nothing | mitigate | The request branch creates NO checkout — no money can move at request time (D-63). Confirmation is still the webhook's sole authority (06-05); the client cannot fabricate a paid/confirmed state. |
| T-06-12 | Tampering | mode-flip affecting in-flight requests | mitigate | Lifecycle correctness keys off booking.status, not the live listing.bookingMode; the mode-flip-independence test proves a flip cannot auto-confirm/drop an in-flight requested/approved row (D-61). |
</threat_model>
