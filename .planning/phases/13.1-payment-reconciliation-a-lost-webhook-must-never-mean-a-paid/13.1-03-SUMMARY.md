## The chosen `RECONCILE_RATE_LIMIT`, and why

**`{ window: 60, max: 5 }`** — the same shape every session-gated privileged action in this repository uses (`CANCEL_RATE_LIMIT`, the capability actions, the Cloudinary sign endpoint), mirroring the Better-Auth credential-endpoint budget.

- **FLOOR.** The client fires once per mount, behind a latch, and only after the poller's ~20s cap. So the fastest a legitimate booker can produce calls is one per ~20s of reloading — at most **three in sixty seconds**. Five is clear of that with headroom, and case (7) asserts the refusal falls no earlier than the fourth call so a future tightening cannot quietly cross into legitimate use.
- **CEILING.** Five provider reads per minute per identity, each itself capped at `CHECKOUT_PROBE_TIMEOUT_MS` (3s). A scripted loop on one signed-in session buys a small, finite amount of PayMongo load.

**It is module-private.** See deviation 1 — the plan's instruction to export it is not satisfiable, and it was proven so rather than argued.

## The observed StrictMode call count

**1, under `<React.StrictMode>`, at the cap.** And the interesting half is that it is **1 for a reason the plan's own rationale gets wrong**:

| Source | Non-strict | StrictMode |
|---|---|---|
| As shipped (early return on `!slow`, plus the latch) | 1 | **1** |
| Latch removed | 1 | **1** |
| Latch removed AND the effect made to fire on mount | 2 | **3** |

The third row is the proof the harness really does exercise the development double-invoke — 3 against 2 in the same run — so case (6) is capable of failing. The second row is the finding: React double-invokes at **mount**, where `slow` is still false and the effect returns before it calls anything, so the thing actually holding "once" is the early return plus `slow` transitioning exactly one time. **The latch is defence in depth**, kept because it is what makes "once" survive an added dependency, a second state that re-enters the branch or a remount — and the component's header now says that instead of repeating the prediction.

## The deletion check, reasoned rather than executed

**If this entire plan were reverted, a booker loses UP TO FIVE MINUTES OF WAITING. That is the whole loss, and it is not the guarantee.**

- The guarantee is `src/inngest/functions/payment-reconcile.ts`, a 5-minute singleton cron that reaches every paid-but-unconfirmed booking with no browser, no session and no page render involved. It was correct and sufficient before this plan and is byte-identical after it (`git diff --stat origin/dev -- src/inngest/functions/payment-reconcile.ts` is empty).
- Nothing in the guarantee was moved here. The action writes no row, holds no state, owns no alert policy, and has no schedule. Delete `src/app/actions/reconcile-payment.ts` and the component's effect and the sweep's behaviour does not change by one row.
- The dependency runs strictly the other way, and is now enforced by a constant rather than by intent: the fast path is bounded by the sweep's own `RECONCILE_EPOCH` and by the same payable-status scope, so **it can only ever accelerate a row the sweep would have reached anyway.** Its reach is a subset of the guarantee's by construction.
- The one asymmetry worth naming: a booker who leaves the page gets nothing from this plan, which is correct — a promise that depends on somebody watching is not a promise, and that is precisely why it is not the one this phase makes.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] `RECONCILE_RATE_LIMIT` cannot be exported, and the plan's own acceptance criterion is what says so**

- **Found during:** Task 1
- **Issue:** The plan's `must_haves.artifacts` list and Task 1's action text both require `RECONCILE_RATE_LIMIT` to be an export of `src/app/actions/reconcile-payment.ts`. A `"use server"` module may export only async functions, Next enforces that at MODULE EVALUATION, and one exported constant therefore kills the whole module — `reconcilePaymentNow` would never run in a browser at all. That is not theoretical: it is the shipped `avatar.ts` defect that broke avatar upload from Phase 1, and `tests/use-server-exports.test.ts` — **one of this same task's acceptance criteria** — is the guard written for it. The two instructions are not jointly satisfiable.
- **Fix:** module-private `const RECONCILE_RATE_LIMIT`, exactly `cancel-booking.ts:109`'s precedent. The spec discovers the budget behaviourally instead, which cannot drift from a constant it never reads.
- **Verification:** break 1 above (verbatim), then reverted; `npx vitest run tests/use-server-exports.test.ts` → 4 passed.
- **Files modified:** `src/app/actions/reconcile-payment.ts`
- **Committed in:** `4198528`

## Issues Encountered

- **Three harness bugs in the jsdom spec, all found by running it.** (a) `db.query.user` is undefined on the test db (it is built without a bound schema) — use `select`.
