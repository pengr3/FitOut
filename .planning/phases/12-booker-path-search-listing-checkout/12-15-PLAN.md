<the_design_decision>
The finding recorded two candidate designs. **Option A is chosen**, and the argument is recorded here
because the next reader will otherwise re-litigate it.

**A — split out a new `gate-visual` job** *(CHOSEN)*. The visual step leaves `gate-db-free` and becomes a
fourth job with a postgis service, migrate + seed, and label addressing, mirroring `baselines.yml`. Job 1
keeps its name, its missing `services:` block and its unreachable URL.

**B — put a database into `gate-db-free`** *(REJECTED)*. Smaller diff, structurally symmetric with
`baselines.yml`. Rejected on four grounds, in descending weight:

  1. **It contradicts D-24, which is the file's organising decision.** `ci.yml`'s header opens with "THE
     JOB SPLIT (D-24 + D-35). THREE jobs, and the split is by DATABASE NEED, not by speed." Option A adds
     a fourth job in that same taxonomy — needs a database and a browser — which is precisely how D-35
     added `gate-price-parity`. Option B puts a service into the job whose entire identity in the
     taxonomy is *needs none*, and the taxonomy stops meaning anything the moment it does.
  2. **It destroys a live tripwire, and the thing that tripwire catches is a product failure, not a
     style one.** With the unreachable URL, `npm run build` exiting 0 PROVES no DB-touching route is
     being prerendered — every one classifies as dynamic and postgres.js connects lazily (measured at
     HEAD 2026-08-13). Point that variable at a live seeded database and a route that silently becomes
     static builds green and ships a page of **frozen availability**. PROJECT.md names double-booking and
     stale-availability as the two unacceptable failure modes of the core value. This is the cheapest
     standing check the repository has against the second one, and B trades it for a smaller diff.
  3. **It forces a rename, and a job rename is a status-check rename.** `gate-db-free` with a service is
     a lie, so B renames it; the name is a GitHub check name, referenced by branch protection if it is
     configured, and quoted throughout `ci.yml`'s header, `baselines.yml`'s header and the 11-22 OBSERVED
     RED records. A rename that silently un-requires a check is a gate removed by accident. Option A
     renames nothing.
  4. **It keeps an asymmetry that A removes for free — and this one was found while reading, not
     inherited from the finding.** `baselines.yml` CAPTURES with the step sequence
     `checkout → npm ci → migrate → seed → playwright`. Today's job 1 COMPARES with
     `checkout → npm ci → npm run build → playwright`, so the capture ran `next dev` against a clean tree
     and the comparison ran it with a production `.next` already on disk. Under A the new job's sequence
     is a step-for-step mirror of the capture job's, and the asymmetry disappears without anyone having to
     remember it. Under B it persists, because job 1 must still build.

**C — a service on job 1, with the reachable URL scoped to the visual step only** *(REJECTED, and named
because it is the clever middle option somebody will propose)*. It appears to keep both properties. It
does not: `ci.yml` moved `DATABASE_URL` from the build step to the JOB on 2026-08-17 with the reason
written in the file — "the visual step needs it too and the app the dev server boots must not be able to
reach a different database from the one the build was checked against. One variable, two steps, no
drift." C reverts that, and then needs the override on the migrate step, the seed step AND the visual
step: three copies of one connection string in one job. Three spellings of the compared database, in the
plan whose entire subject is the compared tree not being the captured tree.

**What A costs, stated rather than hidden:** a second `npm ci` and a second pull of the Playwright image
(three pulls per run instead of two, all in parallel). Against it: the ~30-minute visual step stops
serialising behind the build, so wall-clock goes down, not up.

**What A does NOT change, deliberately:** `gate-db-free` stays IN the container. It no longer needs a
browser, but the container is the environment in which `tests/design/gitignore-baselines.test.ts`'s git
shell-out has been *proven* to behave — run 32020141784's `detected dubious ownership` red, and the
guard-the-guard assertion that caught it, both exist because of it. Removing the container would be a
second unrelated structural change in the same edit, verified by nothing, whose failure mode is a silent
green (git unavailable → the D-29 rule enforced by nothing). Out of scope. Say so in the header.
</the_design_decision>
