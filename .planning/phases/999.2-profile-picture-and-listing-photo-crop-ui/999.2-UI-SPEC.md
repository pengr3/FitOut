# Phase 999.2 — UI Design Contract

> Visual and interaction contract for the image crop/framing UI — profile picture and listing photos. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This phase adds NO new design system, tokens, fonts, spacing steps, or color values.** It EXTENDS the FitOut design system locked across Phases 02–09 (shadcn `radix-nova` / neutral / lucide / Geist; the 8-point spacing scale; 4-size / 2-weight typography; the 60/30/10 coral-accent contract). Two shadcn OFFICIAL blocks (`slider`, `alert-dialog`) and one stack dependency (`react-easy-crop`) are added; nothing else.
>
> **The phase exists because of one sentence from the operator**, recorded 2026-08-10 immediately after the first real avatar upload succeeded: *"it just inserted the photo without confirming or adjusting the zoom and whatever. That's the standard."* Neither AUTH-05 nor LIST-02 is unmet — both are SATISFIED and both upload round-trips are proven against real Cloudinary. This is the framing experience on top of a working pipeline, and **the pipeline is not being rewritten.**
>
> **The phase's shape is set by ONE invariant (IC-01): the product never guesses a framing again.** Today `src/lib/cloudinary.ts:29` guesses — `gravity: "face"` on a source with no face falls back to an arbitrary region, which is literally what the operator got. Everything below follows from replacing that guess with either the user's own choice (the avatar) or with an honest disclosure of what the app will cut (the listing cover).
>
> **The second invariant is IC-02: the preview IS the contract.** Whatever the mask shows is byte-for-byte what gets stored. This single rule is what makes every degenerate source (§ 2e) behave rather than feel broken, and it is why almost none of them need warning copy.

### The three findings that overturned "listing photos are nearly free"

The ROADMAP 999.2 capture said the listing side *"is nearly free: Cloudinary's own widget supports `cropping` / `croppingAspectRatio`."* **That is wrong on three counts**, each measured 2026-08-10. A dated correction has been written into the ROADMAP entry; it is restated here because a future reader will otherwise "simplify" this back to `cropping: true`.

| # | Finding | Evidence |
|---|---|---|
| **N1** | `cropping: true` **forces `multiple: false`.** Cloudinary: *"Interactive cropping is only supported for single-file uploads, so ensure `multiple` is set to `false`."* The wizard uploader ships `multiple: true, maxFiles: 20` (`photo-uploader.tsx:158-159`). Enabling cropping turns a host's batch of 8 photos into 8 separate widget round-trips. | Cloudinary Upload Widget Reference › Cropping parameters › `cropping` |
| **N2** | **It does not crop the asset — it would be a visible no-op here.** Cloudinary: *"The selected dimensions are sent as `customCoordinates` or `faceCoordinates`. To deliver cropped images, set `gravity` to `custom` or `faces` in delivery URLs and include the crop mode in your upload preset."* FitOut delivers the raw, untransformed `secure_url` through a plain `<img>` at **all three** sites: `photo-gallery.tsx:43` (cover) and `:56` (rest), `listing-card.tsx:228`, `search-result-card.tsx:172`. Enabling the key changes nothing on screen until every delivery URL is rewritten — which is the pipeline rewrite this phase is forbidden to do. | Cloudinary Upload Widget Reference › `croppingCoordinatesMode`; the four `<img src={…url}>` call sites |
| **N3** | **The signature endpoint would 400.** `src/app/api/cloudinary/sign/route.ts:35` fixes `ALLOWED_SIGN_KEYS = { folder, source, timestamp }` and returns `400 Bad Request — unexpected upload param` for any other key (T-04-SIGMATCH). A signed upload carrying `custom_coordinates` must have it signed, so the widget's first cropped upload fails at the signature step. | `route.ts:33-35, 94-99` |

### The fourth finding — why the listing side is a **preview** and not a crop

**There is no single cover aspect ratio to crop to.** The cover photo is rendered at **two different shapes** on shipped surfaces:

| Surface | Ratio | Site |
|---|---|---|
| Public listing hero | **16 : 9** | `photo-gallery.tsx:40` |
| Public search result card | **4 : 3** | `search-result-card.tsx:172` |
| Host "Your listings" card | **4 : 3** | `listing-card.tsx:224` |
| Wizard cover tile (editing thumbnail) | 4 : 3 | `photo-uploader.tsx:268` |

Any destructive cover crop bakes in the wrong framing for at least one of them, and then `object-cover` crops it a **second** time. The avatar is the exact opposite case — one shape, one size, one canonical asset — which is precisely why a destructive crop is correct there and wrong here.

The correct listing-side fix is a stored focal region delivered per-surface. That is a delivery-pipeline change (new persisted geometry + a URL builder + three rewritten render sites), explicitly out of scope. So this phase ships the honest half: **show the host both shapes and what each one cuts.** See § 3 and Open Question 6.

**Accent (FitOut Coral) reserved for — EXPLICIT, exhaustive list this phase:**

Accent is **NOT** used for: `Upload photo` (stays the shipped neutral `outline`), `Cancel`, `Remove photo` (either the trigger or the confirm), `Keep photo`, the Slider track or thumb or range, the crop circle's edge, the crop scrim, the cover-preview frames or their captions, or any host-side surface in § 3.

### The Slider is neutral, not coral

The zoom Slider uses the shipped shadcn neutral treatment (`--primary` range, `--secondary`/`--muted` track). Rationale, continuous with the 09-UI-SPEC mode-card decision: **coral marks the one decision per screen, and the decision here is `Save photo`, not the zoom level.** A coral slider would put the accent on the adjustment rather than on the commitment, and it competes with the confirm button 16px below it.

### `Remove photo` — destructive color appears once, in a dialog, paired with a verb

02-UI-SPEC recorded the rule this follows: coral (hue ≈25) and destructive (hue ≈27) are visually adjacent, so *"destructive actions always pair the color with a destructive icon + verb and live in confirmation dialogs — never as a bare colored button in normal flow."* Accordingly:

- The **trigger** on `/profile` is a neutral `outline` `Button` reading `Remove photo` with a lucide `Trash2` glyph. Not red.
- The **confirm** inside the `AlertDialog` is `variant="destructive"` reading `Remove photo`.
- The cancel is `Keep photo`, neutral `outline` — matching the shipped Phase-7 `Cancel booking` / `Keep booking` grammar.

### The crop scrim is a fixed dark value in BOTH themes — deliberate [researcher's call]

The area outside the circular mask renders the source photo under a fixed **`oklch(0 0 0 / 55%)`** scrim in light AND dark mode. This is the phase's one intentional departure from "always use a theme token", and it has a shipped precedent: the `Cover` badge at `photo-uploader.tsx:278` uses `bg-foreground/80` over arbitrary host photography for the same reason. **The scrim sits over the user's photo, not over a theme surface** — a token that inverts between themes would dim a dark photo in light mode and brighten it in dark mode, i.e. the mask would mean two different things. It is not a new token; it is an inline value on one element, and it is not registered in `@theme inline`.

## Frame + mask contract (IC-03 … IC-06) — **the researcher-owned core of this phase**

### IC-03 — the mask matches the RENDER; the bytes are the circumscribing SQUARE

| | Contract |
|---|---|
| Mask shape shown to the user | **Circle** (`cropShape="round"`), aspect 1 : 1 — the same shape and ratio as the only place the avatar renders (`avatar.tsx:36` `rounded-full`, `profile-form.tsx:99` `size-16`). |
| Bytes stored | The **square that circumscribes that circle**, 400 × 400. Not a circle. |
| Why not store a circle | `AvatarImage` already clips with `rounded-full`, so a circular PNG would be clipped identically and gain nothing — while its transparent corners would show as artefacts in any future square context (a transactional email, a host card, an OG image) and would force the whole pipeline off JPEG. The mask is a **statement about the frame**; the asset is a **statement about the pixels**. |
| Mechanical note | `react-easy-crop` reports `croppedAreaPixels` as the bounding square even when `cropShape="round"`. The square is free; no extra geometry is computed. |

**This is the explicit answer to "does the cropper's mask match the actual render frame":** yes for what the user sees, no for what is stored, and the difference is invisible because the render clips it back to the circle.

### IC-04 — what the user sees outside the mask

The source photo **remains visible** outside the circle, under the § Color scrim. It is never hidden, never blurred, never replaced by a solid fill.

*Rationale: the entire question the user is answering is "what is being cut off". A mask that hides the answer makes the user re-open the file picker to check. Dimmed-but-visible is the standard (and is `react-easy-crop`'s default `cropAreaStyle` box-shadow behaviour, so this costs nothing).*

The circle's edge carries a **2px solid `--background` ring** so it reads as a mask boundary rather than a vignette. Never coral, never `--brand`, never dashed.

Behind everything, the stage backing is `bg-muted` — visible only as letterboxing when the source's aspect is extreme (§ 2e).

### IC-05 — zoom range, default, and the anti-blur bound

```ts
// src/lib/avatar.ts — directive-free (see the "use server" trap, § 2f)
export const AVATAR_OUTPUT_PX      = 400;  // the stored square; matches cloudinary.ts:29 today
export const AVATAR_MIN_SOURCE_PX  = 200;  // hard floor on the SHORTER source side
export const AVATAR_MAX_ZOOM_CEILING = 3;

/** Largest zoom that still yields >= AVATAR_OUTPUT_PX of real source pixels. */
export function avatarMaxZoom(shorterSourcePx: number): number {
  return clamp(shorterSourcePx / AVATAR_OUTPUT_PX, 1, AVATAR_MAX_ZOOM_CEILING);
}
```

| Property | Contract | Why |
|---|---|---|
| **Default zoom** | **Exactly 1.0, always.** Never a computed "smart" start, never a face-detected start, never a remembered value. | IC-01. At zoom 1 the crop square equals the shorter source side, i.e. **the maximum of the photo that can be in frame**. The product stopped guessing framings; the default must not reintroduce one. |
| **Minimum zoom** | 1.0. The user can never zoom *out* past the shorter side, because `restrictPosition` keeps the image covering the mask — an avatar with letterboxed bars inside the circle is not a thing FitOut ships. | |
| **Maximum zoom** | `avatarMaxZoom(min(naturalWidth, naturalHeight))`, computed per image from `onMediaLoaded`. | **This is the answer to "what stops a user zooming into a blurry crop."** At zoom *z* the crop window is `min(w,h) / z` source pixels; requiring that to stay ≥ 400 gives `z ≤ min(w,h) / 400`. The bound is therefore *derived from the output size*, not picked. |
| **Ceiling** | 3.0, regardless of how large the source is. | A 4000px photo would otherwise permit 10× — enough to crop a nostril. 3× is the standard avatar range and keeps the slider's full travel meaningful. |
| **Slider step** | `0.01` over `[minZoom, maxZoom]`. | On a source where `maxZoom` is 1.25, a coarse step gives four usable positions. |
| **Keyboard zoom** | Radix `Slider` arrow keys, native. No custom handler. | |

Worked examples (all computable by the planner without re-deriving anything):

| Source | shorter side | `maxZoom` | Behaviour |
|---|---|---|---|
| 3000 × 4000 phone photo | 3000 | 3.0 (ceiling) | Full range |
| 1200 × 900 | 900 | 2.25 | Full range |
| 600 × 800 | 600 | 1.5 | Reduced range — correct, not a bug |
| 400 × 400 | 400 | **1.0** | Zoom row **disabled** + soft note (§ 2e) |
| 300 × 300 | 300 | 1.0 (clamped) | Zoom row disabled + soft note; output is upscaled 300 → 400 |
| 180 × 240 | 180 | — | **Refused before the dialog opens** (below `AVATAR_MIN_SOURCE_PX`) |
| 4000 × 500 panorama | 500 | 1.25 | Pans horizontally, pinned vertically. No special case. |

### IC-06 — output encoding

| Property | Value | Why |
|---|---|---|
| Size | 400 × 400 | Matches what `cloudinary.ts:29` already stores. Nothing downstream changes. |
| Format | **`image/jpeg`** | One predictable format, no branching. A 400 × 400 JPEG is ~30–60 KB, three orders of magnitude under the shipped 5 MB guard (`validation/profile.ts:33`). |
| Quality | **0.9** | |
| Transparency | **Flattened onto opaque white** before encoding | JPEG has no alpha. Flattening is not a hidden step: the crop stage renders the same white behind the masked region, so **the user sees the white matte in the preview before confirming** (IC-02). A transparent PNG logo cannot surprise anyone. |
| Animation | **First frame only** | Same reason — the stage shows a still frame, so what the user approves is what is stored. No detection, no warning copy. See § 2e. |
| Orientation | The saved bytes MUST match the preview on an EXIF-rotated source | **Non-negotiable, and it must be proven, not assumed.** The executor uses the same decode path for the canvas as the cropper used for the stage, and the phase's verification includes one EXIF-orientation-6 JPEG walked end to end. IC-02 is the whole contract; an orientation mismatch breaks it silently. |

| Zoom | Two-finger pinch **and** the Slider. **The Slider is never hidden on mobile** — pinch is undiscoverable and unusable one-handed, and the dialog description names both. |
| Page scroll during drag | Prevented (`touch-action: none` + Radix body lock) |
| Stage size | Fills the dialog's inner width (§ Spacing), so a 360px phone gets a 280px stage — large enough that a fingertip is not most of the frame |
| Footer | Full-width stacked buttons via the shipped `DialogFooter`; `Save photo` on top (reachable with the thumb, above `Cancel`) |
| Hit areas | Every control ≥ 44 × 44, Slider thumb included |
| Rotation | **Not offered.** `react-easy-crop` supports it; this phase does not ship it. Rotation is a second decision on a screen whose whole value is being a single decision, and modern cameras write EXIF orientation that the browser already applies. Open Question 4. |

#### 2e. Degenerate sources — the cases that make crop UIs feel broken

Handled in this order. **Everything before the dialog opens produces a message on `/profile` and no dialog; nothing after it needs copy, because IC-02 makes the preview self-explanatory.**

| Source | Where it is caught | Behaviour |
|---|---|---|
| **Not JPEG/PNG/WebP** (GIF, SVG, HEIC, PDF, anything) | The `accept` attribute filters the picker; the client re-checks because `accept` is a hint, not a gate | `AVATAR_WRONG_TYPE_MESSAGE` on `/profile`, no dialog. Narrowing from the shipped `image/*` also stops SVG reaching Cloudinary, which is a security tidy-up, not the reason. |
| **Over 5 MB** | Existing `AVATAR_MAX_BYTES` guard, now also applied client-side before decode | The shipped message `Image must be 5 MB or smaller.` — **reuse verbatim**, do not write a second one |
| **Undecodable** (corrupt file, HEIC that slipped through, browser can't decode) | Decode step throws / `onerror` | `AVATAR_UNREADABLE_MESSAGE`, no dialog |
| **Tiny** — shorter side < 200px | Measured after decode | `AVATAR_TOO_SMALL_MESSAGE`, no dialog. Refusing beats shipping a visibly bad avatar the user chose blind. |
| **Small** — shorter side 200–399px | Measured after decode | **Dialog opens.** Zoom row disabled (`maxZoom === 1`), `AVATAR_SOFT_SOURCE_NOTE` renders at 14/400 muted below it. The user decides; the app does not decide for them. |
| **Extreme panorama** (e.g. 4000 × 500) | No special case needed | `maxZoom = 1.25`; at zoom 1 the mask holds a 500 × 500 centre crop, the user pans along the long axis and is pinned on the short one. `restrictPosition` makes this correct by construction. |
| **Extreme portrait strip** (e.g. 500 × 4000) | Same | Identical, axes swapped |
| **Transparent PNG** | No special case needed | Transparent pixels composite onto white — **and the stage renders that same white behind the mask, so the user sees it before confirming** (IC-02/IC-06) |
| **Animated WebP** | No special case needed | The stage shows a still first frame; the saved JPEG is that frame. What you saw is what you got. No detection, no warning. |

**No spinner, no progress bar, no skeleton in the dialog.** Decoding a ≤ 5 MB local image is instant and the file never leaves the device. The only busy state in the phase is `Saving…` on the confirm (§ 2f).

#### 2f. Cancel and save semantics

| Path | What it leaves behind |
|---|---|
| **Cancel** (button, `Esc`, or overlay click) | **The old avatar, byte-unchanged. Nothing uploaded, nothing half-written, no orphan on Cloudinary.** The dialog closes, the cropper unmounts, the object URL is revoked, and — critically — **the file input's `value` is reset to `""`** so re-picking the same file fires `change` again. Without that reset, cancel-then-retry-the-same-photo is silently dead. |
| Cancel confirmation | **None.** Nothing has been created, so a "are you sure" would be friction on a no-op. Overlay click and `Esc` are both allowed for the same reason. |
| **`Save photo`** | Confirm reads `Saving…` and is disabled; `Cancel` is disabled; **the dialog is not dismissable** (`onEscapeKeyDown` / `onInteractOutside` prevented) |
| Save **succeeds** | Dialog closes, preview swaps to the returned URL, `router.refresh()` — the shipped behaviour at `profile-form.tsx:78-79` |
| Save **fails** | **The dialog STAYS OPEN** with the framing intact, and the error renders inside it via `role="alert"`. Closing on failure would discard work the user just did and send them back to the file picker for a problem that was not theirs. Copy: the shipped `Could not upload your photo. Please try again.` — reuse verbatim. |

#### 2g. Accessibility (non-negotiable)

- **The stage is keyboard-operable.** It carries `tabIndex={0}` and `aria-label="Photo position. Use the arrow keys to move your photo."`, with an `onKeyDown` that maps ↑↓←→ to an 8px crop translation and Shift+arrow to 24px. `react-easy-crop` does not provide this; without it the one control this phase exists for is pointer-only. **This is not optional.**
- Zoom is keyboard-native through Radix `Slider`.
- Radix `Dialog` supplies the focus trap and returns focus to the triggering button on close; do not override it.
- The alert dialog's initially focused action is the **safe** one (`Keep photo`).
- Both pre-dialog rejections and the in-dialog save failure announce via `role="alert"` (the shipped pattern at `profile-form.tsx:127`).
- The crop scrim is **not** the sole signal for anything — the mask is a shape, not a color.
- Every state resolves in light and dark via tokens, with the single documented scrim exception (§ Color).
- `Cover` / preview images in § 3 carry real `alt` text, never `alt=""` on a photo the host is being asked to judge.

### 4. The server transform — `src/lib/cloudinary.ts:29`

**Today:**

```ts
transformation: { width: 400, height: 400, crop: "fill", gravity: "face" }
```

**After:**

```ts
transformation: { width: 400, height: 400, crop: "fill", gravity: "center" }
```

**The entire server-side change this phase makes is one word.**

| Question | Answer |
|---|---|
| Why not delete it? | Because deleting it opens a hole. `uploadAvatarAction` is a public server action; its shipped Zod guard checks **type and size only** (`validation/profile.ts:39-47`) — it does not check dimensions. A non-browser client can POST a 4.9 MB 8000 × 6000 JPEG straight to it and never touch the cropper. The transform is what makes that case store a bounded 400 × 400 asset. It stays as a **fail-closed normalizer**. |
| Why is it no longer "wrong"? | Because it stops being a **framing decision**. On the contract-honouring path the input is already a 400 × 400 square, so `crop: "fill"` at 400 × 400 crops nothing and `gravity: "center"` has nothing to centre — **the transform is arithmetically the identity.** It is present but inert. |
| Why `center` and not `auto`/`faces`/`custom`? | `gravity` must never again select a region. `center` is the only value that cannot invent a framing: on a square it is a no-op, and on a bypassed non-square input it takes the middle, which is the least-surprising possible fallback. `gravity: "face"` on a faceless source picking an arbitrary region is the literal bug that opened this phase. |
| Anything else on the server? | **No.** No `format`, no `quality`, no `fetch_format`, no eager transformations, no new folder, no `public_id` change. `overwrite: true` and `folder: "fitout/avatars"` stay (D-C: one canonical asset). |

**Two documentation corrections ship with it** — both are currently-true comments that this change makes false:

| File | Line | Says today | Must say |
|---|---|---|---|
| `src/app/actions/avatar.ts` | 10 | *"Cloudinary's transformation additionally normalizes to 400x400 face-cropped, so a hostile aspect ratio cannot blow up storage."* | The framing is the user's; the transform is a dimension normalizer for the bypass path only |
| `src/lib/cloudinary.ts` | 1-9 | header docblock describing the avatar path | Note that bytes now arrive pre-framed and that `gravity` must never re-select a region |

A false comment on the money-adjacent-adjacent path is how the next reader reintroduces `gravity: "face"`.

## The consistency question — decided explicitly

> **Should the avatar's bespoke in-app cropper and the listing side's preview overlay read as one product?**

**Yes — and after decision D-A they trivially do, because there is no second UI toolkit anywhere in this phase.**

The version of this question the ROADMAP posed — *"whether the avatar's bespoke cropper and Cloudinary's widget UI should look like one product"* — **has been dissolved rather than answered.** Cloudinary's cropping UI is not being enabled, for the three measured reasons N1/N2/N3, so the two-visual-languages problem never arises. That is a genuine second-order benefit of D-A, and it is worth stating plainly so nobody reintroduces the problem while "simplifying".

What remains is a real and deliberate asymmetry, and it is **not** a design inconsistency:

| | Avatar | Listing cover |
|---|---|---|
| Surface | Modal `Dialog` with a live cropper | Static preview block in the wizard |
| The user's power | **Chooses** the framing | **Sees** the framing |
| Why | The framing is destroyed at upload (`cloudinary.ts:29`) and there is exactly **one** render frame (a 64px circle) to choose for | Nothing is destroyed — the original is stored whole — and there are **two** render shapes (16:9, 4:3), so no single choice can be right |

**The rule that makes them one product** is not "same widget"; it is: **wherever FitOut is going to cut a photo, it shows the user the cut before it matters.** The avatar earns a control because a control can fix it. The cover earns a disclosure because a control there would bake in a wrong answer for one of two surfaces. Both are built from the same Radix/shadcn primitives, the same Geist scale, the same 60/30/10 tokens, the same `AspectRatio` + `object-cover` rendering, and the same voice. A user moving between them sees one product with two appropriate affordances — not two products.

**They would stop being one product if:** the listing side gained a Cloudinary-chrome crop step (a second visual language *and* a second interaction grammar), or the avatar side shipped a non-Radix cropper with its own stylesheet (§ Component Inventory records why `cropperjs` was rejected on exactly this ground).

## Copywriting Contract

Voice (continued from Phases 2–9): clear, warm, plain verbs, sentence case. Follows the 09-UI-SPEC discipline exactly — **every user-visible string in this phase is an exported single literal**, so the component, the server action and the test assert the same bytes.

**Where the constants live — and the trap that will kill the phase if ignored.** They go in **directive-free** modules (`src/lib/avatar.ts`, `src/lib/listing/cover-frames.ts`). They must **NOT** be added to `src/app/actions/avatar.ts`, and must **NOT** be re-exported from it. That file is `"use server"`, and Next rejects a `"use server"` module that exports anything but an async function **at module evaluation** — which is exactly how avatar upload was silently dead for all of Phase 1 while its tests stayed green (`actions/avatar.ts:19-27` records the whole incident; `validation/profile.ts:10-18` records the fix; `tests/use-server-exports.test.ts` holds the line repo-wide). ### The locked copy rules (contract, not suggestion)

| # | Rule | Why it is locked |
|---|---|---|
| **F1** | Copy never names the vendor, the transport, or the mechanism. No `Cloudinary`, no `canvas`, no `aspect ratio`, no `resolution`. ## Screen / State Contract

| Screen | States the executor must implement |
|---|---|
| `/profile` avatar field | no avatar (initials + `Upload photo`) · has avatar (image + `Change photo` + `Remove photo`) · rejected: wrong type · rejected: too large · rejected: undecodable · rejected: too small · removing (pending) · removal failed |
| `ImageCropDialog` | open at zoom 1 (default, always) · dragging · zooming (slider) · zooming (pinch) · zoom row **disabled** + soft note (small source) · saving (`Saving…`, non-dismissable) · save failed (open, framing intact, `role="alert"`) · cancelled (nothing left behind, file input reset) |
| Crop stage geometry | normal source · square source (`maxZoom === 1`) · extreme panorama (pans one axis, pinned on the other) · extreme portrait strip · transparent PNG (white matte visible) · animated source (still first frame) |
| Removal confirmation | idle (focus on `Keep photo`) · pending (`Removing…`, both disabled) · failed (open + `role="alert"`) · confirmed (closes, initials return) |
| Wizard photos step | 0 photos (shipped empty state, **no preview**) · ≥ 1 photo (grid + cover preview, two frames) · below minimum (shipped `Add N more…` line, unchanged) · reorder in flight (preview follows `photos[0]`) |

**Visual hierarchy / focal point (locked, per surface):**
- **Crop dialog:** the **stage is the entire screen**. Title above it, one slider below it, two buttons under that. Nothing else may be added — no filters, no rotation, no format picker, no dimension readout.
- **`/profile` avatar field:** the 64px circle is the anchor; the controls sit beside it, `Change photo` before `Remove photo`.
- **Wizard photos step:** the **grid stays the working area**; the cover preview is a footnote beneath it, never above and never inside a tile.

**Interaction rules (locked):**
- **Nothing reaches the network before `Save photo`.** No pre-upload, no speculative upload, no "we'll clean it up if you cancel".
- **The default framing is always zoom 1, centred.** The product does not guess (IC-01).
- **Zoom can never exceed the source's real pixels** beyond the derived bound (IC-05).
- **The preview is byte-honest** (IC-02) — including EXIF orientation, which must be proven with a rotated test image.
- **A cancel is a true no-op**, including resetting the file input's `value` so the same file can be re-picked.
- **A save failure never closes the dialog** (F5).
- **The listing side changes no bytes and no upload params.** If a future task finds itself editing `ALLOWED_SIGN_KEYS` or a delivery URL, it has left this phase.
- **Every control is reachable and operable by keyboard**, including panning the crop.

## New Tokens to Add

**None.** Zero new color tokens, zero new type sizes, zero new spacing steps, zero new radii.

Everything new — the crop stage, the circular mask, the scrim, the zoom row, the removal confirmation, the cover-frame preview — is expressed through existing tokens (`--muted` / `--secondary` / `--border` / `--background` for the calm surfaces, `--brand` for the single `Save photo`, `--destructive` for the single removal confirm) plus non-color signals (shape, words, `disabled`, icon + text).

The one non-token value in the phase is the fixed `oklch(0 0 0 / 55%)` crop scrim, which is an inline value on one element, is **not** registered in `@theme inline`, and is justified in § Color.

**Do NOT introduce** a "cropper background" token, an "overlay" token, a "mask ring" color, or a brand-tinted slider. A crop dialog is plumbing; it gets no visual identity of its own.

## Open Questions — [researcher's call]s the planner or user may override

| # | Call | Rationale | Risk if wrong |
|---|---|---|---|
| **1** | **`AVATAR_MIN_SOURCE_PX = 200`**, with 200–399 allowed but flagged soft — rather than a hard floor at the 400px output size. | A 400 floor rejects plenty of real profile pictures imported from other sites. 200 refuses only what will visibly fail while letting the user make the call in between. | If soft avatars appear in UAT, raise the constant to 400 and delete the `AVATAR_SOFT_SOURCE_NOTE` branch — a one-constant change plus one removed conditional. |
| **2** | **`AVATAR_MAX_ZOOM_CEILING = 3`** on top of the derived bound. | Without a ceiling a 4000px source permits 10×, which is enough to crop a nostril and makes the slider's usable travel a sliver at one end. | Trivially tunable; it is one exported constant. |
| **3** | **The output is JPEG with transparency flattened onto white**, not format-preserving PNG-when-alpha. | One format, no branching, bounded size, predictable in both themes — and IC-02 makes the matte visible before confirming. | A logo-style transparent avatar gets white corners inside a circle mask (mostly invisible). If that matters, branch to PNG when the decoded source has alpha; the geometry is unaffected. |
| **4** | **No rotation control.** | A second decision on a screen whose value is being one decision; EXIF orientation is already applied by the browser. | A user with a sideways photo from a camera that wrote no EXIF has no fix but to rotate it before uploading. `react-easy-crop` supports `rotation`; adding it later is a prop and one more control in the zoom row. |
| **5** | **The crop scrim is a fixed dark value in both themes.** | It sits over the user's photo, not over a theme surface; an inverting token would make the mask mean two different things. Shipped precedent at `photo-uploader.tsx:278`. | If a reviewer wants strict token purity, register it — but then the dark-mode value must stay dark, which makes the token misleadingly named. |
| **6** | **The cover-frame ratios are exported once and imported by all four sites**, including three shipped, UAT-passed render surfaces. | A preview whose only value is accuracy must be structurally unable to disagree with what it previews (09-UI-SPEC's *imported, not copied*). | It edits three shipped files for a same-value refactor. Lower-risk alternative: leave the literals and add a test asserting the preview's ratios equal the render sites'. Equally binding, zero edits to shipped surfaces — planner may take it, but must state the choice explicitly. |
| **7** | **The cover preview shows two frames, not three**, and covers only the cover photo. | 4:3 serves both card surfaces; the wizard's own tiles are editing thumbnails, not promises to a booker. | A host is not shown that non-cover photos are 1:1 in the wizard and 4:3 publicly. Adding a third frame is one array entry. |
| **8** | **The preview sits below the grid, not on the cover tile.** | That tile already carries a badge, a drag handle and three icon buttons; a fourth affordance is unreadable at 320px. | If UAT wants it adjacent, it can move inside the cover tile's 2×2 desktop span — but it must not render on mobile in that position. |
| **9** | **Avatar removal ships as an `alert-dialog`, adding a second official block.** | It is the correct primitive for a destructive confirm; the alternatives are repurposing `dialog` (wrong role, no enforced safe focus) or a bespoke inline two-step. | One more block in the bundle. Operator confirmed removal is in scope (D-B), so the confirmation is required either way. |
| **10** | **`gravity: "center"` rather than deleting the server transform.** | The action is publicly reachable and its Zod guard checks type and size but not dimensions, so a bypassing client could store an arbitrary-size asset. On the honest path the transform is the identity. | If a reviewer prefers deletion, a server-side dimension guard must be added to `avatarFileSchema`'s consumers first — strictly more work for the same outcome. |
| **11** | **No numeric zoom readout anywhere.** | A percentage invites optimising a value with no meaning to the user, and would be the only figure on the screen. | If UAT reports users wanting precision, a `tabular-nums` label is additive and needs no token. |

**Not decided here (correctly out of a UI contract's scope):** the exact canvas/decode API used to produce the blob (any path that satisfies IC-06 and the EXIF proof is acceptable), where `removeAvatarAction` sequences the Cloudinary destroy relative to the column null-out, whether the client dimension guard shares a module with the Zod schema, and the future non-destructive listing-cover focal-point model (§ Source of truth, finding 4) — which is a delivery-pipeline phase, not this one.
