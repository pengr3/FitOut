# Phase 18.1 Plan 15: Close D5 — the seven-day verification lockout Summary

An abandoned Didit flow no longer locks a host out for up to seven days: `pending` joins the submission path's `WHERE` as a third positive equality, the write is a RESUME that preserves the host's ops-queue position, and a session the partner has already finished is refused rather than replaced.

## What shipped

**The defect, restated once because it is unusual.** Nothing was broken. Three individually-correct behaviours composed into a trap: the submission upsert's `WHERE` admitted only `unverified` or a cooled-down `rejected` (which is what stopped a host minting a second session and paying twice); the hosted-flow `url` was not stored (its `session_token` is a bearer secret); and the reconciliation sweep read `"Not Started"` — a *live* session — and correctly did nothing. The PM found it by hand during 18.1-14's sandbox walk and measured it at 128 minutes: `status: "Not Started"`, `expires_at` exactly seven days out, no way to re-press, no way to resume, no route to a human (D-262/D-263) and no listing to create (D-255).

**Task 1 — the ruling table learns one more thing about the vendor's vocabulary.** `sessionOpen: boolean` joined `DiditStatusOutcome` on the *existing* `STATUS_OUTCOMES` table rather than in a second map beside it, so `tsc` enumerates all ten and a status added to the tuple without a ruling stays a compile error. `true` for the four unfinished states (`Not Started`, `In Progress`, `Awaiting User`, `Resubmitted` — ADDENDUM A3's reuse set, transcribed rather than inferred), `false` for the six finished ones, and **`false` on `UNKNOWN_STATUS_OUTCOME`**: on this axis "open" is the permissive answer, and permissive costs a billable session and repoints a compliance handle. `isDiditSessionOpen(sessionId)` on the adapter is two lines — `fetchDiditDecision` plus the shared mapper — with no second normaliser, no status literal and, deliberately, **no `catch`**.

**Task 2 — the submission path.** The `WHERE` is now three positive equalities, `suspended` still structurally absent. `created_at = CASE WHEN host_verification.status = 'pending' THEN host_verification.created_at ELSE now() END` — inside `ON CONFLICT DO UPDATE` a bare `host_verification.x` is the existing row's value, which keeps the "one guarded statement" property. A new **guard 5** reads the caller's own row (a narrow two-column read of the action's own — `loadHostVerification` was NOT widened, because it feeds three RSC pages and a session handle would travel into an initial RSC payload, the shape F-6/D-271 already refused) and, only for a `pending` row holding a non-blank handle, asks whether the session is still open.

**Task 3 — the words and the panel.** `VERIFICATION_SIGNAL.pending.wayOut` is `"Finish the check"`, and the reason gained one clause. Not one sentence was typed into a component.

## The three properties worth reading twice

**1. `created_at` does not move on a resume, and that is FINDING F-1 in reverse.** F-1's content is that a *resubmission* must re-stamp so a repeat submitter cannot permanently outrank first-timers in the `created_at ASC` queue. A resume is not a new ask — same session, same `vendor_ref`, same wait — so re-stamping it would move a host who has been waiting **up** the queue for pressing a button, which is the same line-jumping D-249 forbids arrived at from the other side. Case 14 pins it by **equality against the seeded instant**, not `<= now()`, against a fixture seeded at `now − 3h` / `now − 30m`. Both margins are deliberate: 18.1-11 measured that `COOLDOWN_HOURS` 24 → 25 left the whole suite green because one fixture sat at exactly `now − 25h`, and a fixture stamped at `now()` cannot tell "preserved" from "re-stamped" at all.

**2. A finished session is refused, not replaced — and this is the part D5 itself did not say.** A bare widening would have recreated D5 through its own remedy. A host pressing while a verdict was in flight — the webhook dropped, the sweep's grace window not yet elapsed — would have minted a *new* billable session and overwritten `vendor_ref`, orphaning a real answer for as long as the row lived. Hence the pre-check *before* the ask. Case 15 drives both `Approved` and `Expired`, because it is the **openness** that decides and not one status, and asserts on the recorded calls (**zero** create-session POSTs) rather than only on the row — "the row did not change" is equally true of a refusal that never asked and of an ask whose write was refused, and only the first is the property.

**3. The pre-check is not the gate.** It is a snapshot taken before two round trips and the row can move underneath it. Case 17 drives exactly that: an `approved` row whose session the partner reports **wide open** is still refused, because that state is simply absent from the `WHERE`. The case also records the accepted cost (T-18.1-1509): the create-session POST still happens on that branch, because moving the vendor ask after the write would break the fail-closed ask-then-write ordering 18.1-07 argued for.
