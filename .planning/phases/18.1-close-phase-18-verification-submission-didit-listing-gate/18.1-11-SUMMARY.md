# Phase 18.1 Plan 11: `/host/verify` — the Surface a Host Asks to Be Checked From Summary

**A host can now ask, from a page under `/host`, and every word on it has one owner, every figure on
it arrives finished from the server, and the instant it promises is the same instant the database
enforces.** The surface renders all six verification states, refuses to read the checking partner's
redirect, and tells a host the check needs a phone *before* they press anything rather than after a
hand-off that would not have run where they were standing.

## What shipped

### 1. `src/lib/host/verification-cooldown.ts` — deferred item D2, resolved

`COOLDOWN_HOURS` lived inside `src/app/actions/host-verification.ts`, a `"use server"` module. It was
correct there for exactly as long as that action's own `WHERE` was its only reader. This surface is
the second reader, and there were three ways to hand it the number:

| Shape | Verdict |
|---|---|
| Export it from the action | ⛔ **Not available.** A server-action module may export only async functions (`tests/use-server-exports.test.ts`, with a shipped incident behind it), and every export of one is a network-reachable POST endpoint besides |
| Spell `24` again at the page | ⛔ **The two-authorities defect.** The figure a host reads would be a different declaration from the clause that refuses them — PROJECT D-130 / GATE-05, one domain over |
| An unguarded declaration module beside the guarded one | ✅ **Shipped.** The `payments/config.ts` ↔ `payments/fees.ts` split that `deferred-items.md` D2 names for this family of value |

The action imports it; its guarded UPDATE is otherwise byte-unchanged. `tests/listing/review-signal.test.ts`'s
fixture stopped re-spelling `24` and reads the constant, so the sentence it scans is the sentence the
shipped cooldown actually produces.

⚠ **Not added to `server-only-guards.test.ts`'s `MUST_NOT_BE_GUARDED`, and that is a decision.** Both
rows in that list were split out of modules carrying the CLIENT-BUNDLE guard and each names the
shipped client importers that make the absence of a guard load-bearing. This value was split out of a
SERVER-ACTION module — a different guard family, with its own gate — and nothing in it is a money
rate, a credential, a connection or an environment read.

### 2. `src/components/host/verification-panel.tsx` — six states, two gates, one region

Composes `PanelCard tone="muted"` and opens no raw box. **Not one sentence is authored in the file:**
every host-visible string is imported from the copy module or returned by the action.

| State | What it draws |
|---|---|
| `unverified` | the panel + THE FORM |
| `pending` | the panel and nothing else — the hosted-flow URL is not storable, so a continue affordance would act on nothing |
| `approved` | terminal; one inline underlined link, no hue, no glyph, no control |
| `rejected` | the stored sentence, then EITHER the retry control and the form (cooldown elapsed) OR one sentence naming the instant. Never both, never neither |
| `suspended` | the shipped `HostingPausedNotice`, unchanged, and **no submit control** — D-266 made visual |
| `grandfathered` | terminal, same shape as `approved` |

The form is **one `<form>`, two gates, one control**: the D-269 email gate on the shipped
`PublishChecklistRow` grammar (label / done / action only when unmet, with the resend called at
`callbackURL: "/host/verify"`), the D-268 phone as a required `tel` input with its helper associated
through `aria-describedby`, and a neutral-solid `size="touch"` submit that carries `disabled` **and**
`aria-disabled` in flight. The checklist's filled success marker is deliberately absent — this phase
spends that hue zero times.

**The cooldown arrives as a finished string.** `retryAfterSentence: string | null` — null is the
permission, the string is the refusal — so the component performs no arithmetic and reads no clock.

**Exactly one `role="status"` region**, author-named, ordinary ink, no retry affordance of its own and
not a toast, carrying the action's sentence verbatim. It is written once and rendered from both
branches that draw the form, which is what keeps it singular.

### 3. `/host/verify`, its plate, and the way in

The page is an **async** RSC on `HOST_PANEL_SHELL`. It is the **fifth** reader of
`loadHostVerification` and writes no new query, and it composes the retry instant from that row's
`updated_at` and the one interval constant the action binds — against the **database's** clock, not
this process's, because the clause that actually refuses is `now() - make_interval(...)` inside
Postgres. The comparison is deliberately the conservative direction: the page reads its clock at
paint and the action reads its own at press, which is strictly later.

**It declares no `searchParams` and the file contains zero occurrences of the identifier.** The
checking partner's `callback` is a browser navigation the host fully controls; `?status=approved`
would be a host asserting their own standing. This is PROJECT D-57's lesson one domain over.

`loading.tsx` composes exactly one `PanelSkeleton`, imports the same shell constant the page imports
and carries the page's own header expressions character for character.

The way in is a **fourth `HostSignals` advisory row** on the shipped `:109-119` shape, rendered for
`unverified | pending | rejected` only. `/host/verify` is **not** in `HOST_NAV` — no honest `why`
exists for a once-ever destination that is dead weight the moment it succeeds.
