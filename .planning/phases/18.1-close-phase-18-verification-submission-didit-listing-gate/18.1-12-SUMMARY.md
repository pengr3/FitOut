# Phase 18.1 Plan 12: The Listing-Creation Gate Summary

**PM-C shipped: a host cannot create a listing until they are checked — enforced server-side in `createDraftListing`, with the refusal routed to `/host/verify` before it can be swallowed, closing FINDING F-2 and pinning FINDING F-7 with a test that argues its own case.**

## What Shipped

### Task 1 — the gate, and the routing that makes it legible (`84f424b`)

**The gate** is in `createDraftListing` (`src/app/actions/listing.ts`), after the session check and
before the insert. It reads `loadHostVerification` — becoming its **sixth reader**, with **no new
query** — and returns `{ ok: false, error: HOST_VERIFICATION_LISTING_REFUSED }` for
`unverified | pending | rejected | suspended`. No type change; the refusal fits the shipped
`ListingResult`.

Two things are written at the site because a later reader will want to undo them:

- **FINDING F-7** — `grandfathered` is deliberately not a refusing state, with the argument
  (D-211/D-224 make those hosts sellable today, so refusing them a new listing is an undecided scope
  change) and the name of the case that pins it.
- **The four states are spelled positively**, not as `!== "approved"`. A negation would refuse every
  enum member added after today, `grandfathered` included — F-7's own defect, reached by accident.

**D-270** is written at `saveListingStep`: it stays **ungated**, because every draft begun before
D-255 landed belongs to a host with no verification row, and gating autosave would turn the wizard
into a form that cannot be left.

**The routing** closes FINDING F-2. `/host/listings/new` now reads the same row from the same session
id and `redirect("/host/verify")`s the same four states **before** `createDraftListing()` is called.
The action's refusal becomes unreachable from the product path and stands as the non-bypassable gate.
The pre-existing bounce to the grid keeps its place for genuine infrastructure failure — still a
silent bounce, still recorded in `18.1-UI-SPEC § NOT COVERED`, deliberately not widened into here.

**The four `Create listing` links are byte-unchanged.** `git diff` on
`(host)/host/listings/page.tsx` and `(host)/host/page.tsx` is empty against the plan's base; both
still carry zero `disabled` / `aria-disabled`.

### Task 2 — the fixture sweep (`7bd5663`)

**The blast radius was measured, not estimated.** Immediately after the gate landed:

three lines: one reflowed import, one docblock line, one function signature).

Every fixture seeds through **`seedHostVerification`**, the helper 18.1-07 declared for this plan —
never a second seeder. It is called from each file's **one** `signInHost` / `beforeAll` rather than
at the ~12 call sites, on that helper's own argument: a copy per site is a chance per site to seed

passes for the wrong reason.

`crud.test.ts`'s `signInHost` gained a `status` parameter (default `approved`, accepting `null` for
the no-row fixture) so Task 3's census could drive all six states through the same door.

**E2E:** `e2e/helpers/booker-seed.ts` gained `seedApprovedHostVerification(email)` — added beside the
existing approved-row insert, not replacing it, because the two close **different** gates (the

creation gate for a host that *signed up through the form* and therefore has no row at all).
`axe-sweep.spec.ts` calls it before `mintDraftListing`; `seedPendingHostVerification` then flips the
same row to `pending`, which its `/host/verify` row's tell depends on. Two stale docblock claims that

`overflow-320.spec.ts` needed no seed change — its host is already `approved` — but its

### Task 3 — proving LVER-05 (`f499aa4`)

**The census: seven cases for six states.** `unverified` has two fixtures that must both refuse — a
row at `unverified`, and **no row at all**, which is the state a real new host is actually in and the
one a refactor is most likely to drop. **Every refusing case asserts the `listing` row count did not
move**, not merely that `ok` is false: a gate that returns a refusal after inserting is not a gate,
and the return value alone cannot tell the two apart.

Plus the F-7 `grandfathered` case, whose failure message states the entire argument and tells the
next reader that changing it is a product decision needing a decision record; and the D-270 case,
which mints a draft while `approved`, moves the same host to `unverified`, proves creation is now
refused, and proves the existing draft still saves.

**CLAIM 4** in `tests/host/verification-surface.test.ts` is the ordering pin the plan's own threat
register names as T-18.1-1202's mitigation: over comment-stripped source, the redirect must appear
before the action call, the page must read the shared helper, and the pre-existing grid bounce must
be neither removed nor duplicated. **It is the only proof of F-2's closure that runs in CI** — D-24
keeps Playwright out.

**The banned-language corpus** now scans the new sentence; its floor moved 49 → 50, measured by
failing it deliberately and reading the reported length back.

### Two flakes met and diagnosed rather than papered over

**1. The streaming-buffer rule (new spec, first hand run).** The `pending` assertion failed with
`strict mode violation: resolved to 2 elements`, both `<h2>Your check is in progress</h2>`, the first
`hidden`. That is this repository's already-documented phenomenon — React parks a Suspense payload in
a `<div hidden id="S:n">` while revealing it, so on a route with a `loading.tsx` every server-rendered
element briefly exists twice. `/host/verify` ships one (18.1-11). Fixed with
`.filter({ visible: true })` on **every** `/host/verify` read, including the one that passed: the two
tests differ only by a race, and a spec that is green today and intermittently red later is worse
than red. The rule and its provenance are written into the file's header.

**2. A cold-compile timeout, twice, and it is NOT this plan's.**

- `overflow-320`'s first full run failed one case — `/host/listings/[id]/edit · court` — at its 60s
  tell timeout, aborting the serial block (19 did not run). **That spec's own failure message names
  this exact condition**: *"If this is the first run since a dev-server restart, the route may still
  be compiling: these five are among the heaviest in the app and the timeout is sized for a cold
  one."* The immediate re-run against the warm `.next` cache passed it in **3.2s** and the whole file
  green.
- The same shape appeared in a narrowly-filtered axe-sweep run (`-g "wizard|availability|…"`): four
  rows failed at 15.8s. Widening the filter to `-g "host"` — which compiles the host tier first —
  made the same rows pass at **2.7s**, and the full file passes them at 2.7s too. Diagnosed, not
  assumed: the hypothesis was tested with a second filtered run rather than believed.

Neither is caused by this plan, and both are visible only under invocations the specs are not
designed for.

## Deviations from Plan

### 1. [Rule 2 — missing critical functionality] CLAIM 4 added to a file outside `files_modified`

- **Found during:** Task 3
- **Issue:** The plan's threat register assigns `mitigate` to T-18.1-1202 with "asserted by an
  ordering grep and by `e2e/host-verification.spec.ts`". The e2e half does not run in CI (D-24), and
  no ordering grep existed anywhere — so F-2's closure, the plan's headline claim, had **zero
  coverage that runs on a commit**.
- **Fix:** `tests/host/verification-surface.test.ts` gained CLAIM 4 (three cases), following that
  file's own comment-stripped source-scan idiom and its two-halves token-splitting discipline.
- **Measured:** mutation 3 above.
- **Commit:** `f499aa4`

### 2. [Rule 2] The refusal sentence got an owner module, not a call-site literal

- **Found during:** Task 1
- **Issue:** The plan says the refusal string comes verbatim from the UI spec; the orchestrator's
  criteria say no sentence may be typed inline. `listing.ts` is a `"use server"` module and cannot
  export a constant (`tests/use-server-exports.test.ts`'s recorded `avatar.ts` incident), so a
  literal there would be module-private and invisible to the banned-language corpus.
- **Fix:** `HOST_VERIFICATION_LISTING_REFUSED` in `src/lib/host/verification-refusals.ts` — the
  module that already owns "the server's sentences" for host verification, for this exact reason —
  imported by the action. Added to the corpus in `tests/listing/review-signal.test.ts` by **name**,
  not by widening `HOST_VERIFICATION_REFUSALS`, whose docblock claims to be "every sentence
  `requestHostVerification` can return" and is consumed as that claim.
- **Commits:** `84f424b`, `f499aa4`

### 3. [Rule 4 territory, decided against the plan text and recorded loudly] The `/host/verify` state rows were NOT added to the two e2e specs

- **Found during:** Task 3
- **Plan text:** *"Add `/host/verify` rows to `e2e/axe-sweep.spec.ts` and `e2e/overflow-320.spec.ts`,
  covering at least the `unverified`, `pending` and `rejected` states."*
- **What is actually on disk:** **both files already carry a `/host/verify` row**, landed by 18.1-11
  one plan ago — axe-sweep's covers `pending`, overflow-320's covers `approved` — and **each states
  in writing why the other states are out of its reach and who owns them**:
  - axe-sweep: *"Reaching them here would need this file to seed an unverified host, which is the
    same host it needs pending for the `/ops` row above… their rendered a11y at these two widths is
    the hand-measured sweep plan 18.1-14 owns."*
  - overflow-320: *"it cannot be reached from this fixture without un-approving the host and breaking
    every row above. It is the hand-measured item plan 18.1-14 owns, at both widths and both themes,
    in the `unverified`, `pending` and `rejected` states."*
- **Why the plan text was not followed:** three reasons, in order of weight.
  1. **It would break other rows.** overflow-320's `/host/verify` fixture host is the same host every
     bookable-listing row depends on; un-approving it is not a local change. axe-sweep's host is the
     same one its `/ops` row needs at `pending`, and a fourth sign-up in that `beforeAll` runs into
     the five-per-sixty-second rate limit the file already documents.
  2. **It could produce a red this plan cannot fix.** A 320px sweep or an axe scan of the submission
     form is exactly the measurement 18.1-14 owns; if it fails, the remedy is UI work on
     `verification-panel.tsx` — a file outside this plan's `files_modified`, owned by 18.1-11.
  3. **It would create two contradicting declarations** in files 18.1-11 reconciled one plan ago, and
     the orchestrator's brief says explicitly not to undo that reconciliation.
- **What was done instead:** both specs were re-run by hand and their existing `/host/verify` rows
  confirmed green; overflow-320's `/host/listings/new` row was corrected where D-255 made its stated
  reasoning incomplete; axe-sweep's fixture was corrected where D-255 made its docblock false. The
  unverified/pending/rejected sweep remains where 18.1-11 put it, with 18.1-14 named as its owner.
- **⚠ For the verifier / 18.1-14:** this is the one place this plan knowingly departs from its
  written instruction. If the PM wants those rows anyway, they are a fixture-shape change to two
  specs and belong in a plan that also owns the panel.
