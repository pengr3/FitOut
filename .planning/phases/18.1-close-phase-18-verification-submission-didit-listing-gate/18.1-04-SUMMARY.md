## Decisions Made

### FINDING F-5 — settled as option (b), two entry points

`VerificationDecision` models exactly one moment: **a verdict handed in**. That fits the ops-manual
provider precisely (a staff member decided, and the decision *is* the input) and it fits applying a
verdict Didit has already reached and sent back. It does **not** fit the moment FitOut *asks* Didit to
look at somebody: nobody has decided anything, there is no `result` to hand in, and the answer arrives
later by webhook on a channel `verify` is not on.

**Chosen — (b) two entry points.** `verify(decision)` keeps its single meaning and stays the only
member of `VerificationProvider`. A provider that must first ask exposes a second named function of
its own — `beginVerification` — which is deliberately *not* part of the interface and therefore not
reachable through `runVerification`. It creates the vendor session and returns the same four-field
`VerificationResult` with `result: null` and `checkedAt: null`, because nothing has been decided and
writing either field would fabricate a check.

**Rejected in writing — (a) widen `VerificationDecision` into a discriminated union.** The rationale is
recorded in the header rather than only here: it changes the contract type **both** providers implement
in order to model a moment only **one** of them has. The manual provider would grow a branch for a
request it can never receive, `runVerification` would start returning things that are not verdicts, and
every reader of a `VerificationResult` would have to learn which `kind` produced it. That is precisely
how one branch point becomes two.

**Why (b) is the right trade.** The property worth protecting is that *the verdict* has exactly one code
path — that is what "the only branch point" and "it fails closed" are statements about, and it is what
makes a verified `host_verification` row impossible to write without coming through the port. A session
*request* decides nothing and writes no verdict, so routing it through the same door buys no safety; it
only adds a discriminator a future reader can get wrong on the path that actually matters.

**The cost, stated rather than hidden:** the asking half of the Didit adapter will not be policed by
`port.ts`. It is an ordinary exported function, and the discipline that keeps it honest is that it may
only ever produce `result: null`. 18.1-05 owns holding that line.

### `isVerified` stays synchronous — a guard, not an oversight

Widening it to accept a promise would have deleted a compile error worth keeping.
`isVerified(runVerification(…))` — the un-awaited form — is now a **rejected program**. Had the
signature been widened, it would instead have been a quiet `false` for a genuinely verified host, which
is the one direction a fail-closed contract must not be silent about.

### Decisions this plan INHERITED rather than made

Both were taken by the PM on 2026-09-02 during Task 1's first-hand account probe, are already applied
to the vendor account, and are written up in `18.1-RESEARCH.md § ADDENDUM B8`. They are recorded here
because they arrived attached to this plan's gate, **not** because this plan decided them.

- **D-272 — raise the vendor retry cap to match D-264, do not tighten D-264.** ADDENDUM B1 falsified
  RESEARCH § R4's "Didit imposes no retry cap": the account's workflow carries
  `max_retry_attempts: 3` / `retry_window_days: 7` by default, while D-264's 24-hour cooldown permits
  seven attempts per seven days. Two systems holding one rule with different numbers — the literal
  D-130 / GATE-05 defect. Settled by raising the vendor to `7` / `7`, i.e. `COOLDOWN_HOURS = 24`
  restated in the vendor's units, so **D-264 remains the single authority** and Didit can never refuse
  a retry FitOut has already promised. ⚠ If `COOLDOWN_HOURS` ever changes, `DECLARED_RETRY` in
  `scripts/didit-setup.ts` changes in the **same commit**. The per-module caps
  (`id_verification_max_retry_attempts: 2`, and two 3s) are deliberately **not** raised — they bound
  retries *within* one session, so 18.1-06 must not present an exhausted-module decline as "you have no
  tries left", because the host does.
- **D-273 — the hosted flow stays mobile-only.** `is_desktop_allowed: false` is now a declared value
