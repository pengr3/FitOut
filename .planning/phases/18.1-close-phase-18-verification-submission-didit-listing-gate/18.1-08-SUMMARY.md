# Phase 18.1 Plan 08: Let the Verdict In — Through One Authenticated Door Summary

A signed `status.updated` delivery now reaches FitOut through a single HMAC-authenticated route and moves a `host_verification` row through a single write module — with a forged, tampered, unsigned, wrongly-secreted, stale or sandbox-environment delivery changing nothing.

## What Shipped

**`src/app/api/didit/webhook/route.ts`** (395 lines) — the trust boundary. Node runtime, `req.text()` as the first statement, HMAC-SHA256 over the raw bytes as primary with `X-Signature-V2` over a canonicalised re-serialisation as a live fallback, `X-Signature-Simple` with no accepting branch at all, a length-guarded `crypto.timingSafeEqual`, a ±300s replay window on both the header and the signed envelope, the ADDENDUM A4 environment gate, and a clean 400 on everything unverifiable.

**`src/lib/verification/apply-verdict.ts`** (446 lines) — the one road to approved. One guarded `UPDATE … WHERE status = 'pending'` per transition, the shared mapper reused rather than re-derived, `vendor_ref` preserved on both verdicts, `recordAudit` on both branches, and the D-245 notice through the shipped payloads.

**`src/lib/notification-guard.ts`** — the fan-out both writers of host standing now share.

## The Blocker the Orchestrator Flagged — Resolved as Option (b), With the Measurement

The plan's `key_links` frontmatter declared `apply-verdict.ts → src/lib/notifications.ts` *"via hostApprovedPayload / hostRejectedPayload through the shipped **guardedNotify** fan-out"*. Two of those three things were true. `guardedNotify` was **module-private at `src/app/actions/ops-review.ts:207`**, with no `export` keyword and two callers in that same file.

The orchestrator asked for a deliberate choice, argued, and specifically for option (a) to be **verified against `tests/use-server-exports.test.ts` rather than assumed in either direction**. Here is what the measurement says.

**Option (a) — export it from `ops-review.ts` — is LEGAL to that test and REFUSED by the gate that matters.**

`tests/use-server-exports.test.ts` classifies exports syntactically: `export function` must carry `async`. `guardedNotify` is `async function`, so that test would have stayed green. **That is exactly why it is the wrong instrument to lean on**: it proves the export SHAPE is legal to Next, and says nothing about whether the export should exist. What actually refuses option (a) is `tests/design/ops-guard-coverage.test.ts`, twice:

1. **Layer 3** — `requireStaff()` must be the FIRST statement of every exported function in `src/app/actions/ops-*.ts`. `guardedNotify` cannot gate on staff standing: it is handed an already-resolved actor, and its second caller is a webhook where **there is no staff session at all**. Exporting it would either fail that clause or bolt a gate on that then refuses every vendor verdict.
2. **The pinned census** — `EXPECTED_OPS_ACTIONS = 6`. Measured with the same TypeScript AST walk that test uses, before writing anything:

```
exported functions in ops-review.ts NOW: 5 approveHost, rejectHost, suspendHost, approveListing, rejectListing
census pinned at 6 (5 here + cancelBookingAsOps). Adding guardedNotify => 7 total.
```

And beneath both gates sits the reason they exist: **every export of a `"use server"` module is a network-reachable POST endpoint.** Exporting the notification fan-out would put a function that looks up an arbitrary user's email address and emits a notification on the public network. That is a security regression, not a lint failure.

**Option (b) — extract to a plain shared module — chosen.** `src/lib/notification-guard.ts` now holds `guardedNotify` and `notifyAccountOwner`, and both `ops-review.ts` and `apply-verdict.ts` import them. This is the repo's shipped answer to exactly this shape (`payments/config.ts` beside guarded `payments/fees.ts`; `availability/horizon.ts` beside guarded `availability/slots.ts`) and its third instance in three plans — 18.1-07 did the same for its refusal constants.

**Option (c) — replicate the guarding shape locally — rejected** for the reason the whole plan is about: a second copy of "never let a notice failure disturb a committed decision" is a second thing to keep true, and the webhook is precisely where getting it wrong is worst.

**The move is behaviour-preserving, and that was measured before it was committed.** The body is `ops-review.ts:207-247` verbatim except that the alert tag became a parameter and `action` widened from that module's private five-verb union to `string`. The `console.error` shape, the swallow, the `needs_attention` outcome and the `meta: { reason: "notify_failed" }` row are unchanged. 26 cases across `tests/ops/ops-audit.test.ts` + `tests/notifications/ops-decision-notify.test.ts` and both design clauses were green on the extraction commit alone.

**The property that matters holds on both paths, and is sharper on the new one.** A notify failure never rolls back or blocks the state flip that preceded it, and each notify is individually guarded. On the ops path a throw would hand an operator a 500 for a decision that in fact succeeded. On the webhook path it would become a **non-2xx, and the vendor would retry an already-applied verdict — twice — before dropping the delivery permanently.**

## The Finding: A Timestamp Header Is Not a Replay Control When the Signature Covers the Body Alone

This is the sharpest thing this plan found, and it is not in the research.

ADDENDUM A7 says *"`X-Timestamp` freshness ≤ 300s (reject outside)"*. Implemented literally — a single check on the header — **that control does not exist**, because Didit's primary `X-Signature` is an HMAC over the raw body **alone**. `X-Timestamp` is therefore a header outside the signed message, and an attacker replaying a captured genuine `Approved` body may set it to `now` and sail through.

PayMongo does not have this problem: it signs `${t}.${rawBody}`, so its timestamp is inside the covered bytes and rewriting it breaks the signature. **Copying PayMongo's single check across to a vendor with a different signed message silently deletes the control.**

The envelope's own `timestamp` field **is** inside the signed bytes. So both are checked: the header first as a cheap pre-filter, and the envelope's field after verification as the control that actually holds. Genuine retries pass both — the vendor re-signs with a fresh timestamp per attempt, and both retries (~1 min, ~4 min) fall inside a 300s window even measured from the original delivery.

Case 19 exists for this and nothing else: a **valid signature over these exact bytes**, a **fresh and well-formed header**, and a body timestamp an hour old. Mutation-measured — with the authenticated check removed it returns **200 instead of 400**.

## Mutation Score — Including One Prediction That Was Wrong

The plan asked for a specific mutation check: *"removing the length guard before `timingSafeEqual` turns the malformed-signature case from 400 into a 500."*

**It does not, and that is a finding rather than a formality.** All four combinations were measured on case 13 (an odd-length, non-hex signature):

| Length guard | Blanket `try/catch` | case 13 |
| ------------ | ------------------- | ------- |
| present      | present (shipped)   | **400** |
| REMOVED      | present             | 400     |
| present      | REMOVED             | 400     |
| REMOVED      | REMOVED             | **500** |

The `RangeError` is absorbed independently by the `catch` that wraps the whole verification, so **the guard and the catch are two sufficient controls rather than one**. The same is true of the PayMongo route this copied, so the prediction was wrong about both files. Keeping the guard is still right — the catch is a blanket that a future refactor could legitimately narrow, and a length mismatch should be "not a match" rather than an exception — but the honest claim is "two independent controls", not "the guard is what stops the 500".

Two further mutations, both aimed:

| Mutation                                                     | Result                                                                        |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| Drop the authenticated body-timestamp check                   | **case 19 RED** — `expected 200 to be 400`                                    |
| Add `vendor_ref = ${check.vendorRef}` to the approve SET list | **case 2 RED** — `expected null to be 'sess_18108_aaaaaaaa'` |

The second is the edit the module header explicitly forbids ("DO NOT 'COMPLETE' THOSE SET LISTS"), and it now reddens on the exact line the prohibition is about.

## Vacuity Discipline

The live-vendor brief warned that *a test asserting the same value a fail-closed guard returns is vacuous unless it also asserts the call happened*. Every 400 in this suite is exactly that shape: a route that refused **everything** would produce an identical 400 with an identical unchanged row.

Two things close it. **Case 1 is a declared positive control** — the same fixture, the same secret, a good signature, and the row *does* flip; a suite whose secret never reached the route could not pass it. And every refusal case additionally asserts the row is still `pending`, so the delivery demonstrably reached a decision point and was turned away rather than the harness having been misconfigured. Case 28 closes the third gap with a guard-the-guard: it asserts the status collector recorded **more than 25 responses** before asserting none was a 500, and that the suite produced **both** 200s and 400s.

Case 14 is worth naming for the same reason: `X-Signature-Simple` is sent **correctly computed with the real secret** over the vendor's own four-field message, so the 400 is caused by the header having no accepting branch rather than by a digest that happened to be wrong.

## What 18.1-09 Inherits

- **Call `applyDiditVerdict`, do not repeat it.** Its `{ transition, status, moved, reason }` return exists for the sweep: `moved: true` means "no webhook arrived and I applied this" (the D-110 operator-visible event); `moved: false` means the webhook won and the sweep should be silent.
- **The sweep does not go through this route's environment gate.** That is correct — the sweep polls the vendor with FitOut's own credential, so the environment is not in question — but it means the sweep is also the recovery path if `DIDIT_ENVIRONMENT` is ever misconfigured. Worth a line in its header.
- **`sessionId` for the sweep always matches `vendor_ref` by construction**, because the sweep reads `GET /v3/session/{vendor_ref}/decision/`. The mismatch alert will therefore only ever fire on a webhook.
- **Free-tier GET limit is 10/min** (research F-4) — batch accordingly.

## Deployment Note

`DIDIT_ENVIRONMENT` is new and **optional**. Production defaults to expecting `live`; set it to `sandbox` only on a staging deployment pointed at the sandbox application. It belongs in `.env.example` as an empty declared key when 18.1-14 walks the sandbox — flagged rather than done here, because this plan's `files_modified` does not include it and the default is already the safe one.
