## Didit vs the ops queue

### Q1 — Didit returns PASS. Auto-approve, or does ops still confirm?

| Option | Description | Selected |
|--------|-------------|----------|
| Auto-approve *(SWE recommended)* | Port writes `approved` with `provider='didit'`, `vendorRef`, `checkedAt`. Ops never sees a passing host. Avoids re-imposing the PM-3 ops-throughput bottleneck. | ✓ |
| Ops confirms every pass | Didit becomes an evidence-fetcher; a human presses Approve. Strongest audit story, but makes the vendor decorative and re-creates the rubber-stamp problem. | |
| Auto-approve, ops can reverse | Pass approves immediately; host stays in a reviewed-recently view ops can suspend from. Needs a second `/ops` view that does not exist (D-246 — one queue, asserted). | |

**User's choice:** Auto-approve.
**Notes:** Became **D-261**.

### Q2 — Didit returns FAIL. What happens?

| Option | Description | Selected |
|--------|-------------|----------|
| Stays pending, ops decides *(SWE recommended)* | Fail lands in the ops queue as `pending` carrying the vendor's verdict. Didit does not name PH in its coverage; PhilSys unprobed; false negatives are a live risk. PM-G's edge-case override exists for exactly this. | |
| Auto-reject | Host told no immediately. Cheapest on ops load; a false negative becomes a dead end because appeals are 999.6. | ✓ |
| Auto-reject, but ops sees rejects | Rejected immediately AND queued for a sanity check. Ops load of option 1 with a worse host experience. | |

**User's choice:** Auto-reject — **against the SWE recommendation**.
**Notes:** Became **D-262**. The consequence was put on the record *before* the next question rather
than after the fact: with both verdicts automatic, the ops host queue becomes vendor-driven, the
human half of the console is reachable mainly via the manual override, and Success Criterion 1's
*"the queue fills from ordinary product use, proven by driving it"* survives only if Didit answers
asynchronously. The PM did not reverse. Recorded as accepted consequence 1 in CONTEXT.md, and the
re-submission area was pulled forward out of order because it became the only remedy in the product.

### Q3 — Can a host reach a human without running Didit?

| Option | Description | Selected |
|--------|-------------|----------|
| No host-facing route *(SWE recommended)* | Manual provider stays ops-initiated only. Holds 18-13's line — no promise of a review with no SLA behind it. Keeps appeals in 999.6. | ✓ |
| Yes, a host can request one | Kinder on edge cases, but an appeals channel by another name; will absorb everyone who finds the vendor flow annoying. | |
| Only after a Didit attempt fails | Narrower, but still promises a review — 999.6 arriving early through a side door. | |

**User's choice:** No host-facing route.
**Notes:** Became **D-263**.

## Re-submission policy

*Discussed second rather than third — D-262 made it the only remedy left in the product.*

### Q1 — After an auto-reject, may the host run the check again?

| Option | Description | Selected |
|--------|-------------|----------|
| Yes, unlimited *(SWE recommended)* | Follows D-249 — resubmission enters the queue at resubmission time. Didit's free tier covers 500 checks/month. | |
| Yes, but rate-limited | Cooldown or hard cap. Protects the $0.33/check spend past the free tier; costs one more piece of state. | ✓ |
| No — rejection is final | Only an ops-initiated override moves them. Cleanest data; a vendor misread ends a real host's account. | |

**User's choice:** Yes, but rate-limited.
**Notes:** Became **D-264**. The *shape* was ruled by the SWE rather than asked, because it is
constrained rather than open: a hard attempt cap needs a counter column, and case 1 of
`tests/ops/verification-schema.test.ts` asserts the table's column set by **set equality**, so a
counter reddens it. Landed as a **24-hour cooldown derived from the existing
`host_verification.updated_at`**, with `src/lib/rate-limit.ts` (the `activateHosting` 5/60s
precedent) retained as the burst guard only — it is process-local and cannot be the durable cap.

### Q2 — An auto-rejected host reads a `reason`, but there is no operator behind it. What goes in the column?

| Option | Description | Selected |
|--------|-------------|----------|
| Canned sentence per failure kind *(SWE recommended)* | Fixed set of host-readable sentences mapped from Didit's failure codes. Keeps D-243's promise without inventing an operator who did not exist. | |
| One generic sentence | Simplest, immune to Didit changing its codes — but it is the "told no without being told why" defect. | |
| Store the vendor's own message | Most specific, zero copywriting — but puts unreviewed third-party text on a FitOut surface (T-18-1301). | ✓ |

**User's choice:** Store the vendor's own message.
**Notes:** Became **D-265**. Implemented faithfully with two SWE-added safeguards that do not change
the decision: stored bounded to the same 280-char ceiling operator sentences carry and rendered
through the same escaped path, plus a canned fallback when Didit returns nothing usable — otherwise
an auto-reject can produce an empty `reason`.

### Q3 — May a SUSPENDED host re-submit their way back?

| Option | Description | Selected |
|--------|-------------|----------|
| No — suspension is ops-only *(SWE recommended)* | The submission action refuses `suspended`. Stops the machine silently reversing a named staff member's enforcement decision (ENF-01/D-233). | ✓ |
| Yes, but it lands in the ops queue | Gives a suspended host a route back — but that route is host appeals, explicitly 999.6. | |

**User's choice:** No — suspension is ops-only.
**Notes:** Became **D-266**.

## The § 21(b) address

### Q1 (first pass) — What geographic address does FitOut ask a host for?

Three options were offered (host self-declares · take it from Didit's document · reuse the listing
address). **The PM did not pick one — they questioned the premise:** *"in the listing there's a box
wherein the host will declare the space's address? what is this? This is out of KYC's scope right?"*
and, on the schema question, *"address is not a host schema but a listing this under the listing."*

**This was correct and the framing was fixed rather than defended.** The listing does carry a
structured address (`addressLine1`, `addressLine2`, `city`, `postalCode`, PostGIS `location`, D-10,
required at publish) and it *is* out of KYC's scope — Didit checks a person, not a place. The
address had been raised for a different reason: RA 11967 § 21(b) is a **merchant-record** duty, not
an identity one. The original three-option question was withdrawn and replaced with the narrower
question the PM's objection actually raised.

### Q1 (re-asked) — Does the listing's address discharge § 21(b), or does FitOut need a separate merchant address?

| Option | Description | Selected |
|--------|-------------|----------|
| Listing address is the record | No new collection. "Prior to listing" satisfied because ops reviews the listing — address included — before it can sell. Gaps: a host who never publishes has no address; a multi-listing host has no single merchant address; deleting the listing takes the record with it. | ✓ |
| Separate host address *(SWE recommended)* | Structured address on `user` beside `city` and `phone`. Matches what the statute literally names, survives any listing coming or going. Costs a few columns and one line in `profile.ts`'s private-column allow-list. | |
| Listing address now, revisit with counsel | Ship the listing address and let counsel decide. If counsel says otherwise: a migration plus a backfill prompt to every verified host. | |

**User's choice:** Listing address is the record.
**Notes:** Became **D-267**. Collapsed two follow-up questions entirely — "where does it live in the
schema" and, in effect, the address half of the ops reveal (the listing queue row already renders it
via `addressOf()`). The four gaps are recorded as accepted consequence 3 in CONTEXT.md, and counsel
gains a fourth open question alongside the two already outstanding on § 21(c).

### Q3 — Who in `/ops` can see the address?

| Option | Description | Selected |
|--------|-------------|----------|
| Behind the same reveal + audit *(SWE recommended)* | Joins email and phone under PM-E's "Show contact", one audit row per reveal. Audit row carries ids only, never the address (D-72). | ✓ |
| Not shown in `/ops` at all | Smallest PII exposure; an operator investigating a fake listing cannot see where the merchant claims to be. | |
| Always visible on the queue row | Fastest for ops; for an individual host this is their home address, revealed with no audit row. | |

**User's choice:** Behind the same reveal + audit.
**Notes:** Answered before D-267 landed. Largely moot for a *host* address, since D-267 means there
is none — the reveal covers email and phone, and the listing row already shows the address. The
principle it expresses (most-sensitive field gets no weaker treatment than the phone number) is
retained in **D-271**.

## Phone and email

### Q1 — Phone required at submission: verified, or self-declared?

| Option | Description | Selected |
|--------|-------------|----------|
| Self-declared, not verified *(SWE recommended)* | Required field, no OTP. Consistent with the address ruling — the statute says collect, not verify. FitOut has no SMS provider (Resend is email-only). | ✓ |
| Verified by SMS OTP | "Valid" becomes provable. Costs an SMS provider, PH sender-ID registration, per-message spend, and a new failure mode on the path to selling. | |
| Let Didit verify it | No new provider — but an unprobed add-on at a vendor that does not name PH, and absent for anyone the manual override approves. | |

**User's choice:** Self-declared, not verified.
**Notes:** Became **D-268**.

### Q2 — Where is the phone actually required?

| Option | Description | Selected |
|--------|-------------|----------|
| At verification submission *(SWE recommended)* | The todo's standing assumption. Stays optional on the profile for bookers. Pairs with PM-E's reveal, which sits on the host row where there is no listing to carry it. | ✓ |
| At listing publish, with the address | Symmetric with D-267 — but the host queue row would then have an empty phone exactly when ops needs it. | |
| Both — submission AND re-confirmed at publish | Belt and braces; a second prompt for a field that has not changed. | |

**User's choice:** At verification submission.
**Notes:** Became **D-268**.

### Q3 (first pass) — Must the account's email be confirmed before requesting verification?

**The PM did not pick an option — they asked a factual question:** *"a registration is email
confirmed right? we have that IAM function?"*

Checked rather than answered from memory. The machinery exists — Better Auth sends a verification
email at signup (`sendOnSignUp: true`) and maintains `user.emailVerified` — but `src/lib/auth.ts:67`
sets `requireEmailVerification: false` (**D-07**, soft gate) with `autoSignIn: true`, so sign-in is
never blocked on it.

⚠ **A claim made while answering was wrong and was corrected in the same turn:** the statement that
*"nothing in the product has ever enforced it"* is false —
`src/app/(host)/host/listings/[id]/edit/wizard.tsx:782` already gates on `emailVerified` and ships a
`resendVerification()` action. The correction changed the shape of the decision, so the question was
re-asked with the precedent in view.

### Q3 (re-asked) — Given the wizard already gates on `emailVerified` with a resend link, should verification submission require a confirmed email too?

| Option | Description | Selected |
|--------|-------------|----------|
| Yes, reuse the wizard's pattern *(SWE recommended)* | No new mechanism. Makes § 21(b)'s "valid email" provable for free — and with D-262's auto-reject there is no operator to notice a bounced rejection notice. | ✓ |
| No — leave the wizard as the only gate | Fewer walls; but a host can be auto-approved and told nothing they can read. | |
| Yes, and make it a hard gate at signup | ⚠ Reverses D-07, changes signup for every booker, outside this phase's boundary. | |

**User's choice:** Yes, reuse the wizard's pattern.
**Notes:** Became **D-269**. Explicitly *not* a D-07 reversal — the gate is local to the action.

## SWE rulings — stated, not asked

Ruled by the SWE and put to the PM as overrulable rather than spending a question turn on them.
Neither was overruled.

- **Existing drafts stay editable; only `createDraftListing` is gated** (**D-270**). Gating
  `saveListingStep` too would strand work hosts already did. Matches the source todo's own suggestion.
- **The contact reveal goes on both queue rows, host and listing** (**D-271**) — ops questions are
  usually about a specific listing. `mailto:` for email, plain text for phone, "Not provided" when
  empty. ⚠ Carries a flagged cost: `ops-queue-row.tsx` is asserted TERMINAL, so a `mailto:` anchor
  needs an explicit documented exemption rather than a deleted assertion.
