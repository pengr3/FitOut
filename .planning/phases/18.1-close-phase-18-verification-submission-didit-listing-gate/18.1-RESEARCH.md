GET https://verification.didit.me/v3/session/{session_id}/decision/
x-api-key: <API_KEY>

- Rate limit: **600 GET/min per API key on paid; 10/min on free.** `429` on exceed. **[CITED — docs.didit.me/api-reference/overview, 2026-09-02]** ⚠ **The free tier's 10/min is a real constraint on any polling design.**

**Response shape (V3):** feature reports are **plural arrays** — `id_verifications[]`, `liveness_checks[]`, `face_matches[]`, `aml_screenings[]`, `nfc_verifications[]` — each with a `node_id`. **Never read a singular field.** V2's singular shape is gone.

⚠ **CASING HAZARD, worth a defensive normaliser:** the webhook envelope and the status reference show `"Approved"` / `"Declined"` (title case), while the decision-endpoint example shows `"status": "APPROVED"` (upper case). **[CITED — docs.didit.me, 2026-09-02, two pages]** Compare case-insensitively, or you will ship a gate that silently never matches. ## Session status values

**[CITED — docs.didit.me/integration/verification-statuses, 2026-09-02]**

| Status | Meaning | Terminal? | FitOut mapping |
|---|---|---|---|
| `Not Started` | Session created, link unopened | No | `pending` |
| `In Progress` | Host is completing steps | No | `pending` |
| `Approved` | All checks passed | Yes* | → **D-261 auto-approve** |
| `Declined` | One or more checks failed | Yes | → **D-262 auto-reject** |
| `In Review` | Flagged for manual compliance review at Didit | No (actionable) | ⚠ **stay `pending`** — see FINDING F-3 |

## Webhooks

**[CITED — docs.didit.me/integration/webhooks, 2026-09-02]**

**Event to subscribe to: `status.updated`** (the only one this phase needs). Nine other event types exist (`data.updated`, `user.status.updated`, `business.*`, `transaction.*`, `travel_rule.*`) — **subscribe to none of them.** No wildcards.

**Envelope, verbatim:**

```json
{
  "event_id": "uuid",
  "webhook_type": "status.updated",
  "timestamp": 1774970000,
  "created_at": 1774969994,
  "application_id": "uuid",
  "environment": "live",
  "sandbox_scenario": null,
  "session_id": "uuid",
  "status": "Approved",
  "workflow_id": "uuid",
  "workflow_version": 1,
  "vendor_data": "your-internal-user-id",
  "metadata": { "user_type": "premium" },
  "decision": { }
}
```

`decision` is populated when `status` is Approved / Declined / In Review / Abandoned. `vendor_data` is the FitOut `user.id`. `event_id` is the idempotency key and is **reused on retries** and identical across destinations.

### Signature verification — three headers, one algorithm

| Header | What is signed | Use |
|---|---|---|
| **`X-Signature-V2`** (recommended) | Sorted-keys, Unicode-preserved, compact JSON canonicalisation of the parsed body | Survives a framework re-encoding the body |
| **`X-Signature`** | The exact raw bytes transmitted | **This is what FitOut should use** — the route already reads `req.text()` before parsing |
| **`X-Signature-Simple`** | `"{timestamp}:{session_id}:{status}:{webhook_type}"` | Envelope-only fallback; pair with IP allow-listing |

All three are **HMAC-SHA256 hex digests** over the shared secret. Plus:

- **`X-Timestamp`** — Unix epoch seconds. **Reject if `abs(now - X-Timestamp) > 300`.** This is a replay window Didit specifies; the PayMongo route has no equivalent, so this is a **strengthening**, not a divergence.
- `User-Agent: DiditWebhook/2.0 +https://didit.me`
- Recommended verification order: try V2 → fall back to raw `X-Signature` → fall back to `X-Signature-Simple`. **Recommendation for FitOut: accept `X-Signature` (raw) as primary, `X-Signature-V2` as fallback; do NOT accept `X-Signature-Simple`** — it authenticates only four envelope fields, which is strictly weaker, and FitOut has the raw bytes.
- Use constant-time comparison (`crypto.timingSafeEqual`). **The repo already has the exact guard**: `verifySignature` at `src/app/api/paymongo/webhook/route.ts:104-115` compares byte lengths first because `timingSafeEqual` throws `RangeError` on unequal-length buffers.

### Retry policy

- Retried up to **2 times** on `5xx`, `404`, timeout, or connection failure. 1st retry ~1 min; 2nd ~4 min. **Then dropped.**
- `2xx` = success. `3xx`/`4xx` (except `404`) are **not** retried.
- Outbound request timeout: **5 seconds.** Return `2xx` immediately; do heavy work after.
- Signatures are recomputed with a fresh `X-Timestamp` on each retry.
- **HTTPS only. Didit blocks private/localhost URLs.** IP `18.203.201.92` if behind a WAF.

⚠ **Only two retries, then permanently dropped.** PayMongo retries far more aggressively. This means a webhook outage during a deploy can lose a verdict *permanently* — which with D-262 means a host sits at `pending` forever with no operator prompted. **This is the single strongest argument for the reconciliation sweep in FINDING F-4.**

## Sandbox — how a PASS and a FAIL are forced

**[CITED — docs.didit.me/integration/sandbox-testing, 2026-09-02]**

Sandbox is a **per-application mode** (`ApplicationDetail.mode == SANDBOX`). Live and sandbox are separate applications with separate API keys; traffic never mixes. Sessions are mocked, unbilled, and simulatable.

**Force an Approved session:**
```json
POST /v3/session/   { "workflow_id": "<uuid>", "sandbox_scenario": "approve" }
```
**Force a Declined session:**
```json
POST /v3/session/   { "workflow_id": "<uuid>", "sandbox_scenario": "decline_document_expired" }
```
**Or simulate after creation:** `POST /v3/session/{session_id}/simulate/` with body `{ "scenario": "approve" }` (at least one of `new_status`, `scenario`, or `risk` is required). Hosted-flow variant: `POST /v3/session/{session_id}/sandbox/simulate/`.

**22 scenario slugs.** The ones that matter here: `approve`; `decline_could_not_recognize_document`, `decline_document_expired`, `decline_face_match_low_similarity`, `decline_liveness_attack`, `decline_database_no_match`, `decline_mrz_validation`, `decline_minimum_age`; `review_face_match_borderline`, `review_document_borderline_age`, `review_aml_possible_match`.

There is also a **"Try Webhook" console feature** that drives your endpoint through approved / declined / in-review payloads without creating a session at all — useful for wiring the route before any credential exists.

`sandbox_scenario` is **rejected on live applications**, which is the guarantee that a test hook cannot be used to auto-approve a real host.

# R3 — Didit's failure-code taxonomy

**VERDICT: a code AND host-readable prose. D-265 is real but bounded mapping work — an allow-list, not a translator.**

## The shape of a failure

**[CITED — docs.didit.me/reference/data-models, 2026-09-02]**

A `Declined` session's `decision` carries per-feature reports; each report has a `status` and a **`warnings[]` array**. A warning object:

```json
{
  "feature": "ID_VERIFICATION",
  "risk": "DOCUMENT_EXPIRED",
  "additional_data": null,
  "log_type": "error",
  "short_description": "Document expired",
  "long_description": "The document's expiration date has passed, rendering it no longer valid for use.",
  "node_id": "first_id_verification"
}
```

| Field | Type | Host-safe? |
|---|---|---|
| `risk` | Stable code (`RiskChoices`) | No — a code, not a sentence |
| `short_description` | End-user phrasing, 2-5 words | **Mostly yes** — see the danger list |
| `long_description` | One-sentence prose | **Mostly yes**, but sometimes internal |
| `log_type` | `error` \| `warning` \| `information` | Filter on this: only `error` caused the decline |
| `additional_data` | e.g. `{ "score": 42.1, "threshold": 70 }` | **NO. Never render.** Leaks the threshold. |
| `node_id` | Workflow node id | No |

**47 documented risk codes for ID verification alone** **[CITED — docs.didit.me/core-technology/id-verification/warnings-id-verification, 2026-09-02]**, plus separate taxonomies for liveness, face match, AML, POA, NFC and KYB.

## Which ones are safe to show a host verbatim

**Safe — actionable, non-accusatory, host can fix:**

| `risk` | `short_description` |
|---|---|
| `DOCUMENT_EXPIRED` | "Document expired" |
| `IMAGE_TOO_BLURRY` | "Document image is too blurry" |
| `IMAGE_TOO_DARK` / `IMAGE_TOO_BRIGHT` | "Document image is too dark" / "…too bright" |
| `COULD_NOT_RECOGNIZE_DOCUMENT` | "Could not validate Document" |
| `COULD_NOT_DETECT_DOCUMENT_TYPE` | "Could not detect document type" |
| `DOCUMENT_NOT_SUPPORTED_FOR_APPLICATION` | "Document not supported for your application" |
| `PORTRAIT_IMAGE_NOT_DETECTED` | "Portrait image not detected" |
| `NAME_NOT_DETECTED` / `DATE_OF_BIRTH_NOT_DETECTED` / `DOCUMENT_NUMBER_NOT_DETECTED` / `EXPIRATION_DATE_NOT_DETECTED` | "… not detected" |

## What D-265 actually costs — the concrete recommendation

**Reuse `composeReason` exactly as `rejectHost` does.** The shipped shape (`src/lib/validation/ops.ts:201-204`) is:

# R4 — The retry cooldown window (D-264)

## Does Didit impose its own limit that should govern?

**NO.** **[CITED — docs.didit.me/integration/verification-statuses, 2026-09-02]**

- *"Resubmission Cycles: Technically unlimited — you can request resubmission multiple times on the same session."*
- *"No Documented Attempt Limits: the materials do not specify maximum resubmission attempts or explicit URL validity periods."*
- Session TTL exists (`Not Started → Expired`, `In Progress → Abandoned`) but is **workflow-configured** and its default duration is **not published**. **[ASSUMED]** — settle by reading the Console's workflow settings once an account exists.

**Therefore the 24-hour SWE default stands unchallenged.** There is no vendor-imposed window to defer to. Two secondary facts worth carrying into the plan:

- **Rate limits are per API key**, not per user: 10 GET/min free, 600/min paid. A 24h per-host cooldown is orders of magnitude below either.
- **A new session per retry costs $0.33** (or a free-tier unit). An unlimited retry endpoint is a **cost-amplification vector** — see § Security Domain.

## ⚠ FINDING F-1 (BLOCKING for plan 18.1-04) — `updated_at` exists, but `created_at` does not move

**The blocking check the brief asked for PASSES.** `updated_at` **EXISTS**:

- `src/lib/db/schema.ts:432-435` —
  ```ts
  updatedAt: timestamp("updated_at", { withTimezone: true })
    .defaultNow()
    .$onUpdate(() => /* @__PURE__ */ new Date())
    .notNull(),
  ```
- `tests/ops/verification-schema.test.ts` `ALLOWED_COLUMNS` includes `"updated_at"` — it is one of the nine set-equality members (`checked_at, created_at, decided_by_staff_id, provider, reason, result, status, updated_at, user_id, vendor_ref` — ten entries; the header's "exactly nine columns" is an off-by-one in prose, the array is the specification).
- Every shipped ops write sets it explicitly in raw SQL (`ops-review.ts:407` `updated_at = now()`), because `$onUpdate` only fires through Drizzle's query **builder**, not through `db.execute(sql\`…\`)`.

**⚠ BUT the second half of D-264 does not come free.** D-264 says: *"D-249's no-line-jumping rule is the precedent: a resubmission enters the queue at **resubmission time**, never at the original time. `host_verification_queue_idx` orders on `created_at ASC`."*

`host_verification` is **1:1, primary-keyed on `user_id`** (`schema.ts:404-406`; asserted by `verification-schema.test.ts` case 2). A resubmission is therefore an **UPDATE of the same row**, and `createdAt` is `.defaultNow()` — **it fires on INSERT only.** Without an explicit assignment, a host who submits in January and resubmits in September re-enters the queue **stamped January** and sits permanently ahead of every first-time submitter. **That is precisely the line-jumping D-249 forbids, in the opposite direction.**

**Required in the plan:** the resubmission write must set `created_at = now()` **as well as** `updated_at = now()`. Note this is *not* what `re-review.ts` does for listings — there, a resubmission **appends** a `listing_review` row and the queue reads `COALESCE(lr.submitted_at, l.created_at)`. `host_verification` has no history table and cannot grow one (set equality forbids nothing here — a *new table* would be legal — but D-256/scope says no). **So the host-side equivalent of D-249 is "re-stamp `created_at` on resubmission", and it must be written down at the site and pinned by a test**, or the property is asserted-not-measured.

**And the cooldown must therefore read `updated_at`, never `created_at`** — because `created_at` is about to become mutable. That is exactly what D-264 already specifies; F-1 explains *why* the distinction is load-bearing rather than arbitrary.

## Recommended cooldown implementation

```
COOLDOWN_HOURS = 24   // one named constant, a literal (not process.env), on the
                      // OPS_CANCEL_REFUNDS_SERVICE_FEE precedent at fees.ts:82:
                      // a behaviour change should be a reviewed one-line code change,
                      // never an env var that can flip silently.

The guard lives in the UPDATE's WHERE, on re-review.ts's discipline
("every source state lives in the UPDATE's own WHERE, so a 0-row result is
the single calm no-op and there is no branch a future edit can forget"):

  UPDATE host_verification
     SET status = 'pending', provider = …, vendor_ref = …, result = NULL,
         checked_at = NULL, reason = NULL, decided_by_staff_id = NULL,
         created_at = now(),          -- FINDING F-1
         updated_at = now()
   WHERE user_id = $1
     AND ( status = 'unverified'
        OR (status = 'rejected' AND updated_at < now() - interval '24 hours') )
  RETURNING user_id
```

- `suspended` is **absent from the WHERE** → D-266 is structural, not a branch. `approved`, `pending` and `grandfathered` are also absent → all are calm 0-row no-ops.
- 0 rows → return the "too soon / not applicable" result, exactly as `approveHost` returns `STALE`.
- **A host with NO ROW needs an INSERT.** Use `INSERT … ON CONFLICT (user_id) DO UPDATE … WHERE <the same predicate>`, or an INSERT with `ON CONFLICT DO NOTHING` followed by the guarded UPDATE. ⚠ On `DO UPDATE`, `created_at` is **not** reset unless assigned — see F-1.
- The in-memory limiter (`rateLimit(\`verify-submit:${userId}\`, {window:60,max:5})`) sits **above** it as the burst guard, writing an audit row on the deny branch — the `activateHosting` shape at `capability.ts:64-73`. **It is process-local (`src/lib/rate-limit.ts:9-16`: "the counter store is a single module-level Map — correct for the single-region / single-instance launch") and must never be described as the durable cap.**

- ⚠ **No PH-specific phone format is enforced anywhere in the repo today.** Recommend a permissive bound (7-20 chars, digits/`+`/spaces/hyphens) rather than a strict E.164 parser — the statute says *collect*, not *validate*, and a strict parser rejecting a legitimate landline is friction on the critical path to selling.

**On idempotency without a new table:** PayMongo uses a `paymongo_event` ledger. Didit's `event_id` is stable across retries and destinations, so a `didit_event` table would be the faithful copy — **and a new table is legal** (the set-equality test governs `host_verification`'s columns only). **But there is a cheaper, stronger option:** the verdict write is a **guarded UPDATE** (`WHERE user_id = $1 AND status = 'pending'`), so a re-delivery flips **0 rows** and is a calm no-op by construction — the same shape `approveHost` already uses to return `STALE`. **Recommend the guarded UPDATE as primary idempotency, and skip the event table** unless the plan wants the delivery ledger for forensics. Document the choice; do not leave it implicit. ⚠ **Return `200` in the 0-row case** — a non-2xx would burn one of Didit's two retries on an already-handled event.

**⚠ Local UAT needs a tunnel.** Didit *"blocks private/localhost URLs"*. The repo's memory already records the working ngrok recipe used for PayMongo webhook UAT; use it. There is **no Didit CLI** (same as PayMongo).

### Anti-patterns to avoid

## Common Pitfalls

### Pitfall 1 — Casing drift between the two Didit surfaces
**What goes wrong:** the webhook says `"Approved"`, the decision endpoint says `"APPROVED"`. A `===` comparison against one silently never matches the other, and with D-262 the failure is invisible: hosts sit at `pending` forever.
**How to avoid:** one normaliser in `didit-verdict.ts`, case-insensitive, exhaustive over all ten statuses, with an explicit `default` that leaves the row at `pending` and writes an audit row. Pin it with a table-driven test over all ten values in both casings.
**Warning sign:** a `pending` row whose `vendor_ref` is set and whose `updated_at` is hours old.

### Pitfall 2 — Reading a singular field off a V3 decision
**What goes wrong:** V3 returns `id_verifications[]`, not `id_verification`. `response.id_verification.status` is `undefined`, which reads as "not approved" — fail-closed, so no money moves, but every host is rejected. **[CITED — docs.didit.me, 2026-09-02: *"read as `response.nfc_verifications[0]`, never singular fields"*]**
**How to avoid:** type the response with arrays and no optional-chain shortcuts; assert against a captured fixture, the `tests/paymongo/webhook-payment-paid.test.ts` precedent (*"the exact nesting is asserted against a captured test event"*).

### Pitfall 3 — Parsing the body before verifying the signature
**What goes wrong:** `req.json()` then re-stringify changes the bytes the HMAC covers. T-06-SPOOF.
**How to avoid:** `const rawBody = await req.text();` first, always. `paymongo/webhook/route.ts:227-228` states the rule at the site.

### Pitfall 4 — Two retries, then permanently dropped
**What goes wrong:** Didit gives up after ~5 minutes. A deploy, a cold start, or a 5-second timeout during a webhook loses the verdict **forever**. With D-262 there is no operator to notice.
**How to avoid:** FINDING F-4's sweep. And return `2xx` **immediately** — do the notification fan-out after the ACK, or accept the 5-second budget knowingly.

### Pitfall 5 — Resubmission line-jumping (FINDING F-1)
**What goes wrong:** `created_at` does not move on an UPDATE of a 1:1 row, so a repeat submitter permanently outranks first-timers in an oldest-first queue.
**How to avoid:** assign `created_at = now()` on the resubmission branch; pin it with a test that submits, rejects, waits past the cooldown, resubmits, and asserts the queue position moved.

### Pitfall 6 — Breaking a gate that was written to stop exactly this edit
**What goes wrong:** eight of this phase's edits land on files whose tests are deliberate tripwires: the terminal-row assertions, `EXPECTED_OPS_ACTIONS`, `MATERIAL_FIELDS` set equality, `withFlippedConstant`, case 1's literal-`false` assertion, the `'withdrawn'` grep, `port.ts`'s directive-free heading, `ALLOWED_COLUMNS`.
**How to avoid:** every one is named with a line number in this document. **Read the failure message before changing an assertion** — several of them contain their own change instructions ("swap cases 1 and 2", "UPDATE rather than delete").

### Pitfall 7 — Spelling a forbidden literal in a comment
**What goes wrong:** this repository has tripped this **seven times** by its own count (`hosting-paused-notice.tsx:31-34`). Four live instances touch this phase: the guard specifier in `port.ts`, `'withdrawn'` in `re-review.ts`, the audit table's name in `review-queue.ts`, and the raw-HTML escape hatch anywhere in `src/`.
**How to avoid:** describe, never quote. `drizzle/0021`'s rule.

### Pitfall 8 — Enabling AML screening or a KYC expiration policy in the Didit workflow
**What goes wrong:** AML adds `In Review` states D-263 has no operator path for, plus $0.20/check, plus a compliance posture the regulatory brief says FitOut does not have. A KYC expiration policy silently un-approves live hosts.
**How to avoid:** configure the workflow as **ID Verification + Liveness + Face Match only**, and write that composition down in the plan so it is reproducible.

### Pitfall 9 — Fixture blast radius from the `createDraftListing` gate
**What goes wrong:** 12+ test call sites and 2 e2e specs mint drafts. All fail at once.
**How to avoid:** budget a task for it; one shared seeding helper.

### Pitfall 10 — Local webhook development without a tunnel
**What goes wrong:** Didit **blocks private/localhost URLs**. Nothing arrives, no error, silence.
**How to avoid:** ngrok/cloudflared, the recorded PayMongo recipe. There is no Didit CLI.

## FINDINGS — things the plan must decide that no decision covers

### FINDING F-1 (BLOCKING, plan 18.1-04) — `created_at` must be re-stamped on resubmission
Detailed in § R4. `updated_at` exists (not blocking); `created_at` does not move on UPDATE, so D-264's cited D-249 property is not free. **Way to settle: it is settled — assign it, and pin it.**

### FINDING F-2 (BLOCKING, plan 18.1-08) — the only caller of `createDraftListing` swallows the refusal
Detailed in § listing.ts. A refusal added today is a silent bounce to `/host/listings`, violating SC5. **Way to settle: gate the action AND route the page; the page is the hint, the action is the gate.**

### FINDING F-3 (DECISION NEEDED, plan 18.1-07) — `In Review`, `Expired` and `Abandoned` have no decision
D-261 covers `Approved`; D-262 covers `Declined`. Three terminal-or-actionable statuses are uncovered:
- **`In Review`** — Didit flagged it for *their* compliance reviewer. It is **not** a FitOut decision and there is no FitOut operator path (D-263). **Recommendation: leave the row at `pending` and wait for the follow-up `status.updated`.** It is genuinely still pending. Write an audit row so the state is observable.
- **`Expired` / `Abandoned`** — the host never finished. **Recommendation: leave at `pending`** and let the host re-submit; the cooldown does not apply because the row is not `rejected`. ⚠ But then the ops queue holds a row nobody will ever decide, which is queue pollution — the alternative is moving it back to `unverified`, which is honest ("nobody checked") and clears the queue. **Recommend `unverified`**, with the reason at the site. **Way to settle: SWE ruling in the plan; PM may overrule.**
- **`Kyc Expired`** — unreachable if no expiration policy is configured. Configure none, and say so.

### FINDING F-4 (STRONGLY RECOMMENDED, new plan or folded into 18.1-07) — a reconciliation sweep
Didit retries twice then **drops permanently**. With D-262 there is no operator to notice a lost verdict, and the host has no route to a human (D-263). FitOut already runs Inngest and already has the precedent (`payment-reconcile.ts`, D-105/D-110). A ~60-line function polling `GET /v3/session/{vendor_ref}/decision/` for `pending` rows older than 30 minutes closes the hole. **It must share the mapping module with the webhook — never a second road to `approved`.** ⚠ Free-tier GET limit is 10/min; batch accordingly.
**Way to settle: SWE ruling. Recommend YES.**

### FINDING F-5 (DECISION NEEDED, plan 18.1-06) — `VerificationDecision`'s shape
The contract type models "a verdict handed in", which Didit's *session request* is not. Two options, both honest, in § port.ts. **Recommendation: option (b), two entry points.**

### FINDING F-6 (NOTE, plan 18.1-09) — D-271's projection wording vs. the RSC-payload rule
18.1-CONTEXT says to add `email` + `phone` to both queue projections; D-271's own ⚠ forbids shipping them in the initial RSC payload. Both cannot hold. § review-queue.ts resolves it: the reveal action returns a **separate type**; the projections already carry the ids the affordance needs. **Way to settle: record the departure in the plan.**

### FINDING F-7 (NOTE) — `grandfathered` hosts and the submission path
`drizzle/0026` grandfathered hosts who owned a published listing at cutover. A `grandfathered` host is sellable (D-211/D-224) but was never checked, and `createDraftListing`'s gate must decide whether they may create a **new** listing. **D-255 lists the four refusing states as `unverified | pending | rejected | suspended` — `grandfathered` is NOT among them, so a grandfathered host may create listings.** That is consistent and needs no decision — but it must be **written down and tested**, because the natural reading of "cannot create a listing until they are verified" excludes them and a later reader will try to "fix" it. Their route to a real check is LVER-04's backfill (deferred).

### Trust boundaries this phase creates

| # | Boundary | Direction | Highest risk |
|---|---|---|---|
| **B1** | Host browser → `requestHostVerification()` | untrusted in | Cost amplification (each call is a paid vendor request); privilege escalation to sellable |

### Known threat patterns

| Pattern | STRIDE | Mitigation (all shipped-precedent) |
|---|---|---|
| **Forged webhook ⇒ fabricated approval** | Spoofing / Elevation | HMAC-SHA256 over the **raw** body; secret from env with a prod boot guard; any failure ⇒ 400. **Fail closed: an unverifiable delivery changes nothing.** |
| **Replay of a captured genuine `Approved`** | Tampering | `X-Timestamp` ±300s **plus** the guarded `WHERE status='pending'` (a second delivery flips 0 rows). Two independent controls. |
| **Cost amplification on the submit action** | DoS | `rateLimit` 5/60s keyed on the authenticated user id **plus** the 24h durable cooldown in the UPDATE's WHERE. ⚠ The limiter is **process-local**; the durable cap is the DB predicate. Say so at the site. |
| **Bucket-flood memory exhaustion** | DoS | Already solved: `MAX_BUCKETS = 50_000` + sweep + insertion-order eviction (CR-04), pinned by `tests/security/rate-limit-bound.test.ts`. Key on the **authenticated** id — never on anything a caller types. |
| **Self-asserted approval via the `callback` redirect** | Spoofing | `/host/verify` **re-reads `host_verification`**; the redirect carries no authority. D-57's lesson (*"NOT the forgeable browser return"*). |
| **XSS via the vendor's sentence** | Tampering | React text node. `dangerouslySetInnerHTML` occurs **zero times in `src/`**, asserted over comment-stripped source at `tests/ops/reject-reason.test.ts` **case 10**, and the escaped path is T-18-1301. **Do not sanitise at write** — `ops.ts:30-40`: *"A half-sanitiser is worse than none, because it reads like the problem was handled."* |
| **Cross-user data leak via a warning code** | Information disclosure | The **allow-list** in § R3. `POSSIBLE_DUPLICATED_USER` and `DOCUMENT_NAME_DIFFERENT_FROM_OTHER_APPROVED_DOCUMENTS` assert facts about other FitOut accounts and are **excluded by name**. |
| **Detector-tuning oracle** | Information disclosure | Same allow-list: anti-fraud codes (`SCREEN_CAPTURE_DETECTED`, `PORTRAIT_MANIPULATION_DETECTED`, liveness scores, `additional_data` thresholds) never reach a host. |
| **PII in the durable audit column** | Information disclosure | **D-72.** The reveal's audit row is `{ actorId: staff.id, action: "ops_reveal_host_contact", outcome: "ok", meta: { userId } }` — **ids and enum-shaped values only.** Assert on the **serialised** meta so a nested value cannot slip through. |
| **Unaudited reveal via the RSC payload** | Repudiation | D-271: **server action, not a CSS toggle.** The payload is readable; a `hidden` attribute is not a control. |
| **IDOR on the reveal** | Elevation | `requireStaff()` as the **first** statement, before parse and before rate limit — so a non-staff caller learns nothing about which ids exist. Pinned by `guardsFirst()`. |
| **Vendor outage silently approving hosts** | Elevation | The port **fails closed**: an unregistered/misspelled provider resolves to `null` ⇒ no `VerificationResult` exists to persist. `PROVIDER_UNAVAILABLE`, never a permissive default. A failed `POST /v3/session/` must return a refusal and write **no** row. |
| **Over-disclosure to Didit** | Information disclosure | Send the **minimum**: `workflow_id`, `vendor_data: user.id`, `callback`. Omit `contact_details`, `expected_details` and `metadata` unless the PM asks. `user.id` is an opaque identifier, not PII. |
| **Secret leakage into a client bundle** | Information disclosure | `providers/didit.ts` opens with the guard import (the `manual.ts` shape). A client component importing a VALUE from the port fails `next build` **naming the adapter**. `tests/design/server-only-guards.test.ts` is the census. |

## A2 — The workflow and the webhook destination are BOTH API-creatable (R1 assumed Console-only)

R1 § Webhooks and 18.1-04's checkpoint both assume the Console is the only surface. It is not:

```
POST https://verification.didit.me/v3/workflows/            -> 201, response.workflow_id
POST https://verification.didit.me/v3/webhook/destinations/ -> 201, response.secret_shared_key
GET  https://verification.didit.me/v3/workflows/            -> list existing
```

Both authenticate with `x-api-key`. `POST /v3/workflows/` body is `{ workflow_label, features[] }`
where each feature is `{ "feature": "<UPPERCASE_ENUM>", "config": {...} }`; **any unknown body field
returns 400** (there is no `workflow_type`). `POST /v3/webhook/destinations/` takes
`{ label, url, webhook_version: "v3", subscribed_events[] }` and the `(application, url)` pair must
be unique — reposting the same URL returns 400.

**Consequence for 18.1-04 Task 1:** the operator's Console work collapses to *(a)* an account, which
exists, and *(b)* an API key, and — if applications cannot be created over the API — a **SANDBOX
application**. Workflow composition and webhook registration move to a script.

**`subscribed_events` stays `["status.updated"]` ONLY.** The vendor example shows
`["status.updated","data.updated"]`; R1 § Webhooks decided one event and that decision stands —
`data.updated` carries no verdict FitOut acts on and doubles the surface 18.1-08 must authenticate.

## A3 — Session reuse on `vendor_data` — this is the mechanism behind FINDING F-1

`POST /v3/session/` is **idempotent over unfinished sessions**: if a session with the same
`vendor_data` in state `Not Started` / `In Progress` / `Resubmitted` / `Awaiting User` already exists
on the workflow's latest published version, **that existing session is returned (still `201`)**, with
only `callback` and `metadata` updated. Finished states (`Approved`, `Declined`, `In Review`,
`Expired`, `Abandoned`, `Kyc Expired`) are never reused.

F-1 recorded the symptom — *"`updated_at` exists, but `created_at` does not move"* — and marked it
BLOCKING for 18.1-04. **This is the cause.** A host pressing *Start the check* twice does not get a
second session; they get the first one back, with its original `created_at`.

**Load-bearing for 18.1-07 (submission) and D-264 (retry cooldown):** the cooldown must be derived
from `hostVerification.updatedAt` — the column 18.1-04 Task 3 adds — and never from a Didit
`created_at`, which is stable across resubmission by design. It also means the submit action's
duplicate-press guard is *already* enforced vendor-side; FitOut's own guard is defence in depth, not
the only defence.

## A4 — `environment: "live" | "sandbox"` on every webhook — a NEW fail-closed check for 18.1-08

The V3 envelope carries `environment`. R1's quoted envelope shows it; the vendor doc states the rule
plainly: **check it before mutating production state.**

**18.1-08 MUST gate on it.** A sandbox-application webhook reaching a production deployment must not
be able to approve a real host, and `sandbox_scenario` being rejected on live applications protects
only the *outbound* direction. This is the inbound half of the same guarantee, and it is cheap:
compare `environment` against the deployment's expected value and refuse the mismatch. Add it to
that plan's threat register as the inbound sibling of T-18.1-0405.

## A5 — Auth failures are 403, never 401, with no machine-readable discriminator

On the session, workflow and standalone endpoints a missing, malformed, expired or wrong-application
`x-api-key` all return **HTTP 403** with `{"detail": "You do not have permission to perform this
action."}`. The management families (`/v3/users/`, `/v3/businesses/`, `/v3/transactions/`,
`/v3/billing/`, `/v3/webhook/destinations/`) use 401 for missing/malformed and 403 for
valid-but-unpermitted.

**For 18.1-05's adapter:** do not branch on 401-vs-403 to distinguish "no key" from "wrong key" — the
information is not there. Treat any 401/403 as one credential fault, fail closed, and surface an
operator-facing reason that says *credential*, never a host-facing one.

## A6 — The complete session status set, verbatim and case-sensitive

`"Not Started"`, `"In Progress"`, `"Awaiting User"`, `"In Review"`, `"Approved"`, `"Declined"`,
`"Resubmitted"`, `"Abandoned"`, `"Expired"`, `"Kyc Expired"`. Mixed-case literals; compare
case-sensitively.

Two additions beyond what R1 § Session status values recorded, both relevant to **FINDING F-3**:

- **`"Awaiting User"`** — KYB only (waiting on a UBO/officer sub-session). FitOut runs no KYB
  workflow, so this is unreachable; 18.1-06 should map it to the same refusal as any unknown status
  rather than adding a state.
- **`"Resubmitted"`** — carries `resubmit_info: { nodes_to_resubmit: [{node_id, feature}], reasons:
  {"<node_id>": "why"} }` **instead of** `decision`. A verdict mapper that reads `decision`

`"Kyc Expired"` remains unreachable while no expiration policy is configured (Pitfall 8), and that is
the second reason to keep it unconfigured.

## A7 — Signature: an unresolved contradiction the sandbox walk must settle

R1 § Signature verification reads `X-Signature` as *"the exact raw bytes transmitted"* and FitOut
chose it as primary because the route already holds `req.text()`. The vendor doc describes the same
header as *"the raw request bytes verbatim (`sort_keys=True, ensure_ascii=True`)"* — which is not raw
bytes if the sender canonicalised before signing, and recommends `X-Signature-V2` precisely because
it *"survives JSON middleware re-encoding"*.

**These two readings cannot both be right, and no amount of further reading settles it.**

**Decision, unchanged for 18.1-08: implement BOTH** — raw `X-Signature` primary, `X-Signature-V2`
fallback, `X-Signature-Simple` never accepted. The plan already specifies this shape, so no plan
edit is needed; what changes is that the fallback is now *expected to matter* rather than defensive.
**18.1-14's sandbox walk settles it empirically** by recording which header actually verified against
real bytes — add that to what the walk captures. V2's canonicalisation, if needed:
`shortenFloats` (whole-number floats to int) then `sortKeys` (recursive lexicographic) then
`JSON.stringify` with unescaped Unicode, HMAC-SHA256 hex.

Unchanged and still correct: `X-Timestamp` freshness <= 300s, `crypto.timingSafeEqual` with a
byte-length pre-check, dedupe on `event_id` (stable across retries and destinations, unlike
`timestamp`), return 2xx inside 5s, two retries then dropped.

- **Media values are short-lived presigned URLs** — never persist the URL; re-fetch

- **`vendor_data` is FitOut's `user.id`**, as R1 recorded.

- **No new npm dependency.** The vendor offers `@didit-protocol/sdk-web` and an MCP server; FitOut

## A9 — What the vendor doc asks for that FitOut deliberately does NOT do

## B5 — Parser trap: `features` is a STRING on read and an ARRAY on write

`GET /v3/workflows/` and `GET /v3/workflows/{id}/` both return
`"features": "OCR + LIVENESS + FACE_MATCH"` — a display string. `POST /v3/workflows/` takes
`features: [{feature, config}]`. The read and write shapes are **not** the same.

The first version of `scripts/didit-setup.ts` assumed the array on read and printed `(no features)`
for all four workflows, **which reads exactly like an empty account rather than like a parse miss.**
Fixed by accepting both shapes. Recorded because the same trap is waiting for 18.1-05's adapter if it
ever reads a workflow back.

## B6 — The per-feature `is_*_enabled` booleans are NOT the composition on a graph workflow

On this workflow `is_liveness_enabled`, `is_face_match_enabled` and `is_nfc_enabled` are **all
`false`** while `features` / `cached_features` say `OCR + LIVENESS + FACE_MATCH` and the Console
renders three nodes. `is_simple_workflow: false` — the real composition lives in `workflow_graph`,
and the flat booleans are the *simple-mode* representation.

**Do not read `is_liveness_enabled` to decide whether liveness runs.** It would report "off" on a
workflow where liveness is demonstrably on. `MUST_BE_FALSE` in the script deliberately checks only
the flags that are meaningful in the negative (`is_aml_enabled`, `is_kyb_enabled`, …), where a stray
`true` is a real finding, and never uses a `false` as evidence a module is absent — module presence
is read from `features`.
