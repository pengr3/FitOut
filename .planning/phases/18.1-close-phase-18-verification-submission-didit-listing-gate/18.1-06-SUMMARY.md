# Phase 18.1 Plan 06: The Didit verdict mapper Summary

**`src/lib/verification/didit-verdict.ts` is the one place a Didit answer becomes a FitOut state change: all ten vendor statuses map deterministically in both casings, FINDING F-3 is settled in favour of releasing an expired session back to `unverified` — which is what makes `/host/verify`'s no-way-out `pending` copy honest — and D-265's rejection sentence is composed through a thirteen-code declared allow-list that is bounded, never empty, and proved by mutation.**

## Accomplishments

- **FINDING F-3 is settled, and the argument is 25 lines of the module header rather than a line in a plan.** `Expired` and `Abandoned` return the row to `unverified` for three stated reasons, and the third is the load-bearing one: the `/host/verify` `pending` panel offers **no way out** because the hosted-flow URL is a redirect target carrying a session token and is not storable. That copy is a true sentence only while an expired session releases the row — otherwise a host who closed the tab reads, forever, a sentence about a session that will never answer. Two cases named for the two statuses pin it and carry that dependency in their **failure messages**, so whoever reddens them learns what breaks upstairs.
- **The census is a census, not a list.** `DIDIT_STATUSES` is a declared tuple of the vendor's complete ten (ADDENDUM A6 — two longer than the research body), the outcome table is a **total `Record`** over the union it derives (so a new member without a decision is a compile error), and the test asserts its own table covers that tuple **member for member** (so a new member without a *recorded* decision is a red). `tsc` cannot enumerate vendor strings; these two halves together can.
- **Both casings, measured 20 ways.** The webhook envelope spells a verdict in title case and the decision endpoint's own example spells it in upper case. Every status is driven in both, plus a sweep asserting the two produce **identical** outcomes. The failure this prevents is invisible: with D-262 auto-rejecting and D-263 offering no route to a human, a casing miss means every host sits at `pending` forever with nobody prompted.
- **The unknown branch never approves, and that is asserted positively.** `"Teleported"`, the empty string, whitespace, `null`, `undefined` and the four prototype-shaped names all resolve to `status: null` / `transition: "none"` — and each case also asserts `not.toBe("approve")`, because "did not approve" and "did something harmless" are different claims.
- **`Resubmitted` does not throw.** It carries resubmission instructions *instead of* a decision object (ADDENDUM A6). The outcome says so in a field, so no caller has to know the exception, and a resubmit-shaped payload composes the canned sentence rather than blowing up.
- **D-265 is an allow-list, not a translator.** Thirteen declared codes, `Object.hasOwn` on a vendor-supplied `risk`, joined and sliced to `REJECT_NOTE_MAX` in the **note slot**, and `composeReason(HOST_REJECT_REASONS[0], kept)` — so when nothing survives, the shipped product sentence is returned alone. **No new fallback string was invented.**
- **D-272's prohibition is structural.** An attempts-exhausted code is not on the allow-list, so no sentence about having no tries left can reach a host — which would be false, because the per-module caps bound retries within one session while the weekly allowance is seven.
- **Zero dependencies.** `git diff package.json package-lock.json` is empty.

## What Was Built

### `src/lib/verification/didit-verdict.ts` (new, 563 lines)

**Pure and unguarded, deliberately.** No directive prologue and no client-bundle guard: it holds no credential, opens no connection, reads nothing from the environment and stamps no clock. `refund-rail.ts`'s position, and `fees.ts:1-30`'s rule — guard the module a client must never REACH, not the one a client legitimately imports. The module that holds the API key is the adapter, and it carries its own guard on line 1. `port.ts` is still directive-free and **byte-unchanged since 18.1-05** (`git diff 9eee399 HEAD -- src/lib/verification/port.ts` → 0 lines).

**The transition vocabulary.** `mapDiditStatus(raw)` returns `{ transition, status, audit, carriesDecision, operatorNote }`:

| Didit status | transition | audit | carriesDecision |
|---|---|---|---|
| `Not Started` · `In Progress` | `none` | no | no |
| `Resubmitted` | `none` | no | **no** — carries resubmit instructions, not a decision |
| `In Review` | `none` | **yes** | yes |
| `Awaiting User` | `none` | **yes** | no |
| `Kyc Expired` | `none` | **yes** | yes |
| `Approved` | **`approve`** | yes | yes |
| `Declined` | **`reject`** | yes | yes |
| `Expired` · `Abandoned` | **`reset-to-unverified`** | yes | (Abandoned yes / Expired no) |
| anything else | `none` + `status: null` | **yes** | no |

`audit` is `false` only for the three statuses that mean the host is mid-flow — writing a trail row every time a session pings would bury the rows that matter. `operatorNote` is named for who reads it: it is for an operator and an audit row, **never** for a host.

**The `status: null` marker.** It is the only value meaning "Didit said something FitOut has never heard of", and it can never accompany a transition other than `none`.

**Normalisation.** Trim, collapse internal whitespace, upper-case — and nothing else. An undocumented spelling (an underscored variant, say) is deliberately *not* tolerated: inventing a reading for a form the vendor has never sent means guessing what it would have meant, and the unknown branch is the honest answer.

**`DIDIT_SAFE_RISKS`** is thirteen codes with the three R3 exclusion reasons written above it, each with named examples, plus the fourth D-272 reason. The two cross-user codes are excluded **by name** in that comment so a later reader cannot add them without reading the line that says why.

**The input types are the exclusion.** `DiditWarning` models three fields — `log_type`, `risk`, `short_description` — all `unknown`, all narrowed at use. `additional_data` and `long_description` are **not on the type at all**, so the detector's score/threshold pair cannot be read by accident. `DiditDecision` models only the V3 **plural** arrays for the three features the workflow actually runs; the V2 singular spellings are absent, so `grep -c "id_verification\b"` returns **0**.

### `tests/verification/didit-verdict.test.ts` (new, 41 cases, DB-free)

Five case groups: the census in both casings (20), the guard-the-guard and casing-identity pair (21–22), FINDING F-3 named for each status (23–24), the unknown branch including the four prototype-shaped names (25–27), the warnings (28–36) and the prototype-shaped risk codes (37–38).

The census table is **hand-written rather than derived from the module**: a table imported from the thing it measures agrees with itself by construction and would pass against any edit at all. Case 21 is what turns that hand-written list into a census.

Warning fixtures are built at the **vendor's real width** — six fields including `additional_data`, `long_description` and the node identity — and cast at the boundary the module reads them through, so the cases prove the unmodelled fields cannot reach a host *even when they are genuinely present in the payload*.

### Additions Beyond the Plan (in scope, argued)

- **`Awaiting User` writes an audit row.** The plan's action text says only "no move"; ADDENDUM A6 says to map it "to the same refusal as any unknown status", and the unknown branch audits. An unreachable status arriving is exactly the signal a person should be able to see later, so it audits — the same argument the plan makes for `Kyc Expired` in the sentence above it. `transition: "none"` is unchanged either way.
- **`carriesDecision` on the outcome (Rule 2).** The plan requires that `Resubmitted` not throw; a boolean on the outcome makes that *structural* for 18.1-08 and 18.1-09 rather than a rule they must remember. It is derived from R1's own statement of when `decision` is populated.
- **`mapDiditStatus` accepts `string | null | undefined` (Rule 2).** The plan's signature is `(raw: string)`. A webhook body carrying no status at all is a real input on an untrusted path, and an absent status is not a verdict — it resolves to the unknown branch, exactly as `resolveVerificationProvider` handles a null provider name. Case 26 pins it.
- **De-duplication of identical kept sentences.** The same finding can warn twice across two reports; a host reading one sentence twice reads it as a FitOut bug rather than as two findings.
- **Punctuation between vendor fragments.** The vendor's `short_description`s are 2–5 word phrases with no terminal stop; running two together produces a sentence FitOut never wrote. They are joined with a full stop **before** the 280 slice, so the bound covers everything in the note slot. This is typography, not copy — no vendor word is altered and nothing is sanitised (`ops.ts:30-40`'s half-sanitiser rule).
- **The log-level comparison is documented as deliberately exact** (a docblock paragraph added in the Task 3 commit, because case 33 is what pins the behaviour). Only the *status* has two documented vendor spellings; the two mismatches fail in opposite directions, and the strict comparison is the one whose failure is merely quieter.
