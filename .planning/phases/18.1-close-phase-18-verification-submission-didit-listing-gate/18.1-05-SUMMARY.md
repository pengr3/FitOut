# Phase 18.1 Plan 05: The Didit adapter behind the port Summary

**Didit is registered behind the shipped verification port as one import and one registry row — the port is still the only branch point, still fails closed, the manual override survives beside it, `'migration'` is still registered nowhere, and not a single package was installed.**

## Accomplishments

- **The port's four-year-old promise was paid.** `port.ts` has claimed since plan 18-05 that adding a real vendor would be *"a REGISTRATION plus a config change rather than a re-architecture"*. It came to one import, one registry row and three environment variables. Nothing else in the codebase learned the vendor's name — an acceptance grep asserts a provider-name comparison appears **zero** times under `src/`.
- **The adapter has two entry points, exactly as FINDING F-5 decided.** `beginDiditVerification(userId)` is FitOut *asking*; `verify(decision)` is a verdict *handed in*. `VerificationDecision` was not widened, `isVerified` is still synchronous, and the asking half is deliberately not on the interface and not reachable through `runVerification`.
- **A created session is NOT a verified host, structurally.** The begin path returns `result: null` / `checkedAt: null`, so `isVerified()` reads a host who opened the hosted flow and walked away exactly as it reads one who never started (case 8).
- **Fail-closed on every failure a network call has.** A non-2xx, an auth refusal, a body without a session handle, a body without a destination, a body that is not JSON, and a rejected `fetch` all throw `DiditSessionError`. No partially-filled result, no invented `vendorRef` — the caller has nothing to write.
- **Over-disclosure is pinned by set equality and proved by mutation.** The request body is `workflow_id`, `vendor_data`, `callback` and nothing else; adding a fourth key reddens case 1 and only case 1 (run, transcribed, reverted).
- **Zero dependencies.** `git diff package.json package-lock.json` is empty. `didit-sdk` — a real, installable, completely wrong package — was not installed.

## What Was Built

### `src/lib/verification/providers/didit.ts` (new, 359 lines)

Line 1 is the bare client-bundle guard, byte-identical in form to `providers/manual.ts:1` — and the case is stronger here, because this module holds an API key. The guard is **not** on `port.ts`; the port inherits it by importing the adapter, so a client component that pulls a VALUE out of the port fails `next build` naming the adapter.

- `DIDIT_PROVIDER_NAME = "didit"` — one constant that is simultaneously the registry key and the value written to `host_verification.provider`, with the manual adapter's drift argument restated.
- A **prod-only boot guard** on `DIDIT_API_KEY` / `DIDIT_WORKFLOW_ID`, carrying `paymongo.ts:41`'s `NEXT_PHASE !== "phase-production-build"` escape. A misconfigured deploy is a loud boot failure; `next build` on a machine that has never held the credentials still compiles.
- `beginDiditVerification(userId)` — `POST https://verification.didit.me/v3/session/` with `x-api-key` and `content-type: application/json`, sending **three body keys**. `vendor_data` is the FitOut `user.id`: an opaque identifier, not PII, and the join key every webhook echoes back. The host's email and phone are deliberately absent, and so is any echoed free-form object.
- Returns `DiditSessionStart` — `{ verification: VerificationResult, hostedUrl: string }`. The hosted URL is beside the result, never inside it, and is not persisted.
- `diditVerificationProvider.verify(decision)` — `{ result, vendorRef: null, checkedAt: new Date(), provider }`, with the meaning of that null argued at the site.

### `src/lib/verification/port.ts` (modified — one import, one row, one docblock)

The registry is now two rows. The docblock records D-258's measured cost, restates D-259 (why the manual row is an ops override rather than a leftover), and restates in words — **without spelling the specifier** — why `'migration'` stays absent and why the client-bundle directive lives on the adapters. The `VerificationResult` docblock's `provider` bullet was corrected: it named `'manual'` as *"what ships in this phase"*, which stopped being true at this commit.

⚠ **Case 13 is green and byte-unchanged.** `git diff` on the test file shows no hunk inside that case, and the port gained no new occurrence of the guard specifier (3 before, 3 after — all pre-existing prose).

### `tests/verification/didit-session.test.ts` (new, 8 cases, DB-free)

Mocks the global `fetch` and imports the **real** adapter — `tests/payments/paymongo-calls.test.ts`'s shape. Cases: the minimal request (key set by **equality**, plus a scan of the serialised bytes for four field names that must not appear); the research's verbatim 201 read correctly; an eleventh response key not disturbing the read (ADDENDUM A7); the four refusal paths; the verdict shape with its `vendorRef` meaning in the failure message; and `isVerified` false for a created-but-uncompleted session.

Every case stubs `DIDIT_API_KEY` / `DIDIT_WORKFLOW_ID` / `BETTER_AUTH_URL` with obvious fakes, so the file behaves identically on a machine that holds the real credentials in `.env.local` (which `tests/setup.ts` loads) and on one that has never seen them. **No real credential is read, printed or asserted against anywhere.**

## For the Next Plan

**18.1-06 (`didit-verdict.ts` — ten statuses, two casings, the D-265 allow-list) is the next plan and is unblocked.** What it inherits:

- `diditVerificationProvider.verify(decision)` is the ONLY door to a non-null verdict. The mapper's job ends at producing a `VerificationDecision`; it must not build a `VerificationResult` itself.
- ⚠ **`checkedAt` must NOT be read from the webhook body.** The adapter stamps it from the JS clock deliberately — a body that can choose when the check happened can choose to have happened before a cooldown started.
- ⚠ **`"Resubmitted"` carries `resubmit_info` INSTEAD of `decision`** (ADDENDUM A6); a mapper reading `decision` unconditionally throws. `"Awaiting User"` is unreachable (KYB only) and should map to the same refusal as any unknown status.
- ⚠ **Do not present an exhausted-module decline as "you have no tries left"** — D-272's per-module caps (2 document attempts, 3 liveness, 3 face-match) bound retries *within one session*, not sessions per week.

**For 18.1-08 (the webhook):** the verdict write must **PRESERVE** `host_verification.vendor_ref`. The adapter's `vendorRef: null` means *no new handle*, and that meaning is now carried in a failure message so a future reader cannot quietly turn it into an overwrite. Also inherited: `environment: "live" | "sandbox"` on the envelope must be gated (A4), and no state may derive from the `callback` redirect (A9) — the adapter sets a callback for UX only and says so at the site.

**For 18.1-11 (`/host/verify`):** `beginDiditVerification` returns the hosted URL as `start.hostedUrl`, separate from the persistable result. Redirect to it; do not store it. D-273's mobile-only promise is still that plan's to keep.
