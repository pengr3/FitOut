# Phase 18.1 — UI Design Contract

> The **continuation** of `18-UI-SPEC.md`, not a competing document. Phase 18 shipped the console that
> *decides*; this phase ships the thing that *submits to it*, the gate that refuses without it, and the
> one ops row change that lets a reviewer reach the person behind a queued row.

---

## What this document is, and what it deliberately does not touch

Phases 10–17 shipped a gated design system, a pattern layer, an app shell, a responsive/a11y/theme audit
and a hard set of build-blocking quality gates. Phase 18 added the `(ops)` shell, the queue row, the
reject dialog, the host review/suspension signals and the booker-facing check badge. **Colour, the four
type roles, focus, status tones, elevation, z-index, motion, the contrast inventory, the three card
patterns, the four state families, the one overlay primitive and the eight typed inventories are LOCKED.**

`npm run build` = `lint && test:design && next build`, so a raw hex, an arbitrary type size, an
undeclared `data-testid`, a raw `<Card>` in an unlisted file, an eleventh accent use, a viewport-
conditional JSX branch, an undeclared live region, an unguarded `mailto:` or a `loading.tsx` writing its
own box measurement **already fails the build today**.

**This document invents no primitive, no token, no font, no icon set and no palette.** Every value in
the tables below was extracted from the working tree on **2026-09-02** and is cited with a file path.
Everything else either *consumes* a shipped token/pattern/recipe, or names precisely which declared
inventory must be **EXTENDED** — and an extension is always "add a row with its reason and move the
number in the same commit", never "invent a value at the call site".

⚠ **An internal tool is not exempt in this repo, and neither is a once-ever host surface.** All five
design gate families reach `/host/verify` and the changed `/ops` row: themes, 320px responsive, a11y,
designed loading/empty/error states, and the pinned inventories. There is no carve-out anywhere in
`tests/design/**` and this spec does not create one.

**Decision-ID namespace.** Bare `D-2xx` means 18.1-CONTEXT `D-255…D-271` unless the number is ≤ D-254,
in which case it is 18-CONTEXT. PROJECT-namespace numbers are written `PROJECT D-NN`.

⚠ **A comment containing a banned token trips the design greps.** Where this document instructs source
prose, it instructs **descriptive naming**, never quotation of a gated string. This repository has
tripped that trap seven times by its own count (`hosting-paused-notice.tsx:31-34`).

## Typography

Inherited unchanged. Four roles, declared in `src/app/globals.css` and pinned by
`tests/design/type-scale.test.ts` against `TYPE_ROLES` (`src/lib/utils.ts:40`), which is
`["display","heading","body","label"]`.

Extracted values, both themes (`globals.css:259-273` court · `:370-384` grove):

| Role | court (default) size / line-height / weight | grove size / line-height / weight | Where Phase 18.1 uses it |
|------|--------------------------------------------|-----------------------------------|--------------------------|
| `text-display` | `1.75rem` (28px) / `1.15` / `600` | `2.125rem` (34px) / `1.2` / `700` | The `<h1>` on `/host/verify`, through `PageHeader`. **Nowhere else in this phase.** |
| `text-heading` | `1.25rem` (20px) / `1.3` / `600` | `1.5rem` (24px) / `1.3` / `700` | `PanelCard`'s own `title` (the STATE) on the verification panel, at the pattern's default `titleAs="h2"`. Unchanged on the ops row's wait figure. |
| `text-body` | `1rem` (16px) / `1.5` / `400` | `1.0625rem` (17px) / `1.6` / `400` | Every REASON sentence on the verification panel, and the frozen-session sentence on `/host/earnings` — matching `hosting-paused-notice.tsx`'s shipped `text-body text-muted-foreground`. |
| `text-label` | `0.875rem` (14px) / `1.43` / `400` | `0.9375rem` (15px) / `1.5` / `400` | Every `<dt>` and `<dd>` on the ops row (`ROW_TERM_CLASS = "text-label text-muted-foreground"`, `ROW_VALUE_CLASS = "text-label"`, `ops-queue-row.tsx:91,97`), the form's field labels and helper lines, and both refusal regions. |

**Three type rules this phase adds, each a continuation of 18-UI-SPEC § Typography:**

1. **THE STATE IS THE PANEL'S HEADING, AND THE REASON IS BODY.** `PanelCard title={…}` carries the state
   at `text-heading`; the reason is a `<p className="text-body text-muted-foreground">`. This is
   `hosting-paused-notice.tsx`'s shipped shape reused literally, and it is why a suspended host reading
   `/host` and a rejected host reading `/host/verify` get the same visual grammar for the same kind of
   news.
2. **NOTHING ON THE OPS ROW IS PROMOTED BY THE REVEAL.** `Contact`, `Email` and `Phone` compute
   `ROW_TERM_CLASS` / `ROW_VALUE_CLASS` — the **identical** constants the six existing facts use. A
   revealed email is not more important than the address; it is one more fact on a row whose loudest
   thing is still the wait figure (`ROW_LEAD_CLASS = "text-heading tabular-nums"`, `:107`).
3. **NO `tabular-nums` ON A PHONE NUMBER.** `ROW_MONEY_CLASS` (`:94`) is for money and counts. A phone
   number is an identifier, not a figure to compare down a column, and giving it the money treatment
   would be the first step toward reading it as one.

### The accent reserved-for list — Phase 18.1 appends ZERO entries. It stays at 10.

`src/lib/design/accent-uses.ts` holds ten entries and `AccentUseCountIsTen` (`:212`) is a **compile**
constraint, so an eleventh fails `next build`'s own type check. Entry 1 is
`<Button variant="brand">`, whose call sites are pinned **by count** at **20** across the adoption trees
by `tests/design/brand-recipe.test.ts`.

- **`Start the check` is a NEUTRAL SOLID `<Button size="touch">` (default variant), never
  `variant="brand"`.** Two reasons, either sufficient. (a) The verification panel has **exactly one**
  control, so it needs no hue to be found — coral's job on this product is to pick one action out of
  several, and there are no others. (b) This is the button that hands a person's identity document to a
  third party; painting the highest-consequence, least-reversible act on the host tree in the conversion
  colour is a nudge on a decision that belongs to the host. 18-UI-SPEC made the same call for `Approve`
  on the same reasoning, one surface over.
- **`Ask for another check`, `Resend the email` and `Show contact` are `variant="outline"`.** Secondary
  weight for secondary acts, the shipped `RequestActions` / `OpsDecisionActions` grammar.
- **Consequence, stated so a planner does not "helpfully" fix it:** `brand-recipe.test.ts`'s per-file
  map and its total of 20 **DO NOT MOVE**, and `ACCENT_USES.length` stays 10.

### `--destructive` gains ZERO occurrences, and that is a decision

`tests/design/host-tone-census.test.ts` holds `EXPECTED_ALARM_OCCURRENCES` as an **equality map in both
directions** over `src/app/(host)/`, `src/components/host/` and `src/components/availability/`. The five
declared spenders are `wizard.tsx` (1), `weekly-hours-editor.tsx` (1), `host-cancel-dialog.tsx` (1),
`payout-banner.tsx` (3), `payout-state-badge.tsx` (3).

**`/host/verify` adds none, and the phone-field refusal is why this is a decision rather than an
omission.** A validation refusal on a control the host just used *is* inside the alarm role's shipped
reservation (`wizard.tsx`'s D-150 entry is exactly that). This spec still declines it:

- The panel has **one outcome**, and it already has **one named `role="status"` region** to announce it
  (GATE-03 rule 6 — exactly one live region announces one outcome). An `aria-invalid` field error
  *beside* that region would be a second announcement of the same outcome on a form with one field.
- The closest sibling by shape — the ops row's refusal region, which reports a server refusal on a
  surface that survives the press — is **explicitly ordinary ink, no alarm colour** (18-UI-SPEC § The
  refusal region), and this is that same shape on the other side of the console.
- ⚠ **The alternative, recorded rather than hidden:** treating the phone refusal as the canonical field
  refusal and adding a sixth row to `EXPECTED_ALARM_OCCURRENCES`. It is defensible; it is not what this
  spec chooses, and a plan that takes it must move the map with a written reason in the same commit.

**`/ops` adds none either.** The reveal is not a decision, not a failure and not destructive. Its refusal
sentence renders in ordinary ink in its own named region — 18-UI-SPEC § The refusal region, verbatim.

### `--success` gains ZERO occurrences, and the `approved` panel is where that bites

`tests/design/status-vocab.test.ts` asserts **set equality** over every file naming the success hue:
`SUCCESS_HUE_SITES` is the union of `POSITIVE_CALL_SITES` (4 files) and `SUCCESS_GLYPH_SITES` (1 file) —
**five, and the scarcity is the point**: *"a hue that appears on every satisfied outcome stops meaning
the one that matters."*

- **The `approved` state of `/host/verify` renders NO green, NO `CheckCircle2`, NO tone prop.** It is the
  same muted panel every other state uses, with different words. A host who has just been checked is
  being told a fact, not congratulated.
- **`SUCCESS_HUE_SITES` therefore stays at 5.** If a plan reaches for `tone="positive"` here, that gate
  goes red and the remedy is to delete the tone, not to add a row.

### Status tones — unchanged at four

`src/lib/design/status-tones.ts` stays `["neutral","positive","attention","soft-accent"]`. Phase 18.1
uses **neutral only**, on the binding DS-10 rule `review-signal.ts`'s header states: *a listing awaiting
a decision, and one that did not get it, are both NORMAL LIFECYCLE STATES of a working marketplace.* A
host waiting on a vendor, and a host a vendor did not pass, are the same category one level up.

## Copywriting Contract

Every sentence below obeys `src/lib/host/requests-signal.ts:56` — **a signal names the STATE, the REASON
and the WAY OUT** — and, where there is genuinely no way out, says so plainly and stops, which is
`hosting-paused-notice.tsx`'s recorded reading of the same rule.

### The four banned families, restated (from `tests/listing/review-signal.test.ts` § the banned language)

| # | Pattern (verbatim from the gate) | Why | What it forbids in THIS phase |
|---|----------------------------------|-----|-------------------------------|
| 1 | `/appeal/i` | host appeals are backlog 999.6 and OUT (D-243/D-263) | no "appeal", no "request a review", no "ask a person to look at this" |
| 2 | `/we'?ll be in touch\|get back to you\|reply to (this\|us)\|contact us\|email us/i` | a promise of a reply into an inbox FitOut does not have | no route to a human anywhere on the host tree (**D-263**) |
| 3 | `/within \d+\|\d+ (business )?(hours?\|days?\|weeks?)\|shortly\|soon/i` | a timeline nothing in the system agrees to keep | ⚠ **this is why D-264's cooldown is quoted as an ABSOLUTE TIMESTAMP and never as "in 24 hours"** — see § Surface 1 |
| 4 | `/[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}\|mailto:\|\bSupport\b/` | `SUPPORT_EMAIL` is null (D-250) | no address, no `mailto:`, no `Support` label in any **host-facing** string |

Family 3 deserves the sharpest note, because a well-meaning implementation walks straight into it. The
ban's stated reason is *a timeline nothing in the system agrees to keep*. A 24-hour cooldown **is** kept
by the system — it is literally the `updated_at < now() - interval '24 hours'` clause of the guarded
UPDATE. The honest and gate-safe way to express a fact the database enforces is the **instant**, not the
**duration**: `"You can ask for another check after 3 Sep 2026, 4:15 pm."` matches none of the four
patterns, cannot disagree with the server (it is `updated_at + 24h`, computed server-side and passed in
finished per PROJECT D-130 / GATE-05), and does not read as a promise about a human.

## Surfaces

Five surfaces. For each: the states, the copy, the layout, and the **named gate that proves it**.

---

### Surface 1 — `/host/verify`, the host verification surface *(Claude's Discretion — adopted from 18.1-RESEARCH § "Where the host-facing verification surface should live", with two improvements)*

**ADOPTED from the research, unchanged:**

- **Route: `src/app/(host)/host/verify/page.tsx`.** A sibling of `earnings` / `requests` / `payouts`, one
  segment, reachable from the `/host` dashboard, from the wizard refusal path and from Didit's
  `callback`. **Not** nested under `listings/` — verification is about the **host**, not a listing.
- **NOT in `HOST_NAV`.** `src/lib/nav.ts` holds `HOST_NAV_IDS = ["earnings","requests"]` and every
  `NavLink` carries a **mandatory `why`** because *"primary nav is the scarcest surface in the app… it
  competes with the mode switch and the bell for 226px at 320px."* No honest `why` can be written for a
  once-ever destination that is dead weight the moment it succeeds.
- **Shape:** `PanelCard tone="muted"` carrying **state / reason / way out**, following
  `hosting-paused-notice.tsx`.
- **Copy lives in a module, not in the page.** New file `src/lib/host/verification-signal.ts`, on
  `review-signal.ts`'s exact shape, for the reason `hosting-paused-notice.tsx:7-11` gives: *"A sentence
  typed into three page files is the shape `requests-signal.ts`'s header describes by name."*

**IMPROVED on the research, and each improvement is argued:**

1. **The signal map is a TOTAL `Record<HostVerificationStatus, VerificationSignal>`, not a partial one.**
   `review-signal.ts` splits its copy across `REVIEW_SIGNAL` (partial) + `SILENT_REVIEW_STATES` (the
   declared silence) because three of its five states render nothing on a *card*. `/host/verify` is a
   **destination**, and a destination that renders nothing is a broken page. So every one of the six
   `host_verification_status` values gets a panel, and `tsc` enumerates them: a seventh enum member
   fails to compile until somebody decides, in writing, what the host reads.
2. **The way IN is a fourth `HostSignals` row, not a nav slot and not a bare link.**
   `src/components/host/host-signals.tsx` already renders three conditional advisories as
   `PanelCard tone="muted"` + a sentence + an inline underlined `<Link>` (`:114` is the shipped
   precedent for a conditional route). A fourth row on the same shape is the cheapest honest entry
   point and costs no new pattern. **Rendered for `unverified | pending | rejected` only** —
   `approved` and `grandfathered` are silent (nothing is owed), and `suspended` already renders
   `HostingPausedNotice` above it, so a second row there would be two panels about one state.

#### The six states

| `host_verification.status` | STATE (`PanelCard title`, `text-heading`) | REASON (`text-body text-muted-foreground`) | WAY OUT |
|---|---|---|---|
| `unverified` | **Get your account checked** | **FitOut checks who a host is before their first listing can go up. The check happens on our checking partner's site — FitOut never sees or keeps what you show them.** | **Start the check** (the form below) |
| `pending` | **Your check is in progress** | **Your check is with our checking partner and FitOut is waiting on the result. You can't create a listing until it lands.** | **none — a decision, see below** |
| `approved` | **Your account is checked** | **FitOut has checked your account. You can create listings and publish them.** | **Go to your listings** → `/host/listings` |

Your spaces can't be booked, and payouts are on hold."** + the operator's sentence | **none** (D-266: cannot re-submit; D-260/D-263: do not name what unfreezes it) |

**Four notes, each of which is the decision rather than the description:**

- **`pending` has NO way out, and the reason is structural rather than stylistic.** FitOut stores
  `vendorRef` (the session id) and **not** the hosted-flow URL — `port.ts:76-98` is emphatic that
  `VerificationResult` has four fields and *"DO NOT ADD A FIELD HERE"*. So a "Continue the check" link
  **cannot be reconstructed**, and offering one would be a control that acts on nothing —
  `REVIEW_SIGNAL.pending`'s recorded reason for the same absence one surface over.
  ⚠ **THIS COPY IS ONLY HONEST IF 18.1-RESEARCH FINDING F-3 LANDS.** If an `Expired`/`Abandoned` session
  leaves the row at `pending` forever, this panel is a permanent dead end and "waiting on the result"
  becomes a lie by omission. **The plan MUST map `Expired`/`Abandoned` → `unverified`** (F-3's own
  recommendation), which returns the host to the `unverified` panel and its control. Recorded in
  § NOT COVERED as the one place this spec's honesty depends on a decision it does not own.
- **`grandfathered` names no check and names no cutover.** It says what is TRUE for that host — they can
  already list — and stops. Saying "your account was set up before FitOut started checking accounts"
  would be accurate and would still be the question-inviting disclosure D-211 refuses. Saying "your
  account is checked" would be a **fabricated verdict**, which is the `pending-copy.test.ts` defect
  exactly. A host reaches this panel only by typing the URL, and what they get is a true, terminal,
  unremarkable sentence.
- **`suspended` renders the SHIPPED component, not new words.** `HostingPausedNotice` is imported and
  used as-is. There is **no submit control** on this branch, and its absence is D-266 made visual: the
  machine cannot reverse a named staff member's enforcement decision, so the product does not draw the
  button that would try.
- **`approved` claims only "your account".** Not "your ID", not "your documents", not "your identity was
  verified by our partner". HVER-05's discipline reaches here: FitOut may state that a check happened
  and who can act on it, never what was inspected.

#### The rejection sentence (D-265) — bounded, escaped, never empty

### Surface 5 — `/host/earnings` names the frozen session *(F11 / D-260)*

**~80% shipped.** `src/app/(host)/host/earnings/page.tsx:160` already reads `loadHostVerification`;
`:172-181` already renders `<HostingPausedNotice reason={verification.reason} />` **first, above the

frozen-session sentence**.

#### Where it sits

**A SECOND paragraph inside `HostingPausedNotice`**, beneath `composeSuspendedSentence(reason)`, rendered
only when the component is passed the new optional prop.

```tsx
<PanelCard tone="muted" title={SUSPENDED_HOST_SIGNAL.state}>
  <p className="text-body text-muted-foreground" data-hosting-paused>
    {composeSuspendedSentence(reason)}
  </p>
```

- **Not a second panel.** One state, one notice. A second panel about the same suspension is a second
  thing to keep in agreement with the first — `hosting-paused-notice.tsx`'s own founding argument.
- **The prop is optional and only `/host/earnings` passes it.** `/host` and `/host/listings` render the
  notice unchanged; the frozen-session fact belongs on the page where a host goes looking for money
  (D-252's whole reasoning), and nowhere else.

  nothing missing from the table, and a sentence about it would be a fabricated absence.

and `hosting-paused-notice.tsx` *"is the one place that decides how they are presented"*.

| 1 | **One session you've already hosted isn't in this table: {space} on {date}. Its payout is on hold.** |

| 0 | *(nothing renders)* |

- **The date is ABSOLUTE, never relative.** `Intl.DateTimeFormat` with `month: "short", day: "numeric",
  year: "numeric"` — `formatSubmitted`'s idiom. A relative phrase ("3 days ago") would trip banned family

- **It does NOT name what unfreezes it.** D-260 is explicit and 18-13's refusal stands: `wayOut: null` is
  *"a DECISION recorded in the data, not a field somebody forgot to fill in."*
- **It does not apologise, promise, or offer a route.** State, reason, stop.
- **Every figure and date arrives FINISHED from the server** — PROJECT D-130 / GATE-05. The component

## NOT COVERED — real blind spots, stated so the next reader under-trusts this document

- **`pending` is only honest if FINDING F-3 lands.** This spec's `pending` panel offers no way out
  because the hosted-flow URL is not storable. That is correct **only** if an `Expired`/`Abandoned`
  session returns the row to `unverified`. If the plan leaves those statuses at `pending`, a host who
  closes the tab is stuck forever reading "FitOut is waiting on the result" about a session that will
  never answer — and the copy becomes a lie by omission. **The plan must decide F-3 before this panel
  ships.**
- **The generic `!res.ok` branch on `/host/listings/new` is still a silent bounce.** This phase routes
  the *verification* refusal before the action is called; a genuine infrastructure failure still
  redirects to the grid with no message. Recorded, not fixed.
- **`OPS_QUEUE_ROW_HEIGHT` is a shipped measurement that this phase may invalidate.** The Contact fact
  adds a `<dl>` row, and the revealed state adds two. Whether `"h-132 lg:h-211"` still holds is a
  **picture**, and it belongs to `e2e/skeleton-geometry.spec.ts` — which PROJECT D-24 keeps out of CI.
- **This document proves nothing about pixels.** It names tokens, patterns and recipes. Whether
  `/host/verify` is legible at 320px in both themes is a picture, and the e2e sweeps that measure it are
  sampled at "whenever a human runs them".
- **The Didit hosted flow is not FitOut's UI and is not specified here.** Assumption A8 in
  18.1-RESEARCH — *the hosted flow is usable at 320px on a mobile browser* — is unverified, and it is on
  the dominant PH device class. **Walk one sandbox session on a phone and record it** before the phase
  gate; nothing in `tests/design/**` can see it.
- **The vendor's `short_description` strings are copy FitOut does not review.** The allow-list bounds
  *which* codes reach a host, not *what those codes say* in a future Didit release (Assumption A4). The
  280-char slice and the canned fallback are the only mechanical protections, and neither can catch a
  vendor rewording a permitted sentence badly.
- **The `mailto:` exemption is a hole in a gate that had none.** It is one file, one scheme, one reason,
  and it is guarded-the-guard — but the null branch of `site-contacts.test.ts` is now *"zero unguarded
  `mailto:` **except one declared row**"*, which is strictly weaker than *"zero"*. That is the cost of
  D-271 and it should be re-read the day `SUPPORT_EMAIL` is set.
- **The tone ruling on the phone-field refusal is a judgement, not a measurement.** Neutral ink in the
  region was chosen over the alarm role at a field. Both are inside the shipped reservations; only one
  can be right about how a host reads a one-field form, and no gate can tell which.
