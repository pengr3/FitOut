<objective>
Build the **one** module that turns a Didit answer into a FitOut state change — and decide the three
statuses no decision covers.

D-261 covers `Approved`. D-262 covers `Declined`. **FINDING F-3** names three more that nobody ruled
on, and this plan settles them. It is also where **D-265**'s rejection sentence is composed: an
allow-list of vendor risk codes, not a translator.

⚠ **This mapper is SHARED.** The webhook (18.1-08) and the reconciliation sweep (18.1-09) both go
through it. Two `UPDATE host_verification SET status='approved'` statements is exactly what D-105
forbids one domain over — *never a second road*.

⚠ **THE SEQUENCING CONSTRAINT THIS PLAN EXISTS TO SATISFY.** `18.1-UI-SPEC.md`'s `pending` panel says
*"Your check is with our checking partner and FitOut is waiting on the result"* and offers **no way
out**, because the hosted-flow URL is not storable. That copy is honest **only if** an
`Expired`/`Abandoned` session returns the row to `unverified`. If it stayed `pending`, a host who
closed the tab would be stuck forever reading a sentence about a session that will never answer.
**This plan must land before or in the same wave as the `/host/verify` panel, and it must carry an
explicit test asserting `Expired` and `Abandoned` map to `unverified`.**

Purpose: one deterministic, case-proof, fail-closed translation from a vendor vocabulary FitOut does
not control.
Output: one pure module, one table-driven test file.
</objective>
