<objective>
Ship **the thing that submits** — the code path Phase 18 never wrote.

Repo-wide, the only `INSERT INTO host_verification` today is a test seed and the `drizzle/0026`
grandfather backfill. `approveHost()` is an `UPDATE … WHERE status IN ('pending','unverified')`, so
with no row it flips nothing and returns `STALE`. **The ops host queue can never fill, no new host can
ever be approved, and no host created after `drizzle/0026` can ever sell.** That is a live production
defect. This plan closes it.

**This plan absorbs the ROADMAP's suggested `18.1-05`.** The reasoning, stated because the ROADMAP's
order is a dependency order rather than a mandate: `18.1-RESEARCH.md § 18.1-05` observes that the
submission path and the § 21(b)(3) contact requirement *"share one action and one test file"* — the
phone and the email are **gates inside `requestHostVerification`**, not a separate surface, and
**D-267 means the address half is zero work** (the listing's own address is the § 21(b) record).
Splitting them would produce a plan whose only artifact is two `if` statements inside another plan's
function.

Purpose: `/ops`'s host queue fills from ordinary product use, and FitOut holds what RA 11967 § 21(b)
obliges it to hold before a listing goes up.
Output: one host server action, one shared test helper, one integration file, one extended queue test.
