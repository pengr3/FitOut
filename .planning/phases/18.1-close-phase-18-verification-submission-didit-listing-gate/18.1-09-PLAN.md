<objective>
Close the hole D-262 opens: **a verdict that never arrives.**

Didit retries a webhook **twice** — roughly one minute and four minutes — and then **drops it
permanently**. PayMongo retries far more aggressively; this is a materially weaker guarantee. A
deploy, a cold start or a five-second timeout during that window loses the verdict **forever**. With
**D-262** there is no operator watching, and with **D-263** the host has no route to a human. The
only thing left is D-264's 24-hour retry, which a host must think to use on a page that is telling
them FitOut is *"waiting on the result"*.

**FINDING F-4 IS DECIDED: the sweep SHIPS IN THIS PHASE.** The `18.1-CONTEXT` premise that FitOut has
no always-on worker is false — Inngest is shipped, mounted at `/api/inngest`, and already runs nine
functions. `payment-reconcile.ts` is the **exact** precedent: it exists because a PayMongo webhook may
never arrive (D-105/D-110). The research sizes this at roughly sixty lines.

⚠ **It must share the mapper and the write module with the webhook.** Never a second road to
`approved` — that is D-105's lesson, one domain over.

Purpose: an auto-verdict that Didit could not deliver still lands, without a human noticing anything.
Output: one decision-endpoint reader, one scheduled function, one registration, one test file.
</objective>
