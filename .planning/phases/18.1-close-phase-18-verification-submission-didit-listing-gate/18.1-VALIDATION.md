### ⚠ Why the latency box is not ticked, with the numbers

The **per-task** half of the contract holds: a single file under either config returns in ~2–35 s, and
that is the latency that actually governs execution. The **per-wave** figure does not. Measured on
this box during 18.1-13 and 18.1-15 and recorded in `deferred-items.md § D4` and `§ D8`:

| `npm test`, full, byte-identical tree | Duration | Result |
|---|---|---|
| 18.1-13 run 1 | **5405 s** | `2 failed \| 214 passed` |
| 18.1-13 run 2 | **258 s** | 1 *different* failure |
| 18.1-13 run 3 | **286 s** | fully green |

**A 21x spread on an unchanged tree is a fact about the machine, not about the suite** — and the two
failures are what that spread does to a 20 s timeout and to a test that presses a control twice. Even
the *fast* runs exceed 240 s before `test:design` and `build` are added. The e2e half is worse: one
sampled run took **1.7 hours**.

⚠ **Ticking this box would have been the easiest and least honest edit in the file.** It is left open
so the number is a claim somebody can check rather than a formality somebody performed. **Do NOT
"fix" it by raising `testTimeout`** — D4 says why: a 5x margin when run alone is the evidence the
tests are correctly sized, and a raised timeout hides the next real regression.
