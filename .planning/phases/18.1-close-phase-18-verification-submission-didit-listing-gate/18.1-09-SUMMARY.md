# Phase 18.1 Plan 09: The Inngest Reconciliation Sweep Summary

**A verdict Didit decided but could never deliver now lands anyway** — a 15-minute Inngest singleton
reads `GET /v3/session/{vendor_ref}/decision/` for `pending` rows idle past 30 minutes and hands the
answer to the same `applyDiditVerdict` the webhook calls, so D-262 survives the vendor's
two-retries-then-drop policy without a second road to the approved state.

## What shipped

**1. `fetchDiditDecision(sessionId)` — the polling fallback** (`src/lib/verification/providers/didit.ts`)

The vendor's own documented fallback, on the same thin `fetch` wrapper `beginDiditVerification`
uses: `GET https://verification.didit.me/v3/session/{id}/decision/` with `x-api-key`. It READS and
translates nothing — it hands back the vendor's status string in whatever spelling arrived and the
vendor's three feature blocks untouched, because `didit-verdict.ts` is already the single
translation and a second normaliser would be a second thing to keep in agreement about the ten
strings that decide whether a host may sell.

Typed with the V3 **plural** arrays only (`id_verifications[]`, `liveness_checks[]`,
`face_matches[]`); the V2 singular keys are not merely unread but unrepresentable, which is Pitfall
2 closed structurally — a singular key would be `undefined`, read as "not approved", and reject
every host. No media value is modelled, so no presigned URL can be persisted (ADDENDUM A8 / D-263).

Fails closed on every failure it has: a transport failure, a 429, a refused credential, any other
non-2xx, a body that is not JSON, and a 2xx carrying no usable status all **throw**. Nothing
half-filled is ever returned, so the sweep has nothing to apply and the row is left where it was.
401 and 403 are handled as ONE credential fault with an operator-facing sentence naming the
credential (ADDENDUM A5 — the vendor gives no discriminator, so neither does the message).

**`DiditRateLimitError`** is a named subclass rather than a `status === 429` test at the call site.
To a batched caller the two refusals mean opposite things — "we did not learn about this row, carry
on" versus "you are asking too fast, and continuing is what makes it worse" — and folding them
together makes the wrong one the default. It extends the module's existing refusal, so a caller that
only knows `DiditSessionError` still fails closed.

**2. The sweep** (`src/inngest/functions/didit-reconcile.ts`, 362 lines)

`import "server-only";` on line 1, byte-identical to `payment-reconcile.ts`'s. Cron `8-59/15`
Asia/Manila, `concurrency: 1`, one `step.run` per row so a row whose GET times out retries only that
row. Each pass:

1. `queryStalePendingVerifications` selects `status = 'pending'` **AND** a non-blank `vendor_ref`
   **AND** `updated_at <= now() - make_interval(mins => 30)`, oldest-first, `LIMIT 8`. The age
   comparison runs on the **Postgres** clock.
2. `reconcileOne` calls `fetchDiditDecision(vendor_ref)`. A 429 returns `rate-limited` and the
   handler **breaks**; every other vendor failure returns `unreachable` and touches nothing.
3. The answer goes to **`applyDiditVerdict`** — same module, same mapper, same port, same
   notification. `sessionId` is the row's own handle, so the write module's divergence observation
   is quiet on this path by construction.
4. When and only when a row actually **moved**, a `didit_reconciled` / `needs_attention` audit row
   plus a `[DIDIT_RECONCILE_ALERT] webhook_missed` console line record that the transport failed —
   D-110's shape, one domain over, on the machinery that already exists.

**3. Registration** — one static import, one entry in the `serve()` functions array, and the
header's census updated from NINE/SEVEN crons to TEN/EIGHT with the new residue argument written
out. `next build` resolves every import.

## Why the numbers are the numbers

| Constant | Value | Derivation |
| --- | --- | --- |
| grace window | 30 min | Didit's second retry lands at ~4 min; 30 is past it by a factor of seven, so a delivery merely in flight is finished long before the sweep is entitled to an opinion. No ceiling — the 7-day session TTL (ADDENDUM B1) means an older row reads `Expired`, and applying that is the F-3 release. |
| batch limit | 8 | Under the **free tier's 10 GET/min**; the paid tier is 600/min and is deliberately not the sizing basis. Even a whole batch issued inside one minute cannot 429 itself. |
| interval | 15 min | Long enough that two passes can never contribute to the same minute; worst-case recovery latency is grace + interval = 45 min, against an alternative of *never*. |
| start minute | :08 | Residue 3 mod 5 — the last residue free, given the hourly crons and digest at residue 0 (:00 :15 :30 :45 :50), payment-reconcile at 2 and checkout-retire at 4. |

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 2 — missing correctness guard, then corrected by measurement] The handle bound is two
predicates, and only one of them is a control.**

- **Found during:** Task 2 (written), Task 3 (measured).
- **Issue:** the plan specifies `vendor_ref IS NOT NULL`. A blank-but-not-null handle would address
  `/v3/session//decision/` — a different endpoint — so `btrim(vendor_ref) <> ''` was added beside
  it as defence in depth. The mutation pass then showed the *added* predicate was the only one
  doing anything.
- **Fix:** both predicates kept (the NULL test reads clearly and is the plan's stated criterion),
  the comment corrected from "defence in depth" to the measured truth, and a whitespace fixture
  added so the dominant predicate is under test.
- **Files:** `src/inngest/functions/didit-reconcile.ts`, `tests/inngest/didit-reconcile.test.ts`
- **Commit:** `831d01a`

**2. [Rule 3 — blocking] The suite leaked into itself, because the sweep is global.**

- **Found during:** Task 3, first run — `6 failed | 7 passed`. Case 7's "zero HTTP calls" saw 1,
  case 11's "exactly one" saw 8, and case 10 was asked about two sessions belonging to two other
  cases.
- **Issue:** the sweep selects every stale `pending` row in the database, not a row the case named,
  so each case's leftovers were legitimate candidates for later passes. Nothing was wrong with the
  sweep; the harness was measuring the leak.
- **Fix:** `TRUNCATE host_verification, audit, "user" CASCADE` in `beforeEach`, with the measured
  numbers recorded at the site so nobody later "simplifies" it away.
- **Commit:** `831d01a`

**3. [Rule 3 — blocking] `$onUpdate` would have made every "stale" fixture fresh.**

- **Issue:** `schema.ts:432-435` declares `$onUpdate` on `host_verification.updated_at`, so seeding
  a handle through the Drizzle query builder stamps `updated_at` to `now()` — the staleness
  fixtures would have asserted the opposite of what they name, silently.
- **Fix:** the fixture sets `vendor_ref` and `updated_at` through raw SQL in one statement, with the
  instant bound as an ISO string + explicit `::timestamptz` (the measured `ops-review.ts:390-401`
  rule). PATTERNS idiom 6, applied in a test.
- **Commit:** `831d01a`

### Documented departures from the plan text

- **The route header names the new function by FILE PATH, not by its export.** The plan requires
  both "extend the ORDERING note to name the new function" and `grep -c "diditReconcile"` = **2**.
