**The one statement that does three jobs:**

```sql
INSERT INTO host_verification
  (user_id, status, provider, vendor_ref, result, checked_at, reason,
   decided_by_staff_id, created_at, updated_at)
VALUES ($uid, 'pending', $provider, $vendorRef, NULL, NULL, NULL, NULL, now(), now())
ON CONFLICT (user_id) DO UPDATE
  SET status = 'pending', provider = $provider, vendor_ref = $vendorRef,
      result = NULL, checked_at = NULL, reason = NULL, decided_by_staff_id = NULL,
      created_at = now(),          -- FINDING F-1
      updated_at = now()           -- $onUpdate does not fire through raw SQL
  WHERE host_verification.status = 'unverified'
     OR ( host_verification.status = 'rejected'
          AND host_verification.updated_at < now() - make_interval(hours => $cooldown::int) )
RETURNING user_id
```

`make_interval(hours => …)` rather than a literal `interval '24 hours'`, so `COOLDOWN_HOURS` is the single authority and the SQL cannot drift from the constant D-272 mirrors in the vendor's units. **No JS `Date` is bound** — every instant comes from Postgres' own `now()`, which sidesteps `ops-review.ts:390-401`'s measured Bind-time failure entirely; the only bound values are two strings and an integer.

**D-267 is a ruling in the header, not a note in a plan.** The listing's structured address is FitOut's § 21(b) geographic-address record, so this action collects a phone and requires a confirmed email and collects **no location of any kind**. Every occurrence of the word "address" in the file is inside that ruling (5), and the header names the one further occurrence in the graph — "Confirm your email **address**…" in the refusals module — so the next reader knows why a bare grep is the wrong instrument and set equality on `host_verification`'s columns is the right one.

## Deviations from Plan

### **1. [Rule 3 — Blocking] The refusal sentences could not be exported from the action**

- **Found during:** Task 1, before the first commit.
- **Issue:** Task 1 asks for the five sentences as **exported named constants of `src/app/actions/host-verification.ts`**, so plan 18.1-10 can add them to the banned-language corpus. That module opens with the server-action directive, and `tests/use-server-exports.test.ts` proves — with a recorded RED and a real incident behind it — that such a module may export **only async functions**. `src/app/actions/avatar.ts` exported a number and a Zod object, Next rejected the whole module at evaluation, and avatar upload was dead in the browser for a phase while the unit tests stayed green. A string constant fails identically.
- **Fix:** the sentences live in a new plain module, **`src/lib/host/verification-refusals.ts`**, which the action imports; the result **objects** stay module-private in the action. The plan's substance is intact — one named constant per refusal, one owner for each sentence, byte-identical to the UI spec, and `HOST_VERIFICATION_REFUSALS` gives 18.1-10 a single import instead of five.
- **Side effect, and it is a happy one:** the acceptance criterion `grep -ci "address"` on the action now counts only the D-267 header ruling, because the one sentence containing the phrase "email address" lives in the other file. The header names that occurrence explicitly so nobody has to re-discover it.
- **Files:** `src/lib/host/verification-refusals.ts` (new, not in `files_modified`), `src/app/actions/host-verification.ts`.
- **Commit:** `c45ad02`.

### **2. [Rule 1 — Bug in this plan's own draft] Two acceptance greps went falsely RED on prose**

- **Found during:** Task 1 and Task 2, both before their commits.
- **Issue:** exactly the collision `18.1-PATTERNS § Describe the forbidden literal; never quote it` and this phase's constraint #4 warn about, twice more. - **Commits:** `c45ad02`, `3a96ca0`.

### **3. [Rule 1 — Bug in this plan's own draft] The fetch stub handed back a consumed `Response`**

- **Found during:** Task 3, first run (3 of 13 cases red).
- **Issue:** `vi.fn().mockResolvedValue(jsonResponse(CAPTURED_201))` resolves to the **same** `Response` instance every call, and a `Response` body may be read only once. The adapter's `await res.text()` therefore threw on the second press, the action's catch-all turned that into the vendor refusal, and cases 8 and 10 failed with *"We couldn't start the check just now"* — a sentence for a condition that did not exist. Case 1 failed separately because Better Auth **normalises the stored email**, so a mixed-case fixture address (`hvs_c1_noRow@…`) was never found by `eq(user.email, …)`.
- **Fix:** an `alwaysRespond()` helper that builds a fresh `Response` per call, with the measurement written into its docblock; fixture emails lowercased with the reason stated. 13/13 green.
- **Commit:** `376fc7a`.

### **4. [Scope] Deferred item D2 stays deferred, and this plan is a named candidate for it**

`deferred-items.md § D2` nominates 18.1-07 or 18.1-11 as the owner of moving `DECLARED_WORKFLOW` / `DECLARED_RETRY` out of `scripts/didit-setup.ts` into an unguarded declaration module.
