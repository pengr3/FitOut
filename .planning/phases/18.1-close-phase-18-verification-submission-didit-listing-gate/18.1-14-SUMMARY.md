## What shipped

### Task 1 — the Didit sandbox round trip, written up (`18.1-EVIDENCE.md § P1`)

**This is the one thing no mock in this repository could do.** `tests/verification/didit-webhook.test.ts`
computes both sides of every signature it checks; if the shared understanding of what Didit signs were
wrong, all 28 cases would be green and every real delivery would be a 400. **This repository has
already paid that exact bill once** on the PayMongo webhook.

Driven by the operator against the live **sandbox** application through an ngrok tunnel, 2026-09-02/03:

| Probe | Result |
|---|---|
| **Approve walk** (`8bb15a5c-…`) | signature VERIFIED · `pending → approved` · `result='pass'` · `checked_at` set · `decided_by_staff_id` **NULL** · **`vendor_ref` unchanged** · route answered **200 in 85 ms** against a 5 s vendor budget · one audit row · **exactly one** notification |
| **Decline walk** (`2ebb6da1-…`, `decline_document_expired`) | `pending → rejected` · `result='fail'` · reason **48 chars**, no risk code / `node_id` / `additional_data` / UUID |
| **Replay** | byte-identical repost → **200**, row unchanged, **no** second notification |
| **Tamper** | `"Approved"` → `"Declined"` under the original signature → **400 `Invalid signature`**, no unhandled exception |
| **A8 — the real phone** | **PASS** — and under D-273's `is_desktop_allowed: false` this was MANDATORY, because the phone is the only path a host can complete |

**Four things the walk settled that the plan did not know it would:**

1. ⚠ **ADDENDUM A7 IS SETTLED.** `X-Signature` and `X-Signature-V2` carried the **identical 64-character
   digest on every delivery observed**. Didit ships already-canonical JSON, so the raw bytes and their
   canonical re-serialisation are the same bytes and the vendor's two contradictory doc pages agree in
   practice. **Raw-as-primary is safe**, which is what the shipped route does.
2. ⚠ **The replay guard is STRUCTURAL, not a ledger.** There is no table of seen `event_id`s — the
   verdict `UPDATE`'s own `WHERE` admits `pending` only, so a replay against any other state is a 0-row
   no-op by construction. `event_id` is captured for traceability and is **not** what makes it safe.
   Written down explicitly, because a future reader who removes the `pending` equality on the grounds
   that "the event id de-dupes it" would remove the guard and keep the decoration.
3. ⚠ **`created_at` is NOT moved by a verdict and IS moved by a submission** — measured on both walks.
   F-1's rule read off real rows in both directions, and the same property 18.1-15's RESUME `CASE`
   preserves from the other side.
4. ⚠ **The decline's stored reason is the CANNED FALLBACK.** Didit supplied **no allow-listed code at
   all**, which makes D-265's fallback the branch a real vendor decline actually took on the first real
   vendor decline this repository has ever seen — not dead code kept for tidiness.

**The fixture was NOT replaced**, and that is a decision. `tests/helpers/mocks.ts` computes the raw and
canonical digests independently so the fallback branch and the header-vs-body timestamp cases are
writable at all. Real deliveries make those two values coincide; collapsing them to "match reality"
would delete the only instrument that can tell the branches apart.

**Environment provenance is recorded because the next person will hit it:** the walk ran under
`next dev`, not a production build. A production build was tried first and refused by a working guard
(`INNGEST_SIGNING_KEY is required in production`), which 500s `/api/inngest` — the endpoint the 18.1-09
sweep registers through. So `DIDIT_ENVIRONMENT` only bites in a production build, which is exactly why
`didit-webhook` case 24 has to **stub** it (D7, fixed for that case in `76fac9c`).
