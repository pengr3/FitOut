<decisions>
Design calls made during planning. Implement these; do not silently substitute alternatives.

**D-J3Z-01 — No schema change, no migration, no new index.** The `audit` table and
`audit_needs_attention_idx` already exist (0024). `listUnresolvedAlerts` must carry a WHERE predicate
**byte-identical** to the index predicate so the existing partial index is usable, and `ORDER BY created_at
DESC NULLS LAST` to match the index's declared ordering (`DESC` alone means `NULLS FIRST` in Postgres and
forces a Sort node on top). The next migration number stays **0025, unused by this task.**

**D-J3Z-02 — The PII contract is enforced STRUCTURALLY, not by a code comment.** `listUnresolvedAlerts`
selects explicit columns (`id, action, actor_id, created_at`) and the `UnresolvedAlert` type has **no `meta`
field at all**. The renderer takes `UnresolvedAlert`-shaped rows, so re-exporting `meta` into an inbox is a
type error, not a review catch. Rationale, and it belongs in the code as a comment: email is an external
service that forwards, archives and indexes; `meta` carries booking ids, transfer ids and masked last-4s
under an explicit column-level rule (D-72, restated verbatim at `cancel-booking.ts:755-756` — *"No account
number, no account name, no BIC — not in this audit meta, not in any log line, NOT IN ANY COLUMN"*). The
digest carries **audit id, action, actor_id, created_at, age** — enough to look the row up, and nothing more.
Where `meta` IS readable: a local psql / Drizzle Studio session, which the runbook documents. That boundary
is the point.

**D-J3Z-03 — Cron slot: `TZ=Asia/Manila 50 8 * * *` (daily, 08:50 Manila).** Minute **50** is occupied by
none of the four existing crons (`:00`, `:15`, `:30`, `:45`), which are all hourly — so at 08:00/:15/:30/:45
they tick and at :50 nothing else is running. 08:50 puts the digest at the top of the operator's working day
rather than overnight, where a money alert would sit unread for hours. Singleton `concurrency: 1`, matching
the established idiom.

**D-J3Z-04 — A missing `OPS_ALERT_EMAIL` logs loudly and no-ops; it MUST NOT throw.** This is deliberately
the OPPOSITE of the `INNGEST_SIGNING_KEY` boot guard at `route.ts:29-37`, and the asymmetry is stated here so
it is not "corrected" later: that guard protects a **security** property (an unverified serve endpoint an
unauthenticated caller could hit), where failing closed at boot is right. A missing notification **address**
is a configuration gap in one of six registered functions; throwing at module load would take down the entire
`/api/inngest` mount — payout sweep, reconcile, request-expiry, notify, guest-email and reminders — over a
missing email address. Instead: `console.error("[ops-alert] OPS_ALERT_EMAIL unset …", { count, ids })` so the
alert degrades to the console sink it already had, and return `{ sent: false, reason: "no_recipient" }`.

**D-J3Z-05 — Zero unresolved rows sends NOTHING, and the recipient check comes SECOND.** Order is: rows
empty → return `{ sent: false, reason: "no_unresolved" }` immediately, no email, **no error log** (the
Inngest run's return value is the record). Only when rows exist is the recipient checked. A daily "all clear"
email is precisely how an alert channel gets filtered to trash, and a daily "you forgot to configure me"
error on an empty queue is the same failure in a different sink.

**D-J3Z-06 — Env reads happen at CALL time, not module load.** `payout-reconcile.ts:40` reads its threshold
at module load; this file must not, because (a) the unset-recipient behaviour has to be *observable* in a
test, and (b) `tests/setup.ts` loads `.env.local`, which after Task 3 contains a real `OPS_ALERT_EMAIL`.
Read both `OPS_ALERT_EMAIL` and `OPS_ALERT_AGING_HOURS` inside the function.

**D-J3Z-07 — `resolveAlert` semantics.** Single guarded UPDATE:
`UPDATE audit SET resolved_at = now() WHERE id = $1 AND resolved_at IS NULL RETURNING id, resolved_at`.
One row → `{ outcome: "resolved", id, resolvedAt }`. Zero rows is ambiguous, so follow with
`SELECT id, resolved_at FROM audit WHERE id = $1`: row present → `{ outcome: "already_resolved", id,
resolvedAt }` **carrying the ORIGINAL timestamp** (the guard is what prevents the clobber — an unguarded
UPDATE would rewrite history); absent → `{ outcome: "not_found", id }`. `now()` is the Postgres clock, per
the project's zero-JS-clock rule (`src/lib/units.ts`), exactly as `recordAudit` leaves `created_at` to the
DB default.

**D-J3Z-08 — Aging uses the JS clock, and that is allowed here.** `payout-reconcile.ts:25-27` sets the
precedent explicitly: *"only the stuck-age comparison uses createdAt vs Date.now() (advisory alert timing,
not a money-moving decision)"*. The aging flag moves no money and gates nothing; it decorates a line in an
email. `OPS_ALERT_AGING_HOURS` defaults to **24** — the digest is daily, so a row that shows up twice is by
definition aging.

**D-J3Z-09 — Bounded digest.** `DEFAULT_ALERT_LIMIT = 200`. The digest requests `limit: 201` and, if it
receives more than 200, renders the 200 newest and states *"200+ unresolved — showing the 200 newest"*. One
query, no separate count, and no claim the code cannot back. Never render an unbounded list into an email.

**D-J3Z-10 — Runbook lives at `.planning/ops/NEEDS-ATTENTION-RUNBOOK.md` (new dir).** The brief suggested
`qrph-overcharge-runbook.md`; this deviates deliberately and the runbook must say why in its own header. The
digest surfaces **every** `needs_attention` seam (~20 call sites — failed auto-refunds, `refund_after_payout`,
stranded checkout sessions, host-cancel autoblock failures, permanently-failed notify sends, and the QRPh
unrefundable-rail alert). A QRPh-only filename would mislead an operator holding a `payout_transfer_failed`
row. **The QRPh out-of-band refund procedure is its central, explicitly-named section.** The existing
`05-UAT-RUNBOOK.md` is phase-scoped by nature; this one outlives Phase 5, so it does not belong inside that
phase folder — and 05-HUMAN-UAT item 3 gets a pointer to it, which is edited in the same task.

**D-J3Z-11 — `resolved_by` is NOT added, and the gap is recorded rather than hidden.** Adding it would be a
migration, which is out of scope by constraint. Consequence, honestly: a resolve is non-repudiable by
absence — the row records *that* it was discharged, never *by whom*. Mitigation: the CLI prints the
discharged id and the runbook instructs the operator to record the refund reference in their own out-of-band
record. Note it in the runbook and in the threat register as `accept`.
</decisions>
