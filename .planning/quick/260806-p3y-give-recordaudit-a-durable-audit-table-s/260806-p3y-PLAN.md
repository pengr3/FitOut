The table to add to `src/lib/db/schema.ts` (place it after `paymongoEvent`, before the
`payoutLedgerState` enum — it is not FK-coupled to anything, so const-TDZ ordering is free):

```typescript
export const audit = pgTable(
  "audit",
  {
    id: text("id").primaryKey(),                                   // randomUUID() — the shipped app-generated-id idiom
    createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull(),
    actorId: text("actor_id").notNull(),                           // NO .references() — see docblock
    action: text("action").notNull(),
    outcome: text("outcome").notNull(),                            // AuditOutcome union, compile-time enforced
    meta: jsonb("meta").$type<Record<string, unknown>>(),          // nullable; NO secrets/PII
    resolvedAt: timestamp("resolved_at", { withTimezone: true }),  // NULL = unresolved
  },
  (t) => [
    index("audit_needs_attention_idx")
      .on(t.createdAt.desc())
      .where(sql`outcome = 'needs_attention' AND resolved_at IS NULL`),
  ],
);
```

`text`, `timestamp`, `jsonb`, `index`, `pgTable` and `sql` are all already imported by schema.ts.

The `recordAudit` body contract (Task 2) — the ORDER is the design:

```
1. build `line` exactly as today (ts / actorId / action / outcome [+ meta])
2. console.info("[audit]", JSON.stringify(line))      // FIRST, unconditional, unchanged
3. try { await db.insert(audit).values({ id: randomUUID(), actorId, action, outcome, meta }) }
   catch { /* swallowed — see docblock */ }
```

Note `createdAt` is NOT passed: it defaults to the Postgres `now()`, per this project's zero-JS-clock
rule (`units.ts`). The console line's `ts` stays the JS attempt-time it is today — unchanged behaviour.
The two can differ by the insert latency; the DB clock is the authority.

<locked_decisions>
<!-- Decided at plan time against the codebase. Implement these; do not relitigate. -->

**D1 — The write is AWAITED on the caller's path, inside try/catch. Not fire-and-forget, not a timeout.**

The project already reversed a `void` on this exact path. `src/app/api/paymongo/webhook/route.ts:208-214`:

> WHY THIS IS NOW AWAITED RATHER THAN `void`ed. […] `void`ing an enqueue is actively worse than awaiting
> it here — the handler can return and the runtime can freeze the process before an un-awaited outbound
> request has flushed, silently losing the notification.

A detached audit INSERT fails in precisely the case the table exists for: the webhook returns 200 and the
runtime freezes the process before the row flushes, so the QRPh alert is lost exactly when it matters.

The `void` idiom in `src/lib/auth.ts:73-82` is not a counter-precedent: it fires an outbound HTTPS call to
Resend on the signup path. This is a single INSERT to the same Postgres pool the caller is already awaiting
several round-trips against, on a money path.

A bounded timeout (`Promise.race` with a timer) is rejected: it does not CANCEL the query, so it neither
bounds the database's work nor prevents a late row. It buys a second failure mode — a row that lands after
the caller has already declared it lost — for nothing.

The shipped precedent for the exact shape chosen is `releaseCheckoutLease`
(`src/lib/payments/checkout-lease.ts:130-143`): awaited, body swallowed, "BEST-EFFORT by design […] it must
never convert a calm refusal into a thrown 500 on the money path."

**D2 — The console line is emitted BEFORE the INSERT is attempted.**

Three reasons, in order of weight:
1. The log line is the currently-shipped, alert-matched behaviour. Emitting it first makes it structurally
   impossible for a slow, hung or failing DB to delay or lose it.
2. It makes the `catch` block genuinely empty. Log-after-insert would need "have we logged yet?" bookkeeping
   in two branches, and a bug there either double-logs (breaking every count assertion in the suite) or
   silently logs nothing.
3. If the process is killed mid-INSERT, the line has already flushed.

Cost, accepted and documented: `line.ts` is the JS attempt time and `created_at` is the Postgres clock at
insert. They differ by the insert latency. That is correct — the DB clock is authoritative, and the console
`ts` is unchanged from today, which is what "byte-identical console line" requires.

**D3 — `outcome` is `text`, not a `pgEnum`.**

The codebase leans on `pgEnum` heavily, so this needs a reason. Nothing branches on `audit.outcome` — it is
a record of what happened, not a state machine like `booking.status`, whose values steer the EXCLUDE
predicate and the payout sweep. The `AuditOutcome` union already constrains all 57 sites at compile time.
And an enum inverts the whole design: a value not yet `ADD VALUE`d on the live enum makes the INSERT throw,
which this function swallows — so the money alert would vanish silently, which is the one outcome the task
forbids. It would also make any future outcome value a 55P04 two-migration split for a column with no
correctness role. Shipped precedent for a documented text status: `host_payout.activation_status`.

**D4 — `actor_id` carries NO foreign key.** Verified against all 57 sites: 8 pass the literal `"system"`
or `"guest"`. An FK would 23503 on those, and the swallow would then eat the QRPh unrefundable-rail alert.
State this in the docblock so nobody "tightens" it later.

**D5 — `resolved_at` exists; retention is explicitly DEFERRED.**

`resolved_at` is what makes requirement 4 ("every **unresolved** needs_attention, newest first") a real
query rather than "every needs_attention ever", which is useless the moment the first alert is handled —
the operator would re-see it forever. Its only v1 writer is the operator's own
`UPDATE audit SET resolved_at = now() WHERE id = …`; there is no ops UI anywhere in this project yet, so a
hand-run queue is the complete workflow, not a stub. The partial index mirrors `notification_unread_idx`
exactly, including its stated property: it indexes only the open rows, so it "stays tiny forever while
[resolved] history grows without bound."

Retention: **deferred, on the record.** Because the index is partial, the operator query stays O(unresolved)
no matter how large the table gets, so growth is a disk-cost question, not a correctness or latency one. An
audit trail on money paths that silently auto-deletes is worse than a large one. When it does become worth
addressing, the honest first move is partitioning or archival to cold storage — never a scheduled DELETE.
Write this into the schema docblock so the deferral is a decision on the record rather than an omission.
</locked_decisions>
