<objective>
Close **T-08-79**, the accepted concurrency residual recorded in finding #5 of the v1.0 milestone audit,
in `.planning/phases/08-group-bookings/deferred-items.md`, in `08-SECURITY.md` (AR-08-02) and in the
comment at `src/app/actions/booking.ts:825-830`.

`confirmBooking`'s expire-before-create gate is READ-THEN-ACT and UNLOCKED. Two concurrent calls for one
`holdId` both read a stale/NULL `checkout_session_id`, both skip the expire, and both mint an
independently payable PayMongo checkout session. Both can be paid. On the `qrph` rail an already-captured
overcharge is NOT API-refundable (`src/lib/payments/refund-rail.ts`), so the second capture needs an
out-of-band operator refund. The SEQUENTIAL form of this bug already cost a real ₱1,470.00 against a
₱735.00 booking in Phase-8 UAT; only the sequential path was closed.

This plan adds a **compare-and-swap checkout lease**: one atomic `UPDATE … WHERE <lease is free>
RETURNING` claims the booking before any PayMongo call, and a concurrent second caller's claim affects
zero rows and is refused. The claim holds no lock across the network — it is a single autocommit
statement that has committed before `fetch` is ever called.

Purpose: make "one booking, one payable session" true under CONCURRENCY, not only under resubmission.
Output: one additive column + migration, one shared lease module, three wired exit paths in
`confirmBooking`, a booker-facing refusal, a genuine two-connection mutation-measured race proof, and an
honest audit trail.
</objective>

<design_decision_where_the_lease_lives>

**DECIDED: (a) — a new nullable `checkout_lock_at timestamptz` column on `booking`, claimed by a single
autocommit `UPDATE … RETURNING`.** Write this reasoning into the `src/lib/payments/checkout-lease.ts`
header; it is the load-bearing justification for the migration.

**Why (b) `pg_try_advisory_lock` is DISQUALIFIED — by the connection model, not by taste.**
`src/lib/db/index.ts` is `drizzle(postgres(process.env.DATABASE_URL!))` — postgres.js with **no options,
i.e. the default pool of `max: 10`**. A session-scoped advisory lock belongs to the BACKEND CONNECTION
that took it. Across the `await` boundaries in a server action, Drizzle gives no connection pinning
without an explicit transaction — and constraint #2 forbids a transaction spanning the HTTP calls, which
is the only thing that would pin one. So the release could land on a different backend, where
`pg_advisory_unlock` returns `false` and the lock leaks until that pooled connection is recycled: the
exact wedge the TTL exists to prevent, with no TTL available to heal it. This is the same hazard
`src/lib/availability/units.ts:869-875` documents when it deliberately chose the TRANSACTION-scoped
variant. And `pg_try_advisory_xact_lock` is unusable here for the reason the finding already states: it
releases at COMMIT, which is *before* the HTTP calls begin.

**Why (a) is correct.**
- **It holds no lock across the network, structurally.** The row lock the `UPDATE` takes lives for the
  duration of that one statement and is gone before `fetch` is called. Constraint #2 is satisfied by
  construction, not by discipline.
- **It is atomic under READ COMMITTED, and this is the load-bearing Postgres fact.** When racer B's
  `UPDATE` meets the row that racer A's uncommitted `UPDATE` holds, B **blocks**, then — after A commits —
  **re-evaluates its `WHERE` clause against the NEW row version** (EvalPlanQual). B therefore sees
  `checkout_lock_at = <A's now()>`, fails the predicate, updates zero rows, and `RETURNING` comes back
  empty. This is precisely why a single `UPDATE … WHERE … RETURNING` is a valid CAS while
  `SELECT`-then-`UPDATE` is not. **Do not wrap it in a transaction and do not add `FOR UPDATE`** — both
  are unnecessary and the latter re-introduces the anti-pattern.
- **It self-heals by construction:** the TTL is a term of the predicate, evaluated against the POSTGRES
  clock, so a crashed attempt frees itself with no sweep, no cron and no operator.
- **It is inspectable:** an operator can `SELECT id, checkout_lock_at FROM booking WHERE checkout_lock_at
  IS NOT NULL` to find every wedged checkout. An advisory lock is an opaque bigint in `pg_locks`.
- **Cost is one additive nullable column** — the same shape as `drizzle/0019_booking_checkout_session.sql`,
  which added `checkout_session_id` to this same subsystem for this same invariant.

**Rejected alternatives under (c).** A partial UNIQUE index on an "in-flight" marker row buys the same
atomicity at the cost of a second table and a TTL sweep. `SELECT … FOR UPDATE NOWAIT` is still a row
lock and still has to be held across the HTTP calls to mean anything — constraint #2. An in-process
JS mutex proves nothing: the app is deployed on a container host and may run multiple instances.

**MIGRATION MECHANICS — this one is GENERATED, not hand-authored.** The project's rule
(`src/lib/db/schema.ts:653-655`) is that only the things Drizzle **cannot** express (the GiST `EXCLUDE`)
are hand-authored; a plain nullable `timestamptz` is exactly what `drizzle-kit generate` handles, and
`0019` — the identical shape on this identical table — is a generated one-liner. Generating also keeps
`drizzle/meta/_journal.json` and the snapshot consistent, which `npm run db:migrate` depends on and a
hand-dropped `.sql` file would silently break. Procedure is in Task 1.

**TTL = 90 seconds** (`CHECKOUT_LEASE_TTL_SECONDS`, env-overridable). Justification, both directions:
- **Floor.** The lease covers exactly two PayMongo HTTPS round-trips (`expire` + `create`) plus two local
  `UPDATE`s. `paymongoFetch` (`src/lib/paymongo.ts:86`) sets **no timeout** — plain `fetch`, no
  `AbortSignal` — so a degraded provider can take tens of seconds. A TTL shorter than the slow path is
  the DANGEROUS direction: it would let a retry overtake a still-live attempt and re-open the exact race
  being closed. 90s is roughly 45× the normal ~2s cost.
- **Ceiling.** A crashed attempt must not wedge the booker for a meaningful slice of the 60-minute
  `PAYMENT_WINDOW_MINUTES` — 90s is 2.5% of it — and one wait-then-retry must still fit inside the
  `CONFIRM_PAY_RATE_LIMIT` budget of 5/60s, which it does with room to spare.
- **Named residual (accept, do not close here):** the TTL bounds the LEASE, not the HTTP call. A request
  hung beyond 90s can still be overtaken. Adding an `AbortSignal.timeout` to `paymongoFetch` is the
  follow-up that would make the bound total; it is deliberately not in this plan's blast radius. Record
  it in the threat register as `T-KV2-04`, not as a silent omission.

</design_decision_where_the_lease_lives>

| Exit path | Lease state | Mechanism |
|-----------|-------------|-----------|
| **Success** (`redirect(checkout.checkoutUrl)`, which throws by design) | **cleared** | `checkoutLockAt: null` is folded into the SAME `.set()` that names `checkout_session_id` — one statement, before the redirect. Clearing it in a later statement would leave a window, the identical reasoning as `updateDeclaredPax:639-642`. If that owner+live-status-scoped write matches ZERO rows (the hold lapsed — "ZERO ROWS IS NOT A FAILURE, AND MUST NOT BECOME ONE", booking.ts:912-916), the lease is left set and the TTL clears it. Do NOT harden that write. |
| **Expire-failure refusal** (the `catch` around `expireCheckoutSession`) | **released** | `releaseCheckoutLease(db, holdId, lockedAt)` after `recordAudit`, before the `return`. Without it, the DOCUMENTED recovery — the booker's retry, whose repeat expire returns the tolerated already-expired 400 and proceeds (08-19 case 4 / 08-21) — would be blocked for the whole TTL, converting a one-retry cost into a 90-second dead end. |

| **Process dies mid-flight** (SIGKILL, container evict, unhandled crash) | **not released** | The TTL. This is the ONLY mechanism for this path and the entire reason constraint #3 requires one. |

| **Every guard ABOVE the claim** (sign-in, owner gate, confirmed short-circuit, status, D-94 cutoff, rate limit, null-quote) | **never claimed** | The claim is placed as LATE as possible — immediately before the expire-before-create block — so no pre-existing guard can return with a lease outstanding, and no existing test's expectations move. |
