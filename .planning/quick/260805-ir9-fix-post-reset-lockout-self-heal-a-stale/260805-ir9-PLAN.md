<objective>
After a password reset, a user is permanently locked out of `/login`.

Confirmed live 2026-08-05 and re-confirmed in source during planning. `revokeSessionsOnPasswordReset:
true` (`src/lib/auth.ts:72`) deletes the session ROW; nothing clears the browser's cookie, and the cookie
is httpOnly so client JS cannot. `src/middleware.ts:17-21` does a PRESENCE-only `getSessionCookie` check
— which `src/middleware.ts:1-7` correctly and deliberately documents as never touching the DB — sees the
stale cookie, concludes "logged in", and redirects `/login` -> `/`. The user lands on the public search
home, which renders identically signed-in and signed-out, and can never get back to `/login`. Typing the
URL directly bounces too. Duration: the 30-day cookie lifetime. The app has no sign-out (a grep for
`signout|sign-out|log ?out` across `src/` returns nothing), so there is no in-app recovery at all.

The automated suite cannot see this: `e2e/password-reset.spec.ts` passes because Playwright drives a
fresh browser context per run and never carries a stale cookie across a reset. 1112 unit/integration
tests are green. Only a human doing the boring thing found it.

This plan makes the stale cookie SELF-HEAL, preserving BOTH existing designs rather than trading one
against the other: middleware stays optimistic-and-DB-free, and the per-page `getSession()` stays the
real security boundary. It fixes every stale-cookie cause, not just password reset — expired session,
admin revocation, wiped dev database.

Purpose: make `/login` reachable, always, without weakening a single prior decision.
Output: one shared module, one Route Handler, a small middleware rewrite, and a two-layer
mutation-measured regression test that would have caught this.
</objective>

<design_decision_where_the_clearing_lives>

**DECIDED: middleware DELEGATES its optimistic bounce to a Route Handler that does the authoritative
check and the (legal) cookie write.**

```
GET /login  (STALE cookie)
  -> middleware: cookie present, no marker  -> 307 /auth/session-check?next=%2Flogin
  -> route handler: getSession() === null   -> 307 /login?_sc=1  + Set-Cookie: ...session_token=; Max-Age=0
  -> browser applies the expiry, then follows
  -> middleware: marker present             -> next()   [and the cookie is gone anyway]
  -> /login renders. The locked-out user is free.

GET /login  (VALID cookie)
  -> middleware: cookie present, no marker  -> 307 /auth/session-check?next=%2Flogin
  -> route handler: getSession() is a user  -> 307 /            (no clearing header at all)
  -> the wanted bounce; constraint 4 intact.

GET /login  (NO cookie)
  -> middleware: next(). Zero cost, zero hops, completely unchanged.
```

**Why this shape and not the alternatives:**

- **Not the reset-password completion path.** Narrow: it fixes only the one cause. Expired sessions,
  admin revocation and a wiped dev DB produce the identical lockout and would stay broken.
- **Not a shared `requireSession()` helper on the gated pages.** Measured above (§2): the clearing
  silently no-ops in an RSC. It also would not fix the plainest repro — typing `/login` directly, which
  touches no gated page at all.
- **Not middleware doing the check itself.** Constraint 1. And there is no DB-free way to know: a revoked
  row still carries a valid HMAC, and `session.cookieCache` is not enabled, so nothing in the request can
  distinguish live from dead.
- **The DB read is rare, not per-request.** It fires only when someone WITH a session cookie visits
  `/login` or `/signup`. A logged-out visitor takes zero extra work, and middleware itself still touches
  nothing.

**The `_sc=1` marker is a LOOP GUARD, and its independence is the whole point.** If the clearing ever
failed to reach the browser — the measured bad-signature path, a cookie-attribute mismatch, a future
Better Auth change — `/login` would redirect to the check, which would redirect back to `/login`,
forever: `ERR_TOO_MANY_REDIRECTS`, a WORSE failure than today's. A marker carried in the URL does not
share a failure mode with the Set-Cookie it guards, which is precisely why it is a query param and NOT a
guard cookie. **Tradeoff, accepted deliberately:** the param is forgeable, so a user who hand-types
`/login?_sc=1` while genuinely logged in reaches the login page instead of being bounced. That is a
bypass of an optimistic UX convenience which `src/middleware.ts:1-7` already declares is not a security
boundary; `/login` is public and exposes no gated data. Record this in the middleware comment.

**Two new source files, not three.** Middleware and the route handler must agree on
`/auth/session-check`, `next` and `_sc`; three literals duplicated across two files is a drift bug
waiting to happen, so they share ONE module, `src/lib/session-check.ts`. It is Edge-safe because its only
value import is `next/server`. If a future edit adds `@/lib/auth` or `@/lib/db` to it, the Edge bundle
breaks LOUDLY at `npm run build` — an acceptable, visible failure mode, and Task 2 gates against it.
</design_decision_where_the_clearing_lives>
